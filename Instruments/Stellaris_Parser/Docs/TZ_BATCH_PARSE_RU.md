## Цель этапа

**Статус — реализовано.** Stellaris Parser включает ядро разбора, модуль библиотек и управление рабочими процессами. Пользователь указывает каталоги и лимит процессов. Парсер выполняет обе стадии прогона.

1. Подготавливает общий для прогона набор библиотек. В режиме пересборки парсер распределяет независимые библиотечные файлы между процессами и объединяет определения. В режиме повторного использования проверяет и загружает сохранённый набор.
2. Когда набор готов, распределяет основные файлы между рабочими процессами. Каждый процесс получает доступ к определениям в памяти до первого задания, использует их для раскрытия объектов во всех своих файлах и записывает JSON каждого исходника. Допустима одна копия набора в памяти на процесс.

Парсер готов к эксплуатации после сквозной проверки обеих стадий одним пакетным запуском. Одиночная команда позволяет проверить работу ядра и библиотек на выбранном файле.

Одиночный и пакетный разбор используют один механизм раскрытия и сериализации документа. Подготовка общих определений предшествует обработке основных файлов. [Точки входа](../stellaris_parser/workspace.py)

## Первый шаг — модуль библиотек

Сначала перенести подготовку, сохранение, проверку и загрузку библиотек в пакет `stellaris_parser.libraries`. Основой служит существующий модуль WEB_STTV, включая его сериализацию определений, связей между ними и подготовленных планов шаблонов. Разбор выполняет существующий код `stellaris_parser.script`. Для выбора источников используются корни и правила самого парсера. Пакет должен работать при самостоятельной установке парсера без импортов из `sttv`. [Сборка прежнего набора](../../../WEB_STTV/src/backend/sttv/libraries/snapshot.py) · [Запись и загрузка](../../../WEB_STTV/src/backend/sttv/libraries/storage.py)

Формат поставки — пять JSON по видам библиотек и манифест прежнего модуля. По умолчанию имена файлов — `inline_scripts.json`, `scripted_effects.json`, `scripted_triggers.json`, `script_values.json`, `scripted_variables.json` и `manifest.json`. Манифест связывает файлы в один набор и хранит версии, состав источников и контрольные суммы. Каталог результата задаётся в пользовательском конфиге, имена шести файлов — в конфигурации библиотек парсера.

Промежуточная проверка модуля выполняется через `parse`. Пересобрать библиотеки по небольшой фикстуре с модом и игрой, затем отдельным запуском загрузить сохранённый набор. В обоих режимах раскрытое дерево и метаданные должны совпасть с результатом прямого разбора той же фикстуры. Отдельно проверить диагностику при изменении исходника и отсутствии одного из пяти JSON.

## Команды и настройки

| Команда | Вход | Результат |
| --- | --- | --- |
| `parse` | `--config`, режим библиотек, один путь относительно корня источников и `--output` с именем файла | JSON указанного исходника по точному пути пользователя |
| `parse-batch` | `--config`, режим библиотек, один или несколько каталогов относительно корней источников, выходной каталог и число процессов | Отдельный JSON для каждого выбранного файла |

Следующий пример предполагает, что `parser.json` лежит в корне монорепозитория. В комплекте инструмента также есть готовый конфиг для каталога технологий. [Готовый конфиг](../examples/parser.json)

```json
{
  "roots": ["E:/SteamLibrary/steamapps/common/Stellaris"],
  "library_directory": "TMP/WEB_STTV/run-01/artifacts/libraries",
  "batch": {
    "directories": ["common/technology", "events"],
    "exclude_files": ["common/technology/000_documentation.txt"],
    "output": "TMP/WEB_STTV/run-01/artifacts/scripts",
    "workers": 10
  }
}
```

`library_directory` задаёт каталог пяти библиотек и манифеста. Следующий прогон может читать этот каталог и писать скрипты в другое место. Пути файловой системы в конфиге отсчитываются от самого конфига, а `batch.directories` — от каждого корня в `roots`.

У `parse-batch` позиционный список каталогов, `--output` и `--workers` переопределяют соответствующие значения `batch` для одного запуска. Явный список каталогов целиком заменяет настроенный. Выходной путь из командной строки отсчитывается от текущего каталога. Число процессов — целое от 1, значение 1 означает последовательный разбор. Команде `parse` настройки `batch` не требуются.

Для приведённого выше конфига команды запускаются из корня монорепозитория.

```powershell
python -m stellaris_parser parse-batch --config parser.json --rebuild-libraries
python -m stellaris_parser parse-batch --config parser.json --reuse-libraries --workers 2 --output TMP/WEB_STTV/run-02/artifacts/scripts common/technology
python -m stellaris_parser parse --config parser.json --reuse-libraries --output TMP/WEB_STTV/run-02/artifacts/physics.json common/technology/00_phys_tech.txt
```

## Подготовка библиотек

В Stellaris 4.6.0 при подготовке библиотек восстанавливать пропущенный знак присваивания перед блоком верхнего уровня `increase_pop_political_power` только в `common/scripted_effects/forceofwill_scripted_effects.txt`. Сохранять исходный текст, позиции и контрольную сумму файла. Корректное объявление обрабатывать по обычным правилам.

В событиях Willpower при раскрытии `move_galactic_halls` использовать `no`, если отсутствует `IS_FROM_RELOCATE`. Явно переданному значению отдавать приоритет. Для вложенного значка `council_no` в `19_forceofwill_leader_traits.txt` применять действующее правило передачи класса из вызывающего шаблона.

Обе команды принимают ровно один ключ режима. Обход основных файлов для разбора начинается после успешной подготовки или проверки библиотек.

- `--rebuild-libraries` собирает определения из текущих источников. После успешной подготовки сохраняются пять JSON, манифест публикуется последним.
- `--reuse-libraries` читает сохранённый набор и проверяет его актуальность один раз на запуск. Если файл отсутствует, повреждён или устарел, команда завершается с причиной и подсказкой запустить `--rebuild-libraries`. На актуальность влияют эффективные библиотечные исходники, приоритет корней, правила подготовки и версия формата библиотеки.

При пакетной пересборке независимые библиотечные файлы распределяются по тому же правилу очереди и с тем же пределом `--workers`, что и основные файлы. После разбора отдельных файлов определения объединяются в установленном порядке с учётом приоритета корней. Ссылки между файлами разрешаются, когда доступны необходимые определения. Порядок завершения процессов не влияет на подготовленный набор. В режиме повторного использования достаточно проверить сохранённый набор и его входы без нового разбора библиотечных файлов.

Набор охватывает inline-шаблоны, scripted effects, scripted triggers, script values и глобальные статические переменные. Пути к этим пяти видам источников, маска и кодировка уже заданы в конфиге парсера. При подготовке учитываются настроенные исключения, включая разрешённый inline-файл без расширения. [Каталоги библиотек](../stellaris_parser/config/libraries.json) · [Исключения](../stellaris_parser/config/exceptions.json)

Каждый рабочий процесс один раз получает подготовленные определения и правила, затем читает их из своей памяти для всех назначенных ему файлов. Аргументы вызовов подставляются при разборе конкретного документа. Локальные переменные, стек вложенных вызовов, идентификаторы раскрытий и их метаданные создаются заново для каждого файла.

## Обратимое раскрытие библиотечных вставок

Цель — по сохранённому набору восстановить структуру выбранных библиотечных TXT, включая исходные вызовы и их аргументы. Допускаются отличия в оформлении. Подготовка должна сохранить данные для будущего экспортёра. В этот этап входит проверка обратимости на фикстуре.

1. В соответствующем библиотечном JSON сохранить для каждого выбранного файла его источник и упорядоченную структуру до раскрытия. Верхнеуровневый `inline_script` остаётся на исходном месте среди соседних записей. Сохраняются исходная форма вызова (ссылка или блок), путь к шаблону, аргументы с их порядком и структурой, а также подстановки и их исходное написание. Например, при передаче аргумента из внешнего шаблона сохраняется выражение `$NAME$`, даже если при индексации оно превратилось в конкретное имя. Тела определений сохраняют вложенные вызовы до применения.
2. Для индекса поиска отдельно раскрыть верхнеуровневые вставки, необходимые для обнаружения имён. Историю сохранить в библиотечном JSON и привязать к файлу, для которого строился индекс. Каждая запись указывает исходное место и цель вызова, его `id`, `parent_id` и упорядоченный результат вставки. Каждое полученное через вставку определение в индексе ссылается на породивший его вызов. Адрес записи учитывает библиотеку и файл, поэтому одинаковые локальные идентификаторы в разных файлах однозначны. Повторные обращения к одному шаблону имеют отдельные записи, в том числе при пустом результате.
3. Например, одна вставка в `effects.txt` создаёт два эффекта. Оба имени доступны в индексе и указывают на одну вставку. При обратном чтении структуры `effects.txt` на её месте восстанавливается ровно один исходный вызов. Если шаблон сам подключал другой шаблон, этот вложенный вызов восстанавливается в своём файле. История использования эффекта в событии остаётся в `metadata.expansions` файла события. История построения библиотеки хранится один раз в наборе из пяти JSON.

## Обход каталогов и запись JSON

1. Пакетный запуск рекурсивно выбирает игровые `.txt` в указанных каталогах. Он пропускает пять настроенных библиотечных каталогов и файлы из необязательного списка `batch.exclude_files`. Каждый элемент списка — точный путь относительно корня игры или мода. Совпадение проверяется до чтения содержимого и постановки задания в очередь. Поэтому документ из примера не создаёт JSON, а файл с таким же именем в другом каталоге обрабатывается. Список действует только при выборе основных файлов пакетного запуска.
2. Единицей выбора служит путь относительно корня игры или мода. При пересечении каталогов один путь ставится в очередь один раз. При совпадении пути в нескольких корнях используется первый файл по порядку `roots`.
3. Выходной путь сохраняет этот относительный путь и меняет расширение на `.json`. При выборе сразу `common` и `common/technology` исходник `common/technology/demo.txt` даст ровно `<output>/common/technology/demo.json`. Одноимённые файлы в разных каталогах получают разные выходы.
4. После выбора исходников и назначения выходных путей парсер формирует общую очередь для всех рабочих процессов. Одно задание содержит пару путей для одного файла. Файлы из всех выбранных каталогов упорядочиваются по убыванию размера исходника в байтах. При равном размере первым выдаётся файл с лексикографически меньшим путём относительно корня (разделитель `/`).
5. Работает до `--workers` процессов. Как только процесс закончил задание, он получает следующий файл из общей очереди. Файлы одного каталога могут обрабатываться одновременно разными процессами. Каждый процесс сам записывает полный JSON с переносами строк и возвращает путь и исход задания. Порядок узлов, подстановка переменных и история раскрытий соответствуют одиночному разбору.
6. Выходы защищены от записи поверх исходников, правил, библиотечных JSON и манифеста. Готовый JSON заменяется только после успешной записи целого документа. При ошибке отдельного файла пакет продолжает остальные задания, указывает исходник и причину в диагностике и завершается с ненулевым кодом. Успешно записанные документы остаются доступны.

Файлы библиотек и документов прогона размещаются в `artifacts/`. Для сохраняемых отчётов используется `reports/`, для отдельных материалов ошибок — `errors/` при необходимости.

## Проверки при приёмке

Проверки ограничены парсером. Для начала достаточно небольшой фикстуры с двумя корнями источников и несколькими файлами.

| Сценарий | Критерий |
| --- | --- |
| Выдача заданий | На файлах из двух каталогов проверить выдачу по убыванию размера, включая пару равного размера для проверки порядка путей. При двух процессах завершить второе задание раньше первого и проверить, что освободившийся процесс получил третье. Выходные пути и полное содержимое JSON должны совпасть с последовательным прогоном |
| Обратимость библиотечной вставки | В фикстуре между двумя обычными записями поместить вызов шаблона, который через вложенную вставку создаёт два определения. Повторить вызов с другими аргументами и проверить вставку с пустым результатом. После `rebuild` и `reuse` по одним сохранённым данным восстановить структуру каждого участвующего файла и сравнить с его разбором до раскрытия. Проверить порядок и число исходных вызовов, форму и аргументы, родительские связи и соответствие определений вызовам |
| Полный рабочий прогон | Запустить `parse-batch` с 2 процессами на нескольких файлах, использующих один шаблон с разными аргументами. Проверить, что основные задания начинаются после подготовки библиотек, а обработка следующего файла тем же процессом обходится без чтения библиотечных TXT и JSON. Проверить раскрытия и выходные пути для каждого файла. Повторить в режиме загрузки сохранённого набора |
| Одиночный и пакетный разбор | Для каждого исходника полное содержимое JSON, включая `source`, `items` и `metadata`, совпадает при одиночном запуске и при пакетном с 1 и 2 процессами |
| Приоритеты и пути | Мод перекрывает одноимённый игровой файл. Пересекающиеся каталоги не удваивают задания. Одноимённые файлы в разных каталогах дают отдельные JSON. Библиотечные каталоги пропускаются |
| Исключённый файл | Внести в список путь к файлу с заведомо неразбираемым текстом. Пакет завершается успешно без задания и JSON для этого пути. Корректный одноимённый файл в соседнем каталоге получает свой JSON |
| Параллельная подготовка | Пересобрать библиотеки с 1 и 2 процессами на файлах со ссылкой между ними. Состав и значения определений и итоговый документ совпадают. При ошибке подготовки разбор основных файлов не начинается |
| Подготовка и повторный запуск | Проверить по одному представителю каждого вида библиотеки и вложенный вызов. Пересборка выполняется один раз, каждый процесс инициализирует определения один раз. Повторный запуск с `--reuse-libraries` даёт тот же результат |
| Актуальность | Изменение библиотечного исходника или влияющего на подготовку конфига обнаруживается до обработки файлов. Повторная сборка учитывает изменение |
| Изоляция файлов | Два файла задают разные локальные значения под одинаковым именем и вызывают один шаблон с разными аргументами. Их результаты и метаданные корректны при обработке одним рабочим процессом в любом порядке |
| Ошибки | Нулевое число процессов и конфликтующие ключи режима отклоняются. Один ошибочный исходник даёт диагностику и ненулевой итоговый код. Для корректного соседнего файла создаётся полный JSON |

## Результаты проверки

20 ноября 2026 года прошли 13 автоматических тестов самостоятельного парсера. Для двух скриптов фикстуры результаты совпали с контрольными суммами прежнего одиночного разбора. Проверены очередь с двумя процессами, приоритет мода, шаблон без расширения, восстановление вложенных вызовов из библиотек и сохранение предыдущего результата при ошибке файла. [Пакетные проверки](../tests/test_batch.py) · [Проверки очереди](../tests/test_scheduling.py)

На установленной игре пересобраны пять библиотек из 750 входных файлов. Пакетный разбор с двумя процессами обработал `common/technology/category/00_category.txt` и `common/technology/tier/00_tier.txt`. При повторном запуске с `--reuse-libraries` оба JSON побайтно совпали с первым прогоном. Проверка основных файлов игры охватывала эти два каталога.
