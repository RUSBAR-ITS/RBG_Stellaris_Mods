## Цель этапа

**Статус — проект на согласование.** Единица работы парсера — один исходный файл и один выходной JSON. Пакетный запуск распределяет такие задания между процессами. Одиночный запуск позволяет разобрать тот же файл отдельно и получить тот же документ.

Сейчас команда `parse` уже пишет JSON одного файла. При каждом вызове `parse_file` заново загружает правила, собирает глобальные переменные и индексы именованных определений. Inline-шаблоны читаются по обращению. На этом этапе подготовка общих данных выносится из обработки файла. [Текущая реализация](../stellaris_parser/workspace.py)

## Команды и настройки

| Команда | Вход | Результат |
| --- | --- | --- |
| `parse` | `--config`, режим библиотек, один путь относительно корня источников и `--output` с именем файла | JSON указанного исходника по точному пути пользователя |
| `parse-batch` | `--config`, режим библиотек, один или несколько каталогов относительно корней источников, выходной каталог и число процессов | Отдельный JSON для каждого выбранного файла |

Предлагаемые настройки пользовательского конфига показаны на примере прогона WEB_STTV. Здесь `parser.json` лежит в корне монорепозитория.

```json
{
  "roots": ["E:/SteamLibrary/steamapps/common/Stellaris"],
  "library_file": "TMP/WEB_STTV/run-01/artifacts/libraries.json",
  "batch": {
    "directories": ["common/technology", "events"],
    "output": "TMP/WEB_STTV/run-01/artifacts/scripts",
    "workers": 10
  }
}
```

`library_file` задаёт путь и имя сохраняемых библиотек. Направить следующий прогон на тот же файл можно независимо от каталога вывода скриптов. Пути файловой системы в конфиге отсчитываются от самого конфига, а `batch.directories` — от каждого корня в `roots`.

У `parse-batch` позиционный список каталогов, `--output` и `--workers` переопределяют соответствующие значения `batch` для одного запуска. Явный список каталогов целиком заменяет настроенный. Выходной путь из командной строки отсчитывается от текущего каталога. Число процессов — целое от 1, значение 1 означает последовательный разбор. Команде `parse` настройки `batch` не требуются.

После реализации из корня монорепозитория можно будет выполнить следующие команды.

```powershell
python -m stellaris_parser parse-batch --config parser.json --rebuild-libraries
python -m stellaris_parser parse-batch --config parser.json --reuse-libraries --workers 2 --output TMP/WEB_STTV/run-02/artifacts/scripts common/technology
python -m stellaris_parser parse --config parser.json --reuse-libraries --output TMP/WEB_STTV/run-02/artifacts/physics.json common/technology/00_phys_tech.txt
```

## Подготовка библиотек

Обе команды принимают ровно один ключ режима. Подготовка выполняется один раз до первого задания.

- `--rebuild-libraries` собирает определения из текущих источников и сохраняет подготовленный набор в JSON. Файл заменяется после успешной подготовки всего набора.
- `--reuse-libraries` читает сохранённый набор и проверяет его актуальность один раз на запуск. Если файл отсутствует, повреждён или устарел, команда завершается с причиной и подсказкой запустить `--rebuild-libraries`. На актуальность влияют эффективные библиотечные исходники, приоритет корней, правила подготовки и версия формата библиотеки.

Набор охватывает inline-шаблоны, scripted effects, scripted triggers, script values и глобальные статические переменные. Пути к этим пяти видам источников, маска и кодировка уже заданы в конфиге парсера. При подготовке учитываются настроенные исключения, включая разрешённый inline-файл без расширения. [Каталоги библиотек](../stellaris_parser/config/libraries.json) · [Исключения](../stellaris_parser/config/exceptions.json)

Каждый рабочий процесс один раз получает подготовленные определения и правила, затем читает их из своей памяти для всех назначенных ему файлов. Аргументы вызовов подставляются при разборе конкретного документа. Локальные переменные, стек вложенных вызовов, идентификаторы раскрытий и их метаданные создаются заново для каждого файла.

## Обход каталогов и запись JSON

1. Пакетный запуск рекурсивно выбирает игровые `.txt` в указанных каталогах. Пять настроенных библиотечных каталогов вместе с их содержимым исключаются из этого обхода.
2. Единицей выбора служит путь относительно корня игры или мода. При пересечении каталогов один путь ставится в очередь один раз. При совпадении пути в нескольких корнях используется первый файл по порядку `roots`.
3. Выходной путь сохраняет этот относительный путь и меняет расширение на `.json`. При выборе сразу `common` и `common/technology` исходник `common/technology/demo.txt` даст ровно `<output>/common/technology/demo.json`. Одноимённые файлы в разных каталогах получают разные выходы.
4. Запуск использует до указанного числа рабочих процессов. Освободившийся процесс получает следующую пару путей. Он сам разбирает исходник и записывает полный JSON с переносами строк. Порядок узлов, подстановка переменных и метаданные раскрытий соответствуют одиночному разбору. Через очередь результатов достаточно вернуть путь и исход задания.
5. Выходы защищены от записи поверх исходников, правил и файла подготовленных библиотек. Готовый JSON заменяется только после успешной записи целого документа. При ошибке отдельного файла пакет продолжает остальные задания, указывает исходник и причину в диагностике и завершается с ненулевым кодом. Успешно записанные документы остаются доступны.

Файлы библиотек и документов прогона размещаются в `artifacts/`. Для сохраняемых отчётов используется `reports/`, для отдельных материалов ошибок — `errors/` при необходимости.

## Проверки при приёмке

Проверки ограничены парсером. Для начала достаточно небольшой фикстуры с двумя корнями источников и несколькими файлами.

| Сценарий | Критерий |
| --- | --- |
| Одиночный и пакетный разбор | Для каждого исходника полное содержимое JSON, включая `source`, `items` и `metadata`, совпадает при одиночном запуске и при пакетном с 1 и 2 процессами |
| Приоритеты и пути | Мод перекрывает одноимённый игровой файл. Пересекающиеся каталоги не удваивают задания. Одноимённые файлы в разных каталогах дают отдельные JSON. Библиотечные каталоги пропускаются |
| Подготовка и повторный запуск | Проверить по одному представителю каждого вида библиотеки и вложенный вызов. Пересборка выполняется один раз, каждый процесс инициализирует определения один раз. Повторный запуск с `--reuse-libraries` даёт тот же результат |
| Актуальность | Изменение библиотечного исходника или влияющего на подготовку конфига обнаруживается до обработки файлов. Повторная сборка учитывает изменение |
| Изоляция файлов | Два файла задают разные локальные значения под одинаковым именем и вызывают один шаблон с разными аргументами. Их результаты и метаданные корректны при обработке одним рабочим процессом в любом порядке |
| Ошибки | Нулевое число процессов и конфликтующие ключи режима отклоняются. Один ошибочный исходник даёт диагностику и ненулевой итоговый код. Для корректного соседнего файла создаётся полный JSON |
