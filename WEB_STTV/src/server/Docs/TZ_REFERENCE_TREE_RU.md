## Назначение

Настоящий документ описывает первоначальный этап справочника. Действующее расширение ключа коллекции, видимости и координат описано в [ТЗ настроек дерева](TZ_REFERENCE_TREE_MODES_RU.md).

**Утверждённое ТЗ.** По запросу сервер открывает или строит в MongoDB дерево-справочник. Единственная пользовательская настройка, определяющая состав дерева, — набор включённых DLC. На первом этапе берём базовое представление каждой технологии. Для одного набора сервер один раз определяет родителей и готовит координаты сразу для русского и английского языков.

Источником служат опубликованные игровые коллекции в `wiki`. При исследовании в `technologies` найдены 679 технологий, в `dlcs` — 36 дополнений. Это характеристики проверенной загрузки. Сервер читает игровой ID из `_id`, раскрытые определения из `tree`, переводы из `localization`. Порядок критериев, базовые характеристики империи и правила размещения задаются отдельным конфигом правил сервера. Путь к нему задаётся в конфиге сервера. Исходные правила для переноса — [выбор родителя](../../../config/enrichment/technology_tree/rules.json), [условия DLC](../../../config/enrichment/dlc.json) и [размещение](../../../config/frontend/tree_layout.json).

## Коллекции и идентификатор дерева

- `tree_configs` содержит один документ на конфигурацию. Он хранит `_id` дерева, `mode = "reference"`, `enabled_dlc`, `state`, ревизии исходных данных и правил. Для неудачной сборки сохраняется причина.
- Входные ID сверяются с `wiki.dlcs`, повторы удаляются, список сортируется по ID. Например, `["dlc036","dlc032","dlc036"]` и `["dlc032","dlc036"]` обозначают одну конфигурацию. Пустой массив отключает все DLC. Первоначальное состояние «все включены» разворачивается в полный список ID текущего каталога.
- `tree_id` — SHA-256 от компактного UTF-8 JSON с полями `mode`, затем `enabled_dlc`, в указанном порядке. В коллекции `tree_<tree_id>` хранится по одному документу на каждую исходную технологию, в том числе исключённую из отображения. Язык и масштаб не входят в ID.

| Поле узла | Значение |
| --- | --- |
| `_id` | Игровой ID технологии |
| `availability` | Булево значение видимости в справочнике при выбранных DLC |
| `parent_tech`, `children` | ID выбранного родителя или `null`, массив ID непосредственных детей без повторов в стабильном порядке |
| `area` | Область науки технологии |
| `location` | Для видимой технологии объект вида `{"ru":[2,7],"en":[2,4]}`. Каждая пара задаёт столбец и строку в своей области с нуля. Для скрытой технологии — `null` |

У скрытой технологии `parent_tech: null` и `children: []`. Обе раскладки используют одни и те же связи. Названия и описания остаются в игровом источнике локализации.

## Первый проход. Доступность по DLC

Функция получает каталог технологий, набор включённых DLC и игровые определения, нужные для проверки условий. Она создаёт запись для каждого ID. Техническое имя для `host_has_dlc` берётся из каталога DLC. Например, `dlc036` соответствует `BioGenesis`.

Скрытие требует доказанной зависимости от DLC: выбранный набор делает `potential` ложным либо активирует модификатор веса с `factor = 0`. Сравнение с вычислением при неизвестном состоянии DLC отделяет влияние дополнений от постоянных условий. Рекурсивно разбирать логические блоки, обёртки и подтверждённые косвенные ссылки с сохранением области проверки. Нулевой базовый вес или требование определённой этики сами по себе сохраняют карточку. При неизвестном результате технология остаётся видимой, причина неопределённости попадает в диагностику. [Правила фильтра](../../../Docs/TZ_BACKEND_STAGE_20_RU.md) · [Косвенные зависимости](../../../Docs/TZ_BACKEND_STAGE_21_RU.md)

У прежнего файлового стенда был индекс способов получения технологий по `common`, `events` и `prescripted_countries`. Полный индекс в текущую MongoDB не импортирован. Для ссылки `has_technology` запрет обычного исследования сам по себе не доказывает невозможность получения через событие. Если полноту путей подтвердить нельзя, ссылка даёт неизвестный результат. Другая ветвь того же условия всё ещё может дать однозначный ответ. В диагностике указывать технологию и путь условия с неполными данными. [Анализ способов получения](../../../Docs/TZ_BACKEND_STAGE_21_ACQUISITION_RU.md)

## Второй проход. Родитель и дети

Функция перебирает видимые технологии. Кандидаты — видимые технологии из их исходного `prerequisites`, с учётом обязательных требований и альтернатив. Применять настроенные критерии в существующем порядке до единственного кандидата. Если правило оставило ноль, сохранить прежних кандидатов и продолжить. При выборе родителя сразу записать его в `parent_tech` ребёнка и добавить ребёнка в `children` родителя. Все узлы к этому моменту уже существуют в памяти.

**Контекст империи определяется отдельно для каждой дочерней технологии.** На прежнем месте критерия `standard_empire`, перед старшинством, выполнить следующие действия:

1. Рекурсивно разобрать собственный `potential` ребёнка, сохраняя смысл `AND`, `OR`, поддерживаемых отрицаний и область действия каждого признака. Например, признак вида-основателя и проверка участника федерации относятся к разным объектам. Характеристики кандидатов не наследуются ребёнком через `prerequisites`.
2. Использовать требования ребёнка для тех характеристик, которые он задаёт. Для свободных характеристик применить базовый профиль обычной империи. Сохранять допустимые альтернативы целиком. Для `A OR B` подходят обе альтернативы, и базовый профиль не должен отбрасывать допустимую ветвь. Если проверка ссылается на другое игровое определение, продолжить обход только по известному правилу этой ссылки с её областью действия. Неизвестный предикат, неразрешимая ссылка или цикл сохраняют неопределённость соответствующей ветви.
3. Проверить собственный `potential` каждого кандидата в полученном контексте и при выбранных DLC. Исключать кандидата только при доказанной несовместимости со всеми допустимыми ветвями. Если кандидат подходит хотя бы в одной ветви или вывод остаётся неизвестным, он остаётся. В лог записать исходные варианты, использованные факты и результат этого критерия. Более раннее правило полного совпадения `potential` сохраняет свой приоритет. [Правило совпадения](../../../Docs/frontend/CHAIN_AVAILABILITY_RU.md)

Если у видимой технологии все кандидаты скрыты, она начинает самостоятельную ветвь с диагностикой `no_visible_parent`. При нескольких оставшихся кандидатах родитель также равен `null`. В лог неоднозначности записываются ID технологии, кандидаты, дерево, DLC и версия правил. Исходная технология без пререквизитов — обычный корень.

## Третий проход. Координаты

Функция дважды размещает один граф, получая названия через серверную локализацию для `ru` и `en`. Порядок областей — физика, социология, инженерия. Столбец соответствует уровню отображения, включая перенос на уровень 6 для `tier = 5`, `levels = -1` и хотя бы одного технологического пререквизита. Межобластная связь сохраняется в данных, а карточка начинает ветвь в собственной области.

Первыми идут деревья со стартовым корнем. Среди детей приоритет имеют продолжения с совпадающим после удаления цифр ID, внутри равных групп применяется языковая сортировка по названию, затем по игровому ID. При отсутствии перевода использовать то же обозначение ключа, что и для карточки. Первый ребёнок пробует строку родителя в другом столбце или следующую строку в том же столбце. Остальные ветви начинаются ниже предыдущего поддерева. У каждой видимой технологии ровно одна свободная ячейка для каждого языка. Линии и пиксельную геометрию рассчитывает интерфейс. [Правила сетки](../../../Docs/frontend/TZ_FRONTEND_STAGE_5_RU.md)

## Открытие и публикация

Вызов `POST /api/trees/reference` с телом `{"enabled_dlc":[]}` открывает справочник без DLC, с телом `{}` — со всеми DLC. Неверный тип, неизвестный ID или неподдерживаемая настройка дают HTTP 400. Готовый ответ HTTP 200 содержит `tree_id`, нормализованный `enabled_dlc`, массив `items` с видимыми узлами и обеими раскладками, а также поля карточек в `cards`.

1. Сервер переиспользует `ready`, если коллекция результата существует и актуальны исходные данные и правила. Ревизия данных охватывает UUID используемых опубликованных коллекций, включая локализацию. Ревизия правил охватывает алгоритм и содержимое его конфигов. Действующий загрузчик заменяет исходные коллекции при повторном импорте. [Проверка версии коллекций в загрузчике](../../loader/sttv_loader/__main__.py)
2. При отсутствии, устаревании или состоянии `failed` сервер начинает сборку. Одновременные запросы одного ID ожидают один расчёт. Три функции работают последовательно в памяти. После проверки связей и раскладок сервер записывает полный результат и переводит конфигурацию из `building` в `ready`.
3. Во время публикации загрузчиком исходных данных или при изменении их ревизии в процессе сборки смешанный результат не выдаётся. Ошибка сборки оставляет причину для повтора. После остановки процесса следующий запрос восстанавливает незавершённую сборку. Для клиента частично заполненное дерево недоступно. Операции записи сервер выполняет только в коллекциях деревьев и их конфигураций.

## Очистка построенных деревьев

В группе действий левой панели меню добавить кнопку **«Очистить построенные деревья»**. Она доступна в том числе при закрытом дереве и относится ко всем наборам DLC справочника. Использовать общую кнопку UI и встроенную локализацию. Пока запрос выполняется, кнопка недоступна. [Панель меню](../../../Docs/frontend/elements/TZ_MENU_PANEL_RU.md)

По нажатию клиент отправляет `DELETE /api/trees/reference` без параметров. Сервер выбирает из `tree_configs` записи режима `reference`. Для каждой записи он удаляет коллекцию `tree_<tree_id>`, если она существует, и затем саму запись конфигурации. Такой порядок позволяет повторить очистку после частичного сбоя. В область очистки входят только вычисленные деревья этого режима и их записи в реестре.

При активной сборке сервер возвращает HTTP 409 до начала удаления. На время очистки запрос открытия дерева также получает HTTP 409. Оставшаяся после прерывания запись `building` без активного расчёта подлежит очистке.

После успеха сервер возвращает HTTP 200 и число фактически удалённых коллекций, например `{"removed_collections":2}`. Для пустого набора результат равен нулю. Клиент освобождает отображаемое дерево, сохраняет выбор DLC и выводит количество в панели состояния. Новая сборка начинается при следующем явном открытии дерева. При ошибке панель состояния показывает причину.

## Матрица наборов DLC

В приёмке через HTTP обязательны **10 различных выборочных наборов** и отдельно два граничных. Для строк 1–9 передавать в `enabled_dlc` только перечисленные ID. Для строки 10 взять все ID из текущей `wiki.dlcs` и исключить два указанных. Повтор запроса с переставленными ID проверяет переиспользование, а переключение языка — вторую раскладку того же дерева.

| Вариант | Настройка DLC | Видны в ответе | Скрыты в ответе |
| --- | --- | --- | --- |
| Все DLC | `{}` | `tech_cosmogenesis_weaver`, `tech_archaeo_pk_devolving_beam` | `tech_archeology_lab` |
| Без DLC | `{"enabled_dlc":[]}` | `tech_archeology_lab`, `tech_missiles_1` | `tech_weaver_bio_anti_evasion_1`, `tech_arcane_deciphering` |
| 1 | `dlc036` | `tech_weaver_bio_anti_evasion_1` | `tech_identity_copy`, `tech_cosmogenesis_weaver` |
| 2 | `dlc032` | `tech_identity_copy` | `tech_weaver_bio_anti_evasion_1`, `tech_cosmogenesis_weaver` |
| 3 | `dlc032`, `dlc036` | `tech_cosmogenesis_weaver` | `tech_titans` |
| 4 | `dlc021` | `tech_archeology_lab_ancrel`, `tech_arcane_deciphering` | `tech_archeology_lab`, `tech_archaeo_pk_devolving_beam` |
| 5 | `dlc017` | `tech_titans`, `tech_archeology_lab` | `tech_archaeo_pk_devolving_beam`, `tech_arcane_deciphering` |
| 6 | `dlc017`, `dlc021` | `tech_archaeo_pk_devolving_beam`, `tech_titans` | `tech_archeology_lab` |
| 7 | `dlc023`, `dlc027` | `tech_juggernaut`, `tech_hyper_relays` | `tech_titans` |
| 8 | `dlc029`, `dlc031` | `tech_cloaking_1`, `tech_rift_sphere` | `tech_hyper_relays` |
| 9 | `dlc034`, `dlc040` | `tech_dyson_gun`, `tech_galactic_archivism` | `tech_rift_sphere` |
| 10 | Все, кроме `dlc032`, `dlc036` | `tech_missiles_1`, `tech_archaeo_pk_devolving_beam` | `tech_identity_copy`, `tech_weaver_bio_anti_evasion_1` |

Строки 1–3 проверяют косвенное условие биологических кораблей в сочетании с The Machine Age. Строки 4–6 различают отрицание Ancient Relics, совместное требование Apocalypse и Ancient Relics и обнуление веса `tech_arcane_deciphering`. В строке 10 ракеты остаются видимыми благодаря альтернативе в `OR`.

Для каждого набора пройти открытие → чтение из MongoDB → повторное открытие. Сверить состав исходных ID с документами коллекции, а флаг `availability` каждого документа — с присутствием ID в HTTP-ответе. Проверить контрольные ID из таблицы, взаимность связей, уникальность ячеек внутри области для RU и EN и `location: null` у скрытых узлов. В отчёте по каждому набору записать переданные ID, `tree_id`, количество видимых и скрытых узлов и расхождения с ожидаемыми ID. У разных наборов должны различаться ID деревьев, при повторном открытии того же набора используется готовая коллекция.

## Приёмка

| Сценарий | Проверяемый результат |
| --- | --- |
| `tech_science_arkship` | Если отбор дошёл до контекста империи, применяется `is_nomadic = yes` ребёнка. Кандидат `tech_arkship_construction` проходит проверку кочевого признака. |
| `tech_modular_engineering` | Собственный `potential` отсутствует. На входе критерия с двумя видимыми кандидатами базовый профиль оставляет `tech_starbase_3` из пары с `tech_waystation_2`. |
| `tech_transcendent_faith` | Сохраняется альтернатива между спиритуализмом и негештальтной империей с соответствующим федерационным бонусом. Полное совпадение с `tech_consecration_fields` проверяется на более раннем шаге. |
| Малые наборы | Проверить вложенные альтернативы, отрицание и неизвестную ветвь, отсутствие видимого родителя, отбор с нулём совпадений и неразрешённую ничью. Цикл выбранных родительских связей блокирует публикацию. |
| Связи и сетка | Для каждого выбранного ребра записи родителя и ребёнка взаимны. Для RU и EN проверить уникальность ячейки внутри области, порядок различающихся переводов, устойчивость при равных названиях и межобластную ветвь. |
| Повтор, конкуренция и сбой | Переставленные или повторённые ID DLC дают то же готовое дерево. Второй запрос не запускает повторный расчёт. Проверить отказ до публикации, восстановление и смену ревизии данных или правил. |
| Очистка из меню | На стенде с изначально пустым реестром собрать все 12 деревьев матрицы. Одно нажатие возвращает `{"removed_collections":12}`: удалены все 12 коллекций и их записи, исходные игровые коллекции доступны, выбор DLC сохранён. Повторное нажатие даёт ноль. Явное открытие заново строит только выбранное дерево. |
| Очистка и сбой | Во время активной сборки очистка даёт HTTP 409 и сохраняет деревья. После прерывания между удалением коллекции и её записи повторная очистка завершает операцию. |

Синтетические проверки провести на малых наборах, интеграционные — через HTTP на Ubuntu VM с опубликованными игровыми данными. Сопоставить матрицу DLC с результатами прежнего этапа для сопоставимых версий и объяснить расхождения. Измерить первый расчёт по проходам и повторное открытие готового дерева.
