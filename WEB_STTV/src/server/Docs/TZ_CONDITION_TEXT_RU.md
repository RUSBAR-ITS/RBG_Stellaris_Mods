## Границы и исходные данные

Сервер формирует RU/EN описание того, **что должно выполняться, для какого объекта и при каких альтернативах**. Первое подключение охватывает `prerequisites`, `potential`, `allow`, условия модификаторов веса и всех трёх способов получения технологии. Такой же вызов должен принимать условие здания, ситуации или события. Вычисление доступности, выбор источников и построение дерева остаются ответственностью существующих функций. Описание требования само по себе не утверждает, что игрок его выполнил.

Основание — аудит 679 базовых технологий v4.5.4 на двух языках. На 379 страницах теряется аргумент или содержимое условия, на 40 булево значение стало названием залежи, на 119 одновременно показаны исходы успешной и неуспешной проверки. Сейчас `Content.unknown` отдаёт исходный узел, а `ProgressContent.unknown` оставляет на странице только ключ. Отправной точкой служат существующий рекурсивный обработчик, серверный поиск локализации и общий компонент страницы и карточки. [Аудит](../../../Docs/frontend/TECHNOLOGY_PAGE_READABILITY_RU.md) · [Условия технологий](../sttv_server/technology_tooltip.py) · [Условия наград](../sttv_server/progress_content.py) · [Компонент вывода](../../frontend/ui/composite/TechnologyTooltipDetails.tsx)

## Контракт общего обработчика

| Вход | Кто и зачем передаёт |
| --- | --- |
| Узел или упорядоченный список узлов разобранного скрипта | Вызывающая функция передаёт исходные операторы, значения и вложенное дерево. Для списка она указывает роль контейнера, например требования, проверки ветви или аргументы команды. |
| Контекст | Тип и ID исходного объекта, раздел, текущий субъект и известные роли цепочки вызовов. Ссылка `from` интерпретируется в месте вызова. Условия входа в событие и условия выбора ответа могут иметь разных субъектов. |
| Представление | Язык, режим справочника и известные настройки, например выбранные DLC. Если известна только настройка DLC, она определяет пометку DLC и не даёт сведений об активном событии или запасах империи. |
| Происхождение | Ссылка на документ и путь к узлу, если известны. Синтетическое условие ветви ссылается на место вызова или на исходную ветвь. |

Результат — упорядоченные узлы для существующего API и отдельные диагностические записи. У узла есть вид (условие, группа, область действия или подпись), локализованный текст и при необходимости дочерние узлы. Для ссылки сохраняется тип и ID объекта, для группы — оператор. Внутри обработки до выбора фразы доступны субъект, оператор сравнения, типизированные аргументы и полярность. Источник запроса определяет внешний раздел, заголовок награды и величину эффекта. Фронтенд отображает текст, вложенность, подсветку и игровые значки. Одна страница и её тултип получают одинаковое содержание при одинаковых настройках.

Например, для отрицания с одним `has_active_event = { crisis.4135 }` результат может быть одним узлом условия с отрицательной формулировкой и ссылкой на событие `crisis.4135`. Для `OR` из двух независимых условий результат содержит группу и оба дочерних узла. Обратная связь с исходным адресом нужна и после такого сокращения.

## Коллекция тултипов и её сброс

Сервер сохраняет подготовленное содержимое в MongoDB в коллекции `technology_tooltips`. Один документ на ID базовой технологии содержит структуру условий, типизированные ссылки, ветви получения и адреса источников. Страница и тултип читают один документ. Перевод и пометки о выбранных DLC применяются при чтении. При первом запросе к технологии сервер использует актуальный документ, в том числе после перезапуска. При отсутствии документа или изменении ревизии исходных данных либо правил сервер заново готовит запись для запрошенного ID.

В **Настройки системы → Операции с БД** добавить кнопку **«Сбросить содержимое тултипов»**. Действие относится ко всей коллекции сразу и не принимает ID технологии. После успеха в коллекции остаётся ноль подготовленных документов, клиент очищает кэш тултипов для всех языков и наборов DLC, а панель состояния сообщает результат. Экспорт загрузчика, построенные деревья и общий указатель источников сохраняются. Следующий явный запрос страницы или тултипа создаёт документ запрошенной технологии. Запоздалый результат запроса, начатого до сброса, не должен восстановить устаревший документ или ответ в кэше клиента.

Общий сброс построенных данных включает эту коллекцию. Сброс указателя источников также инвалидирует зависящие от него документы тултипов. Интерфейс страницы технологии сохраняет обычные действия просмотра. [Операции с производными данными](TZ_TOOLTIP_RESEARCH_PROGRESS_RU.md)

## Как добавить правило

1. **Определить значение конструкции.** Для простых правил достаточно строки в общей таблице сервера: игровой ключ, допустимая форма значения, операции, предметный тип аргумента и ключ фразы. Различитель контекста добавлять только при подтверждённой разнице значений. В отдельных языковых файлах хранятся парные шаблоны RU/EN с одинаковыми именованными параметрами. Имена предметов получает действующая функция локализации. [Словарь фраз](TZ_TOOLTIP_DICTIONARY_RU.md) · [Настройки ключей](../config/localization_keys.json)
2. **Выбрать правило однозначно.** Сначала точное совпадение ключа, контекста, операции и формы, затем общая форма того же ключа. Для перегруженной команды различать допустимое булево, число, ссылку, список ссылок и блок именованных полей. Игровые ключевики и известные переходы сопоставлять без учёта регистра. ID, ключи локализации и строковые значения сохранять в исходном написании. Конфликт равноценных правил выдаёт диагностику. Неизвестный оператор, лишнее поле или иное значение не получают смысл ближайшего похожего правила.
3. **Подставить аргумент.** Например, для `has_starbase_module = <id>` достаточно правила с аргументом «модуль базы», поиском `sm_<id>` и шаблоном «На станции установлен модуль „{module}“». Следующий модуль с такой же формой и игровым переводом появляется автоматически. Для `has_deposit` требуются отдельные формы проверки наличия и ссылки на конкретную залежь. Префиксы `has_`, `is_` и `any_` сами по себе не устанавливают семантику.
4. **Выделить сложную форму при необходимости.** Для блока с разными ролями полей, счётчика с фильтром или вычисляемой величины использовать именованный обработчик в коде. Например, в `resource_stockpile_compare` поля `resource`, `value` и `mult` образуют одно сравнение. Сохранить знак у `value`, единицу и вычисляемый множитель. Дополнительные дочерние проверки обрабатывать только там, где это позволяет форма блока. Для обычной проверки добавления правила и переводов должно быть достаточно без правок страницы, парсера или загрузчика.

Пример записей для предлагаемого `src/server/config/condition_rules.json`. У `has_deposit` литералы `yes` и `no` выбирают булеву форму до поиска залежи по ID. Правило имени модуля `sm_<id>` добавить в действующий `localization_keys.json`. Если заголовок задан полем самого объекта, сервер берёт ключ из этого поля.

```json
[
  {"key": "has_starbase_module", "operator": "=", "form": "reference", "reference": "starbase_module", "phrase": "sttv_tooltip_has_starbase_module"},
  {"key": "has_deposit", "operator": "=", "form": "boolean", "phrases": {"yes": "sttv_tooltip_has_any_deposit", "no": "sttv_tooltip_has_no_deposit"}},
  {"key": "has_deposit", "operator": "=", "form": "reference", "reference": "deposit", "phrase": "sttv_tooltip_has_deposit"}
]
```

## Логика и субъект

- В контейнере условий сохранять неявное И, явные `AND`, `OR`, `NOT`, `NAND`, `NOR`, порядок и повторения. Для ИЛИ годится «хотя бы одно». Для NAND — «выполнены не все условия», для NOR — «не выполнено ни одно условие». Одиночные И/ИЛИ сокращать по действующим правилам. Для отрицания одного известного предиката применять согласованную отрицательную фразу либо точную инверсию сравнения. В остальных случаях оставить группу со всеми операндами, в том числе у многочленного `NOT`. Пустая или частично распознанная группа не даёт основания объявлять проверку безусловной. [Семантика](../../../Docs/semantics/LOGIC_AND_CONTEXT_RU.md) · [Согласованные сокращения](TZ_TOOLTIP_CONDITION_SIMPLIFICATION_RU.md)
- Смена области действия переносит субъект только внутрь соответствующего блока. Учитывать `root`, `this`, `prev`, `from`, составные пути, сохранённые цели, необязательные переходы с `?` и кванторы. Для `any_owned_…` две проверки внутри одного блока должен выполнять **один и тот же** объект. `exists = owner` проверяет наличие владельца. `owner = { … }` применяет проверки к владельцу. При отсутствии данных о роли `from` показывать известную связь с вызывающим контекстом и сохранять неопределённость.
- В цепочках `if / else_if / else` сохранять условие текущей ветви и исключения для предыдущих ветвей той же цепочки. У `switch` сохранять предмет выбора, ветвь и условие перехода в `default`. Порог, прибавку веса, множитель, относительный вес случайного исхода и процент прогресса подписывать по их роли. Ноль — значимое значение. Вычисляемый порог можно показать формулой.
- У скалярного `custom_tooltip` есть подпись. В блоковой форме отделять текстовые поля от проверок. Для справочника строить одно нейтральное требование. Готовая игровая фраза может заменить показ поддерева, если передаёт его смысл целиком. Иначе показывать реальные условия. `success_text` и `fail_text` — варианты сообщения об одной проверке. `hidden_trigger` сохраняет действие вложенных условий. Соблюдать согласованный игнор `has_country_flag = crystal_armor_1_weight`: скрытый единственный guard не должен превратить модификатор в безусловный бонус. [Игровые подсказки](../../../Docs/semantics/TOOLTIPS_RU.md) · [Исключение для флага](TZ_TOOLTIP_FLAGS_RU.md)

## Язык и неполные данные

- Законченная фраза должна называть действие и предмет. Для однородных групп исследованных технологий допустим общий заголовок со сказуемым. В смешанной группе отдельная технология получает фразу «Исследована технология…». Каждый заголовок перед списком завершается одним двоеточием. Для модификатора сохранять принятую запись «(×N) условие». Числа и формулы форматируются на выбранном языке.
- Имя по типу объекта и ID получать пакетно существующим поиском для языка запроса. Например, `primitive` в `is_country_type` требует предметного названия «досветовая цивилизация». Для словаря именованных объектов, переменных и флагов использовать подтверждённое значение именно в этой области. У флага учитывать владельца и места установки/снятия. Статическую переменную подставлять из данных версии. Имя правителя или планеты из партии заменять ролью, если роль установлена. Готовые RU/EN строки сохраняют приоритеты источников проекта. В пользовательском тексте не должны оставаться обрезанные основы, таблицы склонений и необработанные токены игровых иконок. [Словарь флагов](TZ_TOOLTIP_FLAGS_RU.md) · [Инвентаризация значков и форм](../../../Docs/frontend/TECHNOLOGY_PAGE_READABILITY_RU.md#иконки-и-локализация)
- Различать **неизвестную команду**, **неизвестную роль объекта**, **отсутствующее имя** и **отсутствующий перевод фразы**. Например, если модуль известен по ID, а заголовка нет, написать «Требуется модуль станции (название не найдено)» с доступным пользователю техническим ID в подробностях. Если неизвестно значение части условия, явно отметить неполное описание на месте этой части и сохранить остальные ветви и их логическую связь. Отсутствующая отрицательная фраза допускает читаемую группу отрицания вокруг положительной.
- Диагностика содержит причину, исходные ключ, оператор и операнд или поддерево, объект, раздел, доступный адрес и язык, когда причина связана с локализацией. Для повторов допустима одна запись со списком мест. Полное исходное выражение доступно для сверки. Сообщение «Дополнительное условие (ключ)», пустая строка и молчаливое удаление узла не удовлетворяют этому контракту.

## Условия в цепочке получения

За поиск пути отвечает существующий индекс источников. При извлечении проверки привязывать к ней субъект и место действия именно в точке проверки. Один путь может сменить владельца несколько раз до выдачи награды. Если для этого понадобится расширить запись производного индекса, пересобрать её существующей операцией сброса. [Индекс источников](../sttv_server/progress_sources.py)

Шаги описываются в порядке «обстоятельство → событие или выбор → получатель и награда». Название события, стадия, обработчик и условие получают собственные подписи. Для события использовать его заголовок, включая наследование через `base` с учётом переопределений и циклов. Для скрытого события без названия указывать подтверждённое обстоятельство его срабатывания. Например, `shroud.1010` — «При завершении ситуации „Экспериментальные опыты“». Ссылки на события имеют единый стиль независимо от исходной окраски названия. [Контракт трёх разделов](../../../Docs/frontend/TZ_TECHNOLOGY_PAGE_AND_ACQUISITION_RU.md)

Общие шаги допускается вынести один раз, если совпадают объект, субъект проверки, получатель, условия и результат на выносимом участке. У альтернатив остаются собственные ответы, ограничения и награды. Одноимённые события и разные величины награды сохраняют идентичность. В режиме справочника источник с отключённым DLC остаётся виден с соответствующей пометкой.

## Контрольные примеры

| Вход или конкретный случай | Ожидаемое прочтение |
| --- | --- |
| `NOT = { has_active_event = { crisis.4135 } }` у пятого уровня кризиса | «Событие „Конец близок“ не должно быть активно». Многоэлементную форму проверить отдельно по семантике списка этой команды. |
| `OR` из некочевого государства и принадлежащей ему маршрутной станции с якорем | «Для кочевой империи нужна хотя бы одна принадлежащая ей маршрутная станция с модулем „Эфирофазный якорь“». Некочевая империя удовлетворяет первой альтернативе. |
| `capital_scope → observation_outpost → has_mission = specimen_collection` | «На орбите столицы наблюдаемой цивилизации есть станция с заданием „Агрессивное наблюдение“». В полном условии сохранить наличие владельца станции. Ответ выбирает наблюдатель. |
| `has_deposit = no` и синтетический `has_deposit = <deposit_id>` | «Залежей нет» и «Есть залежь „{название}“». |
| `resource_stockpile_compare = { resource = astral_threads value >= 1000 }` | «В запасе не менее 1 000 астральных нитей». Смена на `>` означает «больше», а не «не менее». |
| Строительство `dark_matter_detector` | «Комплекс обнаружения уже установлен или стоит в очереди перед детектором». Используется то же правило `has_starbase_module`, что у якоря. Отдельный запрет из соседнего `NOT` сохраняется. |
| `OR` из известной технологии и неизвестной проверки с аргументом | Альтернатива с технологией и пометка о второй проверке видимы вместе. В диагностике доступен её точный аргумент. |
| Путь «Синих лазеров» через «Побочные эффекты» | При выполнении условий выдачи закрытый вариант исследования открывается с +80% прогресса, уже открытый получает +100%. Вес 50 в таблице наблюдения подписывается как относительный вес. Эти три числа имеют разные роли. |

## Этапы и приёмка

1. **Общий обработчик.** Подключить его к четырём разделам технологии и условиям трёх наград. Проверить рекурсию, перегрузки ключей, вложенные субъекты, отрицания, пороги, сохранность неизвестных ветвей. Один фрагмент с одинаковым субъектом и назначением должен давать одинаковый смысл в разных местах. Фрагмент здания из таблицы принимается тем же входом без отдельной страницы здания.
2. **Словарь и источники.** Разобрать перечисленные ниже формы на данных снимка. Для каждой указать, какая форма поддержана, какими игровыми данными подтверждена роль и что ещё требует исследования. Для 148 событий и 57 имён `on_…` сначала использовать тип источника и существующие игровые подписи. Отдельно сверить 281 пару «проверка — флаг» без специальной подписи. Подтверждённым значениям дать фразы RU/EN, для остальных зафиксировать конкретную причину и места использования. Общая заглушка не засчитывается как поддержка.
3. **Вывод и проверка.** Подключить общие узлы к существующему компоненту. Проверить шесть значков из аудита, отсутствие служебной разметки, читабельную вложенность, локализацию чисел и равенство содержания страницы и тултипа. Для флагов и динамических целей проверить и заведомо неполный пример.
4. **Приёмка снимка.** До и после сравнить все 679 технологий в RU/EN при всех включённых DLC. Для каждой формы повторно посчитать затронутые страницы и уникальные значения, отдельно отметить осмысленный вывод, частичный вывод с причиной и расхождения. Ноль потерянных операндов и дочерних ветвей, ноль объектов с именем `no` из булева условия и ноль пар взаимоисключающих статусов в справочнике. Фразы без исходного игрового ID в основном тексте сверять по ID и адресу в данных. Для условий с подтверждённой семантикой проверять именно текст, включая отрицание. Для разобранных примеров таблицы общая заглушка считается ошибкой. В примере с неизвестной командой проверяется сохранность частичного результата.
5. **Регрессии.** Сверить ID источников, адреса наград, выбор, получателя, исходы, величины и принадлежность к трём разделам до и после. Для структурных сокращений сравнить значения на комбинациях истинности малых выражений, включая NAND/NOR и неизвестную ветвь. Проверить одну ветвь с включённым и отключённым требуемым DLC. На неизменном снимке ориентиры числа технологий с разделом — 289, 248 и 298 соответственно. Запрос страницы по-прежнему использует индекс получения и пакетный поиск строк. Массовый обход событий при каждом наведении и запрос БД на каждый лист исключаются. Итог сверки хранить в `TMP/WEB_STTV/<прогон>/reports/`.

6. **Полный проход страниц в браузере.** После реализации взять все ID базовых технологий из проверяемого снимка. Для каждого ID при всех включённых DLC открыть в браузере прямую страницу `#/technology/<id>?lang=ru`, затем английскую версию с `lang=en`. Дождаться отрисовки и для каждой пары «ID, язык» сверить заголовок, состав разделов и видимый текст условий с проверенными данными API. Проверить вложенность списков, отсутствие необработанных игровых токенов и загрузку предусмотренных текстом значков. В отчёте указать результат для каждой пары и причину каждого сбоя. Для снимка v4.5.4 ожидаются 679 × 2 = **1 358** уникальных страниц. Критерий приёмки — успешная проверка каждой ожидаемой пары без пропусков. При смене снимка пересчитать охват по его ID.

7. **Сброс коллекции.** Подготовить документы двух разных технологий, открыть их с разными языками и DLC, выполнить сброс в системных настройках. Сверить пустую коллекцию и очищенный кэш клиента до нового запроса. Повторный сброс пустой коллекции должен завершиться успешно. После запроса одной из технологий проверить, что создан только её документ. Проверить сброс при незавершённом запросе, общий сброс и сброс указателя источников.

8. При проверке стенда выполнить полный цикл от чистого экспорта до загрузки и сверки всех коллекций после `dropDatabase`. Проверить локализацию и значки штатными профилями. Снять перечень исходных ID до сброса.
