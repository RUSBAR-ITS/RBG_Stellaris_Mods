## 3. Границы этапа

Входят выбор объектов готовой БД, чтение RU/EN, выбор текста по приоритетам, раскрытие обычных статических ссылок, наследование описания варианта, сохранение результата в БД, отчёт, программная операция и неинтерактивный запуск, схемы и проверки.

Не входят локализация других объектов, автоматический перевод, наполнение глоссария, иконки, HTML и визуальное исполнение игровой разметки, вычисление динамических значений, условия доступности для государства, интерфейс, HTTP-служба, сжатие/разбиение БД и удаление игровых механик. Старый профиль допустимых команд не возвращается. Переводы извлекаются из файлов, а не сочиняются.

## 4. Конфигурация и источники

Отдельный конфиг `config/enrichment/localization.json` с `format_version: 1` задаёт следующие группы настроек. Он не становится девятым конфигом парсера и не требуется обычной сборке деревьев.

| Группа | Требования и начальные значения |
|---|---|
| Вход и выход | `database: "database.json"`, `report: "reports/localization_report.json"`, относительно `WORK_DIR`; БД читается и обновляется по одному пути |
| Выбор технологий | Переменная `TECH_PATH`, `pattern: "*.txt"`, `recursive: false`; сопоставление с путями документов БД |
| Ключи | Основное название из ключа объекта; вариант из прямого поля `name` в прямом блоке `technology_swap`; суффикс описания `_desc` |
| Языки | `ru` / `l_russian`, `en` / `l_english`; отдельные упорядоченные списки источников |
| Чтение | `pattern: "*.yml"`, `recursive: true`, `encoding: "utf-8-sig"` |
| Ссылки | Разделитель `$`, обычный ключ соответствует `[A-Za-z0-9_.:-]+`; предел глубины 64, предел итогового текста одного поля 1 000 000 символов |
| Наследование | Использовать описание основной технологии при отсутствии собственного ключа варианта |

Пути брать из `global_variables.json`, раскрывая `${...}` существующим механизмом. Относительные каталоги локализации отсчитывать от `STELLARIS_ROOT`:

| Язык | Приоритет, от высшего к низшему |
|---|---|
| RU | `RU_LOC_TIER_1` → `RU_LOC_TIER_2` → `RU_LOC_TIER_3` |
| EN | `EN_LOC_TIER_1` |

Список источников настраиваемый; конкретный мод не является обязательной зависимостью продукта. Каждый явно включённый источник должен быть доступен для чтения; отсутствующий каталог не пропускать молча. Пользователь может убрать источник из конфигурации. Существующий пустой каталог допустим, а отсутствие текста диагностируется отдельно.

Чтение готовой обогащённой БД не требует исходников. Для самой операции нужны БД и выбранные каталоги локализации; каталоги технологий, inline-вставок, эффектов, триггеров, переменных и script values не перечитываются. `TECH_PATH` используется как адресная настройка, без проверки наличия каталога на диске.

## 5. Выбор объектов и ключей

В выбранных документах технология — корневое присваивание `имя = { ... }`. Имя не определяется префиксом `tech_`: например, существует `null_void_beam`. Скалярные декларации и другие формы не становятся технологиями. Стандартный нерекурсивный селектор исключает документы `category/` и `tier/`, сохраняя их данные в БД.

У технологии обрабатывать прямые присваивания `technology_swap = { ... }`; внутри каждого брать единственное прямое скалярное поле `name`. Не искать произвольные поля `name` или `desc` по всему дереву. `prereqfor_desc.desc` описывает открываемые возможности и в общее описание технологии не переносится. Отсутствующее, повторное или нескалярное имя варианта — ошибка выбора объекта с координатами.

| Объект | Ключ названия | Ключ описания |
|---|---|---|
| Основная технология | Ключ корневого присваивания | Тот же ключ + `_desc` |
| Условный вариант | Значение его поля `name` | Это значение + `_desc` |

Объект адресуется своим местом в БД: JSON Pointer от корня, например `/documents/0/items/2`. Для варианта путь ведёт к самому присваиванию `technology_swap`, а не к его полю `name`. Повторяющиеся имена не объединять: это отдельные узлы. Родителем варианта является окружающая технология.

Правила выбора отделить от чтения текстов и разрешения ссылок. Этот этап реализует один тип правил для технологий и вариантов; универсальный язык запросов или реестр всех типов игровых объектов не требуется. Если в БД нет подходящих технологий, завершать операцию ошибкой выбора, не выдавая пустую обработку за успех.

## 6. Чтение локализации и приоритеты

Читать игровой формат строк `key:0 "text"` и `key: "text"`, заголовки языка, пустые строки и комментарии; поддержать UTF-8 с BOM и без него. Номер после двоеточия не является приоритетом источника. Общий YAML-парсер с автоматическим преобразованием типов не применять.

Хранить содержимое между внешними кавычками без изменения регистра, пробелов внутри строки, экранирования, игровых значков, цветовой и грамматической разметки. `#` внутри текста не становится комментарием; комментарий после внешней закрывающей кавычки не включается в текст. Учитывать экранированные и встречающиеся внутренние кавычки. Последовательность `\n` из игрового файла после чтения JSON остаётся двумя символами, а не автоматически превращается в перевод строки. JSON-экранирование выполнять стандартным сериализатором.

Индексировать ключи точно, с учётом регистра, отдельно по языкам. Из смешанных источников учитывать только секции требуемого языка. Нечитаемый файл, ошибка кодировки или неоднозначная/неподдержанная строка локализации дают диагностику с файлом и строкой; не терять их молча.

Приоритет применять к каждому ключу независимо, включая вложенные ссылки. Переходить ниже только при отсутствии ключа. Пустая строка `""` считается найденным значением. Не заменять отсутствующий RU английским текстом, идентификатором технологии или самостоятельно придуманным переводом.

Одинаковые дубли внутри одного приоритета допустимы: источник выбирать детерминированно по относительному пути и номеру строки. Разные значения одного ключа в выбранном приоритете — ошибка; не выбирать произвольно и не переходить ниже. Конфликт в недостигнутом ключе или перекрытом нижнем приоритете отражать в отчёте, но не блокировать выбранные тексты. Для сравнения брать исходный текст, до раскрытия ссылок.

## 7. Ссылки и наследование описания

Обычную ссылку `$key$` раскрывать рекурсивно, если точный ключ найден в индексе того же языка. Каждый переход заново использует упорядоченный список источников. Например, `$tech_archeology_lab_desc$` заменяется выбранным описанием и его достижимыми статическими ссылками. Исходную строку поля сохранять отдельно от результата.

Разбирать границы токенов: динамические `[...]`, форматированные `$KEY|...$` и значки `£...£` сохраняются целиком; их содержимое не интерпретируется как обычные ссылки. Цветовые коды и остальная игровая разметка сохраняются, но не мешают раскрытию обычных ссылок в окружаемом ими тексте. Подстановки параметров игрового кода и их значения по умолчанию здесь не применяются. Точная форма `$NAME$` без найденного ключа сама по себе не доказывает ошибку: это может быть динамическая подстановка. Оставлять её без изменений, записывая неразрешённый токен и предупреждение; не угадывать значение.

Цикл статических ссылок или превышение настроенного предела — ошибка с цепочкой ключей. Общие зависимости можно кешировать по языку и ключу, но кеш не должен скрывать цикл или нарушать предел глубины/размера. Результат не зависит от порядка обработки объектов.

Для описания варианта сначала искать его собственный ключ **во всех приоритетах нужного языка**. Только если ключ отсутствует, брать описание основной технологии того же языка и отмечать наследование. Собственное пустое описание не заменять; ошибку или неразрешённую ссылку в существующем описании не обходить наследованием. Название варианта от основной технологии не наследуется.

Если нет и описания основной технологии, сохранять отсутствие текста и предупреждение. Наследование успешно найденного родительского описания — нормальный результат, учитываемый отдельным счётчиком. На разных языках один вариант может иметь собственное и унаследованное описания.

## 8. Хранение в БД

Целевой формат — `sttv.parse_database`, `format_version: 4`. Структурные поля девяти видов узлов остаются прежними. У узла `assignment` допускается необязательное служебное поле `enrichments`, в этом этапе с объявленным подразделом `localization`. Отсутствие обогащения допустимо: обычный сборщик выдаёт формат 4 без локализации и не читает её источники.

Результат находится непосредственно у основной технологии или присваивания варианта. Структура доступа:

```text
node.enrichments.localization.ru.name
node.enrichments.localization.ru.description
node.enrichments.localization.en.name
node.enrichments.localization.en.description
```

Каждое из четырёх полей имеет одинаковую объявленную структуру:

| Поле | Тип и смысл |
|---|---|
| `requested_key` | Строка: собственный ключ названия/описания объекта |
| `key` | Строка фактически выбранного ключа либо `null`, если текст отсутствует |
| `raw` | Исходное содержимое выбранной строки либо `null` |
| `text` | Текст после раскрытия обычных статических ссылок либо `null` |
| `source` | `{tier, file, line}` либо `null`; `tier` — имя переменной источника, `file` — путь относительно него с `/`, `line` — номер от 1 |
| `inherited_from` | JSON Pointer к основной технологии при успешном наследовании описания, иначе `null` |
| `unresolved_references` | Массив уникальных неразрешённых обычных токенов `$...$`, включая пришедшие из вложенных ссылок, в стабильном порядке |

При наследовании `requested_key` остаётся ключом варианта, а `key`, `raw`, `text` и `source` относятся к описанию основной технологии. Отдельный булев флаг не нужен: ненулевой `inherited_from` однозначно отмечает наследование. Если текста нет, все поля выбора и наследования равны `null`, массив ссылок пуст; запрос сохраняется. Для найденного пустого текста `raw` и `text` равны `""`, источник и ключ заполнены.

Не вставлять локализацию в игровые `items`, `key`, `value` и не менять порядок, повторы, `span`, `origin` или историю `expansions`. Аналитика обходит только дочерние синтаксические узлы; обогащение не добавляет игровых узлов или вхождений в частотную статистику. Структура служебного раздела проверяется схемой, а имена игровых полей по-прежнему не ограничиваются реестром.

Полные словари языков и промежуточные индексы в БД не копировать. Источники достигнутых ссылок и контрольные хеши перечисляются в отчёте. Для просмотра сохранённых названий и описаний достаточно самой БД; отдельный файл локализации для связывания с ней не создаётся.

## 9. Обновление и публикация

Операция читает и валидирует БД, выбирает объекты, загружает локализации, готовит все четыре поля каждого объекта и заменяет только подраздел `enrichments.localization`. При изменении селектора старые подразделы локализации, созданные этой операцией, удаляются у переставших попадать в выборку объектов. Остальные поддерживаемые служебные данные и всё игровое дерево сохраняются. Повтор с неизменными входами даёт побайтно одинаковую БД; время запуска хранится только в отчёте.

Полная повторная сборка парсером создаёт новую БД без прежнего обогащения. Локализация запускается снова явно; автоматически переносить её из старого дерева по совпадению имён нельзя. Старые форматы не поддерживаются рабочей операцией: требуется пересборка. Для проверки этого этапа готовится новая база в `data/stage10/`, прежние результаты сохраняются.

Путь БД намеренно совпадает для чтения и записи. Это локальное исключение из проверки коллизий входов/выходов; оно не разрешает перезапись исходников, конфигов, схем или отчёта тем же файлом. Все записи — в разрешённом `WORK_DIR` внутри репозитория. Проверять разрешённые физические пути существующими средствами.

Публиковать через временный файл рядом с БД: сериализация, проверка схемы и связей, повторное чтение, затем атомарная замена. При ошибке подготовки прежняя БД остаётся целой. Перед заменой проверять, что входная БД и прочитанные источники/настройки не изменились за время операции. Одновременную запись несколькими процессами в одну БД этот этап не поддерживает.

Отчёт сохраняется отдельно существующим безопасным механизмом. Два файла не объявлять общей транзакцией: если БД уже заменена, а запись отчёта не удалась, результат операции обязан сообщить об этом и сохранить правдивый `database_written`. Не сообщать, что старая БД сохранена, если замена состоялась.

## 10. Диагностика

Отчёт `sttv.localization_report`, версия 1, содержит статус, `database_written`, хеш БД до/после, настройки и их хеши, перечень прочитанных файлов с хешами, счётчики по языкам/полям и диагностику. Включить выбранные источники транзитивных ссылок, сведения о дублях, пропусках, наследовании и неразрешённых токенах. Абсолютные пути окружения допустимы в рабочем отчёте, но не требуются в обогащённых узлах.

Диагностика объекта содержит JSON Pointer, язык, поле, запрошенный ключ и доступные координаты источника; для ссылок — цепочку. Отсутствующий текст и неразрешённый обычный токен дают предупреждение, допускающее публикацию с явно неполным полем. Динамическая разметка, сохранённая по правилам, сама по себе предупреждения не требует.

Ошибки конфигурации, чтения, формата БД, выбора объекта, неоднозначного выбранного текста, цикла, лимита или записи препятствуют успешному результату. Не публиковать частично обработанную БД при ошибках. Числа из исследования не являются условием успешности для другой установки игры.

## 11. Модули и схемы

Добавить пакет `sttv/enrichment/localization/`: настройки, выбор целей, чтение строк, индекс приоритетов, разрешение ссылок, прикрепление результата и координация операции — отдельные компактные обязанности. Использовать существующие средства JSON, путей, ошибок и безопасной публикации. Если общий код раскрытия переменных настроек нужен отдельно от загрузчика парсера, вынести только этот общий код, без стороннего рефакторинга.

Предоставить Python-операцию и неинтерактивную команду с путями конфигурации/глобальных переменных. Не создавать диалог настройки или веб-интерфейс. Программный результат возвращает статус и пути, пригодные для последующего интерфейса; конкретный вызов описать в руководстве реализации.

Обновить генератор `database.schema.json` для формата 4; добавить генерируемые `localization.schema.json` и `localization_report.schema.json`. Итого ожидаются 13 схем. Схемы редактируются через код генератора; игровой профиль команд не нужен. Проверка наследования требует существующего родительского узла и соответствующего текста, проверка происхождения не открывает игру. Существующие читатели и аналитика должны принимать обогащённую БД, не обходя её служебные разделы как код.

## 12. Проверки и приёмка

Синтетические проверки должны покрыть:

1. Независимые RU/EN, приоритет по каждому ключу и каждой вложенной ссылке, пустые/отсутствующие значения, одинаковые и конфликтующие дубли; никакого межъязыкового замещения.
2. BOM, кавычки, комментарии, `#` внутри строк, экранирование, буквальное `\n`, игровую разметку и ошибки чтения.
3. Технологию без `tech_`, исключение категорий/ступеней, повторяющиеся имена вариантов, прямой выбор `name`, некорректное имя варианта и отсутствие целей.
4. Несколько уровней ссылок, общую зависимость, неизвестный токен, динамические/форматированные подстановки, цикл и оба предела; сохранение `raw`.
5. Поиск собственного описания во всех приоритетах до наследования, наследование отдельно по языкам, собственное пустое описание, отсутствие родительского описания и корректность `inherited_from`.
6. Неизменность всех исходных полей дерева и истории, прежние количества узлов/частоты после обогащения, повторяемость, удаление устаревшего результата при смене селектора, обновление только локализации.
7. Обогащение без каталогов игровых определений, чтение готовой БД без локализации и игры, безопасные пути, ошибки до замены, изменение входа во время операции и отказ записи отчёта после замены.
8. Генерацию схем, валидацию обогащённого и необогащённого формата 4, регрессионные проверки существующего бэкэнда.

Реальная проверка: собрать необогащённую базу формата 4 из прежних 35 файлов отдельно под `data/stage10/`, затем обогатить и сравнить исходные деревья и историю до/после. При неизменных исходниках ожидаются 679 технологий и 206 вариантов, по 885 названий RU/EN, по 679 основных описаний и 125 собственных + 81 унаследованному описанию вариантов. Проверить реальные цепочки ссылок и источники независимо от рабочего обработчика; повторить операцию и сравнить байты.

Зафиксировать размер БД до/после, время и контроль неизменности источников. Исследовательские инвентаризации не подменяют независимую проверку результата. Полный обход `common/` и `events/` не требуется для этого этапа. Игровая и визуальная проверки не выполнены и не входят в приёмку извлечения текста; отображение остаётся отдельным этапом.
