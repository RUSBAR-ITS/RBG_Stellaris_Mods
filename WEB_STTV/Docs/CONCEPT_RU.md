## Статус концепта

Проект — **Stellaris Technological Tree View**, каталог — `WEB_STTV`. Документ описывает концепцию самостоятельного приложения и **не является ТЗ**. Технологическая основа и принципы кода сохранены в [общем ТЗ](TZ_RU.md).

**Решение пользователя от 2026-11-15:** основной базой становится JSON с результатами парсинга. От обязательного преобразования в строгую предметную модель технологий и проверки игровых имён по профилю отказываемся. Обогащение по конкретным полям и правилам относится к следующим этапам.

**Решение пользователя от 2026-11-16:** локализация хранится непосредственно при объектах в той же БД и добавляется отдельной операцией. Первое обогащение — названия и описания RU/EN технологий и их вариантов; реализовано по утверждённому [ТЗ этапа 10](TZ_BACKEND_STAGE_10_RU.md). Возможная будущая очистка данных для справочника относится только к обработке БД; универсальный парсер сохраняет полную поддерживаемую структуру.

Переход реализован по утверждённому [ТЗ шестого этапа](TZ_BACKEND_STAGE_6_RU.md). Седьмой этап добавил статические переменные, восьмой — раскрытие именованных эффектов и триггеров вместе с inline-вставками, девятый — узлы script values с параметрами и областями вычисления. Десятый этап добавил локализацию RU/EN в БД. Текущий процесс и результаты описаны в [руководстве этапа 10](BACKEND_STAGE_10_RU.md).

[Прежняя модель БД](DATABASE_MODEL_RU.md) и [руководство пятого этапа](BACKEND_STAGE_5_RU.md) описывают историческую реализацию. Игровые файлы доступны только для чтения. Интерфейс и portable-поставка ещё не реализованы.

## Назначение и основной экран

Справочник помогает изучать технологии Stellaris и связи между ними на основе данных выбранной установки игры.

Основной режим — интерактивное дерево связей, состоящее из карточек технологий. Карточки используют соответствующие ванильные изображения. Дерево строится по внутренней базе, полученной из игровых данных, и обновляется после её перестроения.

Точный состав карточки, способ раскрытия подробностей, расположение ветвей и элементы управления предстоит обсудить. Отдельный режим каталога, поиск и фильтры пока не определены.

## Локальный запуск и переносимость

Целевая платформа — Windows. Предполагается portable-поставка в одном каталоге с запускаемым файлом, настройками и данными приложения. Пользователю не требуется отдельно устанавливать веб-сервер.

Обсуждённый вариант запуска: исполняемый файл открывает веб-интерфейс в браузере и запускает необходимую локальную служебную часть. В первой части ТЗ выбраны Python для обработки и локальной служебной части, TypeScript и HTML/CSS для интерфейса, PyInstaller в режиме `onedir` для упаковки. Зависимость и проверенное окружение сборщика указаны в [руководстве](BACKEND_STAGE_1_RU.md#подготовка-окружения); библиотеки интерфейса и служебной части ещё не выбраны.

Настройки находятся в каталоге приложения, готовая база, отчёты и будущие подготовленные изображения — в настраиваемой рабочей папке `WORK_DIR`, по умолчанию `data` внутри приложения. Код разделён на `src/frontend` и `src/backend`. Внутренние ссылки используют относительные пути. Пути к внешним источникам задаёт пользователь; после переноса приложения их может потребоваться изменить для следующего обновления.

Уже сформированная база вместе с будущими подготовленными изображениями позволяет просматривать справочник без доступа к исходным каталогам игры. При разработке рабочая папка остаётся внутри репозитория; `data` предназначена и для проверок продукта. Ранее собранные исследовательские материалы остаются в `TMP/WEB_STTV/` и не являются зависимостью приложения.

## Три процесса работы с данными

Результат парсинга сохраняется в JSON и становится самостоятельной управляемой базой. Дальнейшие действия используют эту структуру без обязательного повторного разбора игровых определений.

| Процесс | Вход | Результат |
| --- | --- | --- |
| Чтение и парсинг | Выбранные исходники и настройки парсера | JSON с разобранной структурой, раскрытыми inline-вставками и происхождением; отдельная диагностика |
| Обогащение — локализация реализована | Сохранённый JSON, правила обработки и необходимые дополнительные источники | Та же JSON-БД с дополнительными служебными данными при объектах; первое обогащение — локализация |
| Отображение — следующие этапы | Подготовленные для просмотра данные и изображения | Дерево, карточки и взаимодействие с пользователем |

```mermaid
flowchart LR
    sources[Выбранные источники] --> parse[Парсинг и раскрытие вставок]
    parse --> database[JSON с результатами парсинга]
    database --> enrich[Обогащение по полям и правилам]
    enrich --> view[Дерево и карточки]
```

Сохранение JSON после парсинга не зависит от наличия локализованных названий, вычисленных значений или подготовленного древа. Обогащение запускается отдельными действиями. Локализация добавляется в служебные поля объектов той же БД, вне игрового дерева; повторное обновление заменяет только её результат. Правила остальных действий уточняются отдельно. Раскрытие `inline_script` остаётся частью обработки исходников; история вызовов сохраняется отдельно от игровой аналитики.

## Внутренние данные

Основная база — JSON-представление результатов парсинга. Сохраняются поддерживаемые парсером конструкции: имена, операторы, значения, вложенность, порядок, повторные записи и происхождение. Неизвестное имя поля или команды само по себе не является причиной отказа от сохранения. Закрытые списки полей технологии и профиль допустимых команд больше не определяют целевую основу хранения.

Формат `sttv.parse_database` версии 4 сохраняет деревья исходных файлов в массиве `documents`; виды узлов, порядок и повторы сохраняются. Актуальное описание — [этап 10](BACKEND_STAGE_10_RU.md#хранение-и-чтение-бд): служебная локализация при объектах, общая история `expansions`, узлы `scripted_trigger_test` и `script_value` дополняют структурное хранение. Тело расчёта и область сохраняются без вычисления результата. Перечислять все игровые поля и команды для хранения не требуется. Ошибки чтения, синтаксиса и раскрытия диагностируются; неполный результат нельзя публиковать как успешный.

| Материал | Назначение |
| --- | --- |
| Настройки источников | Выбранные пути и приоритеты источников |
| База результатов парсинга | Сохранённая структура определений и её происхождение |
| Служебные сведения | История inline-вызовов, эффектов и триггеров и привязки к источникам вне игровой аналитики |
| Обогащённые данные | Первое реализованное обогащение — названия и описания RU/EN при объектах той же БД; связи и другие сведения проектируются отдельно |
| Отчёт обработки | Проверки и диагностика отдельно от БД |
| Подготовленные изображения | Изображения для интерфейса на последующих этапах |

JSON с результатами парсинга сохраняется на диск; исходные игровые файлы не копируются в продукт. Прежняя модель технологий не ограничивает новый формат. Пользовательская поставка по-прежнему предполагает пустую базу, наполняемую из выбранных источников.

Позднее из БД справочника можно будет удалять ненужные ему игровые механики по отдельно согласованным правилам. Это обработка конкретного результата, а не ограничение универсального парсера, который нужен и для других задач. Текущий этап локализации ничего из игрового дерева не удаляет; формат и состав будущей сокращённой базы пока не определены.

## Источники и локализация

Пользователь выбирает каталоги, из которых приложение получает игровые данные. Конкретные пути разработчика не закрепляются в приложении как обязательные.

Локализация выполняется отдельным обогащением; для неё сохраняется упорядоченный список источников. Приоритет применяется **по каждому ключу отдельно**: используется найденное значение из источника с наивысшим приоритетом. Если ключ отсутствует, поиск продолжается в следующем источнике. Так неполные переводы дополняются последующими источниками. Происхождение выбранного текста сохраняется.

Для первого этапа согласованы названия и описания технологий и их `technology_swap` на русском и английском. Обычные статические ссылки раскрываются с сохранением исходной строки; динамические подстановки остаются. При отсутствии собственного ключа описания вариант получает описание основной технологии на том же языке с отметкой о наследовании. Настроенные источники `RU_LOC_TIER_1` → `RU_LOC_TIER_2` → `RU_LOC_TIER_3` и `EN_LOC_TIER_1` описаны в [README](../README_RU.md#глобальные-переменные).

Пример действующего порядка русского перевода в этом репозитории:

1. `Localisation_Base/1-Prio_Russian_Localization_Fix_RE/replace/`.
2. Остальные файлы `Localisation_Base/1-Prio_Russian_Localization_Fix_RE/`.
3. Ванильная локализация из `Localisation_Base/2-Prio_Vanilla/`.

Этот пример иллюстрирует настраиваемый порядок. Он не делает конкретный мод локализации обязательной зависимостью приложения.

Известный путь к установленной игре для исследования в текущем окружении: `E:\SteamLibrary\steamapps\common\Stellaris\`. Он доступен исключительно для чтения. Отдельные определения технологий находятся в `common/technology/`; связанные переменные, локализация и изображения также читаются из источников по мере необходимости обработки.

Поддержка игровых определений из модов и правила их объединения пока не определены. Приоритеты локализации сами по себе не задают порядок переопределения игрового кода.

## Первый запуск

Предполагаемый сценарий будущего приложения:

1. Пользователь запускает приложение; при пустой базе открывается настройка источников.
2. Пользователь указывает необходимые каталоги.
3. Приложение читает и разбирает исходники, затем сохраняет результат в JSON.
4. Отдельные действия обогащают данные по согласованным полям и правилам, при необходимости запрашивая дополнительные источники.
5. После подготовки необходимых для просмотра данных открывается справочник. Изображения, интерфейс и остальные действия обогащения относятся к следующим этапам; один экспорт структуры ещё не означает готовность древа.

При последующих запусках используются сохранённые результаты. Работа с ними не требует повторного выбора исходных каталогов и разбора игры.

## Обновление и перестроение базы

Повторный парсинг заново читает выбранные источники в режиме read-only и создаёт новый JSON с результатами. Для этого нужен доступ к исходным каталогам. После обновления игры повторный парсинг использует её новые файлы.

Обогащение работает с сохранённым JSON. Дополнительные источники нужны только соответствующим действиям, например для получения локализации. Изменение правил обогащения само по себе не требует заново разбирать игровые определения, если нужная структура уже сохранена.

Локализация обновляет ту же БД через проверенный временный файл и атомарную замену. Повторный парсинг создаёт новую БД без прежнего обогащения; локализацию запускают заново отдельным действием. Подробности обновления и диагностики реализованы по ТЗ десятого этапа и описаны в его руководстве.

Ошибка чтения, разбора или сохранения не должна подменять рабочую базу частичным результатом. Проверки, обновление обогащённых данных после нового парсинга и отображение состояния будут определены в ТЗ соответствующих этапов. Проверка игровых команд по старому профилю не является условием сохранения структурного результата в новой концепции.

## Открытые решения

Следующие темы остаются для дальнейшего обсуждения:

- Состав карточек и подробностей технологии, навигация по дереву, поиск и фильтры.
- Языки интерфейса и отображение отсутствующих текстов; получение названий и описаний RU/EN согласовано для первого обогащения.
- Отображение условий доступности, условных вариантов технологий и связей с другими игровыми объектами.
- Работа с модами, DLC и несколькими наборами источников.
- Следующие действия обогащения и возможная очистка БД для справочника; локализация уже выбрана для хранения при объектах той же БД.
- Фреймворк интерфейса, библиотека графов, конкретные версии выбранных технологий, детали сборки и требования к среде Windows.
- Отображение ошибок источников, неразрешённых ссылок и прерванной обработки в будущем интерфейсе.

Эти темы не включают дополнительные функции автоматически. Объём реализации будет зафиксирован отдельно в ТЗ после обсуждения.
