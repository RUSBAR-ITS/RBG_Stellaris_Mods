## 1. Статус и цель

**Статус: утверждено пользователем и реализовано.** Дата: 2026-11-15. Интерфейс, ограничения и результаты проверок описаны в [руководстве этапа](BACKEND_STAGE_4_RU.md).

Основания: [согласованная классификация](KEYWORDS_AND_VALUES_RU.md), [реализованный третий этап](TZ_BACKEND_STAGE_3_RU.md), исходники `sttv/script/` и текущие потребители парсера. Общие принципы кода — в [основном ТЗ](TZ_RU.md#2-структура-проекта-и-принципы-кода).

Цель: представить `AND`, `OR`, `NOT`, `NAND`, `NOR` в дереве как логические операции с отдельным конфигом. Для `inline_script` предусмотреть функцию разворота, которая на этом этапе является заглушкой и возвращает пустой результат. И ссылка, и блочная форма передаются этой функции одним непрозрачным значением; их содержимое не разбирается.

Последнее уточнение пользователя заменяет прежнюю идею оставлять непрозрачный скаляр в итоговом дереве: значение существует только на входе обработчика, а весь вызов `inline_script` пропускается. Исходный текст остаётся доступен в документе.

## 2. Границы этапа

Входят:

- Отдельный конфиг логических операторов, его схема и подключение через настройки бэкэнда.
- Узел логической операции и его распознавание без проверки игрового смысла условий.
- Чтение внешних границ значения `inline_script`, отдельная функция разворота и заглушка с пустым результатом.
- Адаптация сериализации, сборщика, анализатора, отчётов и проверок к изменению дерева.
- Проверка корпуса, сохранности исходников и точно определённых изменений результата сборки.

Не входят: настоящий разворот inline-файлов, разбор их параметров, исполнение условий, логическое упрощение, классификация других команд, замена профиля/реестра, расширение модели зависимостей технологий, UI и новый проход частотной статистики. `yes`/`no` и `id` не получают новых типов узлов в этом этапе.

Игровые файлы доступны только для чтения. Рабочие отчёты сохраняются в настроенном `WORK_DIR`; временные материалы допускаются в `TMP/WEB_STTV/`. Обратная совместимость внутренних интерфейсов не требуется.

## 3. Конфигурация

Добавить **`config/parser/logical_operators.json`**:

```json
{
  "format_version": 1,
  "case_sensitive": false,
  "assignment_operator": "=",
  "operators": ["AND", "OR", "NOT", "NAND", "NOR"]
}
```

`operators` задаёт имена и их каноническое написание в узле логической операции. При `case_sensitive: false` сопоставлять имена через `casefold`, сохраняя исходное написание отдельно. Пустой список допустим и отключает специальное распознавание. Список не дублировать в Python, `lexical.json`, `constructs.json` или игровом профиле ради работы парсера. Конфиг задаёт распознавание формы, не таблицу вычисления истинности.

`assignment_operator` должен присутствовать среди лексических операторов. Проверять уникальность имён с учётом выбранного режима регистра, непустые имена без пробелов и синтаксических разделителей, конфликты с именем inline-обработчика. Не вводить неявный запасной набор операторов при ошибке или отсутствии файла. Изменение списка должно реально менять распознавание без изменения кода; это не доказывает поддержку новых имён движком игры.

Добавить обязательный выбор `parser.logical_operators` в `config/backend.json` по существующей форме `{"base":"product","path":"config/parser/logical_operators.json"}`. Поддержать те же основания путей, что у `lexical` и `constructs`. Анализатор получает эти настройки через общий `Settings`, без второго независимо настроенного парсера.

В `constructs.json` добавить настройку имени конструкции; это не правила разбора её содержимого:

```json
{
  "inline_script": {
    "keyword": "inline_script",
    "case_sensitive": false
  }
}
```

Это добавляемый фрагмент существующего конфига. Лексические обозначения строк, комментариев и фигурных скобок продолжают браться из `lexical.json`. Имя обработчика связывается с реализованной функцией в коде; конфиг не загружает произвольные Python-функции.

Закрытые схемы обновлять через постоянный генератор: новая `parser_logical_operators.schema.json`, изменённые `parser_constructs.schema.json` и `backend.schema.json`. Загрузчик `Syntax` получает три явно заданных конфига. Старые конфиги без обязательных новых полей не подменяются настройками по умолчанию.

## 4. Представление результата

| Элемент | Предлагаемые поля и назначение |
| --- | --- |
| `LogicalOperation` | `operator`: каноническое имя из конфига; `name`: исходный `Scalar` имени; `assignment_operator`: фактический знак связи; `body`: `Block`; `span`: координаты всей операции |
| `InlineScriptValue` | Внутренний непрозрачный скаляр: `raw`: точный текст значения; `form`: `reference` или `block`; `span`: координаты значения. Нет полей параметров или дочерних узлов |
| `Document.skipped_inline_scripts` | Упорядоченный список `Span` целых вызовов, пропущенных заглушкой; служебный учёт, не элементы дерева |

`LogicalOperation` — самостоятельный тип узла, а не обычный `Assignment` с текстовым ключом. Он может находиться в любой последовательности элементов. При проверке смешанных контейнеров считать его именованной конструкцией наравне с `Assignment`, чтобы изменение типа не запрещало ранее допустимые блоки.

`InlineScriptValue` используется только при обращении к обработчику и не попадает в `Document.items` или дочерние блоки. Пропущенный вызов не заменяется `null`, пустым узлом или строкой. Пустой родительский блок сохраняется; соседние записи не исчезают и не переставляются.

`Document.source` и последовательность токенов сохраняют весь исходный текст. Непрозрачное значение можно представить одним токеном `opaque_value`: токен не содержит разобранных параметров. Координаты остаются в символах декодированного текста, конечная граница исключающая. Служебный список пропусков позволяет отличить намеренное исключение от потери данных при обходе.

## 5. Распознавание логических операторов

1. Вне строк, комментариев и непрозрачных inline-значений сопоставить отдельное имя без кавычек с конфигом.
2. Признать логическую операцию только при настроенном знаке связи и фигурном блоке справа.
3. Создать `LogicalOperation`, рекурсивно разбирая тело обычным механизмом, с сохранением порядка и повторений.
4. Поддерживать отдельные идентификаторы, именованные выражения и вложенные операции в теле. Не ограничивать `NOT` одной записью; пустой блок также сохранять.
5. Не вычислять истинность, не проверять технологию/этику/область видимости и не упрощать вложенность.

Например, `or = { tech_a tech_b }` даёт операцию с `operator = "OR"`, исходным именем `or` и двумя самостоятельными скалярами в теле. `NOT = { has_technology = tech_a has_technology = tech_b }` сохраняет обе записи.

`localization = AND`, `"AND" = { … }`, `and_flag = yes`, `$AND$` и `NOT = tech_a` не отвечают всему правилу и остаются обычными структурными формами. Отсутствие логической классификации само по себе не создаёт новой ошибки синтаксиса. Имена внутри непрозрачного `inline_script` не рассматриваются вообще.

Лексер не превращает каждое слово `AND` в оператор независимо от позиции. Класс операции определяется механизмом разбора по полной конструкции.

## 6. Обработчик inline_script

Для отдельного настроенного имени без кавычек слева от `=` применяется специальный путь до общего разбора значения. Обрабатываются обе формы: `inline_script = path` и `inline_script = { … }`, включая ссылку в кавычках.

Последовательность:

1. Прочитать внешние границы значения и сформировать `InlineScriptValue`, сохранив точный исходный фрагмент.
2. Вызвать отдельную функцию `expand_inline_script(value, source)` ровно один раз для этого внешнего вызова.
3. Функция возвращает последовательность узлов для места вставки. **На этом этапе её тело — заглушка, возвращающая пустой список.**
4. Не добавлять вызов в итоговую последовательность; записать его координаты в `Document.skipped_inline_scripts` и продолжить с соседней записи.

Функция не открывает файлы, не разрешает путь, не проверяет наличие шаблона, параметры или профиль и не анализирует содержимое. Обычная ссылка и блок обрабатываются одинаково. Это намеренно заданное поведение этапа, а не подавление ошибки неудавшегося раскрытия.

Для блочного значения читать баланс фигурных скобок с учётом строк, экранирования кавычек и комментариев. Для ссылки читать одну внешнюю строку или атом. Обрабатывать только необходимые внешние границы; внутри блока не проверять присваивания, `$…$`, формулы, условные вставки или имена. Вложенный `inline_script` внутри такого значения не вызывает обработчик повторно.

Нельзя сначала построить обычный AST содержимого, а затем удалить его: такой путь продолжает разбирать игнорируемый код. Нынешнюю предварительную токенизацию всего документа необходимо адаптировать так, чтобы непрозрачная область читалась до обычных обработчиков её внутреннего текста. Общие функции чтения строк и комментариев переиспользовать.

Незавершённая внешняя строка, отсутствие значения и незакрытый фигурный блок остаются ошибками: без границы невозможно надёжно найти следующую запись. Корректно ограниченное значение с неизвестными или структурно неразбираемыми внутренними записями пропускается.

Правило относится к вызову конструкции. Оно не является фильтром файлов по имени каталога: явно переданный парсеру текст шаблона разбирается как самостоятельный документ, а встреченные в нём вызовы снова проходят через заглушку. Автоматического чтения шаблонов нет.

## 7. Модули и интеграция

| Место | Изменение |
| --- | --- |
| `script/syntax.py`, `sources/settings.py` | Третий конфиг, проверка согласованности, пути и защита конфигов от перезаписи результатами |
| `script/nodes.py`, `script/parser.py` | Логический узел, применение правил, обработчик вставок и учёт пропусков |
| `script/lexer.py`, небольшой помощник чтения | Непрозрачный фрагмент до внутренней токенизации, сохранение координат и текста |
| `script/inline.py` | Входная структура и функция разворота с пустой заглушкой; без внутреннего парсера inline |
| `script/serialization.py` | Явная проекция логических узлов в текущую модель данных; пропущенных вызовов уже нет во входе |
| Сборщик, анализатор, генератор схем и тесты | Адаптация потребителей и учёт намеренно пропущенных вставок |

Названия небольших вспомогательных модулей допускается уточнить при реализации. Сохранять модульность, DRY и ограничения размера из основного ТЗ; не создавать универсальную систему плагинов ради одной функции.

В проекции `LogicalOperation` в `DataEntry`/`ScriptBlock` использовать каноническое имя как `key`, сохранённый знак связи как `operator`, тело как последовательность записей. Это явное преобразование между AST и существующей моделью БД; исходное написание остаётся в AST. Обычные ключи и значения не нормализовать.

Схема самой БД остаётся прежней. Сборщик и анализатор не должны восстанавливать пропущенный `inline_script`, извлекать его параметры из исходной строки или проверять его сигнатуру. Проверка остальных полей/команд и защита существующей БД при ошибке сохраняются. Распознавание всех пяти логических операторов парсером не расширяет автоматически отдельную модель `prerequisites`, которая сейчас представляет `all`/`any`.

В отчёт сборки и отчёт анализа добавить обязательный счётчик `counts.skipped_inline_scripts` с нулём при отсутствии пропусков; для отчёта анализа добавить соответствующий контейнер `counts`. Обновить декларации и сгенерированные схемы отчётов. Это учёт известной заглушки, не ошибка и не отдельное предупреждение для каждого вызова. Подробные координаты сохранять в отчёте проверки корпуса. Счётчик анализа учитывает фактически разобранные выбранные источники.

Ожидаемые отличия БД от третьего этапа: исчезновение целых записей `inline_script` из `ScriptBlock.entries` и канонизация регистра имён распознанных логических блоков. Не удалять опустевшие родительские блоки. Числа, локализация, идентификаторы и остальные данные должны сохраниться. Обновить описание модели БД и руководства при реализации: база этого этапа не включает вклад пропущенных вставок.

## 8. Диагностика и проверки

Проверки конфигов: отдельный файл, выбор относительно `product`/`work`, отсутствие скрытого набора по умолчанию, дубли имён в разном регистре, конфликты обозначений, отсутствие знака связи в лексическом конфиге. Удаление/добавление имени и изменение чувствительности к регистру должны менять AST; не менять игровой реестр ради такой проверки механизма.

Проверки логических узлов: все пять имён, разные регистры, вложенность, списки идентификаторов, несколько записей в `NOT`, пустые тела, повторения, неизвестные команды внутри, координаты и контрпримеры из раздела 5. Проверить режим `mixed_blocks = false` для соседства обычных именованных записей и логических операций.

Проверки заглушки: ссылка без кавычек, ссылка в кавычках, блок, пустой блок, многострочный текст с кодом, скобки внутри строк/комментариев и экранированные кавычки. Поставить до и после вставки обычные записи и логические операции; проверить их полное сохранение. Отдельно проверить несбалансированную подстановку `$…` и неверную внутреннюю запись внутри внешне корректного блока: игнорируемое содержимое не должно вызывать внутренний парсер. Незакрытая внешняя оболочка должна дать координатную ошибку.

Проверка функции разворота подтверждает один вызов с точным `raw` и пустой результат, без файлового ввода-вывода. Вложенная ссылка внутри непрозрачного блока не вызывает второй вызов. Исходный текст восстанавливается из токенов целиком; реконструкция AST сопоставляется с токенами после исключения ровно зарегистрированных диапазонов пропуска.

До реализации сохранить контрольную БД. Независимо подготовить ожидаемый результат: убрать только записи `inline_script` и нормализовать имена только логических блоков. Новая сборка должна совпасть с этим результатом, пройти валидацию схемы и сохранить число технологий/вариантов и обе локализации. Побайтное совпадение с неизменённой старой БД из третьего этапа больше не является критерием.

## 9. Критерии приёмки

1. Логические операции имеют отдельный тип узла, а их перечень берётся только из отдельного конфига.
2. Обе формы `inline_script` передаются функции разворота как непрозрачное значение; заглушка исключает весь вызов из дерева и проекции.
3. Внутренние поля и строки вставки не разбираются, ссылка не открывается, прочие данные не теряются.
4. Все потребители, схемы конфигов/отчётов и содержательные тесты обновлены. Строгая проверка остальных данных не ослаблена.
5. На неизменном исследованном корпусе проверяются 2 238 `.txt`: ожидаются 2 235 успешных разборов, два отдельно учтённых прозаических документа и известная ошибка `common/named_colors/01_trait_colors.txt:65`. Ожидаются 36 026 логических узлов и 6 885 пропущенных внешних вызовов; inline-текст внутри строк отдельно не раскрывается и в эти числа не добавляется.
6. Для корпуса проверены полный охват текста, точные диапазоны пропусков, порядок узлов и отсутствие неожиданных диагностик. Старое число значимых токенов и пустых деревьев не фиксируется: непрозрачные токены и пропуски меняют эти показатели.
7. Сборка соответствует независимо преобразованной контрольной БД; отчёты показывают число пропусков. При ошибках прежняя рабочая БД сохраняется.
8. Хеши игровых исходников до и после совпадают. Изменение установки относительно манифеста фиксируется отдельно, без подгонки результатов.

Приёмка проверяет синтаксический механизм и согласованное временное исключение вставок. Исполнение игровых условий и полнота эффекта развёрнутых шаблонов не заявляются.
