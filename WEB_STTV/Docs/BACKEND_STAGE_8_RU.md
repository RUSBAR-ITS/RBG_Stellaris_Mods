## Процесс и запуск

Документ сохраняет результаты восьмого этапа. Актуальная реализация описана в [руководстве этапа 9](BACKEND_STAGE_9_RU.md).

Реализация следует утверждённому [ТЗ восьмого этапа](TZ_BACKEND_STAGE_8_RU.md). Источники читаются без изменения. Бэкэнд индексирует библиотеки, разбирает независимые документы, раскрывает смешанные вызовы, подставляет статические значения и сохраняет структурный JSON. [Руководство этапа 7](BACKEND_STAGE_7_RU.md) описывает прежний формат.

Штатный запуск из корня репозитория:

```powershell
& WEB_STTV/data/.venv/Scripts/python.exe -B WEB_STTV/src/backend/main.py
```

Сохранены `--variables`, `--config`, Python-функции `sttv.builder.build` и `sttv.database.storage.read_database`. Нет интерактивного консольного диалога. Штатные пути — `data/database.json` и `data/reports/build_report.json`. Проверки этапа пишут отдельно в `data/stage8/`, сохраняя стандартную БД и вручную обработанные частотные списки.

## Библиотеки и конфигурация

Четыре каталога относительно `STELLARIS_ROOT` читаются отдельно и исключаются из самостоятельного обхода:

| Переменная | Значение по умолчанию |
|---|---|
| `INLINE_SCRIPTS_DIR` | `common/inline_scripts` |
| `SCRIPTED_EFFECTS_DIR` | `common/scripted_effects` |
| `SCRIPTED_TRIGGERS_DIR` | `common/scripted_triggers` |
| `SCRIPTED_VARIABLES_DIR` | `common/scripted_variables` |

Седьмой селектор `parser.scripted_calls` указывает на [scripted_calls.json](../../Instruments/Stellaris_Parser/stellaris_parser/config/scripted_calls.json). Маска, рекурсивный обход, кодировка, регистр имён/параметров, глубина, бюджет узлов и служебные поля настраиваются. Значения по умолчанию: `*.txt`, `utf-8-sig`, рекурсивно, имена без учёта регистра, параметры с учётом регистра, смешанная глубина 64, не более 1 000 000 создаваемых узлов на документ. Отдельный предел inline-глубины также действует.

Индексы строятся из игры при каждой операции. Повторные нормализованные имена, в том числе между библиотеками, — ошибка. `namespace` сохраняется как поле файла в отчёте; `optimize_memory` исключается из рабочих команд и отражается в истории. Кеш не переносит обработанные тела между вызовами или сборками. Перед публикацией повторно проверяются хеши всех прочитанных источников.

## Правила раскрытия

- `root_definition_files = ["common/game_rules/*.txt"]`: согласованное правило сохраняет корневые блочные определения игровых правил, раскрывая вызовы внутри. Контекст передаётся корневым inline-вставкам; на другие файлы не распространяется. Маски задаются относительно `STELLARIS_ROOT`.
- Эффект с `= yes` или блоком аргументов заменяется последовательностью элементов тела. Порядок соседей и повторные ключи сохраняются; результат может быть пустым.
- Триггер с `= yes` или аргументами заменяется `AND = { ... }`; с `= no` — `NOT = { AND = { ... } }`. Оболочки сохраняют целостность результата, например внутри `OR`.
- Другие скалярные или формульные проверки триггера становятся `scripted_trigger_test`: исходный оператор, правая часть и раскрытое тело. Его числовой результат не вычисляется.
- Раскрыватели взаимодействуют через координатор: эффект → inline → триггер и другие комбинации обрабатываются рекурсивно. Повтор в активной цепочке, превышение глубины или бюджета узлов дают диагностику.
- Аргументы известного вызова сначала связываются как данные. Совпадение имени аргумента с именем известного вызова или логической операции не превращает его в команду.

## Аргументы и переменные

Поддерживаются текстовые скаляры, строки, блоки и формулы в аргументах именованных вызовов. `$PARAM|fallback$` использует fallback только при отсутствии аргумента; явное `no` и пустая строка не заменяются default. Fallback — буквальный текст, без дополнительного поиска одноимённого параметра. Условный фрагмент `[[PARAM] ... ]` включается при наличии аргумента, отличного от `no`; `[[!PARAM] ... ]` выбирает обратный случай.

Не требуются параметры и файлы из исключённой условной ветви. Вложенному вызову передаются только явно записанные аргументы. Формулы остаются формулами; параметры внутри них заменяются, но математические выражения не вычисляются. Общий помощник используется и inline-раскрывателем.

У каждого файла библиотеки отдельное локальное окружение `@name`. Собственный текст определения использует его, аргумент — окружение места передачи, default — окружение определения, inline-текст — окружение места вставки. Пример: `@cost=20` в библиотеке, `@cost=10` у вызывающего документа; собственный `value=@cost` получает 20, переданный `AMOUNT=@cost` получает 10.

Массовая подстановка рабочих скаляров выполняется после смешанного раскрытия. Если статический аргумент определяет выбор условного фрагмента или форму вызова, его значение читается из таблицы по запросу раньше. Неоднозначное окружение ссылки, составленной из нескольких источников, — ошибка. Окружения не сериализуются; отдельной истории каждой подстановки переменной нет.

## Формат базы и история

Формат БД — `sttv.parse_database`, версия 2. Помимо прежних семи видов узлов добавлен `scripted_trigger_test` с `operator`, `value`, `body`, `span`, `origin`. Схема не содержит закрытого перечня игровых команд и полей.

Единый массив `metadata.expansions` содержит inline-вызовы, эффекты и триггеры. Записи хранят вид и цель вызова, исходную форму, явные аргументы, снятые директивы, родительский ID и диапазон вставки в итоговом дереве. `origin.expansion_id` связывает узлы с историей; синтетические оболочки помечены `synthetic: true`. Происхождение исходного тела и аргументов сохраняется.

История проверяется при чтении без доступа к игре: уникальность ID, родители, циклы, диапазоны и ссылки узлов. Метаданные, библиотечные заготовки и объявления переменных не участвуют в частотной статистике. Статистика нового узла обходит только его значение и тело.

Отчёт версии 4 отдельно содержит манифесты эффектов/триггеров, число определений и локальных объявлений, счётчики вызовов, defaults и условных фрагментов, максимальную глубину. Локальные объявления библиотек считаются в `scripted_calls`, независимых документов — в `static_variables`. Для чтения старой БД нужен прежний код либо пересборка: слой совместимости не добавлен.

## Код и схемы

`script/scripted/` отвечает за индексы, связывание аргументов и раскрытие именованных тел; `script/coordination.py` — за смешанные цепочки, ограничения и позиции вставки; `script/inlining/` сохраняет обработку inline-файлов. Условный выбор текста вынесен в `script/parameters/`. Чтение и проверка источников находятся в `sources/`, окружения и окончательная подстановка — в `script/variables/`.

Десять схем генерируются из деклараций в `schema_generation/`:

```powershell
$env:PYTHONPATH = "$PWD/WEB_STTV/src/backend"
& WEB_STTV/data/.venv/Scripts/python.exe -B -m sttv.schema_generation
```

## Общий аудит и проблемные входы

Первый полный аудит текущей установки: 2 238 TXT, из которых отдельно читаются 631 inline-шаблон, 43 файла эффектов, 37 файлов триггеров и 23 файла статических переменных. Из 1 504 самостоятельных входов успешно обработан 1 481, пропущены две прежние TXT-документации, 21 завершился ошибкой. JSON-проверку и проверку истории прошли 7 177 784 узла. Отчёт имеет статус `partial`, а не полного успеха.

Во всём прогоне раскрыты 40 174 вызова эффектов, 130 762 вызова триггеров и 13 317 inline-вставок; сохранены 928 небулевых проверок. Применены 1 132 default, оставлен 1 081 условный фрагмент, исключены 939; максимальная смешанная глубина — 8. Счётчики включают обработанные части неуспешных файлов. Новые списки содержат 53 279 частотных записей, 34 405 скалярных значений и 3 569 скалярных конструкций. Метаданные, объявления переменных и ранее согласованные исключения в них не считаются.

Все прежние 17 проблем сохранились: 14 входов с `CLASS`, два с `RELIC`, один с неизвестной `@max_unlocked_council_positions`. Четыре дополнительных случая требуют разных решений:

Игровые файлы не изменены. Аналитические списки относятся только к успешно обработанным входам и не представляют полный корпус. Подробные диагностики содержат координаты и историю вызовов. Новая ошибка в библиотеке приводит к ошибке её вызывающего независимого файла; сами библиотеки не прибавляются к числу самостоятельных входов.

После согласованного исправления контекста `game_rules` отдельно пересобраны оба файла каталога: 14 709 узлов, 364 вызова триггеров, 10 небулевых проверок, одна inline-вставка, без ошибок и предупреждений. Независимое сравнение сохранившихся имён подтвердило все 218 внешних определений `00_rules.txt` и пять определений `01_gui_rules.txt`; раскрыт именно внутренний вызов в строке 4678. Источники не изменены. Отчёт — `data/stage8/game_rules_validation_report.json`, отдельная БД — `data/stage8/game_rules/database.json`.

Итоговое покрытие полного аудита и целевой перепроверки: 1 482 успешных входа, два документационных пропуска, 20 проблемных. Из трёх дополнительных оставшихся случаев один связан с отсутствующим `RANDOM`, два — с ограничениями утверждённого контракта (`effect = no` и смешанное окружение составной ссылки). Исправления ванили или новые трактовки этих конструкций не выполнялись.

Повторный прогон после исправления директив подтвердил исходные корпусные счётчики, диагностики и побайтное совпадение трёх текстовых списков. Он выполнен до правила `game_rules`; после изменения этого единственного контекста проверены оба затронутых файла, полный обход заново не выполнялся. Списки в `data/stage8/text_frequency/` и `repeated_text_frequency/` сохраняют результаты исходного полного прогона. Сводка — `verification_report.json`, сравнение с этапом 7 — `corpus_comparison.json`, сравнение повторов — `repeat_comparison.json`.

## Ограничения

Раскрытие не исполняет игру: игровые условия, циклы, случайный выбор, ссылки на события, значения script values, области состояния и формулы не вычисляются. Неизвестные обычные ключи сохраняются, поскольку реестр команд не используется. Неподдержанная форма известного эффекта не получает придуманной семантики.

`is_arkship_fleet = ye` сохраняется небулевой проверкой; `$HIDEAGE|IMMORTAL$` без `HIDEAGE` даёт буквальный `IMMORTAL`. Это сохранение структуры по контракту, не подтверждение корректности исходной команды в движке. Известные ванильные ошибки не исправляются подстановкой запасных значений.

Проверка полного корпуса может быть частичной из-за ошибок источников или ограничений раскрытия; причины должны быть перечислены в отчёте. Синтетические проверки подтверждают контракт бэкэнда, но не все пограничные правила закрытого игрового движка.
