## 1. Статус и цель

**Основная часть и дополнение утверждены пользователем 2026-11-19 и реализованы.** Анализ получения технологий описан в [утверждённом дополнении](TZ_BACKEND_STAGE_21_ACQUISITION_RU.md). Результаты проверок и границы приёмки — в [руководстве](BACKEND_STAGE_21_RU.md); проверка браузера и движка не заявляется выполненной.

Расширить [этап 20](TZ_BACKEND_STAGE_20_RU.md), чтобы DLC-ограничение определялось через ссылки на игровые объекты. Пример: технология → категория кораблей → доступные игроку наборы кораблей → BioGenesis. Другой маршрут: технология → традиция → категория традиций → DLC.

Охват определяется всем импортированным каталогом DLC. Имена дополнений и перечни их технологий не зашиваются в код. Правила описывают типы связей; конкретные объекты и ограничения берутся из подготовленных БД.

Сохраняется справочный режим без выбора конкретной империи. Для ограничений выбора стартовых объектов используется контекст играемой империи; служебные варианты NPC не считаются способом выбора такого объекта игроком. Это не утверждение об отсутствии соответствующих NPC во вселенной. Контекст должен входить в конфиг, доказательство и ревизию расчёта.

Этап не вычисляет историю конкретной партии, вероятность исследования, владение DLC, конкретную этику/происхождение пользователя или автоматический выбор `technology_swap`. Статический анализ путей выдачи технологий добавляется по отдельному проекту дополнения. Сервисы и сборка запускаются явно. При переключении DLC игра не перечитывается.

## 2. Подтверждённые входы

В `data/stage20/dlc_none_report.json` технология `tech_weaver_bio_fire_rate_2` осталась видимой: раскрытый `country_uses_bio_ships` содержит `exists = this` и `uses_ship_category = bio_ship`, которые вычислитель этапа 20 оставил неизвестными. У выбираемых наборов `biogenesis_01` и `biogenesis_02` поле `selectable` требует BioGenesis. Отдельный `biogenesis_01_fallen_empire` имеет `selectable = { always = no }` и не должен открывать игроку этот путь.

Первичная инвентаризация исходников, без раскрытия вставок и вычисления достижимости:

| Новый вид БД | TXT-файлы | Корневые определения |
| --- | ---: | ---: |
| `ascension_perks` | 2 | 49 |
| `traditions` | 33 | 234 |
| `tradition_categories` | 34 | 33 |

В двух последних каталогах по одному комментарию-README без объектов. Дубликатов корневых ID и синтаксических ошибок в этом ограниченном проходе не найдено. Это не проверка полной сборки. Рабочие результаты: `TMP/WEB_STTV/stage21_design_inventory.json` относительно корня репозитория.

Среди диагностик текущего профиля без DLC встречаются `uses_ship_category` у 88 технологий, `has_ascension_perk` у 53, `has_origin` у 49, `has_authority` у 36 и `has_tradition` у 3. Счётчики пересекаются и обозначают неизвестные проверки, а не число ошибочно показанных технологий. Они не включают все листья под неподдержанными обёртками. Новый аудит обязан отдельно инвентаризировать такие поддеревья.

## 3. Дополнительные БД

Основная часть расширяет единый реестр с 25 до 28 видов:

| Переменная | Путь относительно `STELLARIS_ROOT` | Вид |
| --- | --- | --- |
| `ASCENSION_PERKS_DIR` | `common/ascension_perks` | `ascension_perks` |
| `TRADITIONS_DIR` | `common/traditions` | `traditions` |
| `TRADITION_CATEGORIES_DIR` | `common/tradition_categories` | `tradition_categories` |

Дополнение по получению технологий предлагает ещё `crisis_paths` и `crisis_levels`, итоговые 30 видов и отдельный технический индекс получения. Эти новые источники пока не импортированы; их требования описаны в [дополнении](TZ_BACKEND_STAGE_21_ACQUISITION_RU.md#2-входы-и-подготовка-индекса).

Все три каталога используют существующий парсер, библиотеки вставок, статические переменные, параллельную подготовку, раздельные документы и атомарную публикацию манифеста. Идентичность корневого объекта задаётся ключом блока. Числа объектов не являются константами. Не копировать исходные файлы игры в продукт.

Добавить RU/EN-локализацию с прежними приоритетами. Для бонусов вознесения использовать ключ объекта и `_desc`; для традиций — ключ объекта и `_delayed`, как указано в игровом README. Для категорий учитывать явное поле `desc`, затем настроенный стандартный ключ. Проверить реальные ключи перед добавлением правил. Сохранять локализацию вложенных `tradition_swap`, когда у них есть собственное имя/описание. Имя для локализации не становится автоматически новым игровым ID.

Новые виды включить в настройки источников, реестр объектов, цели локализации, необходимые схемы и общий читатель фронтенда. Они загружаются адресно для расчёта, а не целиком при каждом открытии экрана. Отдельные экраны традиций и новые изображения в этот этап не входят. Старые наборы без обязательных справочников не подменяются частично работающим режимом: сообщать о необходимости подготовить новый набор.

## 4. Модель вычисления

Различать два вопроса:

1. **Можно ли получить/выбрать требуемый объект в рассматриваемом контексте с данным набором DLC?**
2. **Есть ли этот объект у конкретной империи сейчас?**

Этап доказывает ограничения первого вопроса. Если объект исключён DLC во всех допустимых путях, положительное условие его наличия получает `false`. Если объект не исключён, наличие остаётся `unknown`, поскольку профиль империи не выбран. Доступность DLC не даёт `true` для `has_origin`, `has_tradition` или аналогичного условия.

Сохранять `true` / `false` / `unknown` для условий, а также признак и доказательство DLC-причины. Вычисление сравнивается с тем же графом, где состояния DLC неизвестны. Независимый запрет не объявляется DLC-запретом. В частности, пустой набор поставщиков из-за ошибки индекса не доказывает отсутствие DLC.

Поле, запрещающее выбор при создании империи, не считается универсальным запретом существования объекта. `playable`, `selectable`, `potential`, `possible`, `species_potential_add` имеют разные контексты. Условия модификации вида не доказывают отсутствие этого признака у встреченного вида; `ai_playable` не добавляется как обязательное требование игроку. Все используемые переносы ограничений должны иметь явно описанное основание в правиле.

Существующее скрытие технологии по DLC-зависимому нулевому множителю веса остаётся отдельным правилом отображения. Такой запрет не доказывает невозможность владения технологией и не распространяется автоматически через `has_technology` или на потомков.

## 5. Правила перехода к объектам

Предлагаемые семейства правил:

| Условие/связь | Разрешение ссылки и границы |
| --- | --- |
| `uses_ship_category = ID` | Категория из `ship_categories`; поставщики из `graphical_culture` по `ship_kinds`. Для играемой империи анализировать `selectable`. Все допустимые поставщики образуют ИЛИ. Не использовать `randomized` как дополнительное обязательное требование ручному выбору. |
| `has_origin = ID` | Объект `civics` с `is_origin = yes`; подтверждённые ограничения выбора происхождения. |
| `has_civic` / `has_valid_civic` | Объект `civics` с соответствующим типом. Отсутствие DLC может исключить оба случая, но доступность модели не доказывает её наличие или действительность. |
| `has_authority = ID` | `authorities`; только ограничения, относящиеся к форме власти и проверяемому контексту. |
| `has_ascension_perk = ID` | `ascension_perks`; условия приобретения `potential`/`possible`, включая ссылки на другие бонусы и традиции. Требования текущего состояния остаются неизвестными. |
| `has_tradition = ID` | `traditions` и все категории, ссылающиеся на ID через `traditions`, `adoption_bonus` либо `finish_bonus`. Ограничения традиции и выбранного пути категории соединяются И; альтернативные категории — ИЛИ. |
| `has_trait`, проверки класса/архетипа вида | `traits`, `species_classes`, `species_archetypes` с учётом вида/лидера и способа получения. Запрет выбора портрета или добавления признака не равен запрету иметь такой вид. Неподтверждённые переносы остаются неизвестными. |
| Ссылки на технологии и прочие объекты | Сохранять и инвентаризировать. Вычислять только по подтверждённому правилу доступности, не по видимости карточки и не по выбранному `parent_tech`. |

Поля ограничений каждой группы проверяются по исходникам до подключения. Синтаксис требований правительств (`origin = { value = ... }` и подобные формы) отличается от обычных триггеров; ему нужен отдельный явно настроенный обработчик. Не считать любое `value` ссылкой.

Для каждого маршрута различать отсутствие поля, отсутствие объекта, неоднозначный ID и неподдержанную форму. Отсутствующее необязательное поле не запрещает объект. Не найденная ссылка означает `unknown` с диагностикой; конфликт уникальных ID — ошибку набора. Несколько категорий или поставщиков одного типа кораблей являются штатными альтернативами, а не конфликтом ID.

`tradition_swap`, `advanced_authority_swap` и сходные конструкции не следует превращать в независимые объекты по одному полю `name`. Связь варианта с базой, условие активации и наследование сохраняются. Если влияние варианта на доступность не подтверждено, оно остаётся в отчёте как нерешённый путь; отключение DLC варианта не запрещает базовый объект целиком. `fallback` графики сам по себе не доказывает наследование игровых ограничений.

## 6. Рекурсивный обход

Рекурсия обязательна на двух уровнях:

- **Внутри условий:** сохранять вложенность, операторы и области видимости до листового условия.
- **Между объектами:** разрешать ссылку через индекс манифеста, брать настроенные поля целевого объекта, рекурсивно обходить их условия и дальнейшие ссылки.

Единый процесс: выбранные варианты технологий → исходные условия доступности/нулевого веса → необходимые объекты → их ограничения и поставщики → результат видимости → существующий выбор родителей/детей. История раскрытия вставок и метаданные не участвуют как исполняемые условия. Повторно раскрывать уже раскрытые scripted triggers не нужно.

`AND`, `OR`, `NOT`, `NAND`, `NOR` вычисляются по подтверждённой семантике этапа 20 на любой глубине. Если ложен необходимый член И, неизвестные соседи не отменяют запрет. ИЛИ ложно только при ложности всех ветвей. Отрицания сохраняются. Неподдержанная форма оператора остаётся неизвестной и диагностируется.

Для условных ветвей `if` / `else_if` / `else` в контексте триггеров предлагается обработчик: известное условие выбирает ветвь, неизвестное требует анализа всех ещё возможных исходов; результат известен только при их согласии. Отсутствующая выполняемая ветвь не добавляет ограничения. Не применять эту семантику к эффектам. `calc_true_if` с постоянным порогом может использовать границы количества истинных условий: от числа `true` до `true + unknown`; сравнение известно, если одинаково для всех значений диапазона. Сложные пороги остаются неизвестными.

Переходы области видимости и кванторы обрабатываются только разрешёнными правилами. Для `any_*` отсутствие удовлетворяющего объекта можно доказать лишь при невозможности условия для всего допустимого домена. Возможность объекта не доказывает его фактическое наличие. Не вынимать `host_has_dlc` из неизвестной обёртки и не применять его к родительскому блоку отдельно от семантики этой обёртки.

Диагностический обход при этом проходит и неизвестные поддеревья, чтобы увидеть неучтённые ссылки/DLC-проверки. Это наблюдения для отчёта, а не доказательства скрытия.

## 7. Циклы и повторное использование

Узел графа задаётся видом БД, ID/адресом объекта, назначением проверки, вариантом и контекстом. Путь рекурсии отслеживается отдельно от общего кеша: повтор в текущем пути — цикл, повтор завершённого узла — переиспользование результата.

Цикл сам по себе не означает `false`. Циклические участки начинают с неизвестных результатов и уточняются до устойчивого результата по доказанным ограничениям. Внешний DLC-запрет может разрешить часть цикла; цикл без достаточного основания остаётся неизвестным. Промежуточный `unknown` при обнаружении обратного ребра не кешируется как окончательный ответ для всех остальных запросов. Результат не должен зависеть от порядка технологий и объектов.

Границы глубины, количества посещённых узлов и шагов уточнения вынести в конфиг. Достижение лимита даёт отдельную диагностику и неизвестный результат незавершённой ветви; уже доказанное независимой ветвью условие может сохранить значение. Нельзя обрывать обход молча или считать незавершённое доказательство запретом.

Документ читать и проверять хеш один раз на необходимый снимок, используя штатный читатель. Повторяемые условия и индексы держать в памяти. Граф ссылок можно переиспользовать для разных DLC-профилей; результаты вычисления зависят от полного нормализованного профиля. Готовые комбинации сохраняются прежним механизмом; дополнительная постоянная БД кеша в этот этап не требуется.

## 8. Конфигурация

Существующий `config/enrichment/dlc.json` оставить точкой входа. Предлагаемое расположение расширяемых правил: `config/enrichment/dlc/`, отдельные файлы групп `ship_categories`, `empire_objects`, `ascension`, `species`; общие настройки обхода и контекста — в корневом конфиге. Имена файлов и адреса подключений объявляются конфигом, а не обходом всех JSON каталога.

Каждое правило описывает:

- стабильный ID, включённость и поддержанный обработчик;
- предикат, допустимую форму значения и контекст;
- целевой вид БД, выбор объектов, поля ограничений и порядок/логику их объединения;
- отношения поставщиков/принадлежности и правила альтернатив;
- применимость к выбору, приобретению либо владению объектом;
- ссылку на подтверждающее определение/документацию и диагностический код.

В коде остаются механизмы обхода, логики, чтения и проверенные семантические обработчики. Конфиг не исполняет Python и не вводит собственный универсальный язык программирования. Неизвестный ID обработчика или некорректная конфигурация — ошибка до расчёта. Технический предикат, для которого нет доказанного правила, — неизвестное игровое условие, а не ошибка парсера.

Адреса новых источников, целей локализации, результатов и лимиты задаются существующими конфигами. Схемы изменяются в генераторе и пересоздаются им. Громоздкий реестр всех игровых команд не возвращается.

## 9. Комбинации и интерфейс

Сохранить операции существующего локального API и явное «Применить». Новые справочники и правила используются на Python. Фронтенд получает подготовленную видимость/связи и обновляет снимок атомарно; отдельного вычислителя условий на TypeScript не добавлять.

Ревизия результата включает версию реализации/семантики, правила обхода, контекст, выбранные варианты, DLC-профиль и ревизии всех влияющих справочников. Для отношений с несколькими поставщиками учитывать ревизию полного соответствующего индекса: добавление нового поставщика должно инвалидировать прежнее доказательство даже без изменения ранее прочитанных объектов. Входные ревизии не включают выходное обогащение самого расчёта.

Комбинации этапа 20 нельзя выдавать за рассчитанные по новым правилам. Несовпадение ревизии требует нового расчёта; ошибка сохраняет прежний опубликованный набор. Источники, локализация и существующие технологические варианты сохраняются.

Не распространять скрытие по `parent_tech`/`children`: это связи размещения, а не полная формула требований. Прежнее правило самостоятельного корня при отсутствии видимых кандидатов сохраняется, пока недоступность самой технологии отдельно не доказана. Статические пути получения рассматриваются в дополнении; полная симуляция событийной истории не требуется.

## 10. Доказательства и полнота

Расширить отчёт расчёта: источник технологии и поле, последовательность переходов, правила/контексты, объекты и их адреса, DLC и выбранное состояние, результаты узлов и baseline. Для ИЛИ/набора поставщиков доказательство запрета должно охватывать все ветви. Общие части можно хранить один раз со ссылками на узлы; циклы не разворачиваются в бесконечный JSON.

Различать прямой DLC-запрет, косвенный запрет, нулевой DLC-вес, отсутствие доказанного запрета и неразрешённый путь. Диагностировать неизвестные команды/обёртки, неподдержанный контекст, отсутствующую ссылку, неполный домен поставщиков, цикл и лимиты. Не смешивать число проверенных файлов с числом семантически обработанных условий.

Отдельный отчёт покрытия содержит все DLC каталога, найденные прямые/косвенные зависимости, число затронутых технологий и неразрешённые пути с причиной. Для DLC без обнаруженного влияния писать «в исследованной области зависимости не найдены», а не «дополнение не влияет на игру». Все дополнения должны присутствовать в отчёте, включая косметические.

Охват всех DLC не означает исполнение всех команд игры. Известный путь к DLC, оставленный неподдержанным, показывается явно как пробел покрытия; его нельзя скрыть общим успешным числом проверок. Перед приёмкой каждый такой путь должен быть устранён в согласованном объёме либо вынесен пользователю с конкретным примером и ограничением.

## 11. Проверки и приёмка

Полезные синтетические сценарии:

1. Глубокая цепочка объектов, общий узел нескольких технологий и чтение каждого документа один раз.
2. Вложенные И/ИЛИ/отрицания, независимый запрет, неизвестный сосед, условные ветви и границы `calc_true_if`.
3. Несколько поставщиков: все запрещены; один доступен; один неизвестен; домен неполон. Порядок поставщиков не влияет на ответ.
4. Бонус вознесения → традиция → категория; бонусы принятия/завершения категории; традиция в нескольких категориях.
5. Независимость базового объекта от DLC только его варианта; сохранение контекстов; отсутствие ошибочного переноса `ai_playable`, графического fallback или запрета модификации вида.
6. Прямой/косвенный цикл, цикл с внешним DLC-запретом, предел обхода, отсутствующая ссылка и конфликт ID. Перестановка входов не меняет результат.
7. Кеш для одинаковых входов; изменение правил, профиля, определения или состава поставщиков отменяет переиспользование. Нулевой вес скрытой технологии не делает `has_technology` ложным автоматически.
8. Неизменность исходного AST, целостность родителей/детей, отказ/отмена до публикации, отсутствие обращения к игре при применении DLC.

Реальный прогон: все DLC включены; все выключены; каждое дополнение выключено отдельно относительно полного набора; каждое включено отдельно относительно пустого; дополнительные смешанные профили для найденных многодополнительных И/ИЛИ/отрицаний. Число DLC брать из каталога, одинаковые профили исключать. Это целевая матрица, не перебор всех `2^N` комбинаций.

Матрица работает над одним подготовленным графом без публикации отдельного полного снимка на каждый профиль. Для нескольких контрольных профилей отдельно пройти полный путь API → публикация → открытие фронтендом. В сценариях без BioGenesis проверить исчезновение ветви оружия ткачей по доказательству категории кораблей; во включённом состоянии DLC само по себе не выбирает биологическую империю.

Проверить RU/EN новых объектов, открытие набора из 28 видов, отсутствие лишней загрузки каталогов, повторное применение, отмену и сохранение прежнего дерева при ошибке. Измерить построение индексов, обход/повторный расчёт, память, прочитанные документы и публикацию. Критерий корректности — объяснимые решения и отсутствие ложных запретов, а не заранее назначенное число видимых технологий.
