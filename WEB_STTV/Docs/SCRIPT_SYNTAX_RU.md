## Статус и основания

Дата: 2026-11-15. Версия источников: **Stellaris Cygnus v4.5.4 (1b4f)**. Документ основан на [полном исследовании `common/` и `events/`](RESEARCH_SCRIPT_PATTERNS_RU.md): 2 238 `.txt`, а также на пояснениях в документации внутри этих каталогов.

Это справочное описание для обсуждения, не ТЗ парсера и не изменение действующего профиля. Примеры показывают форму; демонстрационные идентификаторы не предлагаются как новые игровые команды. Полнота языка закрытого движка не заявляется.

Статусы сведений:

- **Код** — конструкция найдена вне комментариев и обычных текстовых инструкций.
- **Документация** — возможность описана в поставляемых с игрой инструкциях; её употребление или все детали исполнения могут быть не подтверждены кодом.
- **Не установлено** — наблюдения недостаточно для общего правила; запись сохраняется отдельно от подтверждённых форм.

Документация помогает объяснить конструкцию, но не является исчерпывающим перечнем. Отсутствие упоминания не означает запрета. При расхождении с кодом фиксируется расхождение; комментарий не заменяет проверку реализации. Имена конкретных объектов и scripted-функций относятся к извлекаемым каталогам, а не к грамматике.

## Текст, комментарии и строки

| Элемент | Правило и наблюдение |
|---|---|
| Кодировка | Все исследованные `.txt` читаются как UTF-8; встречаются файлы с BOM и без него. Это характеристика корпуса, не перечень всех кодировок движка. |
| Разделители | Пробел, табуляция и перевод строки разделяют элементы вне строк. Вложенность определяют скобки; отступы не задают структуру. |
| Комментарий | `#` начинает комментарий до конца строки вне строкового значения. Комментарии могут содержать любые примеры скобок и команд. |
| Строка | Двойные кавычки: `"text"`. Содержимое сохраняется целиком, включая пробелы и переводы строк. Найдены 21 многострочная строка и ключи в кавычках. |
| Апостроф | Может быть частью неквотированного имени, например `TOX1_FLEET_Avogadro's_Moles`; по наблюдениям он не является альтернативной кавычкой. |
| Регистр | Сохраняется как в источнике. Сосуществование `root`, `ROOT`, `This` в разных контекстах не доказывает общую нечувствительность всех идентификаторов к регистру. |
| Завершение записи | В наблюдаемых формах нет обязательных `;` и запятых между элементами. На одной строке могут быть несколько записей. |

Скобки и похожие на операторы символы внутри строки не являются внешней структурой. Строка может содержать имя, путь, текст или отложенный фрагмент кода. Нельзя превращать её в блок только потому, что внутри есть `{ ... }`.

Экранирование зависит от уровня обработки. В коде встречается `log = "... \\[This.GetName]"`; документация scripted effects/triggers отдельно описывает экранирование текстовых подстановок (S2, S8). Это не основание автоматически декодировать все строки по правилам JSON или Python. Написание обратных косых черт нужно сохранять.

## Операторы

**Связь ключа со значением и сравнения — полный набор, найденный в активном тексте корпуса:**

| Запись | Назначение | Статус |
|---|---|---|
| `=` | Связывает ключ со значением или блоком; в условии точный смысл определяется командой | Код |
| `<` | Сравнение «меньше» в поддерживающем его контексте | Код |
| `>` | Сравнение «больше» | Код |
| `<=` | Сравнение «меньше или равно» | Код |
| `>=` | Сравнение «больше или равно» | Код |
| `!=` | Проверка неравенства в поддерживающем её контексте | Код |

Один знак `=` нельзя универсально трактовать как математическое равенство: `name = value`, `has_trait = trait_x` и числовая проверка являются разными предметными операциями. Наличие оператора в грамматике не означает, что он разрешён для любого поля.

**Внутри формул `@[ ... ]` и `@\[ ... ]`:**

| Запись | Назначение | Основание |
|---|---|---|
| `+`, `-` | Сложение и вычитание | Код и S2 |
| `*`, `/` | Умножение и деление | Код и S2 |
| `%` | Остаток от деления | S2; в 74 активных формулах не обнаружен |
| `( ... )` | Группировка выражения | Код и S2 |
| `\| ... \|` | Абсолютное значение | Форма найдена в коде, смысл описан в S2 |

S2 описывает обычный математический приоритет, в частности умножение перед сложением. Точная числовая точность движка и все пограничные случаи здесь не устанавливались. Вне формулы `-` может быть частью отрицательного числа или имени, а `/` — частью пути; это не арифметическая операция по одному лишь символу.

**Именованные операции:** `AND`, `OR`, `NOT`, `NOR`, `NAND` найдены как имена логических блоков. Это записи вида `NAME = { ... }`, а не отдельные знаки лексического уровня. `if`, `else_if`, `else`, `switch`, `while`, `limit` и `random_list` также являются именованными конструкциями; их назначение зависит от места использования.

S4 перечисляет числовые команды `set`, `weight`, `add`, `subtract`, `factor`, `mult`, `multiply`, `divide`, `modulo`, `round_to`, `max`, `min`, `pow`, `round`, `ceiling`, `floor`, `abs`, `square`, `square_root`. Они используют обычную форму записи; перечень из документации не объявляется отдельным набором синтаксических операторов или универсальными командами для всех блоков.

`==`, `&&`, `||` как самостоятельные операторы и `?=` как единый оператор в корпусе не найдены. Наблюдаемая запись `owner? = { ... }` состоит из имени с суффиксом `?` и отдельного `=`. `!` в `[[!PARAM]` относится к условному фрагменту, а не к универсальному префиксному отрицанию.

## Специальные символы

| Символ или оболочка | Роль | Контекст |
|---|---|---|
| `{ ... }` | Вложенный контейнер | Блок, список, запись без имени |
| `" ... "` | Строковый токен | Значение или ключ |
| `#` | Комментарий | Вне строки |
| `@NAME` | Объявление либо ссылка на скриптовую константу | Слева либо справа от `=` |
| `@[ ... ]` | Формула | Одно значение |
| `@\[ ... ]` | Форма записи формулы в параметризованных скриптах | Код и пояснения S2 |
| `$NAME$` | Подстановка параметра | Ключ, значение, часть имени, строка или фрагмент |
| `$NAME\|fallback$` | Параметр со значением по умолчанию | Параметризованный текст |
| `[[NAME] ... ]` | Условно включаемый фрагмент | Параметризованный скрипт |
| `[[!NAME] ... ]` | Отрицательный вариант условия | Параметризованный скрипт |
| `.` | Часть цепочки области или идентификатора | `root.owner`, `assimilation.40`; также часть числа `0.5` |
| `:` | Разделитель префикса ссылки | `event_target:target`, `value:formula` |
| `?` | Суффикс наблюдаемого перехода области | `owner?`, `colony.controller?` |
| `\|` | Разделитель аргументов, значения по умолчанию либо граница модуля | Значение зависит от оболочки |
| `@` внутри имени | Часть составного имени, связанного с областью | `violation_of_equal_standing@prev.owner` |
| `/` | Разделитель пути или деление | Путь inline-файла либо формула |
| `\` | Экранирование на соответствующем уровне | Формулы, строковые подстановки; сохраняется буквально |
| `[This.GetName]` | Текстовая подстановка | Содержимое строки; не скриптовый список |

Одному символу нельзя назначить единственный смысл без окружающей конструкции. Например, `@cost` и `flag@root` относятся к разным семействам; `|` в формуле и в `$PARAM|0$` требует разных правил.

## Значения и переменные

Скаляр — один токен либо целая формула. Наблюдаются целые и десятичные числа, отрицательные значения, `yes/no`, неквотированные имена и строки. Категория токена не всегда определяет предметный тип: `1` может быть весом, уровнем или числовым ключом ветви; `name = some_key` может ссылаться на локализацию.

Следует различать три механизма:

| Механизм | Пример | Что означает |
|---|---|---|
| Скриптовое значение с `@` | `@cost = 100`, затем `cost = @cost` | Объявленное в файлах значение; отдельные общие объявления находятся в `common/scripted_variables/` |
| Параметр шаблона | `$COST$`, `$COST\|100$` | Подстановка из места вызова либо предусмотренное значение по умолчанию |
| Переменная игрового состояния | `set_variable = { which = progress value = 10 }` | Значение, устанавливаемое эффектом в игровом контексте, а не объявление `@progress` |

В формуле имя скриптовой константы может употребляться без `@`: `@[ count * 2 ]` (S2 и код). Для ссылки на переменную игрового состояния встречается цепочка `owner.capital_scope.my_variable` (S3). Нельзя объявлять любое неквотированное имя неизвестной константой или автоматически вычислять его из одного файла.

При отсутствии объявления значение остаётся ссылкой с зафиксированным источником. Приоритет конфликтующих объявлений между файлами и точные правила времени их разрешения этим исследованием не установлены.

## Виды конструкций

| Форма | Пример |
|---|---|
| Скалярная запись | `tier = 3` |
| Вложенный именованный блок | `potential = { is_machine_empire = yes }` |
| Список скаляров | `category = { biology }` |
| Список анонимных записей | `entries = { { key = a value = b } { key = c value = d } }` |
| Смешанный контейнер | `prerequisites = { tech_stingers OR = { tech_mauler_growth_1 tech_weaver_growth_1 } }` |
| Пустой блок | `potential = { }` |
| Числовой ключ | `random_list = { 10 = { ... } 90 = { ... } }` |
| Значение с цветовой меткой | `atmosphere_color = hsv { 0.50 0.2 0.8 }` |
| Цветовая запись в списке | `rgb { 142 188 241 }` |
| Самостоятельный маркер | `optimize_memory` внутри scripted effect/trigger |
| Самостоятельный параметр | `$TRIGGER$` между обычными записями |
| Условный фрагмент | `[[PARAM] add_resource = { energy = $PARAM$ } ]` |

Фигурные скобки сами по себе не различают объект, список и набор условий. В списке могут быть вложенные именованные группы. Цветовые блоки бывают с тремя и четырьмя компонентами; универсальное ограничение «ровно три значения» по этому корпусу неверно.

Верхний уровень файла — последовательность. Технологии обычно именованы ключом определения; события могут повторять `country_event = { id = ... }`; файлы тегов содержат самостоятельные имена; встречаются анонимные корневые блоки. Расширение `.txt` не гарантирует, что файл является скриптом: есть обычная документация.

## Вставки, шаблоны и вызовы

**`inline_script` — включение содержимого файла.** Имя записывается именно как в коде: `inline_script`. S1 описывает путь относительно `common/inline_scripts/`, без расширения `.txt`.

```text
inline_script = "ai/hull_preference_weight"

inline_script = {
    script = ai/weapon_preference_weight
    WEAPON_TYPE = weapon_type_energy
}
```

Обе формы используются в `common/technology/00_eng_tech.txt` (строки 497 и 333). Поле `script` задаёт подключаемый файл в блочной форме; остальные поля передают параметры. S1 предупреждает, что включение поддерживается не во всех контекстах. Этот комментарий не превращается в автоматически доказанную таблицу разрешённых мест.

**Scripted triggers и scripted effects — вызов именованного определения.** Имя берётся из `common/scripted_triggers/` или `common/scripted_effects/`, а не из пути вызывающего файла. S2 описывает формы `example_effect = yes` и `example_effect = { PARAM = value }`. В коде scripted triggers также вызываются с `no`, например `species_rights_robot_full_rights_check = no` в S8. Это значение проверки, не параметр с именем `no`.

**Script values — обращение к вычисляемому определению.** S4 описывает `value:my_value` и форму с аргументами:

```text
value:my_value|PARAM1|value1|PARAM2|value2|
```

Пары имени и значения, включая завершающий `|`, сохраняются. Реальный пример: `common/artifact_actions/artifact_actions.txt:1052`. Script values используют параметры и условные фрагменты того же семейства; это не включение файла по пути.

**Подстановка текста и условное включение.** `$PARAM$` может заменить часть имени (`"$PARAM$_flag"`), ключ, значение или несколько записей. S1 явно описывает передачу кода строкой; это подтверждается многострочными параметрами в `common/buildings/01_pop_assembly_buildings.txt:1131`.

По S2, `[[PARAM] ... ]` включает фрагмент, если параметр передан и не равен `no`; `[[!PARAM] ... ]` — если не передан или равен `no`. Наличие обеих форм подтверждено исходниками. Это условие подстановки параметра, его нельзя автоматически подменить игровым `if = { limit = ... }`.

**Похожие названия с другим назначением:**

| Запись | Установленный контекст |
|---|---|
| `include`, `included_building_sets`, `included_zone_sets` | Списки доступных зданий или зон и их наборов; не директивы чтения файла. S5 и `common/zones/00_zones.txt:34`. |
| `scripted_action = some_id` | Ссылка на определение действия из компонента корабля; S6. |
| `injected_modifier = { ... }` | Поле компонента оружия с модификатором, длительностью и настройками наложения; `common/component_templates/00_weapons_energy.txt:1280`. |

В исследованном корпусе подтверждена одна явная общая команда включения скриптового файла — `inline_script`. Другие механизмы повторного использования описаны отдельно; это не утверждение об отсутствии иных возможностей во всём движке.

## Ссылки и области действия

| Вид | Пример | Как отличать |
|---|---|---|
| Идентификатор объекта | `has_technology = tech_synthetic_workers` | Целевой каталог определяет поле/команда; специальный префикс необязателен |
| Идентификатор события | `id = assimilation.40`, `namespace = assimilation` | Точка является частью имени события; это не обязательно переход области |
| Цепочка области | `root.owner`, `prev.owner`, `owner.capital_scope` | Нужен текущий контекст и известные переходы |
| Сохранённая цель | `event_target:target_planet` | Имя цели, сохраняемое соответствующим эффектом; не путь к файлу |
| Вычисляемое значение | `value:my_value` | Определение в `common/script_values/` |
| Численное значение триггера | `trigger:pop_amount` | Механизм описан S3; конкретный триггер должен его поддерживать |
| Значение модификатора | `modifier:pop_citizen_happiness` | Чтение значения из контекста, S3 |
| Составная ссылка | `owner.capital_scope.trigger:pop_amount` | Переход области и специализированное чтение, S3 |
| Составное имя с `@` | `violation_of_equal_standing@prev.owner` | Найдено в установке флага; не скриптовая константа `@name` |
| Текстовая ссылка | `[This.GetName]` внутри строки | Отдельная текстовая интерпретация; строка остаётся одним внешним токеном |
| Имя локализации или графического ресурса | Значения `title`, `desc`, `icon` | Назначение устанавливает поле; не все строковые значения являются локализацией |
| Файловая ссылка | `ai/hull_preference_weight` у `inline_script` | Разрешается относительно каталога включаемых файлов по S1 |

`this`, `root`, `prev`, `from` и их цепочки встречаются в коде, но доступность и точный смысл зависят от текущей области. Нельзя назначить единственную начальную область всему `common/` или всем событиям.

Формы с `?` наблюдаются у переходов (`owner?`, `event_target:arkship.leader?`). Они выделяются как отдельная особенность записи. Полная семантика отсутствующей цели, а также эквивалентность форм с пробелом и без него здесь не доказаны.

Составные имена с `@` наблюдаются, например, в `common/scripted_effects/first_contact_dlc_effects.txt:3598` и `:3778`. По контексту они связывают имя флага с областью; точный алгоритм формирования внутреннего имени не выводится из текстов.

## Порядок и контекст

- Хранить записи последовательно, включая повторяющиеся ключи. Словарь с правилом «последнее значение заменяет предыдущее» не является общей моделью контейнера.
- Сохранять исходное написание, кавычки, операторы, границы формул, условных фрагментов и координаты. Сортировка команд может менять смысл.
- Различать чтение структуры, раскрытие параметров/вставок и предметную интерпретацию. Наличие фигурного блока не определяет, является ли он условием, эффектом или данными объекта.
- Имя поля не является глобальным контрактом: `modifier`, `trigger`, `value`, `id` встречаются в разных контекстах.
- Наблюдение формы не доказывает её допустимость во всех областях; отсутствие формы в выбранном каталоге не доказывает её запрета.

Для дальнейшего проектирования отдельно понадобятся правила разрешения ссылок, обработки циклов включения, конфликтов определений и неизвестных конструкций. Этот документ описывает синтаксис и имеющиеся свидетельства, не выбирает поведение продукта в этих ситуациях.

## Сводная схема форм

Ниже — сокращённая схема наблюдаемых форм, не формальная спецификация языка движка. `*` здесь означает повторение элементов схемы, а не оператор игрового текста; `|` между вариантами — метаобозначение выбора.

```text
document    := entry*
entry       := assignment | scalar | block | color_block | conditional
assignment  := key operator value
key         := atom | quoted_string
operator    := "=" | "<" | ">" | "<=" | ">=" | "!="
value       := scalar | block | color_block
scalar      := atom | quoted_string | formula
block       := "{" entry* "}"
color_block := color_tag block
color_tag   := "rgb" | "hsv"
formula     := "@[" expression "]" | "@\[" expression "]"
conditional := "[[" parameter_name "]" entry* "]"
             | "[[!" parameter_name "]" entry* "]"
```

Для цветовой формы подтверждены `field = rgb/hsv { ... }` и самостоятельные `rgb { ... }` в цветовых списках. Схема не утверждает допустимость каждого сочетания во всех местах. `atom`, `quoted_string` и `expression` здесь намеренно не превращены в окончательные регулярные выражения или правила вычисления. Параметры могут находиться внутри атомов и строк либо занимать место целого элемента.

## Неподтверждённые границы

- `trait_bg_active_glow { ... }` без `=` в `common/named_colors/01_trait_colors.txt:65` — единичная спорная запись. Она не включена в правило «произвольный именованный блок без оператора».
- `%` и некоторые числовые операции описаны документацией; их полный набор и исполнение не проверялись запуском игры.
- Экспоненциальная запись числа, универсальные правила регистра, экранирования и разрешения одинаковых имён не установлены. Не следует превращать отсутствие примеров в запреты движка.
- Исследование не охватывает синтаксис `.gui`, `.gfx`, YAML-локализаций, ODS, CSV и других форматов как самостоятельных языков.
- Приведённые правила не подменяют проверку игровых условий и не означают, что все выражения вычисляются без состояния партии.
