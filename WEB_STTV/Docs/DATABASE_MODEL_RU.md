## Статус и состав данных

Дата: **2026-11-15**. Модель первой JSON-базы согласована пользователем и реализована в рамках отдельно утверждённого [первого этапа бэкэнда](TZ_RU.md#3-первый-этап-бэкэнда--сборка-бд). Она развивает [описание игрового объекта](TECHNOLOGY_MODEL_RU.md).

Данные этапа:

- Определения технологий из `STELLARIS_ROOT / TECH_PATH / *.txt`.
- Определения категорий и уровней из подкаталогов `category/` и `tier/`.
- Локальные определения `@...` из этих же файлов.
- **Только названия технологий и их условных вариантов**, отдельно на русском и английском, из настроенных источников локализации.

Описания технологий, тексты эффектов, названия категорий и прочие локализованные тексты пока не добавляются. Их ключи остаются в игровых полях, если там присутствуют. Внешние игровые переменные, scripted triggers, inline-вставки, изображения и определения открываемых объектов на этом этапе не загружаются. Например, `common/scripted_variables/` находится за пределами `TECH_PATH`.

База хранит структуру, известную из перечисленных источников. Она не вычисляет доступность для государства, активный вариант, итоговую цену или вероятность выпадения. Способ отображения — граф или другой интерактивный интерфейс — не меняет эту модель.

## Строгая схема и неизвестные элементы

Модель базы **закрытая и явно объявленная**. `fields` не является свободным словарём исходного скрипта. В базу допускается поле, для которого определены назначение, допустимый контекст, тип значения, кратность и правило преобразования. Сам факт успешного синтаксического разбора не означает поддержку поля.

Правила действуют на всех уровнях:

- Оболочки записей содержат только перечисленные для них поля. Дополнительные свойства запрещены, включая произвольные `raw`, `extra` или `unknown`.
- В `TechnologyRecord.fields` разрешены только поля таблицы базовой технологии; в `VariantRecord.fields`, категориях и уровнях — только поля соответствующих отдельных таблиц. Совпадение имени не переносит правила между контекстами: например, базовый `weight` и `weight` варианта имеют разные типы.
- У каждого варианта объединённого типа проверяется собственная полная структура. Например, `Requirement` содержит ровно один ключ `tech`, `all` или `any`; `RepeatedValue` не разрешает неизвестные поля или значения других типов.
- Динамические ключи разрешены только в объявленных коллекциях: ID технологий, категорий и уровней, пути файлов в `file_variables`. Новый ID является данными, а не новым полем схемы; значение записи всё равно проверяется по установленному типу.
- Вложенные скрипты также требуют объявленных правил для команд, аргументов, операторов и областей видимости. `ScriptBlock` не служит обходом строгой схемы.

Неизвестное поле, неподдержанная вложенная конструкция или недопустимый тип записываются в **отдельный отчёт разбора вне рабочей БД**: файл, строка, ID определения, путь к элементу и причина отказа. Небольшой исходный фрагмент можно включить в отчёт; автоматически переносить его в базу, подменять `null` либо молча отбрасывать условие запрещено. Источники читаются непосредственно в режиме read-only; копии файлов и постоянный первичный снимок не создаются.

Сборка с такими ошибками не считается успешной и не заменяет рабочую базу неполным результатом. Сначала исследуется конструкция и уточняются модель и её обработка. Это отличается от явно предусмотренной неразрешённой ссылки: например, известная форма `VariableValue` с `resolved: null` допустима по правилам текущего этапа.

Ограничения реализованы в [машиночитаемой схеме JSON](../schemas/database.schema.json) и контекстных проверках сборщика. Поддерживаемые вложенные команды и их аргументы явно перечислены в [реестре правил](../schemas/script_rules.json); общая форма `ScriptBlock` сама по себе этот перечень не задаёт. Запуск и устройство реализации описаны в [руководстве первого этапа](BACKEND_STAGE_1_RU.md).

## Корневой объект базы

Один JSON-файл в UTF-8 содержит следующие обязательные поля:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `format_version` | Целое число | Версия структуры файла; для этой модели `1`. Это не версия приложения или игры |
| `technologies` | Объект `ID → TechnologyRecord` | Базовые технологии; ID — ключ записи, отдельно внутри записи не дублируется |
| `categories` | Объект `ID → DefinitionRecord` | Категории из `category/` |
| `tiers` | Объект `ID → DefinitionRecord` | Уровни из `tier/`; ключи JSON являются строками, например `"0"`, `"5"` |
| `file_variables` | Объект `путь файла → VariableDefinition[]` | Локальные определения игровых переменных с сохранением области файла и порядка |

Пустая база имеет корректную форму:

```json
{
  "format_version": 1,
  "technologies": {},
  "categories": {},
  "tiers": {},
  "file_variables": {}
}
```

Порядок ключей объектов не задаёт игровой порядок. Там, где порядок важен, используются массивы. Дубли ключей JSON запрещены. Повторные базовые ID требуют отдельного решения при сборке; нельзя терять определение через молчаливую замену записи.

Абсолютные корни и приоритеты источников остаются в `global_variables.json`. База содержит относительные ссылки на происхождение данных и может читаться без исходных каталогов. Поле версии игры здесь не предусмотрено: оно не выводится достоверно из одной папки технологий.

## Запись технологии

Все поля оболочки `TechnologyRecord` обязательны:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `source` | `SourceLocation` | Место исходного определения |
| `name` | `{ "ru": string или null, "en": string или null }` | Две строки названия; отсутствие одного языка не скрывает другой |
| `name_sources` | `{ "ru": LocalizationSource или null, "en": LocalizationSource или null }` | Происхождение выбранных названий |
| `fields` | Закрытый объект игровых полей | Только подготовленные значения разрешённых полей из таблицы ниже; отсутствующие в игре поля пропускаются |

`SourceLocation` содержит `file: string` и `line: integer`. Путь `file` задаётся относительно `TECH_PATH`, номер строки начинается с 1. Например: `{"file":"00_megastructures.txt","line":1}`. Для вложенных записей используется тот же корень пути.

`fields` отделяет игровые имена от служебных полей базы. В частности, `name` оболочки — локализованное название, а не дополнительное поле в игровом определении.

## Названия на двух языках

Для базовой технологии ключ локализации равен её ID. Для варианта используется его исходное поле `name`, записанное в базе как `name_key`.

Поиск русского названия выполняется **по конкретному ключу**: `RU_LOC_TIER_1` → `RU_LOC_TIER_2` → `RU_LOC_TIER_3`. Английское название ищется независимо в `EN_LOC_TIER_1`. Проверяется соответствующий языковой заголовок `l_russian` или `l_english`.

`LocalizationSource` содержит:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `tier` | Строка | Имя использованной переменной источника, например `RU_LOC_TIER_2` |
| `file` | Строка | Путь файла относительно каталога этого источника |
| `line` | Целое число от 1 | Строка найденной записи |
| `key` | Строка | Найденный ключ локализации |

Правила содержания:

- `name.ru` и `name.en` содержат значения выбранных строк без внешних кавычек и служебного номера после ключа. Это данные локализации, а не вновь написанный перевод.
- Игровая разметка, грамматические маркеры, ссылки `$...$` и подстановки сохраняются в строке. Их вычисление и визуальное оформление не входят в этот этап; наличие строки ещё не означает, что она является простым текстом без разметки.
- JSON-экранирование должно сохранять содержимое: например, игровая последовательность обратного слеша и `n` хранится как `\\n`. После чтения JSON должна получаться исходная последовательность символов значения.
- Если ключ отсутствует во всех источниках языка, соответствующие `name` и `name_sources` равны `null`. ID или текст другого языка не записывается вместо отсутствующего перевода. Выбор подписи для интерфейса будет отдельным решением.
- Явное пустое значение хранится как `""` с источником. Оно отличается от отсутствующего ключа; переход к следующему уровню выполняется при отсутствии ключа.
- Если в одном уровне несколько одинаковых записей, текст однозначен; для воспроизводимости источник выбирается по относительному пути файла, затем по номеру строки. Разные значения одного ключа внутри выбранного уровня требуют сообщения об ошибке сборки, а не произвольного выбора или перехода на более низкий уровень.

Описания `<ID>_desc` не запрашиваются для наполнения базы. Ключи `description`, `custom_tooltip`, `title`, `desc` внутри скриптов сохраняются как ссылки. Локализация названий не расширяется на них автоматически.

## Представление игровых полей

Обычные поля сохраняют исходные имена внутри `fields`. Числа становятся числами JSON, известные логические поля `yes` / `no` — `true` / `false`, списки идентификаторов — массивами строк. Разбор вложенного скрипта описан отдельно.

| Игровое поле | Представление в JSON |
| --- | --- |
| `area` | Строка: `physics`, `society` или `engineering` |
| `tier`, `levels` | Целое число либо `VariableValue`, если значение задано переменной |
| `cost` | Число, `VariableValue` или `ScriptBlock` |
| `cost_per_level`, `weight` | Число или `VariableValue` |
| `category`, `feature_flags`, `weight_groups` | Массив строк; пустой исходный список становится `[]` |
| `is_rare`, `is_dangerous`, `is_insight`, `is_reverse_engineerable`, `start_tech` | Логическое значение JSON |
| `icon`, `gateway` | Строка с исходным идентификатором или меткой; файл изображения не загружается |
| `prerequisites` | `Requirement`: логическая структура ссылок, описанная ниже |
| `potential`, `starting_potential`, `ai_weight`, `modifier`, `mod_weight_if_group_picked` | `ScriptBlock` |
| `weight_modifier`, `prereqfor_desc` | Массив `ScriptBlock` в исходном порядке, даже если блок один |
| `technology_swap` | Массив `VariantRecord` в исходном порядке, даже если вариант один |

Таблица охватывает все 25 полей изученных базовых определений. Значения не дополняются предполагаемыми игровыми значениями по умолчанию. Особое представление неожиданного повторения обычного поля задано в разделе о повторах.

## Числа и игровые переменные

`VariableValue` содержит ровно два поля:

```json
{
  "variable": "@tier5cost3",
  "resolved": null
}
```

`variable` — исходная ссылка, `resolved` — известное числовое значение или `null`. На этом этапе разрешается только однозначная цепочка локальных определений в том же исходном файле. Отсутствующая локальная переменная, цикл или неоднозначность оставляют `resolved: null`. `null` не равен нулевой стоимости.

Например, хотя предыдущим исследованием установлено значение `@tier5cost3` в общей папке переменных, текущий сбор его оттуда не читает и не подставляет число по памяти. Определения из другого файла `TECH_PATH` также не считаются автоматически глобальными.

Вложенные скриптовые выражения `@...`, `value:...` и ссылки inline сохраняются в `ScriptBlock`. Этот этап не рассчитывает стоимость и веса целиком. `resolved` прямой ссылки означает только локальную константу, а не окончательную игровую цену.

## Требования и связи

`Requirement` имеет одну из трёх форм:

| Форма | Значение |
| --- | --- |
| `{ "tech": "tech_id" }` | Ссылка на технологию |
| `{ "all": [Requirement, ...] }` | Все вложенные требования нужны совместно |
| `{ "any": [Requirement, ...] }` | Достаточно одного вложенного требования |

У каждой записи только один из ключей `tech`, `all`, `any`. Внешний `prerequisites` преобразуется в `all`, каждая исходная группа `OR` — в отдельный `any`. Порядок сохраняется. Пример для `tech_mega_engineering`:

```json
{
  "all": [
    { "any": [{ "tech": "tech_starbase_5" }, { "tech": "tech_arkship_tier_3" }] },
    { "tech": "tech_zero_point_power" },
    { "any": [{ "tech": "tech_battleships" }, { "tech": "tech_stingers" }] }
  ]
}
```

Явный пустой блок становится `{"all":[]}`. Отсутствующее поле пропускается. Неизвестная конструкция не превращается в обычную ссылку по предположению: её обработка требует уточнения модели.

Отдельного массива рёбер и копии обратных связей в файле пока нет. Они однозначно получаются из этих выражений в загруженной базе. Это предотвращает рассогласование двух сохранённых представлений. `has_technology` в весах или условиях не добавляется в требования.

## Условия доступности и выбора

Требования к предыдущим технологиям — только одна часть условий. Ограничения по государству, гражданским моделям, принципам, происхождению, видам, планетам и прочим обстоятельствам сохраняются в соответствующих скриптовых полях, если для конструкции объявлено правило обработки. Они не сводятся к дополнительным рёбрам дерева.

| Механизм | Где хранится | Что означает |
| --- | --- | --- |
| Предыдущие технологии | `fields.prerequisites` | Логические требования к технологиям-предшественникам |
| Уровень исследований | `fields.tier` и определения `tiers` | Требования уровня учитываются отдельно от конкретных предшественников |
| Общие условия технологии | `fields.potential` | Условия допустимости для государства: например, DLC, гражданская модель, происхождение или флаг |
| Стартовые условия | `fields.starting_potential` совместно с `start_tech` | Отдельные условия стартового получения; не подмена общих условий исследований |
| Условия выпадения | `fields.weight`, `fields.weight_modifier` и правила групп | Изменяют вес предложения технологии. Нулевой множитель может исключать обычное выпадение; положительная поправка не становится обязательным требованием |
| Условия варианта | `fields.technology_swap[].fields.trigger` | Определяют применимость варианта основной технологии; не заменяют её `potential` |
| Предпочтения ИИ | `fields.ai_weight` | Влияют на выбор ИИ, а не задают самостоятельное ограничение для игрока |

Примеры из установленной игры, пути относительно `TECH_PATH`:

- У `tech_pk_nanobots` условие `has_valid_civic = civic_machine_assimilator` находится в `potential` (`00_apocalypse_tech.txt:269`). Это часть условий технологии наряду с DLC и флагом проекта.
- У `tech_synthetic_leaders` проверки `has_origin = origin_necrophage` и `has_trait = trait_necrophage` находятся в одном модификаторе веса с `factor = 0.33` (`00_eng_tech.txt:3407–3410`). Это поправка веса при совместном выполнении условий, а не требование иметь такое происхождение и признак для исследования.

У вложенных условий сохраняются логические группы и область проверки. Например, проверка признака вида внутри перебора видов не равнозначна проверке государства. Условия наличия зданий, если они встретятся, также требуют объявленного правила и сохранения области планеты; для них не создаётся произвольное поле верхнего уровня `buildings`.

**Сохранить условие — не значит вычислить его выполнение.** В этой базе нет состояния конкретной партии: принципов и гражданских моделей государства, состава видов, построенных зданий, текущих флагов и прочего. Поэтому готовый результат «доступно этому игроку» здесь не записывается. Отсутствие сведений нельзя считать выполнением или невыполнением условия; нулевой вес обычного выпадения также не доказывает невозможность получения технологии другим способом.

Известные ссылки на внешние scripted triggers, inline-вставки и значения могут сохраняться только по явно объявленным правилам для соответствующей ссылки. Их тела на этом этапе не читаются, поэтому полная логика доступности из одной папки технологий не всегда раскрывается. Неизвестная команда не становится допустимой внешней ссылкой автоматически: для неё действует порядок отказа и отчёта из раздела о строгой схеме.

## Скриптовые блоки

`ScriptBlock` — объект с обязательным `entries: ScriptEntry[]`. Пустой блок представлен как `{"entries":[]}`. `ScriptEntry` содержит:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `key` | Строка или `null` | Только имя, разрешённое правилом текущего контекста; `null` для разрешённого самостоятельного элемента списка |
| `operator` | Строка или `null` | Только оператор, разрешённый для этой команды, например `=` или `<`; `null` только у самостоятельного элемента |
| `value` | Строка или `ScriptBlock` | Форма значения и содержимое проверяются по объявленному правилу команды |
| `line` | Целое число от 1 | Номер строки в файле содержащего определения |

Внутри скриптового блока скаляры хранятся строками: `"yes"`, `"0.50"`, `"@some_value"`. Это способ хранения известных аргументов, а не разрешение принимать неизвестные. Правило каждой команды определяет допустимый смысл значения: `yes` / `no`, числовой токен, идентификатор определённого вида, объявленная ссылка или вложенный блок. Неверная форма отвергается, даже если она является корректной строкой JSON. Числа и Boolean у внешних игровых полей подготовлены по предыдущей таблице. Синтаксические внешние кавычки скалярного токена не входят в его значение; исходное форматирование и комментарии остаются в исходных файлах и в базу не переносятся.

Для каждой поддерживаемой команды необходимо объявить допустимые родительские блоки, входную и вложенную области видимости, операторы, форму и тип аргументов, обязательность, кратность и правило обработки. Известная команда в неподдержанном контексте также считается ошибкой. `key` и `operator` равны `null` только вместе и только там, где правило разрешает самостоятельные элементы. Распознавание внешней ссылки не означает вычисление её тела.

Пример значения `potential`:

```json
{
  "entries": [
    { "key": "is_nomadic", "operator": "=", "value": "no", "line": 16 }
  ]
}
```

Формат сохраняет повторяющиеся ключи, операторы, вложенность и порядок поддерживаемых конструкций. В нём остаются объявленные условия, числовые правила, модификаторы, ключи описаний и внешние ссылки. Неизвестные элементы не копируются в `entries`. Интерфейс получает проверенный структурированный JSON и не разбирает исходный синтаксис Stellaris заново.

## Условные варианты

Каждый элемент `fields.technology_swap` — `VariantRecord` с полями:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `source` | `SourceLocation` | Положение исходного блока |
| `name_key` | Строка | Исходное поле `name` варианта; ключ поиска локализованного названия |
| `name` | Объект с `ru` и `en` | Две строки названия по тем же правилам, что для базовой технологии |
| `name_sources` | Объект с `ru` и `en` | Источники найденных названий |
| `fields` | Закрытый объект игровых полей | Только разрешённые поля варианта из таблицы ниже |

Соответствие оставшихся восьми полей:

| Игровое поле | Представление |
| --- | --- |
| `trigger`, `modifier`, `weight` | `ScriptBlock`; `weight` варианта не приводится к числу по правилам базовой технологии |
| `inherit_icon`, `inherit_effects` | Boolean |
| `area` | Строка: `physics`, `society` или `engineering` |
| `category` | Массив строк |
| `prereqfor_desc` | Массив `ScriptBlock` |

Отсутствующие поля не дополняются наследуемыми значениями. Не выбирается активный вариант и не выполняется слияние его эффектов с базовыми. Одинаковый `name_key` у нескольких вариантов допустим: записи различаются родительской технологией и индексом в массиве. Исходное `name` не дублируется внутри `fields`.

Связь с основной технологией задаётся **вложенностью**, а не отдельным полем ссылки. Например, `technologies.tech_titans.fields.technology_swap[0]` — первый вариант основной технологии `tech_titans`. Поля `parent_id` в записи варианта нет: оно дублировало бы уже известного родителя. `name_key` является ключом локализации названия варианта, а не ID основной технологии. Вариант не становится отдельной записью в `technologies` и отдельным узлом требований.

## Повторные и отсутствующие поля

Массивы `technology_swap`, `weight_modifier`, `prereqfor_desc` предназначены для обычных повторяемых блоков. Для повторения поля, которое обычно одиночное, используется `RepeatedValue` вместо его обычного значения:

```json
{
  "occurrences": [
    { "line": 665, "value": 0 },
    { "line": 668, "value": { "variable": "@tier2weight3", "resolved": null } }
  ]
}
```

Так выглядит `fields.weight` у `tech_orbital_arc_furnace`. Каждый `value` имеет обычный тип соответствующего поля; `line` указывает исходное вхождение. Массив содержит не меньше двух записей и сохраняет исходный порядок. Это не сложение, не выбор последнего значения и не установленное правило приоритета движка. Одинаковые повторы также сохраняются.

Различаются:

- Нет ключа в `fields` — поле отсутствует в определении.
- `false`, `0`, `""`, `[]`, `{"entries":[]}` — явно заданные значения соответствующего типа.
- `VariableValue.resolved = null` — значение игровой ссылки не разрешено.
- `name.ru = null` или `name.en = null` — название на этом языке не найдено.
- `RepeatedValue` — несколько исходных вхождений одиночного поля.

Произвольный `null` вместо неизвестного игрового поля не используется. Новое неподдержанное поле попадает в отдельный отчёт и препятствует успешной сборке до уточнения модели и правил преобразования. Его нельзя автоматически сохранить или молча отбросить. Правила миграции старых форматов на этом этапе не вводятся.

## Категории и уровни

`DefinitionRecord` содержит только обязательные `source: SourceLocation` и `fields: object`. Для категории и уровня используются разные закрытые наборы полей `fields`, перечисленные ниже. Названия этих объектов пока не локализуются.

Для категории в `fields` сохраняются `icon: string`, если задан, и `weight_modifier: ScriptBlock[]`, если задан. Для уровня — `previously_unlocked: number или VariableValue`, если задан, и `weight_modifier: ScriptBlock[]`, если задан. Повтор одиночного поля использует `RepeatedValue`.

Пустое определение уровня 0 остаётся записью с `fields: {}`, а не удаляется. Категория технологии ссылается на ключ в `categories`; известное числовое значение `tier` сопоставляется со строковым ключом в `tiers`. Неразрешённая переменная уровня не считается отсутствующим определением уровня.

## Локальные определения переменных

`file_variables` хранит определения только в прочитанных файлах `TECH_PATH`, отдельно для каждого файла. Значение записи — упорядоченный массив `VariableDefinition`:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `name` | Строка | Имя вместе с `@` |
| `value` | Строка | Скалярное содержимое определения, включая возможную ссылку на другую переменную |
| `line` | Целое число от 1 | Положение определения |

Путь файла использует тот же корень, что `SourceLocation.file`. Файл без локальных переменных можно не включать в этот объект. Повторяющиеся имена не превращаются в один ключ словаря. Это игровые переменные; настройки проекта из `global_variables.json` сюда не копируются.

## Пример записи

Ниже сокращённая запись `technologies.tech_arcane_deciphering`. Показаны оболочка и часть игровых полей; при настоящем сборе оставшиеся поля, включая `weight_modifier`, также обязательны к переносу из источника.

```json
{
  "source": { "file": "00_ancient_relics_tech.txt", "line": 2 },
  "name": {
    "ru": "Расшифровка загадок",
    "en": "Arcane Deciphering"
  },
  "name_sources": {
    "ru": {
      "tier": "RU_LOC_TIER_2",
      "file": "ancient_relics_l_russian.yml",
      "line": 280,
      "key": "tech_arcane_deciphering"
    },
    "en": {
      "tier": "EN_LOC_TIER_1",
      "file": "ancient_relics_l_english.yml",
      "line": 280,
      "key": "tech_arcane_deciphering"
    }
  },
  "fields": {
    "area": "society",
    "tier": 2,
    "category": ["archaeostudies"],
    "cost": { "variable": "@tier2cost3", "resolved": null },
    "weight": { "variable": "@tier2weight3", "resolved": null },
    "is_rare": true,
    "feature_flags": ["unlock_arcane_deciphering"]
  }
}
```

Название и его источник проверены в текущих каталогах: в `RU_LOC_TIER_1` ключ не найден, в `RU_LOC_TIER_2` он есть. В базу не добавлено описание этой технологии. Пример показывает данные документации, а не результат уже реализованного импортера.

## Правила проверки

При реализации формирование базы должно проверять:

1. Закрытую структуру всех объектов, `format_version`, допустимые поля каждого контекста, типы значений и уникальность ключей JSON.
2. Сохранение всех поддерживаемых игровых полей, повторов, логических групп и порядка массивов; отсутствие подстановки предполагаемых значений по умолчанию.
3. Существование ID в `prerequisites` и определений категорий; корректность известных ссылок на уровни. Проверка циклов относится к графу требований, не ко всем упоминаниям технологий в скриптах.
4. Отсутствие чтения внешних определений при разрешении `@...`, inline и scripted triggers; недоступные значения остаются явно неразрешёнными.
5. Независимое получение названий RU/EN по ключу, приоритет русского источника, совпадение текста с указанным происхождением и отсутствие загрузки описаний в локализованные поля.
6. Различение отсутствия поля, пустого значения, неразрешённой ссылки и повторных записей.
7. Относительность всех путей происхождения и возможность прочитать готовые данные без доступа к исходникам.
8. Вложенные команды, операторы, аргументы и области видимости по объявленным правилам; отсутствие произвольного переноса неизвестных элементов в `fields` или `entries`.
9. Отдельный отчёт для неподдержанных конструкций и отказ от замены рабочей базы при ошибке. Неизвестное условие нельзя отбрасывать или считать истинным.
10. Сохранение различий между предшественниками, общими и стартовыми условиями, весами, предпочтениями ИИ и триггерами вариантов. Связь варианта с родителем определяется его положением в основной технологии.

Для документа проверены корректность JSON-примеров, соответствие таблиц текущей модели технологии и согласованность языковых версий. Реализованный сборщик прошёл синтетические проверки и сборку полной базы на текущих источниках; [результаты первого этапа](BACKEND_STAGE_1_RU.md#проверки) приведены отдельно.
