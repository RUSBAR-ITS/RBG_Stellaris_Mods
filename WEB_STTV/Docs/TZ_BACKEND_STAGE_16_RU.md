## 1. Статус и цель

**Утверждено пользователем и реализовано 2026-11-19.** Документ конкретизирует [согласованный подход](TECHNOLOGY_TREE_ENRICHMENT_RU.md). Запуск, формат результата и результаты проверки описаны в [руководстве этапа 16](BACKEND_STAGE_16_RU.md).

По готовому набору БД рассчитывать технологического родителя каждой технологии и сразу дополнять список детей родителя. Сохранять результат внутри БД технологий как обогащение объектов, отдельно для именованных комбинаций. Первая поставляемая комбинация — справочник с базовыми представлениями и согласованным профилем обычной империи.

Основа критериев — [общий аналитический прогон](frontend/CHAIN_RULES_FULL_REVIEW_RU.md). Исследовательские скрипты и отчёты служат материалом переноса и контрольными данными; продукт не импортирует код из `data` и не использует готовые исследовательские решения вместо расчёта.

## 2. Объём этапа

Включены самостоятельная Python-операция, отдельный конфиг правил, параметры комбинаций, извлечение свидетельств из готовых БД, обработка ручного выбора вариантов, сохранение результатов, контроль актуальности, диагностический отчёт и неинтерактивный CLI.

Не включены сетка, `location`, визуальная сортировка детей, HTTP API, изменения фронтенда, автоматическая генерация при запуске, MongoDB и миграция хранения. Событийные способы получения технологий остаются отложенными; согласованный анализ назначения вооружения через действия и события сохраняется.

Игровые файлы, парсер, библиотека вставок и исходные технологические требования этой операцией не изменяются. Новый реестр допустимых игровых команд, произвольный интерпретатор состояния империи и ручные переопределения родителей не вводятся.

## 3. Входы и конфигурация операции

Вход — набор из 15 БД актуального формата `sttv.parse_database`, `format_version = 6`. У файлов должны быть разные ожидаемые `dataset.kind` и одинаковый `dataset.set_id`. Отсутствие файла, несовпадение наборов или неподдерживаемый формат завершают операцию до публикации.

Отдельная конфигурация `config/enrichment/technology_tree.json` содержит:

| Поле | Назначение |
| --- | --- |
| `format`, `format_version` | `sttv.technology_tree_config`, версия 1 |
| `backend_config` | Ссылка на `config/backend.json`; используются пути выходных БД, а не запуск сборки |
| `dataset_registry` | Ссылка на `config/datasets.json` для видов объектов и способов извлечения ID |
| `technology_targets` | Ссылка на `config/enrichment/targets/technologies.json` для выбора технологических документов |
| `rules` | Ссылка на `config/enrichment/technology_tree/rules.json` |
| `combination` | Ссылка на `config/enrichment/technology_tree/combinations/reference_default.json` |
| `report` | `reports/technology_tree.json` относительно `WORK_DIR` |
| `staging_directory` | `staging/technology_tree` относительно `WORK_DIR` |

Ссылки конфигурации используют действующий формат `base`/`path`. Рабочие пути настраиваются через `WORK_DIR`; абсолютные адреса конкретной машины в коде отсутствуют. Загрузка настроек не вызывает проверку каталогов игры, сборщик, локализатор или подготовку библиотек.

Подготовить отдельный профиль `config/enrichment/technology_tree/profiles/reference_empire.json`. Все значения соответствий, функциональных групп, направлений перехода между объектами и профильных фактов находятся в конфигурациях, а не в списках конкретных технологий в Python.

## 4. Расширяемые правила

`rules.json` имеет `format = sttv.technology_tree_rules`, `format_version = 1`, массив `rules` и словарь переиспользуемых блоков `definitions`. Запись массива содержит уникальный `id`, `enabled` и `parameters`; порядок массива — порядок применения. `parameters` содержит параметры обработчика непосредственно либо единственное поле `definition_ref` с именем блока `definitions`. Ссылка заменяет объект параметров целиком, без переопределений и цепочек ссылок; блок проверяется по схеме использующего его обработчика. Произвольные выражения и исполняемый текст не допускаются.

Поставляемый порядок и содержание:

| ID | Критерий и настраиваемые сведения |
| --- | --- |
| `normalized_id` | Равенство ID после удаления цифр `0–9`; другие части ID не отбрасываются |
| `same_area` | Совпадение действующей области науки |
| `same_category` | Непустое пересечение действующих научных категорий |
| `mandatory` | Приоритет обязательных технологических требований перед альтернативами |
| `direct_upgrades` | Прямые улучшения объектов; виды, поля и направление связей задаются конфигом |
| `same_potential` | Полное структурное совпадение непустого базового `potential`, без происхождения узлов |
| `functional_groups` | Подвижный боевой корабль, изменение класса планеты, вооружение против кораблей |
| `direct_relations` | Согласованные прямые функциональные связи объектов |
| `indirect_affinity` | Родство через исходные требования кандидата; начальная глубина 1, поля эффектов задаются конфигом |
| `production_affinity` | Собственный бонус производства → экономическая категория → профессия → предоставляющее её здание |
| `capacity_affinity` | Собственный бонус лимита → использующий лимит объект → связанный корпус → требуемая технология |
| `standard_empire` | Исключение кандидатов, противоречащих известным фактам профиля |
| `highest_tier` | Наибольший игровой `tier` среди оставшихся кандидатов |

Точные границы свидетельств сохраняются по связанным документам [общего прогона](frontend/CHAIN_RULES_FULL_REVIEW_RU.md), [прямых улучшений](frontend/CHAIN_DIRECT_UPGRADES_RU.md), [условий](frontend/CHAIN_AVAILABILITY_RU.md), [функциональных групп](frontend/CHAIN_FUNCTIONAL_GROUPS_RU.md), [прямых связей](frontend/CHAIN_DIRECT_RELATIONS_RU.md), [косвенного родства](frontend/CHAIN_INDIRECT_AFFINITY_RU.md), [производства](frontend/CHAIN_PRODUCTION_AFFINITY_RU.md), [лимитов](frontend/CHAIN_CAPACITY_AFFINITY_RU.md) и [вооружения](frontend/CHAIN_WEAPONRY_RU.md). Не расширять глубину поиска или смысл соответствий неявно при переносе.

Движок вызывает обработчик по известному ID. Каждый обработчик получает текущий набор кандидатов и возвращает совпавшее подмножество, ссылки на свидетельства и состояние применимости. Новое соответствие поддержанного типа добавляется конфигом; принципиально новый тип вычисления — отдельным обработчиком и описанием параметров в генераторе схем. Неизвестный ID, дубли, несуществующие ссылки блоков или неверные параметры — ошибки конфигурации, в том числе у выключенных правил.

Количество свидетельств не является голосованием. Условные бонусы и связи сохраняют условия и область, а не объявляются безусловными. Если применимость критерия неизвестна для части текущих кандидатов и это мешает корректному сравнению, критерий не сокращает набор и оставляет диагностику. Исключение — определённая семантика `standard_empire`: удалять только подтверждённо несовместимых; неизвестных сохранять. Это анализ используемых полей, а не валидация всех игровых команд.

## 5. Комбинация и выбранные варианты

Файл комбинации имеет `format = sttv.technology_tree_combination`, `format_version = 1`, поля `id`, `mode`, `profile`, `variants`. `id` соответствует `^[a-z][a-z0-9_]*$`; начальные значения — `reference_default` и `reference`. В этом этапе поддерживается только режим `reference`.

`profile` ссылается на файл фактов. Поставляемый профиль: некочевая империя без гештальт-сознания, биологические основатели, обычные корабли. Другие этики, происхождение, DLC и пути развития остаются неизвестными. Использовать согласованную трёхзначную трактовку условий и области `country`/`founder_species`; незнакомые предикаты и переходы областей не превращаются в ложь.

Файл профиля имеет `format = sttv.technology_tree_profile`, `format_version = 1`, `id` и `facts`. Структура фактов — область → предикат → строковое значение аргумента → булев результат. Отсутствующий факт означает неизвестность. Начальные факты переносятся из проверенного профиля исследовательского прогона; исторические списки критериев и ручных пар из исследовательских материалов не переносятся.

`variants` — отображение базового ID технологии в `base` или `swap:N`, где N начинается с 1 и соответствует порядку `technology_swap`, как в действующем фронтенде. Пропуск технологии означает `base`; перед хешированием и сохранением строится полный нормализованный выбор для всех технологий. Несуществующая технология или вариант — ошибка запроса. Ручной выбор не требует выполнения игрового `trigger` варианта и не запускает автоматический выбор по состоянию империи.

Идентификатор комбинации — именованное место хранения результата. Изменение её параметров заменяет этот результат после успешного расчёта; другая комбинация использует другой ID. Сохраняются только запрошенные комбинации. Одинаковое название режима без совпадения входов и параметров не разрешает переиспользование.

## 6. Представление технологии для анализа

Технологии выбираются из целевых верхнеуровневых определений с игровым `tier`; определения категорий и уровней исследований не становятся технологиями. ID берётся из ключа определения. Дубли ID технологий запрещены. Ссылки на связанные объекты адресуются видом БД и ID, а происхождение — видом БД и JSON Pointer. Неоднозначное разрешение используемой ссылки — ошибка, без выбора первого совпадения.

Базовый ID, игровой `tier`, `prerequisites` и базовый `potential` сохраняются при выборе варианта. Указанные в варианте `area` и `category` заменяют соответствующие значения; отсутствующие наследуются. `technology_swap.trigger` сохраняется как условие представления и не присоединяется автоматически к базовому `potential`.

Для критериев собственных эффектов учитывать `inherit_effects`: `yes` разрешает учитывать эффекты основы вместе с эффектами варианта; `no` исключает эффекты основы из этого сравнения. Игровые требования связанных объектов продолжают ссылаться на базовый ID. Не переносить наследование эффектов на все поля технологии автоматически.

**Согласованная политика для отсутствующего `inherit_effects`:** в исследованной проекции оно отсутствует у 23 из 206 вариантов. При отсутствии подтверждённого значения по умолчанию наследование считать неизвестным; зависящий от него критерий не сужает кандидатов и пишет `variant_effects_unknown`. Аналогично не угадывать итоговое числовое значение конфликтующих записей одного модификатора. Критерии ID, области, категории и другие независимые критерии продолжают работать. Значения по умолчанию не выводятся из названия технологии. Политика утверждена вместе с ТЗ.

Все исходные AND/OR-требования сохраняются. Множество кандидатов — объединение встречающихся ID; обязательные требования: ID для листа, объединение для AND/неявного списка, пересечение для OR. Пустой список требований означает корень. Несуществующий ID, пустой OR или неподдерживаемая конструкция — диагностируемая ошибка; ранее согласованная остановка на NOT/NAND/NOR в технологических требованиях сохраняется. Логические условия `potential` обрабатываются отдельно.

## 7. Расчёт родителей и детей

До отбора доступны все объекты по ID, их эффективные представления и пустые списки детей рассчитываемой комбинации. Обработка идёт детерминированно по базовым ID:

1. Нет кандидатов — `root`; один кандидат — `resolved` без запуска критериев.
2. Для нескольких кандидатов применять включённые критерии к текущему набору. Непустое совпадение заменяет набор; пустое пропускается; ранее исключённые кандидаты не возвращаются.
3. Как только остаётся один кандидат, прекратить отбор. После исчерпания критериев несколько кандидатов означают `ambiguous`, без назначения родителя.
4. Сразу после выбора записать `parent_tech` и добавить ID технологии в `children` родителя, исключая дубли. Последующая обработка родителя не обнуляет уже накопленных детей.

Отдельного прохода для построения обратных связей нет. Финальные проверки и каноническое упорядочивание списков допустимы. В JSON `children` упорядочены по ID для воспроизводимости; это не алфавитный порядок карточек и не правило размещения.

Выбранный родитель всегда входит в исходные непосредственные требования. Все остальные игровые связи сохраняются. Родитель из другой области или более высокого игрового уровня допустим; эта особенность отражается в отчёте, а не исправляется подменой уровня. Проверить взаимность связей и отсутствие циклов. Цикл или нарушение взаимности — ошибка с отменой публикации; неоднозначность — допустимый результат с предупреждением.

## 8. Результат у объекта

В узле базовой технологии использовать `enrichments.technology_tree[combination_id]`. Вариант не создаёт новую технологию или отдельный узел дерева. Запись содержит только:

| Поле | Значение |
| --- | --- |
| `parent_tech` | ID непосредственного родителя либо `null` |
| `children` | Уникальные ID технологий, выбравших этот объект родителем |
| `status` | `root`, `resolved` или `ambiguous` |

Для `root` и `ambiguous` родитель равен `null`; отсутствие требований и неразрешённый выбор не смешиваются. У любой из этих технологий могут быть дети. Трассы и доказательства остаются в отчёте; параметры комбинации не дублируются у каждой технологии. `location` пока отсутствует.

Иллюстрация фрагмента узла без его существующей локализации:

```json
{
  "enrichments": {
    "technology_tree": {
      "reference_default": {
        "parent_tech": "tech_a",
        "children": ["tech_c"],
        "status": "resolved"
      }
    }
  }
}
```

## 9. Общие сведения о комбинации

В корне БД технологий добавить необязательный `technology_tree` с `format_version = 1` и словарём `combinations`. У каждой комбинации хранить:

- `mode`, полный нормализованный `parameters` с фактами профиля и выбором вариантов;
- `source_set_id`, перечень `inputs` с видом БД, алгоритмом и хешем, `input_revision`;
- полный применённый `rules_snapshot`, `rules_revision`, `parameters_revision`, `implementation_revision`;
- `calculation_revision`, `result_revision`.

JSON Pointer исходных объектов не меняется. Контейнер комбинаций и записи у узлов публикуются вместе в одном файле. Параметры и ревизии не включают время выполнения, абсолютные пути или случайные идентификаторы. Время и рабочие пути относятся к отчёту. Формат БД остаётся 6: это необязательное обогащение версии 1, не замена AST. Остальные виды БД не получают записей дерева технологий.

Такая принадлежность результата объекту соответствует будущему правилу «одна технология, здание и т. п. — один документ MongoDB». Ссылки содержат ID, без вложенных копий объектов. Новый слой хранилища или подготовка MongoDB сейчас не требуются.

## 10. Идентичность и актуальность

`dataset.set_id` сохраняется как идентичность исходного опубликованного набора. Он не пересчитывается по обогащённым файлам. Фактически использованные входы и результат имеют отдельные ревизии; одного равенства заголовков для повторного использования недостаточно.

Для БД технологий вычислять исходный хеш по действующему алгоритму `sttv.document_hashes.v1`, исключив только корневой служебный `technology_tree` и `enrichments.technology_tree` узлов. Созданный только этим обогащением пустой контейнер `enrichments` также исключается. Исходное игровое поле с таким именем не удаляется: исключаются структурные служебные пути, а не строки скрипта. Локализация, исходный AST, происхождение и порядок документов остаются во входном хеше.

Для остальных 14 БД использовать потоковый SHA-256 фактических байтов, алгоритм `sha256.file.v1`. `input_revision` — канонический SHA-256 отсортированного по виду перечня этих входов и `source_set_id`. Форматирование другого входного файла может вызвать консервативный пересчёт; изменение только обогащения дерева не должно менять входную ревизию.

`rules_revision` хеширует полную раскрытую конфигурацию правил и соответствий. `parameters_revision` хеширует режим, факты профиля и полный выбор вариантов. `implementation_revision` — явная версия семантики вычислений в коде, изменяемая при изменении результатов обработчиков или извлечения свидетельств. Пути файлов конфигурации не заменяют хеш их содержимого.

`calculation_revision` — хеш перечисленных ревизий входа, правил, параметров и реализации. `result_revision` — хеш этой ревизии и отсортированного отображения ID технологий в их результаты. Канонический JSON использует действующие настройки сортировки ключей, UTF-8, компактные разделители и запрет нечисловых значений NaN/Infinity.

Совпадение `calculation_revision` вместе с успешной проверкой результата разрешает повторное использование. Иначе операция рассчитывает новый результат выбранной комбинации. Другие комбинации сохраняются; их актуальность определяется собственными ревизиями. При смене исходных данных прежняя комбинация не объявляется актуальной только потому, что её запись сохранилась.

Сборщик продолжает создавать исходный набор без автоматического расчёта связей. Исторический отчёт сборки описывает исходную публикацию; новый отчёт фиксирует фактический хеш файла до и после обогащения. Не перезаписывать исторический отчёт утверждением, будто файл не изменился.

## 11. Чтение и сохранение

Читать текущие JSON напрямую. БД событий нельзя загружать целиком через `json.load`: она превышает 9 ГБ. Извлекать необходимые объекты последовательно, освобождать ненужные AST и сохранять компактные индексы свидетельств. Для вооружения прослеживать только согласованные явные маршруты действия и события. Обработчик чтения JSON должен корректно учитывать строки и экранирование; произвольное текстовое совпадение ID не доказывает связь.

При неизменной комбинации достаточно проверки входных хешей и сохранённого результата; повторное извлечение всех функциональных свидетельств не требуется. При расчёте индексы подготавливаются один раз для операции и переиспользуются всеми критериями. Новый постоянный кэш проекций и новый параллелизм не входят в этап.

Подготавливать новый результат в памяти/рабочем каталоге, сохраняя действующую БД до завершения проверок. Публиковать только изменённую БД технологий через временный файл рядом с назначением и атомарную замену. JSON остаётся форматированным: отступ 2 пробела, UTF-8, реальные переводы строк.

При замене комбинации удалять её старые записи, включая записи у объектов, которые перестали быть целями, и прикреплять полный новый результат. Другие комбинации и локализация сохраняются. В служебной метадате и объектах не должно остаться смеси старой и новой версии одной комбинации.

Перед заменой убедиться, что входные файлы и конфиги не изменились относительно снимка операции. Не допускать двух одновременных публикаций одной БД: использовать блокировку назначения и проверку актуальности снимка. Ошибка подготовки, чтения, проверки или сохранения оставляет старую БД; временные файлы убираются. Проверки и хеширование объединять с чтением, где возможно; отдельные повторные проходы отражать в метриках.

## 12. Интерфейс операции

Предоставить функцию `enrich_technology_tree(variables_path=None, config_path=None, combination_path=None, *, recalculate=False)` из `sttv.enrichment.technology_tree`. По умолчанию используются глобальные переменные продукта, основной конфиг операции и указанная в нём комбинация. Явный `combination_path` заменяет только выбор запроса комбинации.

`recalculate=False` разрешает переиспользование актуального результата, иначе выполняется расчёт. `recalculate=True` принудительно пересчитывает выбранную комбинацию. Даже принудительный пересчёт не требует перезаписи, если итоговый канонический результат полностью совпал и проверен.

Функция возвращает отчёт, а не полный AST. CLI `python -m sttv.enrichment.technology_tree` поддерживает `--variables`, `--config`, `--combination`, `--recalculate`; интерактивных вопросов нет. Код завершения 0 означает успешный результат, включая предупреждения; ошибка — ненулевой код.

Транспорт вызова не входит в функцию. HTTP API, сопоставление выбранных браузером файлов с серверным набором, кнопка пересчёта и обновление интерфейса будут отдельным этапом.

## 13. Диагностика и отчёт

Отчёт имеет `format = sttv.technology_tree_report`, `format_version = 1`, `status` (`success`, `success_with_warnings`, `failed`), `action` (`reused`, `computed` или `null` при незавершённом расчёте), `database_written`, рабочие пути, снимок комбинации и правил, входные и выходные ревизии, количества и время этапов.

Для каждой технологии сохранять исходных кандидатов, обязательные ID, выбранный вариант, состояние, родителя и трассу реально пройденных критериев: до, совпадения, после, причина пропуска, ссылки на свидетельства. Не добавлять фиктивные шаги после нахождения единственного кандидата. Неизвестное наследование эффектов, неоднозначность и условность свидетельств должны быть различимы.

Для неоднозначностей применять [согласованный состав лога](frontend/CHAIN_AMBIGUITIES_RU.md): полный контекст расчёта, оставшиеся кандидаты, настройки и источники. Поскольку интерфейс ещё не подключён, размеры окна и прокрутку не выдумывать; отметить их как непереданные. Результат с неоднозначностью допускается к публикации как `success_with_warnings`.

Ошибки включают неверные настройки/варианты, неполный набор, конфликт ID или разрешения ссылки, отсутствующий технологический пререквизит, неподдерживаемые требования, цикл, нарушение взаимности, изменение входа и сбой записи. При ошибке публикации нельзя сообщать `database_written = true`. Ошибка записи отчёта после успешной замены БД фиксируется отдельно, с сохранением фактического признака уже выполненной публикации.

## 14. Модули и схемы

Добавить `src/backend/sttv/enrichment/technology_tree/` с разделением настроек, чтения/индексов, представлений, свидетельств, обработчиков критериев, отбора, прикрепления, ревизий, отчёта и координации. Повторяющиеся части используют общие хелперы. Ориентир — до 200 строк; файл более 300 строк требует разделения, кроме обоснованного неделимого блока.

Добавить генераторы схем `technology_tree.schema.json`, `technology_tree_rules.schema.json`, `technology_tree_combination.schema.json`, `technology_tree_profile.schema.json`, `technology_tree_report.schema.json`. Расширить генератор `database.schema.json` необязательной метадатой и объектным обогащением, а структурные проверки — взаимностью связей и ревизиями. Схемы не редактируются вручную.

Для входных готовых БД проверять формат набора и необходимые анализу структуры; повторная полная валидация всех AST по JSON Schema и повторный разбор игровых файлов не нужны. Строго проверять новые конфиги, новое обогащение и его ссылки. Сохранять оптимизации этапов 13–15 и единый источник правил структурной проверки. Не добавлять фронтенд-зависимости в вычисляющий модуль.

## 15. Проверки и приёмка

Синтетические проверки:

1. Корень, единственный и несколько родителей; AND/OR и обязательные пересечения; пропуск пустого результата, остановка при одном кандидате, выключенные и переставленные правила.
2. Родитель обрабатывается позже ребёнка; несколько детей; отсутствие дублей; обратный порядок обхода даёт те же связи; структурный порядок списков не зависит от RU/EN.
3. Неоднозначность с логом, отсутствующий пререквизит, конфликт ID, цикл, неподдерживаемые требования и неизвестное правило. Ошибки не портят прежний результат.
4. Смена области/категории варианта у ребёнка и кандидата, сохранение базовых ID и требований; `inherit_effects` со значениями yes/no/отсутствует; условные и неизвестные свидетельства.
5. Изменение только обогащения не меняет входную ревизию; изменения AST, другого входного файла, правил, профиля, вариантов или реализации делают прежний расчёт неприменимым. Повреждённые результаты не переиспользуются.
6. Повторное выполнение, принудительный пересчёт, сохранение второй комбинации и локализации, удаление старых детей при смене родителя, отсутствие частично обновлённого результата при ошибке и конкурирующих вызовах.
7. Потоковый разбор больших JSON, скобки и экранирование в строках; неизменность остальных 14 файлов; генерация схем и относящиеся к изменению существующие тесты бэкенда.

Реальные проверки выполнить с рабочей копией БД технологий в `WORK_DIR/stage16`, не заменяя эталон до проверки. Отдельный конфиг приёмки указывает на эту копию и остальные 14 исходных БД только для чтения; копировать все большие файлы необязательно. Не запускать генератор игры заново.

Для базовой комбинации на исследованном наборе ожидать **679 технологий: 178 корней, 501 выбранный родитель (412 с одним исходным требованием и 89 с несколькими), 0 неоднозначностей, 0 циклов**. Сопоставить все решения и 12 контрольных примеров с [эталонным отчётом](../tests/fixtures/technology_tree/report.json). Проверка читает эталон после расчёта; модуль отбора не имеет доступа к ожидаемым парам. Несовпадения исследуются, а не маскируются ручной правкой.

На один раз подготовленных индексах проверить все 206 вариантов по одному и несколько сочетаний, включая семь вариантов с изменением области/категории. Для вариантов проверяются инварианты, диагностика неизвестностей и воспроизводимость; нулевая неоднозначность для них заранее не обещается. Отдельно проверить сохранение и повторную загрузку как минимум базовой и одной изменённой комбинации.

Зафиксировать время чтения/хеширования, подготовки индексов, критериев, проверки, записи и повторного использования, а также объём прочитанных и записанных данных. Конкретный коэффициент ускорения заранее не задаётся. Тесты не вычисляют игровую доступность империи и не заменяют проверку поведения игры.
