## 1. Статус и цель

**ТЗ утверждено пользователем 2026-11-19 и реализовано.** Фактические проверки, запуск и ограничения — в [руководстве этапа](BACKEND_STAGE_17_RU.md).

Сохранять результат обработки каждого исходного файла отдельно; находить объекты через манифест без сканирования всех больших БД. Использовать файловый параллелизм при сборке и подготовке свидетельств. Новый формат не меняет игровые данные и критерии выбора родителя.

Основа — [этап 15](TZ_BACKEND_STAGE_15_RU.md) и [этап 16](TZ_BACKEND_STAGE_16_RU.md). При первом расчёте этапа 16 подготовка индексов заняла около 262 из 279 секунд, отбор — около 0,004 секунды: это ориентир существующего узкого места, а не обещание коэффициента ускорения. Совместная часть интерфейса описана в [ТЗ фронтенда, этап 4](frontend/TZ_FRONTEND_STAGE_4_RU.md).

## 2. Границы этапа

Включены новый формат хранения всех 15 видов БД, манифест, индекс объектов, общий механизм чтения, адаптация сборки с локализацией и обогащения дерева, безопасная публикация, аудит, схемы и проверки. Фронтенд открывает каталог и читает необходимые документы по отдельному ТЗ.

Не включены MongoDB, сетка и `location`, изменение критериев/профилей/семантики вариантов, HTTP API, автоматический запуск сборки, постоянный кэш функциональных проекций и инкрементальный повторный парсинг изменённых игровых исходников. Последний требует отдельного учёта зависимостей от вставок, статических переменных и локализации. Перезапись только изменённых документов при обогащении входит в этот этап.

Продукт переходит на новый формат без совместимого чтения прежних 15 монолитных JSON и без обязательного экспорта в них. Старые наборы остаются неизменными как эталон проверки; преобразователь старого формата не является отдельной продуктовой функцией. Поставка библиотек вставок и их явные режимы сохраняются.

## 3. Конфигурация и размещение

Ручной `config/storage.json` задаёт адрес набора относительно `WORK_DIR`, имя манифеста, подкаталог документов, каталог временных операций, ссылку на `config/parallel.json` и путь отчёта аудита. Настройки источников и определения видов объектов остаются в `config/backend.json` и `config/datasets.json`. Список фактических файлов и объектов в конфиг вручную не вписывается.

Предлагаемые значения: каталог `database_set`, манифест `manifest.json`, документы `documents`, временные операции `staging/storage`, отчёт `reports/storage_audit.json`. Число рабочих процессов берётся из общего конфига: по умолчанию 10. Конфиг обогащения получает ссылку на конфиг хранения вместо поиска 15 выходных файлов в конфиге сборщика.

```text
data/database_set/
  manifest.json
  documents/
    technologies/<document_id>/<file_hash>.json
    components/<document_id>/<file_hash>.json
    events/<document_id>/<file_hash>.json
    ...
```

В манифесте хранятся относительные пути от его каталога с разделителем `/`. Абсолютные пути, URL, `..`, выход через файловые ссылки за корень набора и конфликтующие после нормализации пути запрещены. Адреса игры не нужны для чтения готового набора. JSON остаётся UTF-8 с отступом 2 пробела, переносами строк и читаемым Unicode.

## 4. Документ и ссылки

Один выбранный игровой файл даёт один постоянный JSON, который может содержать несколько объектов. Формат `sttv.parse_document`, версия 1: поля `format`, `format_version`, `database`, `document_id`, `source`, `items`, `metadata`. Последние три сохраняют документ текущего парсера: все исходные записи, порядок, раскрытое дерево, происхождение и историю вставок. Поля игровых объектов не ограничиваются новым списком.

`document_id` — SHA-256 канонической тройки вида БД, корня источника и относительного пути источника. Для идентичности пути использовать `/` и регистронезависимое сравнение Windows; исходное написание сохранить в `source.file`. Два входа с одной нормализованной тройкой — ошибка. ID не зависит от номера работника, порядка завершения задач, содержимого или местоположения рабочего каталога.

Ссылка на узел принимает вид `NodeRef = {database, document_id, pointer}`, где `pointer` — JSON Pointer относительно документа, например `/items/7`. Ссылка по игровому ID — `ObjectRef = {database, id}`. Идентификаторы игры сохраняются с исходным регистром. Позиционная ссылка разрешается только в контексте выбранной ревизии набора; при редактировании самого исходника номер записи может измениться.

Убрать зависимость сохраняемых ссылок от глобального `/documents/N`: адаптировать ссылки наследования локализации, диагностические ссылки, ссылки свидетельств и фронтенда. Менять только служебные структурные поля, не похожий текст внутри игрового AST. Локальные адреса истории вставок `/items/...` и связи `expansion_id` сохраняются. Новый формат не требует перенумерации существующих вызовов вставок.

Условные варианты технологий остаются вложенными в основную технологию. Поля `enrichments.localization` и `enrichments.technology_tree[combination_id]` остаются при узлах. Общая метадата комбинаций перемещается из корня монолитной БД в `technology_tree` манифеста; отдельные копии этой метадаты в каждом документе не создаются.

## 5. Манифест и индекс объектов

Манифест формируется из реально подготовленных и проверенных результатов. В памяти его можно читать целиком; полного AST и текстов локализации в нём нет. Первый формат использует один манифест без отдельных индексных файлов для каждого вида.

| Поле | Содержание |
| --- | --- |
| `format`, `format_version` | `sttv.database_manifest`, версия 1 |
| `set_id` | Ревизия исходного содержимого набора без обогащения дерева |
| `snapshot_revision` | Ревизия текущего опубликованного состояния, включая обогащения |
| `registry_revision` | Хеш правил идентификации объектов из реестра видов |
| `datasets` | Все 15 видов; для каждого `source_revision`, `documents` и `objects` |
| `technology_tree` | Необязательная общая метадата именованных комбинаций этапа 16 |

Описатель документа содержит `document_id`, `source`, `path`, `byte_size`, `file_hash`, `source_hash`, `item_count`. Строка индекса объекта содержит `id` (строка либо `null`), `type`, `document_id`, `pointer`. Вид БД определяется содержащим разделом `datasets`. Все ссылки указывают на объявленные документы. Индекс строится по расширенному дереву, не по поиску текста в исходнике.

Правила выбора корневых объектов и чтения ID берутся из существующего `config/datasets.json`. Служебные записи, которые не являются индексируемыми объектами, сохраняются в документе. Каталоги внутри `common/technology` не превращаются автоматически в отображаемые технологии: действующие правила выбора целей сохраняются.

- `identity = key` и `field`: повтор одного ID внутри вида — ошибка с обеими ссылками.
- `identity = fragments`: один ID, например `on_actions`, разрешается в упорядоченный список всех фрагментов; выбор только первого запрещён.
- `identity = anonymous`: у `terraform_link` сохраняется `id = null`; идентичность задаётся `NodeRef`, а не искусственным игровым ID.
- Совпадение ID в разных видах допустимо. `technology_swap` не становится отдельным корневым объектом индекса.

Документы упорядочиваются по нормализованному пути источника, объекты — по документу и позиции в нём. Порядок выполнения процессов не влияет на опубликованный порядок. Поиск ID строит компактное отображение из манифеста без чтения файлов данных.

## 6. Идентичность и ревизии

`file_hash` — SHA-256 точных записанных байтов; он вычисляется при записи и определяет имя версии файла. Сам файл своего хеша не содержит. Изменение форматирования меняет этот хеш.

`source_hash` — канонический хеш содержимого документа с исключением только служебного `enrichments.technology_tree` и контейнера `enrichments`, если тот стал пустым именно после исключения. AST, порядок записей, локализация и история остаются. Служебный конверт формата и ID документа включаются по фиксированному алгоритму `sttv.document_source.v1`. Другие обогащения автоматически не исключаются.

`source_revision` вида — хеш упорядоченных пар `document_id`/`source_hash`. `set_id` — хеш версии алгоритма, `registry_revision` и упорядоченных ревизий всех видов. Обогащение дерева не меняет `set_id`; изменение локализации или игровых данных меняет. `snapshot_revision` хеширует весь манифест, кроме самого `snapshot_revision`; включает пути, хеши файлов, индекс и метадату комбинаций. Временные метрики и абсолютные пути в манифест не входят.

Канонизация использует существующие правила Python: сортировка ключей, UTF-8, компактные разделители, запрет NaN/Infinity. Браузер сверяет точные байтовые хеши документов; ему не требуется воспроизводить все семантические хеши Python.

Ревизии расчёта этапа 16 переходят на ревизии исходного содержимого из манифеста и фактические конфиги правил/параметров/реализации. Для первого перехода учитывать все 15 `source_revision` консервативно: добавление нового свидетельства должно инвалидировать результат, даже если старый расчёт его не читал. Не сужать актуальность до хешей только найденных объектов. Обогащение не должно инвалидировать само себя.

## 7. Подготовка набора

Сохраняются параллельные задачи по файлам внутри одного вида БД и последовательность видов из этапа 15. Работник разбирает источник, раскрывает вставки и переменные, выполняет локализацию RU/EN, структурную проверку и запись документа. В этом же процессе он собирает строки индекса и хеши. Координатор получает небольшие описатели и диагностические данные, а не полные деревья.

Координатор проверяет полноту задач, идентичности и ссылки индекса, затем готовит манифест. Обязательные стадии объединения документов в монолит и дописывания заголовка через повторное копирование всего массива исключаются. Проверки этапа 13 не заменяются повторным полным обходом AST по JSON Schema.

Полная сборка сохраняет явные `--rebuild-libraries` и `--reuse-libraries`; открытие готового набора не вызывает ни один из них. Постоянные документы не должны удаляться обработчиком очистки временных фрагментов. Первичный манифест не содержит вычисленных комбинаций дерева: их добавляет отдельная операция.

## 8. Чтение и проверка

Общий читатель открывает манифест один раз, проверяет его контракт, виды, ссылки, уникальность адресов и наличие объявленных файлов. Далее доступны перечисление объектов, разрешение `ObjectRef`, чтение одного документа и проход выбранного вида. Перечисление индекса и проверка наличия файлов не читают их содержимое.

**Согласованный режим по умолчанию — проверка при чтении.** Каждый используемый файл проверяется по размеру и SHA-256 в том же потоке, из которого извлекаются данные. Дополнительно сверяются конверт документа, источник, ID и индексируемые корневые записи. До завершения проверки его результаты не используются для публикации или показа готового поля. В пределах операции повторный доступ использует уже проверенную компактную проекцию; полный AST без необходимости не удерживается.

При запросе события по ID читатель открывает только содержащий его документ. JSON Pointer не является байтовым смещением: документ всё равно читается потоково целиком для хеша и поиска узла. Большой документ не превращается в одну гигантскую строку; ненужные узлы и историю можно не удерживать в проекции. Другие документы событий не открываются.

Хеширование защищает от несогласованной или повреждённой записи; цифровые подписи и защита от намеренной замены всего набора не вводятся. Размер и дата изменения не заменяют хеш. Не прочитанные файлы имеют статус `not_checked`, даже если манифест корректен. Режим доверяет опубликованному каталогу для неиспользованных файлов и не обещает обнаружить их внешнее редактирование.

Отдельный аудит проходит все объявленные файлы: проверяет байтовые хеши, конверты и соответствие индекса объектам, публикует отчёт о полном охвате. Он не пересобирает БД и не запускает интерпретацию игровых команд. В успешной собственной сборке охват уже обеспечивается проверкой каждого нового документа; последующее открытие его не повторяет для неиспользуемых файлов.

## 9. Обогащение дерева

Операция этапа 16 читает технологии и общую метадату через читатель набора. Для нового расчёта компактные свидетельства остальных видов извлекаются по документам в ограниченном пуле из общего конфига. Результаты соединяются детерминированно; полный набор AST не передаётся между процессами. События извлекаются только по согласованным маршрутам и ID через индекс манифеста.

После подготовки общих индексов выбор родителей выполняется действующим общим алгоритмом. Не рассчитывать независимые деревья по файлам: родитель и ребёнок могут находиться в разных документах. Сохраняются все 13 критериев, остановка на одном кандидате, пропуск пустого результата, комбинации и вариантность.

При переиспользовании сверяются исходные ревизии манифеста, конфиги и сохранённый результат; читаются и проверяются содержащие технологии документы, но функциональные индексы не строятся. Отчёт прямо указывает, что остальные документы в этом запуске не хешировались. Принудительный пересчёт сохраняется.

Новый результат проверяется на взаимность `parent_tech`/`children`, полноту, циклы и соответствие исходным пререквизитам. Обновляются только документы с фактически изменёнными записями, включая удаление устаревших записей выбранной комбинации. Остальные комбинации и локализация сохраняются. Манифест публикует все изменения комбинации вместе; файл с неизменным содержимым не переписывается.

## 10. Публикация изменений

Опубликованные версии документов неизменяемы. Запись готовится во временном каталоге той же файловой системы, проверяется и переносится на окончательный адрес с `file_hash`. Если адрес уже существует, его содержимое проверяется до переиспользования. Файлы не получают новый общий `set_id` в собственном конверте: он относится к манифесту.

Единственная точка переключения набора — атомарная замена `manifest.json` после подготовки всех требуемых документов. Блокировка действует на корень набора для всех записывающих операций. Перед заменой проверяются исходная ревизия манифеста, снимок прочитанных входов и конфигов; изменение опубликованного снимка завершает операцию с конфликтом, без смешивания результатов.

Ошибка или отмена до замены оставляет прежний манифест рабочим. Ошибка записи отчёта после замены не отменяет факта публикации и отражается отдельно. Читатель фиксирует одну ревизию манифеста на операцию; старые версии файлов сохраняются, чтобы уже открытый снимок продолжал разрешать ссылки.

Автоматическое удаление старых опубликованных версий и сборка мусора не входят в этап. Очищаются только временные файлы, принадлежащие текущей операции, после проверки границ пути. Новые файлы, оставшиеся после прерывания до публикации, не считаются частью набора без ссылки из манифеста; их наличие отражается отдельно от ошибки данных. Архивирование копии манифеста для каждого изменения не требуется.

## 11. Модули и интерфейсы

Добавить `sttv.storage` с небольшими модулями конфигурации, манифеста, адресации, чтения, проверки, ревизий, публикации и отчёта. Повторно использовать существующие структурные проверки и потоковый разбор. Реализации выбора игровых объектов в сборке и обогащении должны опираться на один реестр, а не расходящиеся списки ID.

Предлагаемый интерфейс: `open_set(manifest_path)` возвращает читатель фиксированного снимка с `iter_objects(kind)`, `resolve_object(kind, id)`, `read_document(kind, document_id)` и `iter_documents(kind)`. Метод `resolve_object` возвращает список ссылок для фрагментного вида; единичный запрос по такому виду не скрывает остальные фрагменты. Потоковые методы для проекций должны позволять не материализовать целый документ.

Существующий CLI сборки использует конфиг хранения. CLI обогащения сохраняет `--config`, `--combination`, `--recalculate`; вход задаётся манифестом через конфиг. Добавить `python -m sttv.storage audit --manifest <path> --report <path>`. Возвращаются отчёты; интерактивные вопросы и транспорт HTTP не вводятся.

Добавить генераторы `storage.schema.json`, `database_manifest.schema.json`, `database_document.schema.json`, `storage_report.schema.json`; адаптировать связанные схемы конфигурации и обогащений. Контракт AST и ссылки обслуживаются общими определениями. Старый корневой формат БД не сохраняется как поддерживаемый путь выполнения. Обновить относящиеся к нему тесты, не стирая исторические документы. Ориентир размера файлов кода — до 200 строк; более 300 требует разделения.

## 12. Отчёт и измерения

Фиксировать исходную/итоговую ревизии, выбранные виды/документы, число объявленных, прочитанных, проверенных, неизменённых и записанных файлов; отдельно — не проверенные документы. Указывать байты чтения для данных и хеширования, запись, повторные проходы, время индекса, критериев, проверок, публикации, аудит и пик памяти процессов. Один общий проход чтения с хешированием не суммируется как два физических чтения.

Диагностика содержит вид, `document_id`, исходный путь, путь JSON, ожидаемый/фактический хеш при расхождении, ссылку на объект и ревизию снимка. Неоднозначности выбора родителей сохраняют контекст этапа 16. Ошибка отсутствующего или повреждённого файла не превращается в пустой каталог.

## 13. Проверки и приёмка

1. Построение манифеста: все 15 видов, несколько объектов в файле, вложенные варианты, константы вне индекса, анонимные переходы, фрагменты `on_actions`, конфликт ID и регистра пути. Смена порядка задач не меняет содержательные результаты.
2. Разрешение ссылок после переноса каталога; локальные адреса, история и наследование локализации. Выход за корень и смешивание документов разных источников обнаруживаются.
3. Проверка при чтении: повреждение, усечение, изменение размера, неверный индекс; неиспользованные документы не открываются. Полный аудит обнаруживает повреждение неиспользованного документа. Файлы с одинаковым размером и датой, но разными байтами, не считаются одинаковыми при чтении.
4. Публикация: сбой до/после записи документов и до замены манифеста, отмена, два писателя, читатель со старым снимком, ошибка отчёта после публикации. Старый набор остаётся читаемым до переключения; частичная комбинация не видна.
5. Обогащение: неизменённые документы не записываются, собственное обогащение не меняет входную ревизию, новое свидетельство или изменённый конфиг инвалидирует результат, изменения локализации учитываются, другие комбинации сохраняются.
6. Параллельность: результаты при одном и десяти процессах совпадают по документам, индексу и решениям; большой документ читается потоково. Сохраняются проверки библиотек и актуальности исходников.

Реальную сборку выполнять в отдельном `WORK_DIR/stage17`, сохраняя текущий эталон. Для всех 15 видов сравнить документы с существующим набором после строго определённой нормализации нового конверта и служебных ссылок; AST, порядок, происхождение и локализация должны совпасть.
