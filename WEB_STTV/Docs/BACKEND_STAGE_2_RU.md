## Результат этапа

После этого этапа реализован [настраиваемый парсер](BACKEND_STAGE_3_RU.md): конфиги синтаксиса, новые узлы и явное преобразование в текущую модель. Описанные здесь профили сохраняют свою отдельную роль.

Утверждённое [ТЗ второго этапа](TZ_BACKEND_STAGE_2_RU.md) реализовано. Бэкэнд разделён на пакеты, генератор схем находится в постоянном коде. Сборщик использует явно выбранный JSON-профиль; отдельный анализатор формирует наблюдения и рекомендации.

Модель БД остаётся в формате 1: технологии, варианты, категории, уровни, локальные переменные и названия RU/EN. На неизменных источниках БД побайтно совпадает с результатом первого этапа. Подготовка Python и базовый запуск описаны в [руководстве сборщика](BACKEND_STAGE_1_RU.md).

## Структура кода

| Пакет в `src/backend/sttv/` | Ответственность |
| --- | --- |
| `common/` | Ошибки, JSON, пути, схемы, диагностика и безопасная запись |
| `sources/` | Настройки источников, переменные, выбор и чтение файлов |
| `script/` | Синтаксический разбор, переменные, проверка команд и значений |
| `technologies/` | Единое описание полей, сбор и преобразование определений |
| `localization/` | Названия по ключам и приоритетам |
| `database/` | Проверка готовой БД, внутренних ссылок и публикация |
| `schema_generation/` | Декларации и генерация схем приложения |
| `rules/` | Загрузка, проверка, разворачивание и сохранение профилей |
| `analysis/` | Дополнительные источники, наблюдения и рекомендации |

`builder.py` координирует сборку; `src/backend/main.py` остаётся входом командной строки. Тесты распределены по подсистемам в `src/backend/tests/`, общая фикстура — `support.py`.

Единственное описание полей объектов находится в [technologies/contracts.py](../src/backend/sttv/technologies/contracts.py): контекст, имя, тип обработки и кратность. Его используют преобразователь и генератор схемы БД. Новое поле технологии требует изменения контракта и поддерживающего кода по согласованному ТЗ.

## Схемы приложения

| Схема в `schemas/` | Что проверяет |
| --- | --- |
| `database.schema.json` | БД формата 1 |
| `backend.schema.json` | Настройки сборки |
| `report.schema.json` | Отчёт сборки |
| `profile.schema.json` | Входной профиль правил |
| `registry.schema.json` | Развёрнутый реестр |
| `analysis.schema.json` | Настройки анализа |
| `analysis_report.schema.json` | Наблюдения, рекомендации и источники |
| `generation_report.schema.json` | Результат сохранения реестра |
| `parser_lexical.schema.json` | Лексический конфиг, добавлен на третьем этапе |
| `parser_constructs.schema.json` | Составные формы, добавлены на третьем этапе |

Генератор получает структуру из деклараций приложения, а не из готовой БД или установки игры. Схемы закрыты; словари с произвольными идентификаторами допускают только объявленный тип значения.

Явная операция разработчика из `WEB_STTV`:

```powershell
$env:PYTHONPATH = (Resolve-Path src/backend).Path
./data/.venv/Scripts/python.exe -B -m sttv.schema_generation
```

После проверки заменяются схемы в `schemas/`; результат сообщает фактически записанные файлы. Одинаковые декларации дают одинаковые байты. Обычная сборка читает схемы и не перезаписывает их. Прежний `data/make_schemas.py` удалён; второго генератора нет.

## Выбор профиля и результаты

В [config/backend.json](../config/backend.json) добавлен раздел:

```json
{
  "rules": {
    "profile": {
      "base": "product",
      "path": "profiles/stellaris_4_5_4.json"
    },
    "registry": "rules/script_rules.json",
    "report": "reports/generation_report.json",
    "game_version": "4.5.4"
  }
}
```

`base: "product"` означает путь от каталога продукта. Для пользовательского профиля задают `base: "work"` и, например, `path: "profiles/my_profile.json"`. Запасной профиль не ищется. `game_version` — заявленная версия источников; `null` означает неизвестную. При известном несовпадении с профилем выдаётся предупреждение; профиль автоматически не меняется.

| Результат относительно `WORK_DIR` | Настройка |
| --- | --- |
| `database.json` | `outputs.database` |
| `reports/build_report.json` | `outputs.report` |
| `rules/script_rules.json` | `rules.registry` |
| `reports/generation_report.json` | `rules.report` |
| `reports/analysis_report.json` | `output` в `config/analysis.json` |
| `profiles/my_profile.json` | Явный аргумент сохранения профиля |

Результаты остаются внутри `WORK_DIR`. Источники, конфигурация, схемы, поставляемые профили, код и документация защищены от рабочих записей. Смена `WORK_DIR` не переносит прежние результаты.

## Устройство профиля

[stellaris_4_5_4.json](../profiles/stellaris_4_5_4.json) переносит эффективные правила первого этапа: 183 общие команды условий, 23 контекста и 10 сигнатур inline-вставок. Общие определения вынесены в 67 шаблонов и 89 групп. Это начальный профиль исследованной версии, а не полная спецификация языка движка.

| Поле | Содержание |
| --- | --- |
| `format_version` | Версия формата профиля; сейчас 1 |
| `profile_id`, `revision`, `game_version` | Идентификатор, положительная ревизия, целевая версия игры или `null` |
| `provenance` | Источники: `id`, `kind`, `file`, `line`, `record`, `game_version`, `notes` |
| `value_types` | Именованные типы аргументов |
| `scopes`, `root_scope` | Объявленные области и начальная область проверки |
| `contexts` | Контексты с `conditions` и списком `required` |
| `templates` | Шаблоны: `rule` и необязательное одиночное `extends` |
| `command_groups` | `context`, `template`, явный список `commands` и ссылки `evidence` |
| `overrides` | `context`, `command`, изменяемые свойства `rule`, `reason` и `evidence` |
| `inline_scripts` | Пути вставок, флаг `scalar` и словарь типов `parameters` |

Поддержаны `boolean`, `number`, `integer`, `identifier`, `string`, `enum`, `block` и `inline`. Для идентификаторов обязателен `pattern`; для строк он необязателен. Числа допускают `minimum`, `maximum` и регулярные выражения разрешённых ссылок в `references`. У `enum` обязателен `values`. Неприменимые ограничения отклоняются.

Развёрнутое правило содержит `type`, `scopes`, `operators`, `many`, `context` и `scope`. `scopes: null` означает отсутствие ограничения области; `scope: null` у блока сохраняет входную область. Блок требует известного вложенного `context`; у скалярного правила `context` и `scope` равны `null`. После наследования каждый шаблон должен содержать все свойства правила.

Специальный контекст группы `"$conditions"` задаёт общие команды условий. Обычный контекст подключает их через `conditions: true`; собственное правило контекста имеет приоритет над общим. Эта явная семантика сохранена из первого этапа.

Идентичные определения в одном контексте объединяются, различающиеся конфликтуют. Исключение меняет существующее правило после групп; несколько исключений одной команды запрещены. Циклы наследования и неизвестные ссылки отклоняются, рекурсивные условия в объявленной грамматике допускаются.

У inline-сигнатуры `scalar: true` разрешает скалярную форму дополнительно к блочной; `false` — только блок. Набор параметров точно совпадает с объявленным; значения скалярные. Наличие параметра во всех примерах само по себе не доказывает обязательность.

Подтверждения каждой команды прежнего реестра не были сохранены. Поэтому происхождение начального профиля помечено `unverified` с хешем старого реестра. Недостающие доказательства не выданы за документацию движка.

## Дополнительные источники анализа

[config/analysis.json](../config/analysis.json) по умолчанию содержит пустой список дополнительных источников. Технологии читаются через существующие настройки `TECH_PATH`, категорий и уровней. Локализация анализатору правил не нужна.

Пример отдельно подключаемого источника:

```json
{
  "id": "trait_triggers",
  "kind": "scripted_triggers",
  "path": "common/scripted_triggers",
  "pattern": "05_scripted_triggers_traits.txt",
  "recursive": false,
  "encoding": "utf-8-sig",
  "enabled": true,
  "game_version": "4.5.4"
}
```

Относительный `path` отсчитывается от `STELLARIS_ROOT`; поддержаны абсолютные пути и подстановка глобальных переменных в форме `${NAME}`. Выключенный источник не открывается, его переменные не разрешаются. Недоступный включённый источник, пустой выбор файлов или неподдерживаемый формат дают ошибку и статус `partial`.

| `kind` | Поддерживаемый формат и ограничения |
| --- | --- |
| `engine_documentation` | Лог с заголовком `== TRIGGER DOCUMENTATION ==`, секциями `command - description`, примерами и `Supported Scopes:`. Извлекаются явно указанные области и операторы; сложные описания аргументов требуют рассмотрения. Другие форматы, включая лог эффектов, не поддержаны. |
| `scripted_triggers` | Именованные блоки в поддерживаемом синтаксисе игры; имена, параметры `$NAME$` и вложенные конструкции. Тело не исполняется и не раскрывается в БД. |
| `inline_scripts` | Файлы вставок; путь от выбранного корня без `.txt`, параметры и вложенные конструкции. Корнем следует выбирать `common/inline_scripts` для сохранения полных имён вроде `technologies/…`. |

`max_examples` ограничивает примеры подтверждений и кандидаты шаблонов для одного наблюдения; полный список наблюдений остаётся в отчёте. `excerpt_length` ограничивает строковый фрагмент от 1 до 500 символов. Машинные пути не зашиты в Python.

## Наблюдения и рекомендации

Наблюдение содержит устойчивый `id`, команду, контекст и область либо `null`, оператор, форму аргумента, имена параметров, `inline_path`, координаты и исходную вложенность. Документированные сведения отделены от фактически встреченных. Манифест сохраняет пути, версии, статусы и хеши прочитанных файлов.

При неизвестном родительском блоке область дочерних команд не подменяется `country`. У внешнего скрипта место вызова также неизвестно, пока явно не установлено. Состояние государства не вычисляется.

Рекомендация содержит цель изменения, текущее правило, варианты действий, подтверждения, вопросы и противоречия. Возможны добавление команды, формы аргумента, оператора, области или параметра вставки, рассмотрение нового блока либо поля модели. Кандидат шаблона — предположение по наблюдаемой форме, требующее проверки.

`profile_id` и `profile_fingerprint` привязывают результат к содержимому профиля. `validate_recommendation_profile` отклоняет устаревшие результаты. Рекомендации не применяются автоматически; пользователь меняет JSON-профиль, повышает ревизию и явно выбирает его для дальнейшей работы.

`complete` означает завершение чтения выбранных источников без ошибок. Это не подтверждение всех конструкций профилем или движком. Отсутствие команды в источниках не является основанием удалить её правило.

## Программные операции

После добавления `src/backend` в путь импорта:

```python
from sttv.common.paths import PRODUCT_ROOT
from sttv.common.json_io import read_json
from sttv.sources.settings import load_settings
from sttv.rules.compiler import load_profile, validate_profile, generate_registry
from sttv.rules.operations import save_profile, generate
from sttv.analysis.operations import analyze, save_analysis
from sttv.analysis.recommendations import validate_recommendation_profile
from sttv.database.validation import validate_database

settings = load_settings(PRODUCT_ROOT / "global_variables.json",
                         PRODUCT_ROOT / "config/backend.json")
profile = load_profile(settings.profile)
validation = validate_profile(profile)
registry = generate_registry(profile)

report = analyze(settings, PRODUCT_ROOT / "config/analysis.json")
validate_recommendation_profile(report, profile)
saved = save_analysis(settings, PRODUCT_ROOT / "config/analysis.json", report)
```

`generate_registry(profile)` возвращает проверенный реестр в памяти. `generate(settings)` явно генерирует и сохраняет реестр и отчёт, возвращает `(registry, report)`. `save_profile(settings, profile, "profiles/my_profile.json")` проверяет и сохраняет пользовательский профиль, но не меняет активную конфигурацию. `save_registry(settings, registry)` доступна отдельно в `rules.operations`.

Проверка готовой БД с явно переданным реестром:

```python
validate_database(read_json(settings.database), read_json(settings.registry))
```

Она не открывает игровые источники и не восстанавливает отсутствующий реестр. `build` генерирует реестр заново из выбранного профиля; ошибочный профиль не позволяет использовать старый файл. Анализ при сборке не запускается. Консольных вопросов, веб-службы и UI в этих операциях нет.

## Сохранение и ошибки

JSON проверяется до записи; временный файл рядом с целевым перечитывается и заменяет результат. Ошибка до замены сохраняет прежний файл. Несколько замен не объявляются общей транзакцией.

Отчёт сборки содержит `database_written`, `registry_written` и `generation_report_written`. Если после записи реестра не сохранился его отчёт, ошибка `generate` содержит `result` с фактом записи реестра; сборщик переносит этот факт в свой отчёт. Генератор схем сообщает фактически заменённые файлы.

Ошибки данных представлены `BuildError` с `code`, сообщением, доступными `line` и `field_path`. Неизвестные конструкции остаются ошибками сборки, даже если анализатор подготовил предложения.

## Проверки и ограничения

На 2026-11-15 пройдены **54 синтетические проверки**, включая прежние 29. Проверены наследование, конфликты, обязательные аргументы, кратность, типы, области, операторы, сигнатуры вставок, выбор профиля, безопасная запись, частичный результат, устаревшие рекомендации и дополнительные форматы.

Сборка установленных источников: **679 технологий, 206 вариантов, 13 категорий, 6 уровней**, все 885 названий присутствуют на обоих языках. Ошибок нет; сохранены 1 265 предупреждений о внешних переменных и 7 повторных полях. БД побайтно совпадает с контрольной версией первого этапа; хеши 741 исходного файла не изменились. Независимая сверка охватывает 7 337 вхождений полей.

Анализ технологических каталогов: **10 231 наблюдение, 0 рекомендаций**. Проверено чтение существующего лога триггеров, файла признаков и одной технологической inline-вставки; неизвестная версия лога явно отмечена. Рекомендации не применялись.

Рабочие свидетельства находятся в `data/reports/`: `validation_report.json`, `stage_two_validation_report.json`, `unittest_output.txt`, `analysis_report.json` и `analysis_optional_sources_report.json`. Это не входы продукта. Python-файлы, включая тесты, не превышают 200 строк.

Интерфейс, HTTP-служба, изображения и portable-сборка остаются для следующих этапов. Полнота языка движка, выполнение игровых условий и поведение в запущенной игре не проверены.
