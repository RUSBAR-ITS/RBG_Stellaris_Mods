## Запуск и результат

Реализация утверждённого [этапа 13](TZ_BACKEND_STAGE_13_RU.md). Полная сборка 15 БД и сравнение с контрольным результатом завершились успешно.

Команда сборки набора из каталога `WEB_STTV` прежняя:

```powershell
$env:PYTHONPATH = 'src/backend'
& ./data/.venv/Scripts/python.exe -B -m sttv.database_sets
```

Одиночная сборка: `python -B src/backend/main.py --config <single_build_config>`. Для неё используется конфиг с `sources` и `outputs`, в отличие от общего `config/backend.json` набора. Настройки источников, локализации и выходов не меняются. Результаты набора — 15 файлов `data/databases/<kind>.json`; фронтенд открывает их только по запросу пользователя. Формат БД остаётся `sttv.parse_database`, версия `6`.

## Подготовка правил

Единственный источник структурных правил — `schemas/database.schema.json`, создаваемая существующим генератором `schema_generation`. При входе в операцию схема проверяется и преобразуется в функции проверки; рекурсивные ссылки связываются между функциями. Девять типов синтаксических узлов выбираются по `kind`. Регулярные выражения, таблицы типов и условий готовятся заранее.

Подготовка общая для всех участников одной сборки. Следующая операция создаёт новый снимок правил. Малые схемы конфигов и отчётов также повторно используются только в пределах операции. Кэша результатов между запусками нет.

Механизм поддерживает используемые текущим контрактом ограничения; незнакомое ограничение вызывает `unsupported_schema`. Второго реестра игровых команд нет. Универсальный JSON Schema-валидатор остаётся эталоном в тестах.

Распределение кода:

| Модуль | Ответственность |
| --- | --- |
| `common/schema.py` | Срок жизни подготовленных схем одной операции |
| `database/checks/` | Подготовка ограничений, выбор ветви и контекст документа |
| `database/validation.py` | Общий интерфейс проверки БД и документа |
| `database/history.py`, `database/enrichment.py` | Ссылки происхождения, история раскрытий и локализация |
| `database/collection.py`, `database_sets/member.py` | Последовательное получение и обогащение документов |
| `database/streaming.py` | Проверка, канонический хеш и форматированная запись документа |

## Обработка документа

Один исходный файл проходит чтение, разбор и раскрытия, подстановку статических переменных, сериализацию, выбор и присоединение локализации. Затем готовый документ проверяется один раз и записывается во временный JSON. Ссылки на его дерево освобождаются перед следующим документом.

Структурная проверка одновременно считает синтаксические узлы и собирает индексы контейнеров, происхождения и локализованных узлов. По индексам завершаются проверки ссылок вперёд, родителей и циклов раскрытий, адресов вставок, расчётов и наследования локализации. Повторного полного обхода для поиска этих данных нет.

Порядковые номера документов сохраняются: адреса `/documents/N/...` не обнуляются между файлами. Индексы дублей ID, общие источники и суммарные счётчики относятся ко всей БД. Ошибка позднего документа запрещает публикацию подготовленного участника.

## Запись и публикация

Записывается обычный JSON с отступами в два пробела, LF, читаемым Unicode и завершающим переводом строки. Канонический SHA-256 рассчитывается постепенно по прежней последовательности байтов. Показатели производительности в БД и в её хеш не входят.

Сборка не перечитывает временную БД и не проверяет неизменённое дерево повторно. Добавление `dataset` после вычисления общего `set_id` выполняется существующим копированием байтов с заголовком. До публикации проверяется неизменность входов; сохраняются `flush`, `fsync`, очистка временных файлов и атомарная замена каждого целевого файла. Замена всех 15 файлов одной транзакцией не является: частичный сбой отражается в отчёте.

Отдельное чтение готовой БД использует тот же валидатор. При отдельной локализации проверяются вход и изменённый результат — это два разных состояния данных.

В одиночной сборке время замены БД фиксируется перед единственным сохранением отчёта. Если сохранить отчёт после успешной замены не удалось, возвращается ошибка с `database_written = true`; опубликованная БД не объявляется несохранённой.

## Измерения в отчётах

Отчёты сборки и набора содержат `performance`:

- `rule_preparations` — число подготовок правил; для успешной операции набора равно 1.
- `validated_documents` — число окончательно проверенных документов.
- `documents` — источник, число узлов, результат и время проверки каждого документа.
- `timings` — секунды подготовки правил и источников, разбора/раскрытий/сериализации, локализации, проверки, хеширования, записи, проверки входов и публикации, где операция применима.

По участнику время проверки и сведения о документах доступны в `datasets.<kind>.performance` сводного отчёта. Общая длительность участника включает все его фазы. Интервалы координатора и вложенных операций нельзя складывать как независимые.

## Проверки и производительность

На шести сохранённых документах выполнены по три измерения прежней и новой полной проверки. Обе серии включают подготовку правил; сравниваются медианы на одинаковых данных. Контрольные исходники, хеши, количество узлов и окружение записаны в `data/stage13/`.

| Выборка | Ускорение проверки |
| --- | ---: |
| Типичный документ технологий | 4,42 раза |
| Крупный документ технологий | 5,71 раза |
| Типичный документ компонентов | 2,65 раза |
| Крупный документ компонентов | 6,08 раза |
| Типичный документ событий | 2,50 раза |
| Крупный документ событий | 5,67 раза |

Это измерения валидатора, а не всей сборки. Подробности: [исходные замеры](../data/stage13/baseline_validation.json), [сравнение](../data/stage13/validation_benchmark.json).

Память измерена Windows `GetProcessMemoryInfo.PeakWorkingSetSize` после сборки, до независимого чтения результатов. Сопоставимого замера пика прежней реализации нет; коэффициент уменьшения памяти не заявляется. Повторная 91-минутная старая сборка не выполнялась: использован сохранённый результат при тех же входах и настройках.

В полном прогоне проверка заняла суммарно 273,4 с, разбор/раскрытия/сериализация — 671,6 с, каноническое хеширование — 365,3 с, запись JSON — 459,7 с. Остальное время относится к подготовке, локализации, проверке входов и публикации. Хеширование и запись теперь занимают больше времени, чем проверка; их дополнительная оптимизация не входит в этот этап.

Ошибок и пропущенных документов нет. Сохранились прежние 50 предупреждений о неиспользованных inline-аргументах, 40 применений исключений, 218 предупреждений об отсутствующих полях локализации и 52 — о нераскрытых ссылках. Отсутствующие тексты не сочиняются.

Подробности: [сводка приёмки](../data/stage13/acceptance_summary.json), [совпадение файлов](../data/stage13/byte_comparison.json), [окружение](../data/stage13/environment.json). Время независимого сравнения и проверок фронтенда не включено во время сборки.

Пройдены **213 тестов Python**: структурная эквивалентность всех девяти типов узлов с эталонной схемой, обновление правил между операциями, освобождение дерева документа, реальные адреса локализации, дубли, отрицательные случаи и ошибки публикации. Все 18 поставляемых схем совпадают с генератором. Итоговый прогон выполнен без работающего dev-сервера: его наблюдение за тестовым каталогом мешало переименованию каталога в Windows.

Пройдены **33 проверки фронтенда**, включая независимое потоковое чтение полного набора. Браузерный тест открыл все 15 файлов, показал 679 карточек, проверил RU/EN, тему, тултип и три варианта титанов; ошибок страницы нет. Открытие заняло 255,8 с. Это проверка совместимости, а не оптимизация фронтенда. В компактном каталоге сохранились 214 прежних предупреждений об отсутствующей локализации.

## Границы оптимизации

Все документы одного участника больше не удерживаются одновременно, однако один крупный документ, общие библиотеки шаблонов и индекс локализации по-прежнему требуют памяти. Запись полного происхождения и истории раскрытий сохраняет прежний размер файлов. Подготовка источников разных участников не распараллеливается.

Потоковое чтение готовой БД в отдельных Python-операциях не добавлено; фронтенд использует существующее потоковое чтение. Игровая грамматика, исключения и сортировка карточек не изменялись. Исходники игры доступны только для чтения; запуск Stellaris для этого этапа не требуется.
