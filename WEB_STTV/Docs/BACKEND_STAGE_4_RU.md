## Результат этапа

Реализовано утверждённое [ТЗ четвёртого этапа](TZ_BACKEND_STAGE_4_RU.md). Парсер создаёт отдельные узлы логических операций по конфигурации. Оба вида вызова `inline_script` передаются функции разворота, которая пока возвращает пустой список. Внутреннее содержимое вызова не разбирается.

## Конфигурации

`config/backend.json` содержит три обязательных пути в `parser`: `lexical`, `constructs`, `logical_operators`. Для каждого поддерживаются основания `product` и `work`; отсутствующий или некорректный файл приводит к ошибке без подстановки настроек по умолчанию. Конфиги защищены от перезаписи выходными файлами.

| Файл | Назначение |
| --- | --- |
| `config/parser/lexical.json` | Символьные операторы, строки, комментарии, скобки и пробельные символы |
| `config/parser/constructs.json` | Структурные формы; `inline_script.keyword` и `case_sensitive` выбирают имя обработчика |
| `config/parser/logical_operators.json` | Список логических имён, их каноническое написание, регистр и соединительный оператор |

Поставляемые логические имена: `AND`, `OR`, `NOT`, `NAND`, `NOR`; сравнение регистронезависимое, соединительный оператор — `=`. Пустой список выключает специальное распознавание. Имена не дублируются в механизме парсера. Изменение списка не означает, что игра поддерживает добавленное имя.

Схемы формируются постоянным генератором `sttv.schema_generation`; добавлена `parser_logical_operators.schema.json`, обновлены схемы конструкций, настроек бэкэнда и отчётов. Схема БД не менялась.

## Интерфейс и дерево

```python
from sttv.common.paths import PRODUCT_ROOT
from sttv.script.parser import parse_text
from sttv.script.syntax import load_syntax

syntax = load_syntax(
    PRODUCT_ROOT / "config/parser/lexical.json",
    PRODUCT_ROOT / "config/parser/constructs.json",
    PRODUCT_ROOT / "config/parser/logical_operators.json",
)
document = parse_text("or = { tech_a tech_b }", syntax, "example.txt")
operation = document.items[0]
assert operation.operator == "OR"
assert operation.name.raw == "or"
assert [item.text for item in operation.body.items] == ["tech_a", "tech_b"]
```

`make_syntax(lexical, constructs, logical_operators)` принимает три уже загруженных словаря. `parse_text` не читает файлы и не использует игровой профиль. Сборщик и анализатор получают одинаковый `Syntax` через `Settings`.

`LogicalOperation` содержит `operator`, исходный `Scalar` в `name`, `assignment_operator`, `body: Block`, `span`. Распознаётся только отдельное имя без кавычек слева от настроенного знака с блоком справа. `NOT = tech_a`, `localization = AND` и `"AND" = {}` остаются обычными присваиваниями.

В теле сохраняются списки, повторения, вложенные операции, пустые блоки и несколько записей внутри `NOT`. При `mixed_blocks: false` логическая операция считается именованной конструкцией, как `Assignment`. Условия не вычисляются.

## Обработка inline_script

Парсер читает токены по мере необходимости. После имени `inline_script` и `=` он переключается на чтение внешних границ значения до обычного разбора параметров, формул и условных фрагментов.

`script/opaque.py` учитывает вложенность скобок, строки, экранирование и комментарии. `script/inline.py` определяет `InlineScriptValue(raw, form, span)` и `expand_inline_script(value, source)`. Функция вызывается один раз для внешнего вызова и возвращает `[]`; вложенные вызовы внутри непрозрачного значения не обрабатываются отдельно.

Значение не становится узлом AST. В `Document.skipped_inline_scripts` сохраняются координаты всего вызова, включая имя; исходный текст полностью остаётся в `source` и токенах. Для значения используется один `opaque_value`-токен. Опустевший родительский блок сохраняется.

Неизвестные команды, незавершённый `$…` или некорректные присваивания внутри корректно ограниченного блока не проверяются. Отсутствующее значение, незакрытая строка или внешний блок остаются ошибками с координатами. Явно переданный текст файла из `common/inline_scripts` разбирается как обычный самостоятельный документ; файлы по ссылкам автоматически не открываются.

## База и отчёты

Проекция логического узла в `DataEntry`/`ScriptBlock` использует каноническое имя как `key`. Обычные ключи и значения сохраняют регистр. Пропущенные вызовы отсутствуют уже до преобразования, поэтому их сигнатуры не проверяются и содержимое не восстанавливается из текста.

Сборка и анализ возвращают обязательный `counts.skipped_inline_scripts`, включая ноль. Пропуск не считается ошибкой или отдельным предупреждением. Координаты каждого вызова находятся в `stage4/corpus_report.json`.

Текущая БД исключает вклад inline-вставок. На ванильных технологиях удалена 301 запись `inline_script`; остальные данные совпали с контрольной БД. Сохранены 679 технологий, 206 вариантов и их названия RU/EN. В текущей папке технологий логические имена уже имели канонический регистр; его изменение проверено синтетически.

## Ограничения

Реальное раскрытие `inline_script` отложено до отдельного этапа. По текущей БД нельзя восстановить вклад пропущенных вставок или вычислить доступность технологий для конкретного государства. Строгие проверки остальных полей сохранены; модель `prerequisites` по-прежнему поддерживает `all`/`any`. Профиль игровых команд не заменялся, частотный список не пересчитывался. Файлы игры не изменялись; запуск игры для проверки этого этапа не требуется.
