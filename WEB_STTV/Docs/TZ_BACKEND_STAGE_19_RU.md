## 1. Статус и границы

Подготовить данные для будущих настроек архетипа, гештальтности, биологических кораблей, происхождения, кочевого статуса, этик, признаков вида, гражданских моделей и набора DLC. Добавить источники в существующий сборщик и обеспечить чтение расширенного набора текущим фронтендом.

Включены импорт полного AST, действующее раскрытие вставок и переменных, индекс объектов, RU/EN-локализация, связывание описателей DLC с каталогом, схемы, отчёты и проверки. Сохранить раздельные документы, библиотеки повторяемых элементов, параллелизм файлов и выборочное чтение этапов 14–18.

Подготовка уже поддерживаемых изображений технологий сохраняется.

Изменённые правила импорта входят в соответствующие ревизии конфигурации; устаревшие результаты не объявляются актуальными.

## 4. Разбор и идентификация объектов

Сохранять полный результат парсинга: неизвестные игровые поля, порядок, повторяющиеся записи, вложенные блоки, операторы, условия, динамические выражения и историю раскрытий. Новый перечень семантических команд не вводится. Служебные данные обогащений не становятся игровыми условиями.

Для девяти обычных видов ID объекта — имя корневого блока. Переменные, комментарии и скалярные служебные записи не превращаются в объекты. Повтор одного ID внутри вида — ошибка с обоими адресами. Один ID в разных видах допустим: например, `MACHINE` в архетипах и классах различается через `database`.

- `is_origin = yes` отличает происхождение от гражданской модели независимо от имени файла. Сам объект и вложенные `swap_type` сохраняются один раз; условные представления не становятся независимыми происхождениями.
- Каталог `traits` сохраняет все определения, включая признаки лидеров. На этом этапе не формируется окончательный список выбираемых признаков вида; ни имя файла, ни отсутствие `allowed_archetypes` не служат основанием для удаления объекта.
- `playable`, `initial`, `pickable_at_start`, `potential`, `possible`, `allowed_*`, `forbidden_*`, `opposites`, `modification`, наследование архетипов и подобные поля сохраняются. Не отфильтровывать объекты по предполагаемой стартовой империи.
- `advanced_authority_swap`, `swap_type` и другие вложенные варианты сохраняются с условиями и исходным порядком. Их активность не вычисляется.
- У форм власти, гражданских моделей и классов видов требования могут использовать `ethics = { value = ... }` и подобный специальный синтаксис. Структура сохраняется без преобразования в обычные триггеры технологии. Вес случайного выбора не превращается в запрет ручного выбора.

Отдельные БД `gestalt`, `bioships` или `nomadic` не создаются. Гештальтность связана с `ethic_gestalt_consciousness`, биологические корабли — с `ship_kinds`/`bio_ship`, а `is_nomadic` является отдельным свойством империи, встречающимся в условиях. `trait_nomadic` не заменяет это свойство. Эти связи описывают назначение данных, но не вводят вычислитель профиля в данном этапе.

## 5. Каталог DLC

### Основные записи

Сохранить `dlc_info.txt` как один исходный документ, включая контейнер `dlcs`. Индексировать его непосредственные блоки `dlc001`, `dlc036` и т. п.; сам контейнер объектом DLC не является. ID брать из имени вложенного блока, сохраняя `name` отдельно как идентификатор, используемый в `host_has_dlc`.

Адрес объекта имеет вид `/items/i/value/items/j`. Не переносить блоки в корень AST ради существующего ограничения индексатора. Вложенные поля `recommendations`, `icon`, `show`, `affects_gameplay` и прочие сохраняются; `show = no` или `affects_gameplay = no` не удаляют DLC из справочника. Рекомендации не являются зависимостями включения.

### Описатели пакетов

Каждый `.dlc` сохранить отдельным документом вида `dlcs` с исходными корневыми полями. Корневые `name`, `archive`, `localizable_name`, `steam_id`, `pops_id`, `category`, `thumbnail` и остальные поля остаются в AST. Описатель не создаёт второй объект DLC в индексе; его роль определяется конфигом источника.

Сопоставлять описатель с записью каталога по точному значению `name`, а не по локализованной строке, числу Steam или сходству имени файла. Дубли ID каталога, неоднозначный `name` и несколько описателей для одного DLC — ошибки с адресами всех участников. Несопоставленный описатель сохраняется и отражается предупреждением; новый ID из имени файла автоматически не изобретать.

У записи каталога добавить `enrichments.dlc.descriptors`: массив ссылок на документы `{database, document_id}`; при отсутствии описателя — пустой массив. Здесь используется ссылка на весь документ, без фиктивного указателя на корневое присваивание. Поля описателя не копируются поверх полей каталога. Связи формируются после подготовки документов, до итоговой публикации, и проверяются аудитом.

Для текущей установки четыре записи каталога (`dlc001`, `dlc003`, `dlc010`, `dlc011`) не имеют отдельных `.dlc`. Это наблюдение фиксируется в отчёте, а не в исключениях или жёстком списке обязательных пакетов.

Наличие документа/архива, Steam ID, флагов `show` и `affects_gameplay` не устанавливает `owned` или `enabled`. Импорт не добавляет такие значения. Выбор включённых DLC будет состоянием будущего пользовательского профиля. Условия вроде `has_shroud_dlc_and_machine_age` раскрываются существующим механизмом с сохранением всей логики; не сводить каждую функцию к одному имени DLC.

## 6. Локализация

Использовать действующий механизм `enrichments.localization`: RU/EN независимо, прежние приоритеты `RU_LOC_TIER_1` → `RU_LOC_TIER_2` → `RU_LOC_TIER_3` и `EN_LOC_TIER_1`, сохранение ключа, исходной строки, раскрытого текста, происхождения и неразрешённых ссылок. Источники переводов не дублируются в новых конфигах.

| Объекты | Правила текстовых целей |
| --- | --- |
| Архетипы, классы, этики, формы власти, гражданские модели/происхождения, признаки | Название по ID; описание по `<id>_desc`, если соответствующий ключ существует |
| Категории этик | Название по ID, если имеется; технические категории без перевода сохраняются по ID |
| Графические культуры | Настроенные кандидаты ключей названия по ID и верхнему регистру ID; описание `<id>_shipset_desc`. Иные подтверждённые соответствия задаются правилами локализации, не догадкой из сходства текста |
| Категории кораблей | Название по ID; явный `desc`, иначе `<id>_desc`, если есть |
| DLC | `localizable_name` основного каталога; при его отсутствии или отсутствии перевода — ключ сопоставленного описателя. Зафиксировать источник выбранного ключа; при отсутствии перевода показываемым резервом остаётся техническое `name` |

Кандидаты локализации проверяются отдельно для каждого языка. Не записывать технический резерв как успешно найденный перевод. Отсутствие необязательного описания не блокирует публикацию; отсутствующие ключи и объекты без текстовой цели различаются в отчёте. Не придумывать описания DLC по суффиксу от `dlc036` или имени магазина.

Явные текстовые поля `description` и `desc`, а также именованные `swap_type`/`advanced_authority_swap` обрабатывать по отдельным настроенным целям на соответствующих узлах. Например, `origin_default_desc` и `description = origin_tooltip_default_effects` — разные тексты; сохранить оба, не перезаписывая повествовательное описание перечнем эффектов. Условные тексты сохраняются вместе с условиями, без выбора одной ветви. Для варианта без собственного `name` не изобретать локализационный ID.

Раскрывать обычные статические ссылки `$key$`. Динамические подстановки, игровые команды форматирования и ссылки на концепты сохранять как есть. Копировать описание основной технологии в её вариант по прежнему правилу; это правило не распространяется автоматически на любые новые вложенные блоки.

## 7. Исключение для исходника DLC

В установленном `dlc_metadata/dlc_info.txt`, внутри `dlcs/dlc002`, встречается `paradoxplaza_store_url ""` без `=` (при исследовании — строка 35). Это обнаруженное отклонение источника; поведение движка по нему не утверждается.

Добавить в `config/parser/source_exceptions.json` адресное правило `sttv_dlc_metadata_store_separator`: только для указанного файла, контейнера, записи DLC и точной последовательности поля с пустой строкой вставлять `=` в памяти перед обычным разбором. Расширение механизма исключений должно сохранять ссылки на исходные позиции и учитывать исходный, неисправленный файл при хешировании входа. Условия и действие правила задаются конфигом.

Номер строки не является единственным условием. Комментарии и вхождения в строковых литералах не подходят. Если поле уже корректно, правило не применяется; несколько неоднозначных совпадений приводят к ошибке. Аналогичный текст в другом файле или объекте не исправляется. Исходник игры остаётся неизменным; отчёт содержит ID правила, адрес, исходную и принятую конструкции. Не разрешать глобально любые присваивания без оператора.

Дополнение, согласованное пользователем: для отсутствующего `CLASS` в ванильных иконках признаков разрешено адресное исключение по содержащему вызов объекту. В настроенном списке файлов `common/traits` и точных шаблонов брать единственный класс из непосредственного поля `leader_class` корневого признака; для нескольких различных допустимых классов использовать `leader`. Допустимые классы, поле, нейтральное значение, файлы и шаблоны задаются конфигом исключений. Сохранить явно переданный аргумент. При отсутствии поля, неизвестном значении, неоднозначном объекте или неверной форме поля оставить ошибку. Вложенный вызов наследует контекст исходного признака через цепочку вызовов; соседние признаки и имя файла не определяют класс. В отчёте фиксировать правило, объект/поле, полученное значение и цепочку вызовов. Это исправление импорта оформления, а не изменение игровых ограничений признака; файлы игры неизменны.

Сохранение явно переданного аргумента включает его передачу через промежуточный шаблон, потерявший `CLASS`: в рамках того же адресного исключения сначала использовать ближайшее явно заданное значение в цепочке вызовов, затем выводить класс по объекту. Это не вводит общего наследования аргументов между inline-вызовами.

Другие обнаруженные проблемы полного раскрытия исследовать и сообщать отдельно. Дополнение не разрешает автоматически добавлять новые исключения или исключать проблемные объекты из результатов.

## 8. Хранение и чтение во фронтенде

Один исходный файл даёт один постоянный JSON в действующем формате раздельного хранения. Использовать общую публикацию набора: сначала подготовленные документы, затем согласованный манифест. Сохраняются UTF-8, отступы 2 пробела и переносы строк. Не возвращать объединение в монолит.

Расширить индексатор, общий читатель, проверку ссылок, локализацию и сгенерированные схемы для разрешённых вложенных объектов. Допустимость адреса определяется селектором соответствующего вида и фактическим AST, а не снятием всех ограничений JSON Pointer. При чтении проверить, что адрес существует, указывает на ожидаемую запись и согласуется с её ID. Отдельно проверить ссылки DLC на объявленные документы-описатели того же вида.

Версии изменённых контрактов/конфигов и ревизия реестра отражают новый формат. Совместимое чтение старых наборов не требуется. Новый набор готовить в отдельном рабочем каталоге; существующий эталон не удалять и не перезаписывать при приёмке.

Новый состав меняет ревизию набора. Готовые комбинации дерева из прежнего набора нельзя пометить актуальными простой заменой `source_set_id`. Для браузерной приёмки подготовить комбинацию штатной операцией по новому набору, с прежними правилами и профилем. Новые справочники не становятся свидетельствами выбора родителей без отдельного согласованного этапа. При неизменных прежних входах проверить сохранение решений `parent_tech`/`children`.

Во фронтенде обновить общий реестр, типы, локализованные названия видов, проверку манифеста, разрешение вложенных адресов и адаптер справочников. Явное открытие каталога должно принимать набор из 25 видов. Первичная загрузка остаётся технологической: дополнительные документы читаются по запросу, затем переиспользуются в сеансе. Сохраняются проверка хеша при чтении, явный учёт покрытия и полный аудит отдельной командой.

Проверить возможность адресного чтения нового объекта и его локализации, включая `dlcs/dlc036`. Добавление справочников не создаёт новые карточки на технологическом поле. Открытие, обновление страницы и запуск приложения не запускают сборку БД. Новые панели выбора империи и DLC в этом этапе не создаются.

## 9. Диагностика

В существующих отчётах отражать по виду число обнаруженных/прочитанных файлов, документов и объектов, успешных/неуспешных раскрытий, целей локализации RU/EN, отсутствующих переводов, применённых исключений, записанных байтов и время стадий. Отдельно показать число происхождений среди `civics` и число всех определений `traits`, не называя последнее количеством доступных признаков вида.

Для DLC добавить числа записей каталога, описателей, сопоставленных пар, записей без описателя, несопоставленных описателей и конфликтов. Для проблемы сохранять вид, исходный файл, ID, адрес узла и причину. Отсутствие DLC-описателя не является сообщением об отсутствии лицензии.

Ошибка обязательной структуры, повтор ID, неоднозначное сопоставление или ошибка раскрытия не должны оставлять опубликованный частичный набор. Не вводить повторный полный обход AST по JSON Schema: расширить действующие проверки этапа 13 и использовать общий аудит хранения.

## 10. Проверки и приёмка

1. На синтетических источниках проверить корневые объекты девяти видов, одинаковые ID в разных видах, повтор ID внутри вида и файл только с комментариями.
2. Проверить происхождение вне `00_origins.txt`, обычную гражданскую модель в том же файле, вложенные варианты и сохранение обоих без дублирования объектов.
3. Проверить совместное сохранение видовых и лидерских признаков, неизвестных полей и условий без фильтрации по стартовой доступности.
4. Проверить раскрытие существующих inline/scripted-вставок, подстановку статических переменных и сохранение условий `AND`/`OR`/`NOT`, специальных списков требований и истории вызовов.
5. Проверить вложенный объект DLC, плоский описатель, отсутствие описателя, лишний описатель, неоднозначные имена, повтор ID и несовпадение `name` с именем файла. ID каталога, техническое имя и ключ перевода не смешиваются.
6. Проверить, что `show = no`, `affects_gameplay = no` и наличие локальных файлов не скрывают объект и не устанавливают владение/включение.
7. Проверить локализацию RU/EN, приоритеты, запасной ключ из описателя, отсутствие перевода, собственный текст варианта, отдельные повествовательные/эффектные описания, циклические/динамические ссылки и описание набора кораблей.
8. Проверить точное исключение DLC, уже исправленную запись, другой файл/объект, комментарий и неоднозначное совпадение. Сверить сохранение исходных позиций, хеша оригинала и диагностической записи.
9. Проверить вложенные адреса и их отклонение при отсутствии узла, неверном ID или неподходящем селекторе; ссылки описателей не выходят за объявленные документы.
10. Проверить публикацию и прерывание, выборочное чтение и обнаружение повреждённого прочитанного файла. Непрочитанные данные не отмечаются проверенными.
11. Сгенерировать схемы из кодовой базы, проверить конфиги, выполнить профильные тесты бэкенда и затронутые модульные/браузерные тесты фронтенда, сборку TypeScript.
12. Построить реальный новый набор из 25 видов, выполнить RU/EN-обогащение, подготовку прежних ресурсов и готовой комбинации, затем полный аудит. Зафиксировать фактические количества и отличия от первичной инвентаризации; ошибки полного раскрытия не выдавать за пройденные проверки.
13. Сравнить прежние 15 видов и решения дерева с эталоном при неизменных исходниках после исключения ожидаемых служебных ревизий/формата. Проверить в браузере открытие, RU/EN, карточки, масштаб и связи; измерить начальное чтение и подтвердить, что новые справочники не загружаются все сразу.

Контрольные 36 DLC и 32 описателя относятся к исследованной установке. Количество строк не зашивается в продукт и не заменяет проверку содержимого. Синтетические проверки и чтение файлов не подтверждают вычисление доступности в игровом движке; такого вычислителя в этом этапе нет.

## 11. Результаты реализации

Подготовить модульные изменения существующего импортёра, индекса, локализации и читателей; конфигурации источников/целей; схемы через штатный генератор; тесты; отчёты реальной сборки и аудита; двуязычное руководство этапа. Обновить README, общий указатель ТЗ, документацию исключений и changelog после реализации. Руководство должно перечислять реально читаемые ванильные источники и ограничения.

Повторяемые операции вынести в общие хелперы. Нормальный размер кодового файла — до 200 строк; свыше 200 рассмотреть разделение, свыше 300 вынести функциональные части, кроме действительно неделимого блока. Не создавать отдельный парсер для DLC или копию сборщика для каждого нового вида.

Изменения вне описанной области и новые исправления ванильных данных согласовывать отдельно. На стадии подготовки этого ТЗ меняются только документы; конфиги и исполняемый код ещё не меняются.
