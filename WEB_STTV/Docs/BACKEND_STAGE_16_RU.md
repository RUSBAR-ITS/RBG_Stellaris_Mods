## Что реализовано

Выполнено [ТЗ этапа 16](TZ_BACKEND_STAGE_16_RU.md). Модуль [enrichment/technology_tree](../src/backend/sttv/enrichment/technology_tree/__init__.py) рассчитывает связи по готовому набору из 15 БД. Он не запускает сборку, локализацию или чтение файлов игры.

Для каждой технологии определяется один родитель, корневое состояние либо неоднозначность. Ребёнок сразу добавляется в список родителя, даже если собственный родитель этого объекта ещё не рассчитан. Итоговые списки детей упорядочены по ID для воспроизводимости; это не порядок размещения карточек.

Обработчики используют 13 согласованных критериев. При пустом результате критерий пропускается; при единственном кандидате отбор заканчивается. Исходные требования и игровые уровни не изменяются. Неоднозначность сохраняется с диагностикой; цикл или нарушенная взаимность блокируют публикацию.

## Запуск

Команды выполняются из каталога `WEB_STTV` с установленными зависимостями бэкенда:

```powershell
$env:PYTHONPATH = "src/backend"
& data/.venv/Scripts/python.exe -B -m sttv.enrichment.technology_tree
```

По умолчанию операция обогащает `data/databases/technologies.json`, беря остальные пути из `config/backend.json`. Актуальная комбинация переиспользуется. Для принудительного расчёта:

```powershell
& data/.venv/Scripts/python.exe -B -m sttv.enrichment.technology_tree --recalculate
```

Доступны `--variables`, `--config`, `--combination`. Для проверки на созданной рабочей копии:

```powershell
& data/.venv/Scripts/python.exe -B -m sttv.enrichment.technology_tree --config data/stage16/operation.json
```

Python-интерфейс возвращает отчёт, а не дерево БД:

```python
from sttv.enrichment.technology_tree import enrich_technology_tree

report = enrich_technology_tree(config_path="data/stage16/operation.json")
```

Успех, включая предупреждения, даёт код выхода 0. Ошибка даёт ненулевой код; конкретная причина находится в `error` отчёта. Автоматического запуска операции при открытии интерфейса нет.

## Конфигурация и комбинации

| Файл | Назначение |
| --- | --- |
| [technology_tree.json](../config/enrichment/technology_tree.json) | Адреса конфигов, отчёт и рабочий каталог |
| [rules.json](../config/enrichment/technology_tree/rules.json) | Порядок, включение критериев и параметры свидетельств |
| [reference_empire.json](../config/enrichment/technology_tree/profiles/reference_empire.json) | Проверенные факты обычной империи; отсутствующие факты неизвестны |
| [reference_default.json](../config/enrichment/technology_tree/combinations/reference_default.json) | Режим справочника, профиль и выбор вариантов |

В `rules` можно менять порядок и `enabled`. `parameters` задаются непосредственно либо единственным `definition_ref`, ссылающимся на блок `definitions`. Ссылки целиком заменяют параметры; переопределений и цепочек ссылок нет. Проверяются и выключенные правила. Новая разновидность вычисления требует обработчика и схемы; новые значения существующих отображений настраиваются конфигом.

`variants` сопоставляет базовый ID технологии со значением `base` или `swap:N`, где N начинается с 1. Неуказанные технологии используют базовое представление. Изменения области и категории кандидатов также участвуют в расчёте. Ручной выбор не требует выполнения игрового условия варианта.

При `inherit_effects = yes` сравниваются эффекты базы и варианта; при `no` — эффекты варианта. Если флаг отсутствует либо числовые модификаторы конфликтуют, зависимый критерий пропускается с диагностикой. Названия технологий не используются для угадывания наследования.

## Формат и актуальность результата

На исходном узле технологии сохраняется `enrichments.technology_tree[combination_id]` с полями `parent_tech`, `children`, `status`. Общие параметры и ревизии находятся в корневом `technology_tree.combinations`. Локализация и остальные комбинации сохраняются.

`dataset.set_id` продолжает обозначать исходный опубликованный набор. Отдельные ревизии учитывают источники, правила, параметры, версию вычислительной реализации и итоговые связи. Собственное обогащение исключается из входного хеша технологий. Другие 14 файлов хешируются побайтно; их форматирование консервативно меняет входную ревизию.

Переиспользование требует совпадающей ревизии расчёта и исправных связей/хеша результата. Старые комбинации не объявляются актуальными автоматически. Пересчёт заменяет выбранную комбинацию целиком, удаляя её устаревшие записи и детей. Даже принудительный расчёт не переписывает БД, если проверенный результат совпал.

Схемы формируются генератором `sttv.schema_generation`: добавлены пять схем операции, правил, профиля, комбинации и отчёта; расширена `database.schema.json`. Явная общая проверка БД дополнительно контролирует размещение записей, взаимность, циклы и ревизии. При обогащении повторная полная проверка исходного AST не выполняется.

## Чтение и сохранение

БД технологий загружается в память. Связанные базы читаются последовательно по корневым объектам; форматирование строк не используется для определения границ JSON. Файл событий целиком в память не загружается. Сохраняются только события, найденные через явные маршруты действий; текстовое совпадение ID не создаёт связи.

Индексы свидетельств готовятся один раз на расчёт. Повторное использование сверяет хеши и сохранённый результат без построения функциональных индексов. Совпадение хешей подтверждает неизменность ранее проверенных заголовков; при изменении входов заголовки проверяются заново. Чтение входных файлов для хеширования всё ещё необходимо. В отчёте раздельно указаны проходы чтения и их объём.

Публикуется только файл технологий: временный JSON рядом с ним, проверка неизменности входов, атомарная замена. Запись имеет отступ 2, UTF-8 и переносы строк. Файл блокировки исключает конкурирующее обновление того же назначения. Ошибка до замены сохраняет прежний файл; сбой записи отчёта после замены честно сохраняет `database_written = true`.

Отчёт содержит реальные шаги отбора, условия и адреса свидетельств. При переиспользовании шаги не выполняются повторно: `trace_state = not_recalculated`, трасса пуста, остаток кандидатов не выдумывается. Подробная трасса доступна в отчёте выполненного расчёта. Неоднозначности расчёта включают комбинацию, правила и настройки; отсутствующее состояние окна помечено явно.

## Проверки и рабочие результаты

Рабочая обогащённая копия: [data/stage16/technologies.json](../data/stage16/technologies.json). Остальные 14 файлов берутся из `data/databases` только для чтения. Исходная БД технологий сохранена.

Базовый результат полностью совпал с аналитическим эталоном: **679 технологий, 178 корней, 501 выбранный родитель; 0 неоднозначностей и циклов**. Среди технологий с родителем 412 имели один исходный пререквизит, 89 — несколько. Сопоставлены все решения и 12 отдельных контрольных примеров.

Приёмка проверила все 206 вариантов по одному и три сочетания на однократно подготовленных индексах, обратный порядок обработки, сохранение и повторное использование двух комбинаций. На текущем наборе неоднозначностей и предупреждений в этих прогонах не возникло; это не гарантирует такой результат для иных данных. Ожидаемые пары читаются проверкой после расчёта и недоступны модулю отбора.

Артефакты проверки:

- [acceptance.json](../data/stage16/acceptance.json) — итог, варианты, контрольные случаи и время операций;
- [base_acceptance_report.json](../data/stage16/base_acceptance_report.json) — базовая трасса;
- [variant_report.json](../data/stage16/variant_report.json) — сохранение изменённой комбинации;
- [base_reuse_report.json](../data/stage16/base_reuse_report.json) и [variant_reuse_report.json](../data/stage16/variant_reuse_report.json) — повторное использование;
- [tests.json](../data/stage16/tests.json) и [tests.txt](../data/stage16/tests.txt) — синтетические и связанные регрессионные проверки.

Пройдены 58 проверок: 33 новых проверки обогащения и 25 проверок генерации схем, структурной валидации и сборки наборов БД. Проверены в том числе ошибки записи, конкурирующий вызов, изменение входа во время расчёта, повреждённые связи и устаревшие записи комбинации.

Первый полный расчёт занял около 279 секунд: около 262 секунд — подготовка индексов, 8 секунд — хеширование, 7 секунд — запись. Сам отбор занял около 0,004 секунды. Измерения относятся к текущей машине и набору; публикация варианта в приёмке использует уже подготовленные индексы и не является замером отдельного холодного запуска.

После исключения повторного просмотра неизменных JSON переиспользование проверено заново: около 11,1 секунды для базовой и 10,9 секунды для изменённой комбинации, без записи БД. Основное время — чтение и хеширование источников. Повторно пройдены 10 проверок операции, включая изменение заголовка уже использованного набора.

## Границы этапа

Фронтенд ещё не использует новые связи для сортировки и размещения. `location`, сетка, локальный API и кнопка пересчёта остаются следующими этапами. Анализ событийного получения технологий отложен; события используются только для ранее согласованных свидетельств о вооружении. Реальное состояние империи и игровое выполнение эффектов не вычисляются.
