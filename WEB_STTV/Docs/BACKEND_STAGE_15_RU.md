## Статус

Реализация [утверждённого ТЗ этапа 15](TZ_BACKEND_STAGE_15_RU.md) завершена и проверена. Фронтенд остаётся версии `0.0.3`; формат БД — `sttv.parse_database`, версия `6`.

## Запуск и конфигурация

Из каталога `WEB_STTV`:

```powershell
$env:PYTHONPATH = (Resolve-Path src/backend).Path
python -B -m sttv.database_sets --reuse-libraries
```

Для подготовки библиотек с нуля использовать `--rebuild-libraries` вместо `--reuse-libraries`. Выбранный режим выполняет координатор; рабочие процессы загружают готовые библиотечные JSON. Открытие приложения или страницы не запускает сборку.

`config/backend.json` ссылается на `config/parallel.json`:

```json
{
  "format_version": 1,
  "workers": 10,
  "staging_directory": "staging/parallel"
}
```

`workers` — максимум рабочих процессов, без учёта координатора. Значение `1` использует тот же механизм для последовательного запуска. При небольшом количестве файлов занятых работников может быть меньше. Число процессов не ограничивается автоматически числом ядер или оценкой свободной памяти.

Путь промежуточных файлов отсчитывается от `WORK_DIR`. Каждая операция создаёт свой подкаталог. Совпадение с источниками, библиотечными артефактами, конфигами или выходами БД отклоняется. Результаты остаются в `data/databases/`, отчёты — в `data/reports/`, если эти пути не изменены в конфиге.

## Порядок обработки

1. Координатор проверяет настройки, фиксирует входы и подготавливает либо загружает библиотечный снимок.
2. Создаётся пул отдельных процессов Windows. Каждый загружает библиотеки и подготавливает правила проверки один раз.
3. Работники получают файлы текущей БД: разбор и раскрытие, подстановка переменных, сериализация, локализация, проверка, хеширование и запись промежуточного JSON.
4. Координатор проверяет комплектность и общие ограничения, затем потоково объединяет документы в исходном порядке файлов.
5. Тот же пул переходит к следующей БД. После подготовки всех 15 участников работники завершаются; координатор проверяет входы и публикует набор.

Деревья не передаются через межпроцессную очередь. Через неё проходят задания, счётчики, пути, хеши, диагностика и статистика. Таблицы локализации и раскрытые тексты переиспользуются при одинаковых источниках и настройках ссылок. Для кешированного текста восстанавливается его точный список источников; выбранные ключи и счётчики остаются отдельными для документа. Общие библиотеки не получают изменяемое состояние игровых вызовов.

## Сохранение идентификаторов раскрытия

В прежней сборке номера `inline_N`, `scripted_effect_N`, `scripted_trigger_N` и `script_value_N` накапливались по БД. Простое независимое раскрытие каждого документа начинало бы нумерацию заново и изменило бы историю.

Поэтому после раскрытия работник отправляет количества вызовов и ожидает смещения для своего документа. Координатор вычисляет их по исходному порядку, независимо от порядка готовности работников. При сериализации смещаются только служебные идентификаторы и их ссылки; игровые строки не переименовываются. Готовое дерево проверяется уже с окончательными идентификаторами.

Это ожидание отражается отдельно как `id_order_wait`; оно вычитается из `parse_expand_serialize`. Дерево остаётся в памяти работника. Медленный ранний файл может задерживать сериализацию более поздних файлов, но дополнительное чтение и повторный разбор промежуточного JSON не требуются.

## Проверки и публикация

Работник проверяет структуру документа, историю раскрытия, происхождение узлов и обогащения до записи. Координатор проверяет отсутствие потерянных/повторных результатов, повторных исходников и повторных ID объектов внутри одной БД. При копировании проверяются размер и хеш промежуточного файла.

Полный повторный обход деревьев при объединении не выполняется. Анонимные определения и фрагменты сохраняют прежние правила идентичности. Ошибка или аварийное завершение работника останавливает сборку; отменённые задания отдельно отмечаются и не увеличивают счётчик ошибочных исходных файлов.

Промежуточные документы удаляются после объединения участника, оставшиеся собственные временные файлы — при завершении операции. Чужие рабочие каталоги и библиотеки не удаляются. Остатки жёстко прерванного процесса не используются для автоматического возобновления.

До успешной подготовки всего набора опубликованные БД не заменяются. Последующая публикация является последовательностью замен файлов: при сбое непосредственно на этом шаге отчёт показывает уже заменённых участников, а разные `set_id` позволяют обнаружить смешанный набор.

## Идентичность БД

Работник вычисляет SHA-256 канонического JSON полного документа и отдельный SHA-256 записанных форматированных байтов. Первый участвует в идентичности содержимого; второй проверяется при копировании.

Новый алгоритм `sttv.document_hashes.v1` вычисляет `content_hash` по версии формата и упорядоченному списку хешей документов. Общий `set_id` вычисляется по отображению видов БД на их `content_hash`. Точный контракт приведён в [разделе 8 ТЗ](TZ_BACKEND_STAGE_15_RU.md#8-идентичность-документов-и-набора).

Число процессов, PID, временные пути и длительности не входят в идентичность. Относительно этапа 14 меняется `dataset.set_id`; формат игровых деревьев и правила открытия набора остаются прежними. Библиотечный `library_set_id` не заменяется этим алгоритмом.

## Отчёты и измерения

В отчёте каждой БД `performance.parallel` содержит настройки и фактическое использование работников, статусы заданий, размеры и хеши документов, показатели инициализации процессов и измерения памяти. Длительности стадий находятся в `performance.timings`; суммарные интервалы работников могут превышать реальное время сборки.

Общие определения и источники объединяются без умножения на количество работников. Число проверенных документов, реальные вызовы и другие события суммируются; максимальная глубина берётся по максимуму. Отчёты записывает координатор.

Память измеряется опросом Windows working set раз в секунду во время жизни пула: отдельно координатор и одновременно наблюдаемая сумма его дерева процессов. Это выборочный максимум, а не сумма индивидуальных исторических пиков. Счётчик `errors` показывает неуспешные выборки. `temporary_peak_bytes` измеряет файлы документов в подкаталоге операции; дополнительные итоговые временные БД при объединении и добавлении заголовков в него не входят.

В измерениях выделяются загрузка таблиц локализации (`localization_load`), ожидание смещений, объединение, добавление метаданных набора и финальная проверка источников. Скорость ограничивается распределением размеров файлов, подготовкой работников, диском и последовательными действиями координатора; коэффициент ускорения заранее не фиксируется.

## Приёмочные результаты

Полная приёмка выполняется в `data/stage15/`. Контроль этапа 14 сохранён в `baseline_hashes.json` и `baseline/`. Сравнение нормализует только значение `set_id` в заголовке, затем проверяет хеш всех остальных байтов файлов.

Полные прогоны выполнены 2026-11-18 на Intel Core Ultra 9 275HX (24 логических процессора), с 64 ГиБ установленной памяти:

| Работники / режим | Полная сборка, с | Минуты и секунды | Пик дерева процессов, ГиБ |
| --- | ---: | ---: | ---: |
| `1 / reuse` | 2083,637 | 34:44 | 4,09 |
| `10 / reuse` | 500,060 | 8:20 | 21,34 |
| `10 / rebuild` | 510,998 | 8:31 | 20,92 |

Ускорение полной сборки `reuse` — **4,17 раза**. Все три результата побайтово одинаковы: 15 БД, 450 документов, 11 762 739 507 байт. По сравнению с этапом 14 изменился только `dataset.set_id`. Совпали игровые счётчики, диагностика, происхождение и локализация; сохранены хеши всех 1612 контрольных входов. В новом отчёте 15 файлов правил локализации классифицированы как конфигурация, но по-прежнему включены в финальную проверку.

Каждый документ проверен один раз. Правила подготовлены два раза при одном работнике и одиннадцать при десяти: координатор плюс каждый работник. В `reuse` координатор загрузил пять артефактов библиотек; работники загрузили ещё пять или пятьдесят соответственно. Число фактических применений шаблонов не изменилось.

| Измерение для полного `reuse`, с | 1 работник | 10 работников |
| --- | ---: | ---: |
| Загрузка библиотек координатором | 63,2 | 67,9 |
| Инициализация работников, сумма | 63,1 | 467,5 |
| Разбор / раскрытие / сериализация, сумма | 631,3 | 479,6 |
| Загрузка таблиц локализации, сумма | 9,2 | 92,0 |
| Проверка документов, сумма | 306,5 | 209,7 |
| Хеширование документов, сумма | 356,6 | 228,5 |
| Запись промежуточных JSON, сумма | 545,7 | 386,4 |
| Ожидание смещений истории, сумма | 14,6 | 676,0 |
| Потоковое объединение координатором | 27,0 | 26,0 |
| Добавление заголовков набора | 16,2 | 16,4 |

Суммы интервалов работников перекрываются во времени: их нельзя складывать и выдавать за длительность сборки или процессорное время. Например, БД событий подготовлена за 1444,0 с одним работником и за 191,7 с десятью. Разовая загрузка библиотек, ожидание ранних файлов и последовательное объединение уменьшают ускорение полного набора относительно этой наиболее объёмной БД.

Фиксированная выборка — 12 файлов технологий, компонентов и событий, 81 100 узлов, около 141,6 МиБ промежуточных JSON. Для неё выполнены три прохода на каждом пуле:

| Работники | Проход 1, с | Проход 2, с | Проход 3, с | Медиана, с |
| --- | ---: | ---: | ---: | ---: |
| 1 | 71,672 | 20,516 | 17,241 | 20,516 |
| 10 | 57,554 | 7,977 | 8,225 | 8,225 |

Все шесть результатов идентичны; отношение медиан — **2,49 раза**. Первый проход включает запуск и загрузку работников; следующие используют тот же пул. Время загрузки библиотек координатором, финальной проверки источников и локализации в этот отдельный замер не входит. Полные сборки выше покрывают эти действия. Инициализация одного работника выборки заняла 49,2 с; зарегистрированные в первом параллельном проходе инициализации занимали 45,5–47,4 с каждая и выполнялись одновременно.

Кеш диска ОС не сбрасывался. Прогоны выполнялись последовательно, без других приёмочных сборок, тяжёлых тестов и чтения полного набора фронтендом. По одному полному прогону на режим недостаточно, чтобы гарантировать постоянный коэффициент ускорения или значимость разницы между `reuse` и `rebuild`.

Память измерялась раз в секунду; в каждом полном прогоне на десяти процессах пропущен один неуспешный опрос. Это не ошибка сборки. Максимум учтённых промежуточных документов — 8,74 ГиБ; временные итоговые БД и копирование заголовков требуют дополнительного места и в этот показатель не включены.

Прошли 240 тестов бэкэнда и 33 проверки фронтенда без пропусков, включая опубликованный набор. Каталоги совпали с этапом 14: 679 технологий, 1506 компонентов, 498 зданий; связи, свидетельства улучшений и прежние 214 предупреждений об отсутствующей локализации сохранены. Игра не запускалась: игровые файлы не менялись, проверка в игре для этого этапа не требуется.

Основные материалы в `data/stage15/`: `acceptance_summary.json`, `one_worker/acceptance.json`, `ten_workers/acceptance.json`, `rebuilt/acceptance.json`, `benchmark/acceptance.json`, `tests_complete.log`, `frontend_tests.log`, `frontend_acceptance.json` и `documentation_check.json`. Опубликованный набор находится в `data/databases/`; основные отчёты соответствуют заключительной полной сборке `rebuild`, отдельные замеры сохранены под `stage15/`.

## Модули

| Модуль | Ответственность |
| --- | --- |
| `parallel/settings.py` | Настройки и ограничения путей |
| `parallel/pool.py` | Пул, ограниченная выдача заданий и владение временным каталогом |
| `parallel/worker.py` | Инициализация процесса и цикл документа |
| `parallel/ordering.py` | Сквозная нумерация раскрытий и отмена ожидания |
| `parallel/localization.py` | Переиспользование таблиц без переноса состояния задания |
| `parallel/text_cache.py` | Переиспользование раскрытых текстов с точным списком источников |
| `parallel/results.py` | Приращения отчётов и межфайловые ограничения |
| `parallel/memory.py` | Выборочные измерения дерева процессов |
| `database/collection.py` | Общая обработка исходного документа |
| `database/streaming.py` | Хеши, промежуточный JSON и потоковое объединение |

Схемы генерируются из `schema_generation/`; добавлена схема конфигурации параллелизма. Старый последовательный `DocumentWriter` заменён общим механизмом промежуточных документов и объединения.
