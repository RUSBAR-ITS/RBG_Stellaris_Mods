## Статус и границы

Зафиксированы решения обсуждения от 2026-11-19: расчёт родителей и детей на бэкенде по существующим БД, результаты для именованных комбинаций, отдельная расширяемая конфигурация правил и объект как единица будущего хранения в MongoDB. Это согласованный подход, а не утверждённое ТЗ программной реализации. Приведённые имена новых полей и будущего файла конфигурации иллюстрируют контракт; окончательная схема определяется в ТЗ.

Основа критериев — [полный аналитический прогон](frontend/CHAIN_RULES_FULL_REVIEW_RU.md). Анализ способов открытия технологий событиями отложен; уже согласованные функциональные свидетельства, включая вооружение, этим не отменяются. Алгоритм сетки и вычисление `location` ещё проектируются.

## Место расчёта

- Выбор `parent_tech` и формирование `children` выполняет самостоятельный модуль Python, относящийся к обогащению БД.
- Вход — текущий подготовленный набор БД, параметры комбинации и настройки правил. Связанные БД нужны для критериев улучшений, назначения, производства и лимитов.
- Операция использует сохранённые данные и не запускает парсер или повторный сбор из игры. Исходные определения и полный граф `prerequisites` сохраняются.
- Фронтенд использует результат; при необходимости пересчёта обращается к операции бэкенда. Вычисление одинаковых правил на двух языках программирования не требуется.

## Расширяемая конфигурация правил

Правила обогащения выносятся в отдельную конфигурацию. Предлагаемое размещение — `config/enrichment/technology_tree.json`, с возможностью выделять переиспользуемые группы в соседние файлы при росте объёма.

Конфигурация описывает идентификаторы правил, порядок применения, включённость, параметры и используемые соответствия. Например, сюда относятся глубина косвенного поиска, поля и виды связанных объектов, функциональные группы, соответствия производственных модификаторов и лимитов. Профиль комбинации передаёт известные факты империи; его не нужно повторять в каждом правиле.

Предлагаемый компактный формат записи правил, показанный на двух критериях, а не как полный рабочий набор:

```json
{
  "rules": [
    {"id": "same_area", "enabled": true, "parameters": {}},
    {"id": "indirect_affinity", "enabled": true, "parameters": {"depth": 1}}
  ]
}
```

Порядок элементов массива задаёт порядок применения. Python содержит реализацию поддержанных типов критериев и общий механизм их вызова. Изменение порядка, параметров и соответствий выполняется в конфигурации; принципиально новый вид вычисления потребует отдельного обработчика. Неизвестное правило диагностируется, а не молча игнорируется. Конфигурация не превращается в реестр всех команд языка игры.

Сохраняются согласованные ограничения отбора: кандидаты — непосредственные технологические пререквизиты; при единственном кандидате отбор завершается; пустой результат правила пропускается; ранее исключённые кандидаты не возвращаются. Эти ограничения не подменяются отдельными исключениями для конкретных пар технологий.

## Комбинации и результат у объекта

Первая комбинация — справочник (`reference`). Общая запись комбинации хранит её идентификатор, режим, профиль империи, выбранные варианты технологий, использованные настройки и ревизию правил, а также идентификацию входных данных. Название режима само по себе не определяет конкретный результат.

У каждой технологии сохраняется её результат для соответствующей комбинации. Схематический фрагмент обогащения объекта:

```json
{
  "technology_tree": {
    "reference_default": {
      "parent_tech": "tech_a",
      "children": ["tech_c"],
      "status": "resolved"
    }
  }
}
```

Общие параметры комбинации хранятся один раз; объекты ссылаются на неё по идентификатору. `status` различает корень без требований, выбранного родителя и неразрешённую неоднозначность. Последняя сохраняется в диагностике со снимком состояния, согласно [согласованным правилам](frontend/CHAIN_AMBIGUITIES_RU.md).

Выбор варианта может менять родителя технологии и списки детей других технологий. Поэтому параметры комбинации описывают выбранные представления поля целиком. Расчёт выполняется для запрошенных комбинаций, без предварительного перебора всех возможных сочетаний вариантов.

Структура связей не зависит от языка. Алфавитный порядок детей и координаты относятся к последующей раскладке и могут зависеть от RU/EN; структурный порядок массива `children` сам по себе не задаёт визуальный порядок.

## Формирование связей

Объекты технологий уже доступны по ID до начала выбора родителей. Для нового расчёта комбинации подготавливаются пустые списки детей. Затем для каждой технологии:

1. Выбирается родитель по настроенной последовательности критериев.
2. Его ID записывается в `parent_tech` технологии.
3. ID технологии сразу добавляется в `children` выбранного родителя, без дублей. Существующий список дополняется.

Родителю необязательно уже иметь рассчитанного собственного родителя. При его последующей обработке накопленные дети сохраняются. При отсутствии выбранного родителя обратная связь не добавляется. Дополнительного прохода по всем технологиям для построения списков детей не требуется.

При пересчёте комбинации формируется новый согласованный результат вместо накопления устаревших связей. После завершения проверяется соответствие обеих сторон связей и отсутствие циклов. Неоднозначности не разрешаются произвольным выбором.

## Актуальность и вызов из фронтенда

Разделяются идентификация исходного набора и ревизия вычисляемого обогащения. Изменение комбинации не должно требовать повторного сбора или перепубликации остальных больших БД. При этом изменение исходных объектов или правил должно делать прежний результат неприменимым. Собственные выходные поля обогащения не должны создавать ложную смену его входных данных.

Это требует изменения текущего контракта идентификации набора: сейчас он основан на содержимом подготовленных файлов, а отдельное обогащение участника набора запрещено существующей операцией локализации. Точный формат раздельных ревизий и безопасного сохранения должен быть определён в ТЗ.

Для обращения браузерного фронтенда к Python требуется локальный API и сопоставление открытого набора с набором, доступным бэкенду. Самостоятельная функция расчёта должна работать независимо от транспорта. Запуск приложения и обновление страницы не запускают генерацию БД; перерасчёт связей является отдельной операцией по запросу.

## Будущая модель хранения

Пользователь определил будущую единицу документа MongoDB: **один игровой объект** — одна технология, здание, компонент и т. п. Это направление развития, не задача текущей реализации.

- Вычисляемые связи относятся к объекту; списки детей и родитель содержат идентификаторы, без вложенных копий поддеревьев.
- Идентичность объекта учитывает его вид и ID; одинаковые ID разных видов не объединяются.
- Варианты технологии остаются представлениями её базового объекта, а результаты комбинаций принадлежат этому объекту.
- Общие описания комбинаций и сведения о наборе остаются служебными данными, без дублирования полного контекста в каждой технологии.

Текущие JSON сохраняют существующий способ хранения исходного дерева. Сейчас не вводятся MongoDB, контейнер, миграция, файл на каждый объект или отдельный универсальный слой хранилища.
