## Назначение и статус

Документ фиксирует результаты последовательного разбора текстовых элементов языка Stellaris: пользователь предлагает трактовку, она проверяется по исходникам, после согласования добавляется сюда. Для каждой принятой группы сохраняются её назначение, правило распознавания, примеры и основания проверки.

Сейчас согласованы **логические значения** `yes`/`no`, **ключевое слово `id`** для указания идентификатора, **логические операторы** `AND`, `OR`, `NOT`, `NAND`, `NOR` и временное представление содержимого **`inline_script` как непрозрачного скалярного значения**. Остальные элементы частотного списка в рамках этого разбора ещё не классифицированы. Новые выводы добавляются по мере проверки и согласования в обе языковые версии документа.

Это справочный документ с согласованными решениями. Запись правила здесь не означает, что оно уже реализовано в парсере или его конфигурации.

## Логические значения

**Статус:** согласовано пользователем 2026-11-15. **Класс:** логическое значение (`boolean`).

| Запись в Stellaris | Значение | Соответствие в JSON | Вхождений в проверенном корпусе |
| --- | --- | --- | ---: |
| `yes` | Истина, да | `true` | 76 437 |
| `no` | Ложь, нет | `false` | 30 092 |

Правило относится к отдельному значению без кавычек, целиком совпадающему с `yes` или `no` в указанном регистре. Логические значения не являются операторами или именами команд.

Границы правила:

- Не распространяется на части идентификаторов, строк или подстановок. Например, наличие `no` внутри `no_name` не делает идентификатор логическим значением.
- Не предписывает преобразовывать строки `"yes"` и `"no"` в логические значения. В проверенных вхождениях таких строк не найдено.
- Не устанавливает поведение вариантов другого регистра, например `YES` или `No`.
- Определяет класс значения, а не смысл всей команды. Конкретная операция и допустимость значения зависят от контекста.

Примеры формы:

```text
is_ai = yes
is_ai = no
clear_deposits = yes
```

Первые две записи проверяют условие с ожидаемым логическим результатом. Третья вызывает эффект. Классификация `yes` как логического значения сама по себе не превращает вызов эффекта в условие и не задаёт поведение этого эффекта при `no`.

Соответствие `true`/`false` в таблице поясняет значение. Оно не означает изменения текущего формата дерева парсера или БД.

## Ключевое слово id — идентификатор

**Статус:** согласовано пользователем 2026-11-15. **Класс:** ключевое слово — поле идентификатора.

**`id` (identifier) задаёт или указывает идентификатор объекта либо группы.** Идентификатор служит для обозначения записи, ссылки на неё или сопоставления записей между собой. Это общее назначение слова; отдельные разновидности `id` по типам объектов в нашем списке не выделяются.

Общая форма:

```text
id = identifier
```

`identifier` в этом образце — место для значения. Само ключевое слово `id` находится слева от `=`, справа записывается одно скалярное значение: число или текст, в том числе в кавычках и с подстановками. Блоков, списков и формул справа в проверенном корпусе нет. Для нашего списка написания `id` и `ID` объединены в одну запись `id`.

Примеры из исходников:

```text
id = 1
id = achievement.1
id = "crisis_8156.trigger.1"
id = $EVENT_ID$
id = fotd.patrol.1.$TIER$@root
```

При определении события `id` задаёт его идентификатор, а при вызове указывает идентификатор запускаемого события. Документация аур также использует `id` для общей группы: среди аур с одинаковым идентификатором применяется аура с наибольшим приоритетом. Поэтому идентификатор может использоваться и для группировки; глобальная уникальность каждого значения не подразумевается.

## Логические операторы

**Статус:** базовое правило согласовано пользователем 2026-11-15. **Класс:** именованный логический оператор.

| Оператор | Назначение | Логических блоков в проверенном корпусе |
| --- | --- | ---: |
| `AND` | Логическое И: выполнение всех условий | 2 869 |
| `OR` | Логическое ИЛИ: выполнение хотя бы одного условия | 11 647 |
| `NOT` | Логическое отрицание | 16 232 |
| `NAND` | Отрицание И: не все условия выполнены | 339 |
| `NOR` | Отрицание ИЛИ: ни одно условие не выполнено | 4 939 |

Базовая форма — имя оператора слева от `=`, справа блок `{ … }`. Для распознавания пяти имён регистр не учитывается; исходное написание сохраняется. Это именованные конструкции над уже разобранной структурой, а не новые знаки лексического уровня наряду с `=`, `>` и другими.

Правило распознавания и сохранения:

1. Сначала учитывать границы строк, комментариев и непрозрачного значения `inline_script`. Внутри них логические операторы не выделять.
2. В доступной для разбора структуре распознавать отдельное имя без кавычек `AND`, `OR`, `NOT`, `NAND` или `NOR`, оператор `=` и блок справа.
3. Сохранять порядок и повторения дочерних записей. Содержимое может включать выражения, отдельные идентификаторы и вложенные логические блоки; не требовать `ключ = значение` у каждого элемента.
4. Не ограничивать `NOT` одной дочерней записью. В исходниках встречаются блоки с несколькими записями; структурный разбор должен сохранять их целиком.
5. Не вычислять истинность условий и не упрощать выражения. Количество и вид элементов не меняют класс распознанного логического блока.

Пример списка идентификаторов внутри логического блока — `common/technology/00_biogenesis_tech.txt:794`:

```text
prerequisites = {
    tech_stingers
    OR = {
        tech_mauler_growth_1
        tech_stinger_growth_1
        tech_weaver_growth_1
        tech_harbinger_growth_1
    }
}
```

Пример нескольких записей внутри `NOT` — `common/anomalies/01_anomaly_categories.txt:676`:

```text
NOT = {
    has_technology = tech_lasers_3
    has_technology = tech_lasers_4
    has_technology = tech_lasers_5
}
```

`localization = AND`, строка `"AND"` и подстановка `$AND$` не соответствуют форме логического блока. Написание `NOT` внутри непрозрачного `inline_script` на этом этапе вообще не классифицируется. Форма `NOT = tech_mauler_growth_1` как сокращённая логическая операция не подтверждена проверенными исходниками и в базовое правило не включена; отсутствие примера не устанавливает запрет движка.

Числа в таблице относятся к исходному исследованию `common/` и `events/`, без раскрытия вставок и без пересчёта частотного списка. Всего проверено 36 028 отдельных вхождений пяти имён: 36 026 логических блоков, одно значение `localization = AND` и один параметр `NOT = xenophile` внутри `inline_script`. Содержимое строк не считалось отдельными внешними узлами. Подробности: [logical_operators_audit.json](../../TMP/WEB_STTV/text_frequency/logical_operators_audit.json).

## Inline_script — непрозрачное значение

**Статус:** временное правило согласовано пользователем 2026-11-15. **Класс содержимого на текущем этапе:** непрозрачное скалярное значение.

Одинаково рассматриваются обе формы:

```text
inline_script = paragon/council_weight_mult
```

```text
inline_script = {
    script = paragon/ethic_weight_mult
    IS = xenophobe
    NOT = xenophile
}
```

Всё значение справа от `=` считается одной неделимой величиной: и обычная ссылка на скрипт, и блок с фигурными скобками. Блочная запись не становится исключением: её внутренние записи на этом этапе не разбираются и не классифицируются.

По последующему уточнению пользователя это значение передаётся **отдельной функции разворота `inline_script`**. Пока функция является заглушкой и возвращает пустой результат: весь вызов пропускается, в итоговом дереве не остаётся ни ссылки, ни блока, ни непрозрачного скаляра. Непрозрачное значение используется только как вход обработчика; исходный текст и координаты пропуска сохраняются отдельно от дерева.

- Сохранять исходное значение целиком, включая кавычки, скобки, строки и координаты источника. Игнорирование содержимого не означает его удаления.
- Определять только внешние границы значения, необходимые для продолжения разбора соседних записей. Скобки внутри строк и комментариев не должны завершать значение.
- Не выделять внутри него поля, параметры, логические операторы или код в строках. Не выполнять подстановки.
- Не раскрывать обычную ссылку и не загружать по ней шаблон; также не раскрывать ссылку, записанную внутри блока.
- Правила работы с содержимым `inline_script` будут определяться отдельно на следующем этапе.

Настройки пяти логических операторов находятся в отдельном `config/parser/logical_operators.json`. Модель узлов, подключение конфига, функция-заглушка и проверки описаны в [реализованном ТЗ четвёртого этапа](TZ_BACKEND_STAGE_4_RU.md).

Реализация завершена: логические блоки представлены узлами `LogicalOperation`, обе формы `inline_script` пропускаются через `expand_inline_script`. `InlineScriptValue` существует только на входе функции. Исходные токены и `Document.skipped_inline_scripts` сохраняют текст и координаты пропусков. Проверены 36 026 логических узлов и 6 885 вызовов; в третьем частотном проходе эти конструкции исключены из статистики. [Интерфейс и ограничения](BACKEND_STAGE_4_RU.md).

## Основания и границы проверки

Исходная база — ванильные `.txt` в `common/` и `events/` установленной Stellaris v4.5.4, исследованные 2026-11-15. Охват и исключённые файлы описаны в [частотной статистике](RESEARCH_TEXT_FREQUENCY_RU.md). Числа для `yes`/`no` относятся к первому проходу с сохранением регистра; статистика `id` объединяет регистр. Текущий [frequencies.txt](../data/text_frequency/frequencies.txt) исключает `yes`/`no`, элементы с частотой 1, распознанные логические операторы и полные вызовы `inline_script`. В четвёртом частотном проходе также исключены переменные `@name` и подстановки `$NAME$`; точные границы фильтра приведены в частотном исследовании. Фильтрация отчёта не расширяет границы проверенных здесь правил классификации.

При отдельной проверке контекста всех **106 529** вхождений `yes` и `no` установлено:

- Все они находятся справа от оператора как отдельные значения без кавычек.
- Использований как имён слева от оператора или самостоятельных элементов списков не найдено.
- Все файлы с учитываемыми вхождениями успешно разобраны; суммы совпали с частотной статистикой. Контрольные суммы исходных файлов совпали с манифестом прогона.
- Контрпримеров принятой трактовке в исследованном корпусе не обнаружено.

При проверке всех **20 358** отдельных вхождений `id` без учёта регистра в **428** файлах установлено:

- Все вхождения находятся слева от `=`, без кавычек; справа всегда один узел `Scalar`. Вхождений `id` справа или отдельным элементом списка нет.
- Найдены 20 357 написаний `id` и одно `ID`. Значение справа заключено в кавычки в 143 случаях, содержит параметр подстановки в 53 случаях.
- Все файлы с учитываемыми вхождениями успешно разобраны; сумма совпала с частотным отчётом. Хеши всех 2 238 файлов исходного манифеста совпали с предыдущим прогоном.
- Подробности сохранены в исследовательском отчёте [id_context_audit.json](../../TMP/WEB_STTV/text_frequency/id_context_audit.json).
