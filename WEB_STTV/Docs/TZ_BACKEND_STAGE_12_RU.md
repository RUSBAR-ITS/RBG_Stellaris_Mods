## 1. Статус и границы

ТЗ утверждено пользователем 2026-11-18; реализация и приёмочные проверки завершены. Полный набор собран и открыт в браузере; результаты приведены в [руководстве этапа](BACKEND_STAGE_12_RU.md). Пользователь согласовал 12 дополнительных БД, их RU/EN-локализацию и открытие полного набора во фронтенде. Дополнительно потребовал сохранять JSON с переносами строк.

Результат этапа — набор из 15 БД: существующие технологии, компоненты и планетарные здания плюс источники из раздела 2. Каждая БД сохраняет результат универсального парсера и обогащения. Новые правила выбора технологической цепочки, вычисление игровых условий и выполнение событий в этот этап не входят. Извлечение подробного графа поведения по ссылкам проектируется отдельно; сами ссылки и определения сохраняются уже сейчас.

Бэкэнд и фронтенд используют общий контракт набора; изменения интерфейса описаны в [ТЗ фронтенда, этап 3](frontend/TZ_FRONTEND_STAGE_3_RU.md). Обратная совместимость с набором из трёх файлов не требуется.

## 2. Состав и источники

Существующие `technologies`, `components`, `buildings` и их переменные сохраняются. Для каждой новой БД добавить переменную в `global_variables.json`; значения относительны к `STELLARIS_ROOT`.

| `dataset.kind` / имя JSON | Переменная | Каталог | TXT в исследованной установке |
| --- | --- | --- | ---: |
| `megastructures` | `MEGASTRUCTURES_DIR` | `common/megastructures` | 30 |
| `ship_sizes` | `SHIP_SIZES_DIR` | `common/ship_sizes` | 40 |
| `starbase_levels` | `STARBASE_LEVELS_DIR` | `common/starbase_levels` | 8 |
| `starbase_modules` | `STARBASE_MODULES_DIR` | `common/starbase_modules` | 10 |
| `starbase_buildings` | `STARBASE_BUILDINGS_DIR` | `common/starbase_buildings` | 4 |
| `terraform` | `TERRAFORM_DIR` | `common/terraform` | 3 |
| `deposits` | `DEPOSITS_DIR` | `common/deposits` | 26 |
| `pop_jobs` | `POP_JOBS_DIR` | `common/pop_jobs` | 22 |
| `economic_categories` | `ECONOMIC_CATEGORIES_DIR` | `common/economic_categories` | 8 |
| `scripted_actions` | `SCRIPTED_ACTIONS_DIR` | `common/scripted_actions` | 6 |
| `on_actions` | `ON_ACTIONS_DIR` | `common/on_actions` | 4 |
| `events` | `EVENTS_DIR` | `events` | 171 |

Всего исследовано 332 TXT. Это число физических файлов, включая пустые и документационные; оно не является числом объектов или константой программы. Результат первичного синтаксического исследования без раскрытия вызовов: `data/stage12/specification_research/source_inventory.json`.

По умолчанию для каждого вида: `*.txt`, рекурсивно, `utf-8-sig`; параметры настраиваемые. Выходы относительно `WORK_DIR`: `databases/<kind>.json`, `reports/<kind>_build.json`, `reports/<kind>_localization.json`; общий отчёт — `reports/database_set.json`. Сводный отчёт не является шестнадцатой БД.

Источники игры и Workshop только читаются. Копирование игровых каталогов не требуется. Общие библиотеки inline/scripts/variables продолжают использоваться существующим механизмом и не становятся дополнительными самостоятельными БД. `starbase_types` и другие не перечисленные каталоги не добавляются.

## 3. Конфигурация и формат

Расширить существующий координатор набора. Перечень поддерживаемых ролей вынести в общий небольшой `config/datasets.json`, используемый бэкэндом, генератором схем и фронтендом; не размножать списки из 15 строк в коде. Источники и выходы остаются в `config/backend.json`, правила локализации — в `config/enrichment/localization.json`.

Настраиваемые правила выбора объектов, полей ID и ключей локализации разделить по видам. Не создавать отдельные сборщики для каждого каталога. Если конфиг становится громоздким, разделить правила по файлам с явными ссылками; не разрабатывать универсальный язык исполнения произвольного кода из JSON.

Формат БД — `sttv.parse_database`, новая версия `6`: расширяются роли и допустимые цели локализации. В каждой БД сохраняется `dataset = {kind, set_id}`. Все 15 файлов имеют одинаковый `set_id`, рассчитанный по содержимому всех участников без корневого `dataset`, как на этапе 11. Имена файлов не определяют роли. Схемы обновляются через код генератора; проверяется точное совпадение состава набора с конфигурацией.

Полное дерево `documents` остаётся основой БД. Не вводить обязательную предметную схему игровых команд и не удалять неизвестные поля. Локализация добавляется к соответствующим узлам отдельно от игрового дерева.

## 4. Разбор и идентичность

Использовать существующий порядок раскрытия inline-вставок, scripted effects/triggers, script values и статических переменных. Сохранять порядок, повторяемые конструкции, условия, области видимости, происхождение и метаданные. Каждый документ разбирается со своим контекстом.

| Вид определения | Идентичность |
| --- | --- |
| Именованные корневые блоки новых каталогов | Ключ корневого определения в пространстве соответствующей БД |
| Событие | Прямое поле `id`; тип блока (`country_event` и другие) хранится отдельно |
| `terraform_link` | Адрес определения в конкретной БД; `from` и `to` — свойства перехода, а не уникальный ID |
| `on_actions` | Имя обработчика и адрес каждого фрагмента его определения |

Настроенный список корневых типов событий не включает `namespace`, переменные или вложенные вызовы событий. Повтор одного типа события допустим; настоящий повтор игрового `id` диагностируется. Для именованных одиночных объектов сохраняется проверка дублей ID в своём виде. Одинаковые ID разных БД не конфликтуют.

Повторяемые `terraform_link`, включая одинаковые пары `from`/`to` с разными условиями, сохраняются все. Не придумывать им игровые ID и не объединять по паре классов планет. Повторные фрагменты `on_actions` сохраняются отдельно; не выбирать первый и не объявлять их отдельными событиями. Исходное дерево не преобразуется в словарь, теряющий повторы.

Корневые определения не должны ошибочно раскрываться как вызовы одноимённых scripted effects/triggers. При необходимости расширить конфигурацию границы «определение / тело», сохраняя раскрытие реальных вызовов внутри определений.

Ссылки из действия в `on_action` и из него в событие остаются ссылками. Не подставлять тело события вместо вызова: это меняет смысл отложенного исполнения, условий и областей видимости. Парсер сохраняет эти данные для последующего анализа.

## 5. Локализация

Обогащение выполняется после раскрытия. RU: `RU_LOC_TIER_1` → 2 → 3; EN: `EN_LOC_TIER_1`. Сохраняются исходная строка, раскрытый статический текст, запрошенный и найденный ключи, происхождение и неразрешённые ссылки. Динамические подстановки и игровая разметка остаются в тексте. Пустая строка не равна отсутствующей; язык не подменяется другим.

Базовые правила новых целей:

| БД | Название | Описание и дополнительные цели |
| --- | --- | --- |
| `megastructures` | `<id>` | `<id>_DESC` |
| `ship_sizes` | `<id>` | Только явно заданный ключ описания, если он присутствует; обязательный суффикс не выдумывается |
| `starbase_levels` | Значение прямого `ship_size` как ключ названия корпуса | Не создавать фиктивное описание уровня |
| `starbase_modules`, `starbase_buildings` | `sm_<id>` | `sm_<id>_desc` |
| `deposits` | `<id>` | `<id>_desc` |
| `pop_jobs` | `job_<id>` | `job_<id>_desc` |
| `economic_categories` | `<id>` | Только явно заданное описание, если оно есть; служебные категории могут не иметь текста |
| `terraform` | Локализация значений `from` и `to` на соответствующих присваиваниях | Для конечных классов — `<class>_desc`; собственного названия/описания переходу не сочинять |
| `scripted_actions` | Прямой `context_menu_name` | `tooltip` как описание; `activity_key` локализуется отдельно на своём присваивании |
| `on_actions` | Только явно заданные текстовые поля по правилу | У служебного обработчика название и описание могут отсутствовать полностью |
| `events` | Прямой `title` | Прямые `desc` и их текстовые варианты; не строить ключи из ID события |

Эти различия подтверждены установленными исходниками: `ring_world_1_DESC`, `sm_detection_array`, `job_foundry`, `starbase_level_outpost.ship_size = starbase_outpost`, `context_menu_name`/`tooltip` у действий. Префиксы, суффиксы и поля задаются конфигурацией. Неподдержанная форма текстового поля получает диагностику с координатами, а не произвольное преобразование.

У события сохранить все описания: повторные скалярные `desc`, блоки с `text`, вложенные текстовые варианты и их исходные условия/порядок. Локализовать только объявленные текстовые позиции внутри структуры описания; не обходить произвольные поля `text` всего события. Не выбирать первый вариант действующим и не вычислять условия. Отсутствие `title`/`desc` у скрытого служебного события допустимо. Локализация кнопок вариантов события и всех произвольных сообщений внутри эффектов не входит в этот этап.

Схема обогащений допускает цели с `name`, с `description` или с обоими полями; пустой объект языка не создаётся. Для каждой выбранной роли сохраняются оба языка, включая запись об отсутствии искомого ключа. Если текстовая роль у определения вообще не предусмотрена, поле отсутствует: это не ошибка отсутствующего перевода. Служебная БД с нулём целей локализации успешно сохраняется и получает отчёт с нулевым количеством целей.

Старые правила технологий, вариантов, компонентов и зданий сохраняются. Условные тексты привязаны к собственным узлам; их адреса и источник ключа проверяются. Обогащение не добавляет человеку читаемые переводы вручную и не исправляет игровые локализации.

## 6. Сборка и сохранение JSON

Одна явная команда `python -m sttv.database_sets` подготавливает весь набор. Временные результаты и отчёты размещаются в `WORK_DIR`. Обработка БД последовательная; все 15 полных деревьев одновременно в памяти не удерживаются. Допустимо переиспользование неизменяемых индексов библиотек и локализации без смешивания контекстов.

До публикации проверяются все результаты, схемы, происхождение и неизменность прочитанных входов. Ошибка подготовки любого участника сохраняет прежние опубликованные БД. Частичная БД с пропущенными ошибочными документами не публикуется как полная. Публикация отдельных файлов атомарна; весь набор не объявляется одной атомарной операцией. При сбое между заменами отчёт фиксирует фактически записанные файлы, а различие `set_id` блокирует открытие смешанного набора.

Все создаваемые этим этапом JSON БД и отчётов сохраняются в UTF-8 без BOM, с отступами в два пробела, переносами LF, завершающим переводом строки и читаемым Unicode (`ensure_ascii=False`). После добавления `dataset` весь файл, включая эту метку, остаётся форматированным. Не использовать текущую вставку компактного префикса в итоговый файл.

Каноническая компактная сериализация с сортировкой ключей остаётся только внутренним способом вычисления хеша. Пробелы и переносы итогового файла не меняют `set_id`, если данные не менялись. Для воспроизводимости порядок ключей итогового JSON фиксирован, порядок массивов исходного дерева сохраняется. Не переформатировать архивные результаты прошлых этапов и посторонние JSON репозитория.

## 7. Известные препятствия

Первичный синтаксический разбор 332 TXT в текущем исследовании успешен, но это не полный прогон раскрытия. В историческом `data/stage9/corpus_report.json` у выбранных источников были семь проблемных документов:

| Источник | Зафиксированная причина |
| --- | --- |
| `common/pop_jobs/06_event_jobs.txt` | `invalid_script_value_arguments` |
| `events/ancient_relics_arcsite_events_2.txt` | `unsupported_scripted_call` |
| `events/first_contact_dlc_operations_events.txt` | Не передан `bonus` |
| `events/grand_archive_events.txt` | Не передан `RELIC` |
| `events/leviathans_events_1.txt` | Не передан `RELIC` |
| `events/nomads_origin_events.txt` | Не передан `RANDOM` |
| `events/shroud_events.txt` | `ambiguous_static_environment` |

**Повторная проверка 2026-11-18:** все семь файлов текущим парсером снова завершились теми же ошибками. Подтверждены шесть разных причин, поскольку `RELIC` общий для двух файлов. Для Покрова дополнительная проверка трёх значений `TIER` выявила ограничение нашего обработчика контекстов при доступной глобальной переменной. Подробности и артефакты — в [отчёте повторной проверки](RESEARCH_STAGE_12_BLOCKERS_RU.md). Разбор останавливался на первой ошибке каждого документа; другие потенциальные ошибки за ней этим прогоном не исключены.

**Уточнение пользователя после проверки:** согласованы регистронезависимые имена параметров и условные исключения для `06_event_jobs.txt`, `grand_archive_events.txt`, `leviathans_events_1.txt`, `nomads_origin_events.txt`, включая временный `RANDOM = 0`. Подготовлен отдельный [source_exceptions.json](../config/parser/source_exceptions.json); его подключение, условия и журналирование описаны в [дополнении к импорту](SOURCE_IMPORT_EXCEPTIONS_RU.md). Файл подключён через `parser.source_exceptions`. Указанные преобразования выполняются только в памяти, с сохранением исходных данных и происхождения.

В дополнении отдельно предложены снятие ограничения на структурное раскрытие `effect = no` с сохранением исходного вызова и разрешение составной статической переменной при совпадающем объявлении во всех контекстах. Оба изменения приняты при утверждении этапа и реализованы; структурное раскрытие не утверждает игровую семантику `no`.

Исследование и диагностика входят в этап; дополнительные произвольные аргументы, скрытое исключение файлов и изменения установленной игры запрещены. Изменения за пределами согласованных правил требуют отдельного решения. Незакрытый блокер полного набора указывается как незавершённый результат, а не успешная приёмка. Задача `VANILLA-002` о `RELIC` уже есть в общем TO_DO; исключение импорта не исправляет установленную игру.

## 8. Проверки и приёмка

1. Проверить 15 ролей, переменные и безопасные выходы; отсутствие, повтор и неизвестную роль. Список ролей согласован с фронтендом и сгенерированными схемами.
2. На небольших данных проверить новые формы определений, события с одинаковым типом и разными ID, настоящие дубли ID, повторные переходы и фрагменты обработчиков. Все игровые узлы и порядок сохраняются.
3. Проверить штатные раскрытия внутри новых определений и отсутствие раскрытия событий как текстовых вставок. Выполнить проверки исключений, регистра и согласованных изменений по [дополнению к импорту](SOURCE_IMPORT_EXCEPTIONS_RU.md#проверки), затем повторить семь полных проблемных файлов.
4. Проверить каждый способ построения ключей, приоритеты RU/EN, цели только с названием/описанием, скрытые события, нулевые цели, отсутствующие/пустые строки и все условные описания без выбора активного.
5. Проверить форматирование всех 15 JSON, в том числе `dataset`; повторный разбор даёт те же данные. Повторная сборка неизменных источников побайтно воспроизводима; изменение одного участника меняет общий `set_id`.
6. Проверить сбой подготовки позднего участника, изменение входа и сбой публикации между файлами: без ложного полного успеха и без потери фактической диагностики.
7. Полный успешный прогон всех 15 БД должен содержать размеры, время, количество документов/объектов/целей, предупреждения и хеши прочитанных входов. Исходники остаются неизменны. Размеры форматированных файлов используются для проверки фронтенда; заранее не заявлять, что весь набор помещается в память браузера.
8. Сборка нового полного набора и его открытие по ТЗ фронтенда обязательны для завершения этапа. Если мешают подтверждённые ошибки источников или пределы памяти, зафиксировать конкретный блокер и согласовать необходимое решение.
9. Обновить руководства запуска, README, changelog RU/EN; сохранить модульность, DRY и ограничения размеров файлов из общего ТЗ. Документационные изменения не выдавать за реализацию. Запуск Stellaris для проверки JSON не требуется.
