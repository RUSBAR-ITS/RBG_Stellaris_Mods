## Результат этапа

**Историческое руководство.** Описывает реализацию до перехода на базу деревьев. Текущий запуск и формат: [шестой этап](BACKEND_STAGE_6_RU.md).

Реализован утверждённый [первый этап](TZ_RU.md#3-первый-этап-бэкэнда--сборка-бд): самостоятельный сборщик JSON-базы на Python. Он читает технологии, категории, уровни и названия RU/EN из выбранных каталогов, проверяет [модель БД](DATABASE_MODEL_RU.md), сохраняет базу и отдельный отчёт.

Сборщик не изменяет источники. Разбор и преобразование выполняются в памяти; исходные файлы и промежуточное дерево разбора в рабочую папку не копируются. Исследовательский аудит не является входом сборщика.

## Подготовка окружения

Команды ниже выполняются в PowerShell из каталога `WEB_STTV`. Проверенное окружение: Windows, Python **3.14.6**, `jsonschema==4.26.0`. Для этой стадии требуется установленный Python; portable-сборка относится к следующим этапам.

Зависимость закреплена в [requirements.txt](../src/backend/requirements.txt). Используется проверка JSON Schema Draft 2020-12 из библиотеки [jsonschema](https://pypi.org/project/jsonschema/); описание API — в [официальной документации](https://python-jsonschema.readthedocs.io/en/stable/validate/).

Подготовка окружения внутри рабочей папки по умолчанию:

```powershell
New-Item -ItemType Directory -Force data/tmp | Out-Null
$env:TEMP = (Resolve-Path data/tmp).Path
$env:TMP = $env:TEMP
python -m venv data/.venv
./data/.venv/Scripts/python.exe -B -m pip install --no-cache-dir --disable-pip-version-check -r src/backend/requirements.txt
```

В текущем рабочем каталоге окружение уже подготовлено. Изменение `WORK_DIR` меняет папку результатов сборщика, но не переносит созданное окружение Python.

## Запуск и перестроение

Обычный запуск:

```powershell
./data/.venv/Scripts/python.exe -B src/backend/main.py
```

Каждый запуск заново читает источники и полностью перестраивает БД. После изменения каталогов или приоритетов достаточно повторить команду. Старая база не используется для заполнения недостающих данных.

Можно явно передать другие файлы конфигурации:

```powershell
./data/.venv/Scripts/python.exe -B src/backend/main.py --variables global_variables.json --config config/backend.json
```

Конфигурация по умолчанию и относительный `WORK_DIR` привязаны к каталогу продукта, а не к текущему каталогу терминала. Относительные аргументы `--variables` и `--config` разрешаются обычным способом относительно терминала.

Командная строка возвращает код **0** при успехе и **1** при ошибке сборки. Полный JSON-отчёт выводится в stdout при успехе и в stderr при ошибке. Ошибки синтаксиса аргументов обрабатывает `argparse` с кодом 2.

Для будущего вызова из служебной части предусмотрена функция `sttv.builder.build(variables_path, config_path)`: два пути к конфигурации на входе, словарь отчёта на выходе. Она не зависит от командной строки или интерфейса. Для проверки готовой базы без источников используется `sttv.database.validation.validate_database(database, registry)`; она возвращается без результата при успехе и выдаёт `BuildError` при нарушении модели.

## Настройки и результаты

| Файл | Назначение |
| --- | --- |
| [global_variables.json](../global_variables.json) | Корни источников, пути локализации, `WORK_DIR` |
| [config/backend.json](../config/backend.json) | Профили чтения, порядок языковых источников, имена результатов |
| [schemas/database.schema.json](../schemas/database.schema.json) | Закрытая схема базы, формат 1 |
| [schemas/backend.schema.json](../schemas/backend.schema.json) | Закрытая схема параметров сборки |
| [schemas/report.schema.json](../schemas/report.schema.json) | Закрытая схема отчёта |
| `profiles/stellaris_4_5_4.json` (удалён на шестом этапе) | Объявленные контексты, команды, аргументы, операторы и области видимости |

Основные результаты находятся в `data/database.json` и `data/reports/build_report.json`. Во втором этапе добавлены `data/rules/script_rules.json` и `data/reports/generation_report.json`; их имена задаёт раздел `rules`. Их относительные имена задаёт `outputs` в конфигурации; абсолютный путь определяется через `WORK_DIR`.

`TECH_PATH` разрешается внутри `STELLARIS_ROOT`. Относительные каталоги локализации также отсчитываются от корня игры. Подстановка ссылок на глобальные переменные выполняется без запуска кода; неизвестные имена и циклы запрещены. Недоступный настроенный источник является ошибкой, а отсутствие конкретного перевода — предупреждением.

Пути результатов не могут выходить за `WORK_DIR`, совпадать между собой или с конфигурацией, попадать в источники, код, схемы, конфигурацию или документацию продукта. Смена рабочей папки не перемещает и не удаляет прежние данные.

`data/` исключён корневым `.gitignore`. При другой рабочей папке её исключение настраивается отдельно.

## Модули и строгая модель

| Модули в `src/backend/sttv/` | Ответственность |
| --- | --- |
| `sources/settings.py`, `sources/files.py` | Конфигурация, разрешение путей, воспроизводимый выбор файлов и чтение |
| `script/parser.py` | Структурный разбор; токенизация и конфиги выделены в модули [третьего этапа](BACKEND_STAGE_3_RU.md) |
| `technologies/`, `script/variables.py` | Закрытый набор полей, преобразование записей и локальных переменных |
| `script/rules.py`, `rules/` | Проверка вложенных команд по явному реестру |
| `localization/names.py` | Названия по ключам и приоритетам, сохранение исходной разметки |
| `common/schema.py`, `database/validation.py` | JSON Schema, контекстные проверки, ссылки и граф требований |
| `common/`, `database/storage.py` | Строгий JSON, запись, замена результатов, диагностика |
| `builder.py` | Последовательность стадий сборки |

`main.py` содержит только вход командной строки. Повторяемая логика чтения, сериализации, проверки и разрешения путей вынесена в отдельные функции.

Рабочий реестр генерируется из явно выбранного JSON-профиля без автоматического пополнения по встреченным словам. Он покрывает изученные конструкции текущих источников, включая переключение областей видимости, числовые ссылки и параметры известных inline-вставок. Сборщик не читает и не исполняет тела внешних скриптов; отдельный анализатор описан в [руководстве второго этапа](BACKEND_STAGE_2_RU.md). Неизвестная команда, неверный аргумент, оператор или область видимости приводят к отказу.

Условия доступности, веса и `technology_swap` сохраняются отдельно от `prerequisites`. Варианты вложены в базовую технологию. Повторы значений сохраняются вместе со строками; числовые ссылки разрешаются только по однозначным локальным определениям того же файла. Внешние значения остаются `resolved: null`.

## Диагностика и сохранение

Отчёт содержит статус, счётчики файлов и записей, ошибки, предупреждения и признаки `database_written`, `registry_written`, `generation_report_written`. Диагностика имеет устойчивый код, стадию, сообщение и доступные координаты проблемы. Отчёт не включается в базу.

| Ситуация | Результат |
| --- | --- |
| Неизвестное поле или команда, повреждённая ссылка, ошибка синтаксиса/схемы | Ошибка; новая БД не публикуется |
| Различающиеся значения выбранного ключа в одном уровне локализации | Ошибка; приоритет не используется для скрытия конфликта внутри уровня |
| Нет названия на одном языке | `null` для названия и источника, предупреждение |
| Явное пустое название | Пустая строка с происхождением; нижний уровень не подставляется |
| Неоднозначная, циклическая или внешняя числовая переменная | Ссылка с `resolved: null`, предупреждение |
| Повторное одиночное поле | `occurrences` с исходным порядком и строками, предупреждение |

База сериализуется во временный файл рядом с целевым, перечитывается и проверяется. Затем используется атомарная замена файла. Ошибка до замены оставляет прежнюю БД; при первом ошибочном запуске частичная база не создаётся. Подготовка отчёта также выполняется до замены базы.

База и отчёт — два отдельных файла. Если окончательная замена отчёта завершится ошибкой уже после замены БД, вызывающая сторона получает ошибку с `database_written: true`. При ошибке самой конфигурации, когда безопасный путь отчёта ещё не определён, диагностика возвращается через API/терминал без записи на диск.

## Проверки

Запуск синтетических проверок из `WEB_STTV`:

```powershell
./data/.venv/Scripts/python.exe -B -m unittest discover -s src/backend/tests -v
```

Все фикстуры и результаты тестов создаются в `data/tests/`; игра для них не требуется.

Исторические результаты первого этапа на 2026-11-15; актуальные 79 проверок и обход ванильного корпуса описаны в [руководстве третьего этапа](BACKEND_STAGE_3_RU.md):

Сборщик обработал 509 файлов. Проверка хешей охватила все 741 файл настроенных профилей, включая нижние уровни локализации, чтение которых сборщик может пропустить после нахождения всех названий.

Рабочие доказательства сохранены в `data/reports/validation_report.json`, `data/reports/unittest_output.txt` и `data/reports/build_report.json`. Дополнительный скрипт сверки в `data/validate_stage_one.py` является рабочим материалом и использует исследовательский аудит только как независимый эталон проверки; запускаемый продукт от него не зависит.

## Границы реализации

Готов сборщик данных. Интерфейс, выбор папок через окно, HTTP-служба, изображения и portable-поставка ещё не реализованы. Из локализации загружаются только названия. Игровые условия, стоимость с внешними переменными и вероятности не вычисляются; поведение движка не проверялось.

Следующий этап оформляется отдельным двуязычным ТЗ, согласно [правилу организации спецификаций](TZ_RU.md#организация-спецификаций-по-этапам).
