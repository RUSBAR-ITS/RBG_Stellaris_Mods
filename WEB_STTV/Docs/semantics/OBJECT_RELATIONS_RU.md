## Требования и улучшения

| Ключ | Контекст и форма | Назначение и использование | Источники |
| --- | --- | --- | --- |
| `prerequisites` | Объект, например компонент или здание; блок ID технологий | Технологические требования объекта. Связывает открываемый объект с технологиями; описание логики — в [разделе технологий](TECHNOLOGIES_RU.md). | R1, R2 |
| `has_technology` | Условие государства; ID технологии | Проверяет исследованную технологию. В условии строительства может подтверждать связь объекта с технологией; в весах ИИ выполняет другую роль. | R3 |
| `upgrades` | Здание; список ID зданий | Указывает направления улучшения здания. Технологии, открывающие исходное и улучшенное здания, дают прямое свидетельство продолжения цепочки. | R2 |
| `upgrades_to` | Компонент; ID компонента | Указывает следующий компонент для улучшения. Связывать по ID компонентов, затем по их технологическим требованиям. | R1 |
| `component_set` | Компонент; ID набора | Принадлежность к набору компонентов. Это группировка, а не направленная связь улучшения; наборы сами определяются отдельно. | R1, R4 |
| `building_sets` | Здание; список ID наборов | Принадлежность к наборам зданий, например `foundry` и `industrial`. Помогает сравнить назначение; одна общая группа не доказывает непосредственное улучшение. | R2 |

## Условия объектов

| Ключ | Контекст и форма | Назначение и использование | Источники |
| --- | --- | --- | --- |
| `potential` | Здание, звёздное здание или компонент; блок условий | Определяет, рассматривается ли объект в соответствующем контексте доступности. Например, у компонента это включение в список доступных для установки. Scope зависит от типа объекта. | R2, R3, R4 |
| `allow` | Планетарное здание; блок условий | Условия, разрешающие строительство. Не заменяет `potential` или технологические требования. | R2 |
| `possible` | Здесь звёздное здание; блок условий | Условия возможности строительства, включая требуемое оборудование базы. У компонента это отдельные ограничения совместимости в проекте корабля. | R3, R4 |
| `has_starbase_module` | Условия звёздной базы; ID модуля | Проверяет наличие модуля. Может подтверждать функциональную связь здания с модулем. | R3 |
| `has_starbase_building` | Условия звёздной базы; ID здания | Проверяет наличие здания. Под отрицанием может обозначать несовместимость, поэтому саму ссылку нельзя считать положительным требованием. | R3 |
| `starbase_buildable_is_in_queue_before` | Условия базы; блок с `first` и `second`, содержащими ID | Проверяет порядок объектов в очереди строительства. У детектора используется как альтернатива уже построенному модулю обнаружения. `first` и `second` здесь являются аргументами этой проверки. | R3 |

## Переходы терраформирования

| Ключ | Контекст и форма | Назначение и использование | Источники |
| --- | --- | --- | --- |
| `terraform_link` | Корневой блок в `common/terraform` | Определение перехода терраформирования между классами планет. Это тип повторяющейся конструкции, а не уникальный ID отдельного перехода. | R5, R6 |
| `from` | Внутри `terraform_link`; ID класса планеты | Исходный класс перехода. В этом контексте не ссылка на scope `FROM`. | R5, R6 |
| `to` | Внутри `terraform_link`; ID класса планеты | Целевой класс перехода. | R5, R6 |
| `condition` | Внутри `terraform_link`; блок условий | Условия доступа к переходу. Проверка `has_technology` связывает его с требуемой технологией; сохранять логику условий и контекст проверки. | R5, R6 |

Разные значения `from` и `to` подтверждают изменение класса планеты. На этом основана согласованная [функциональная группа](../frontend/CHAIN_FUNCTIONAL_GROUPS_RU.md#изменение-класса-планеты). Технологическое требование ищется в `condition`, а не в произвольном упоминании ID, весах ИИ или тексте подсказки. Отрицание не превращается в положительную разблокировку; альтернативы сохраняются.

## Отображение разблокировок

| Ключ | Контекст и форма | Назначение и использование | Источники |
| --- | --- | --- | --- |
| `show_in_tech` | Здесь звёздное здание; ID технологии | Связывает отображение объекта с технологией. Полезно для поиска связанных объектов, но не заменяет проверку фактических условий строительства. | R3 |
| `show_tech_unlock_if` | Объект; блок условий | Управляет показом разблокировки у технологии. Само по себе не устанавливает доступность объекта. | R2, R3 |

## Границы трактовки

Для прямой связи улучшения нужны обе стороны: объект A улучшается до объекта B и известны технологические требования этих объектов. Если объект требует несколько технологий, сама связь объектов ещё не даёт единственного предшественника. Согласованное [правило выбора по прямым улучшениям](../frontend/CHAIN_DIRECT_UPGRADES_RU.md) описывает сравнение обязательных требований с вычитанием общей части; исходные зависимости сохраняются.

`component_set` и `building_sets` содержат ссылки на определения за пределами словарной записи. Этот этап не добавляет базы наборов и не выдумывает их содержимое. Аналогично значение `upgrades_to` у другого типа объекта требует отдельного описания контекста.

У `dark_matter_detector` блок `possible` содержит альтернативу «модуль уже существует или стоит раньше в очереди», а также запрет другого здания. При извлечении связей необходимо сохранять альтернативу и знак условия. Строки подсказки не являются ID требуемых объектов.

Применение таких связей к выбору предшественника описано в согласованном [правиле прямых функциональных связей](../frontend/CHAIN_DIRECT_RELATIONS_RU.md). Оно использует связь «требует или усиливает объект» и сохраняет её условия; расход ресурса не приравнивается к ней.
