## Назначение

**Утверждено.** Загрузчик — самостоятельное приложение WEB_STTV. По явной команде пользователя оно читает готовые JSON с диска и публикует документы в MongoDB. Содержимое документов переносится без обогащения.

Согласованный корень проекта загрузчика — `WEB_STTV/src/loader/`. Здесь будут находиться его `pyproject.toml`, исходный код и тесты.

## Запуск и источники данных

Пользователь запускает `sttv-loader` со своим конфигом загрузчика `WEB_STTV/config/loader.json`. В конфиге задаются пути и имена входных файлов или каталогов, соответствующие коллекции и профиль подключения к MongoDB. Загрузчик сам открывает указанные источники. Для повторной загрузки достаточно сохранённых JSON и конфига. Связь с процессом парсера, его настройки и сведения о его прогоне для работы не требуются.

## Управление БД и коллекциями

Выделить в загрузчике модуль управления БД. Предлагаются две самостоятельные команды.

- `drop` удаляет целиком БД, указанную в выбранном профиле. Удаление выполняется только по явному вызову этой команды.
- `create` создаёт в целевой БД коллекции, перечисленные в конфиге, в том числе для пустых каталогов. При повторном запуске добавляет недостающие коллекции и сохраняет содержимое существующих. Создание первой коллекции создаёт и саму БД. [Документация MongoDB](https://www.mongodb.com/docs/manual/core/databases-and-collections/).

При переходе на новую версию игры БД пересобирается полностью. Пользователь вызывает `drop` для удаления всей целевой БД, затем `create` и `load` для загрузки данных новой версии. В рамках одной версии тот же набор JSON можно загрузить повторно.

Каждому входному каталогу конфиг явно назначает целевую коллекцию. Например, `scripts/common/technology/` можно сопоставить с `technologies`, а `scripts/events/` — с `events`. Вложенные каталоги с собственным назначением, такие как `technology/category/`, обрабатываются по своему правилу. Каждый файл импортируется в рамках одного сопоставления.

## Один объект — один документ

Загрузчик выделяет объекты по правилам входного каталога. Один игровой объект со всеми его вложенными полями образует один документ MongoDB. Один входной файл может дать ноль, один или несколько документов. Для локализации единицей импорта остаётся готовая запись со своим составным `_id`.

| Источник | Объект для импорта | Пример из готовых JSON |
| --- | --- | --- |
| Технологии | Одно определение технологии верхнего уровня | Два определения в `00_strange_worlds_tech.json` дают два документа |
| События | Одно определение события с полем `id` в его теле | В `apocalypse_events.json` выделяются 15 событий. Объявление `namespace = apoc` служит контекстом файла |
| Терраформирование | Каждое отдельное определение `terraform_link` | В `00_basic_terraform_links.json` выделяются 19 переходов. Два объявления переменных в том же файле служат контекстом |

Для каждого анонимного определения загрузчик формирует технический `_id` с полями `root`, `file`, `item` в этом порядке. Значения `root` и `file` берутся из `source.root` и `source.file` входного JSON. Целое число `item` — индекс определения с нуля в корневом массиве `items` до отбора объектов для импорта.

Например, два перехода `pc_nuked → pc_hive` в `02_special_terraform_links.json` имеют разные ключи. У первого `_id` равен `{"root":"STELLARIS_ROOT","file":"common/terraform/02_special_terraform_links.txt","item":92}`, у второго поле `item` равно `167`. При пересборке из тех же JSON ключи воспроизводятся при любом порядке чтения файлов и любом расположении рабочего каталога. При изменении порядка определений в исходном массиве их ключи могут измениться.

## Игровое дерево и привязки к исходнику

При импорте каждого скриптового объекта загрузчик разделяет дерево и служебные привязки. Правило едино для всех размеров объектов. Для готовых документов локализации действует прежний формат.

| Данные | Где и как хранятся |
| --- | --- |
| Игровой объект | Один документ в предметной коллекции. Поле `tree` содержит обычные вложенные BSON-документы и массивы. Игровые ключи, операторы, значения, порядок, повторения и вложенность сохраняются. Для поиска по игровым полям достаточно предметной коллекции. Поля `source` и `pointer` указывают на исходный файл и позицию объекта в нём. |
| Привязки узлов | Один документ с тем же типом и значением `_id` в сопоставленной служебной коллекции. Имена обеих коллекций задаёт конфиг загрузчика, например `events` и `events_provenance`. В `tree` на местах служебных записей `origin` и `span` остаются целочисленные индексы в таблицах этого объекта. Загрузчик сохраняет различие между отсутствующим полем и `null`. |
| История раскрытий файла | Один служебный документ на исходный файл, включая файлы с пустым списком объектов. В отдельной коллекции, заданной конфигом, ключом служит `{root, file}` из `source`. Исходный раздел `metadata` сохраняется целиком, включая порядок раскрытий, `id`, `parent_id` и пути вставок. Позиции в истории отсчитываются от исходного файла. |

В таблицах привязок одинаковые записи хранятся один раз в пределах объекта. Это относится к координатам `span` и `generated_span`, корням и путям файлов, идентификаторам раскрытий и записям `origin`, которые на них ссылаются. Все таблицы доступны как BSON. По ссылкам загрузчик должен уметь точно восстановить исходный узел для сверки. Одноимённые игровые команды сохраняются как игровые данные.

`create` учитывает предметные и служебные коллекции из конфига. Перед публикацией `load` проверяет размер каждого BSON-документа с учётом его оболочки и лимита 16 МиБ. `verify` проверяет принадлежность привязок объекту, разрешимость ссылок, восстановленное дерево и файловую историю по входным JSON. При сбое загрузка должна сохранить согласованность ранее опубликованных деревьев и их служебных данных.

Проверка предложенного формата в памяти на текущих входных данных: у всех пяти событий, исходное дерево которых превышало 16 МиБ, оба документа укладываются в лимит. Для `colony.9850` получились 6,23 МиБ дерева и 13,84 МиБ привязок. Максимальный документ привязок среди пяти — 14,05 МиБ у `nomads.4100`. Исходное дерево восстановлено для всех пяти. Среди 619 отдельно проверенных документов файловой истории наибольший занимает 6,15 МиБ.

## Текущая реализация

Самостоятельный загрузчик открывает источники из своего конфига. Установка, команды и результаты проверок приведены в [руководстве загрузчика](../src/loader/README_RU.md).

## Проверки загрузчика

- Установить только загрузчик с его зависимостями. В отдельном рабочем каталоге разместить конфиг и небольшую фикстуру локализации по указанному в конфиге пути.
- Загрузить фикстуру в изолированную коллекцию, повторить запуск с теми же файлами и выполнить сверку. Состав документов и их идентификаторы должны совпасть в обоих прогонах.
- Проверить сбой до публикации. В целевой коллекции должна остаться предыдущая версия данных.
- В отдельной тестовой БД проверить создание настроенных коллекций, включая пустую. Повторить `create` после вставки документа, проверить его сохранность, затем выполнить `drop` и пересоздать коллекции.
- На небольших фикстурах проверить несколько объектов в одном файле, файл с одними служебными объявлениями, вложенный каталог со своей коллекцией и два анонимных определения с одинаковой парой `from`/`to`. Сверить число, назначение и содержимое документов после импорта.
- Для анонимных определений сверить точные `_id` с исходными позициями, включая служебную запись перед определением. После пересоздания тестовой БД загрузить копии тех же JSON из другого каталога в обратном порядке файлов. Набор `_id` должен совпасть с первым прогоном.
- Проверить запрос MongoDB к вложенному игровому полю в предметной коллекции. На фикстуре с повторяющимися координатами и вложенным раскрытием проверить дедупликацию, точное восстановление узлов и связь с историей файла. Повреждённая ссылка должна обнаруживаться при сверке. Проверить отказ публикации при ошибке записи служебных данных.
