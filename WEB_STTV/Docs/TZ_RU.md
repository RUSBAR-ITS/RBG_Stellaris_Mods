## 1. Языки и технологическая основа

Основные языки программирования — **Python и TypeScript**. HTML и CSS используются для структуры и оформления интерфейса. JSON — формат внутренней базы и обмена структурированными данными. Portable-поставка для Windows собирается с помощью **PyInstaller в режиме одного каталога (`onedir`)**.

### 1.1. Выбранные технологии

| Часть приложения | Технология | Ответственность |
| --- | --- | --- |
| Сбор первичной информации | Python | Прямое чтение выбранных каталогов, передача данных в памяти и сохранение сведений об источниках |
| Преобразование информации | Python | Разбор игрового синтаксиса, разрешение переменных и ссылок, локализация по приоритетам, построение связей, подготовка базы и изображений |
| Локальная служебная часть | Python | Работа с настройками источников, запуск сбора и перестроения, предоставление подготовленных данных интерфейсу |
| Интерактивный интерфейс | TypeScript | Дерево, карточки, масштабирование, перемещение по дереву и выбор технологий |
| Разметка и оформление | HTML + CSS | Структура карточек и панелей, изображения, цвета и расположение элементов |
| Хранение и обмен данными | JSON | Внутренняя база и структурированные сообщения между частями приложения |
| Упаковка для Windows | PyInstaller, `onedir` | Запускаемый файл, встроенный Python, зависимости и собранные файлы интерфейса в одном каталоге |

### 1.2. Границы ответственности

Сохраняется разделение трёх процессов из концепта: чтение первичной информации, преобразование в базу и отображение. Чтение и преобразование реализуются на Python как самостоятельные этапы обработки с передачей данных в памяти. Копия исходников и постоянный промежуточный снимок не создаются. В дальнейшем локальная служебная часть свяжет сборщик с пользовательским интерфейсом.

Python читает игровые источники и формирует готовую смысловую модель технологий: определения, связи, подготовленные тексты и происхождение данных. Разбор синтаксиса игровых файлов относится к этой части; JSON является форматом подготовленных данных, а не предположением о формате исходных игровых скриптов.

TypeScript получает готовую модель и отвечает за её отображение и взаимодействие с пользователем. Разрешение игровых переменных, приоритетов локализации и исходных ссылок выполняется при подготовке базы на Python. Размещение карточек на экране и обработка действий пользователя относятся к интерфейсу.

Просмотр использует готовую базу и подготовленные изображения. Повторный сбор и преобразование запускаются отдельно от обычного открытия карточек. Исходные каталоги игры доступны только для чтения.

### 1.3. Типы и формат данных

Код интерактивного интерфейса пишется на TypeScript и преобразуется в JavaScript для выполнения в браузере. Типы описывают технологии, связи, источники и состояния обработки; проверка типов помогает обнаруживать несогласованное использование полей при разработке. [Документация TypeScript](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch.html).

Проверка типов TypeScript не заменяет проверку содержимого загружаемого JSON. Для первой базы обязательны машиночитаемая схема и контекстные проверки по разделу 3. Формат будущих сообщений интерфейса и конкретная библиотека проверки пока не выбраны.

Для чтения и записи JSON на стороне Python используется стандартный модуль `json`. Первая БД — один JSON-файл по [модели данных](DATABASE_MODEL_RU.md); диагностический отчёт хранится отдельно. Постоянного промежуточного снимка нет. Подготовка изображений относится к последующим этапам. [Документация Python](https://docs.python.org/3/library/json.html).

### 1.4. Запуск и portable-поставка

Целевая платформа — Windows. Пользователь распаковывает каталог приложения и запускает `.exe`. Запускаемый файл поднимает локальную служебную часть на Python и открывает подготовленный веб-интерфейс в браузере.

Поставка включает интерпретатор Python, необходимые зависимости и собранные файлы интерфейса. Отдельная установка Python, веб-сервера и инструментов сборки интерфейса пользователю не требуется. Такой способ включения Python и зависимостей предусмотрен PyInstaller; выбран режим `onedir`. [Документация PyInstaller](https://pyinstaller.org/en/stable/operating-mode.html#bundling-to-one-folder).

Настройки находятся в каталоге приложения; рабочие данные размещаются в настраиваемой папке `WORK_DIR`, по умолчанию `data` внутри приложения. Внутренние ссылки используют относительные пути. Внешние источники задаются пользователем и могут потребовать повторного выбора после переноса приложения. Просмотр уже собранной базы вместе с её будущими изображениями сохраняет независимость от доступности исходных каталогов.

Первая пользовательская поставка имеет пустую базу и предлагает настроить источники. Инструменты разработки и сборки применяются при подготовке поставки; пользователь запускает готовое приложение.

### 1.5. Предполагаемые проверки

При реализации этой части предусматриваются следующие проверки:

1. Проверка типов TypeScript и успешная сборка интерфейса в файлы, выполняемые браузером.
2. Проверка разделения ответственности: игровые определения и локализация обрабатываются на Python, интерфейс получает подготовленные данные.
3. Проверка записи и чтения JSON, а после определения схемы — отдельная проверка структуры и обязательных полей.
4. Запуск готовой Windows-поставки без отдельно установленного Python, веб-сервера и инструментов сборки интерфейса.
5. Перенос каталога приложения с готовой базой и изображениями: проверка внутренних путей и просмотра при недоступных исходных каталогах игры.

Это план проверок полного продукта. Чтение, запись и схема JSON проверены в первом этапе бэкэнда; интерфейс и portable-поставка ещё не созданы, проверки их работы не выполнялись. Точный состав оставшихся сценариев уточняется после определения остальных частей ТЗ.

## 2. Структура проекта и принципы кода

### 2.1. Каталоги и рабочая папка

| Путь относительно `WEB_STTV` | Назначение |
| --- | --- |
| `src/frontend/` | Код будущего интерфейса |
| `src/backend/` | Код Python: сборщик, обработка данных и последующая служебная часть |
| `data/` | Рабочая папка по умолчанию: БД, отчёты, временные результаты и материалы проверок |
| `Docs/` | Двуязычная документация |
| `global_variables.json` | Общие переменные проекта, включая источники и `WORK_DIR` |
| `config/` | Настраиваемые параметры обработки; создаются при реализации |
| `schemas/` | Объявленные структуры и правила проверки данных; создаются при реализации |

`WORK_DIR` имеет начальное значение `"data"`. Относительный путь отсчитывается от каталога проекта/продукта, а не от текущей папки терминала. Допускается абсолютный путь. Изменение `WORK_DIR` задаёт место следующей сборки и проверок; существующие файлы автоматически не перемещаются и не удаляются.

База, отчёты и временные файлы сборки размещаются внутри разрешённой рабочей папки. При работе агента она должна оставаться внутри репозитория. Нормализованные итоговые пути проверяются до записи: нельзя направлять результаты в каталоги источников или за пределы рабочей папки. Файлы игры и Workshop всегда доступны только для чтения.

В корневом `.gitignore` используется правило `/WEB_STTV/data/`. При выборе другой рабочей папки её исключение настраивается отдельно; приложение не выполняет действий с Git. Существующие исследовательские материалы в `TMP/WEB_STTV/` не переносятся и не становятся входом продукта.

### 2.2. Модульность и конфигурация

- Код должен быть модульным, расширяемым и легко обслуживаемым. Каждый модуль отвечает за понятную задачу; расширение одного этапа не должно требовать переписывания остальных.
- Повторяемую логику выносить в общие функции и хелперы, соблюдая DRY. Хелперы группировать по назначению; избегать общего файла с несвязанными функциями и абстракций без текущей необходимости.
- Настраиваемые пути, порядок источников, параметры чтения и имена выходных файлов хранить в отдельных конфигурационных файлах. Не дублировать пути и параметры в коде, не зашивать каталоги конкретного компьютера.
- Структура допустимых данных и поддерживаемые конструкции объявляются отдельно от пользовательских настроек. Настройка не должна разрешать неизвестное поле или отключать обязательную проверку схемы.
- Код, комментарии и имена полей пишутся на английском. Русские названия технологий остаются данными локализации.
- Не добавлять поддержку прежних форматов, резервные механизмы или зависимости, не требуемые текущим этапом.

### 2.3. Размер файлов

Ориентир для обычного файла кода — **до 200 строк**. Считаются физические строки, включая комментарии и пустые строки; правило относится и к тестовому коду.

- **201–300 строк:** обязательно пересмотреть структуру и определить, какие самостоятельные части или повторяемые операции стоит вынести. Это порог пересмотра, а не требование искусственно дробить связную функцию.
- **Больше 300 строк:** обязательное выделение самостоятельных частей в модули или хелперы.
- Исключение допустимо, если большой блок нельзя разумно разделить на функциональные составляющие. Причину конкретного исключения фиксировать в документации, не считать большие файлы исключением автоматически.

Не сокращать число строк за счёт уплотнения выражений и ухудшения читаемости. Документация, схемы JSON и игровые данные не являются файлами кода и не дробятся только ради этого ограничения.

## 3. Первый этап бэкэнда — сборка БД

### 3.1. Цель и границы этапа

Результат этапа — запускаемый сборщик на Python, который читает заданные источники и формирует первую версию JSON-базы по `DATABASE_MODEL_RU.md`, а также отдельный отчёт. Сборщик работает самостоятельно и допускает последующий вызов из локальной служебной части.

Входные игровые определения ограничены `TECH_PATH`: базовые файлы `*.txt`, `category/*.txt`, `tier/*.txt` и локальные переменные из этих файлов. Локализация используется только для названий технологий и их вариантов на русском и английском.

В этап не входят интерфейс, HTTP-сервис, изображения, упаковка `.exe`, чтение сохранений, переопределения технологий модами и загрузка игровых определений из других каталогов. Разрешение ссылок внутри текстов локализации и локализация описаний также остаются за пределами этапа.

### 3.2. Входы и настройки

Общие переменные читаются из `global_variables.json`: `WORK_DIR`, `STELLARIS_ROOT`, `TECH_PATH`, `WORKSHOP_DIR`, `RU_LOC_TIER_1`, `RU_LOC_TIER_2`, `RU_LOC_TIER_3`, `EN_LOC_TIER_1`. Их значения не дублируются в другом конфиге.

При реализации создаётся `config/backend.json` с параметрами сборки:

- Профили чтения: именованные входные переменные, относительные подкаталоги, маски файлов, рекурсивность, кодировка и ожидаемый язык локализации.
- Порядок русских источников `RU_LOC_TIER_1` → `RU_LOC_TIER_2` → `RU_LOC_TIER_3`; отдельный английский источник `EN_LOC_TIER_1`.
- Относительные пути результатов внутри `WORK_DIR`: по умолчанию `database.json` и `reports/build_report.json`.

Технологии читаются в указанных трёх каталогах без общего рекурсивного обхода игры. В каждом каталоге локализации ищутся `*.yml`, включая вложенные папки. Чтение — UTF-8 с поддержкой BOM; ошибка декодирования сообщается без замены повреждённых символов. Изменение профиля источника не вводит поддержку нового вида данных автоматически.

Подстановка `${NAME}` выполняется по объявленным переменным без запуска кода. Неизвестное имя, циклическая ссылка, неверный тип настройки или недоступный выбранный каталог — ошибка подготовки. `TECH_PATH`, `RU_LOC_TIER_3`, `EN_LOC_TIER_1` относительны `STELLARIS_ROOT`; `WORK_DIR` — каталогу продукта. Отсутствие ключа локализации и недоступность её каталога различаются: недоступный источник нельзя молча пропустить.

### 3.3. Разделение ответственности

Внутри `src/backend/` выделяются модули по следующим задачам; конкретные файлы делятся с соблюдением раздела 2:

| Часть | Ответственность |
| --- | --- |
| Настройки и источники | Проверка конфигурации, разрешение путей, выбор файлов, чтение только разрешённых источников |
| Парсер игрового скрипта | Разбор синтаксиса с сохранением порядка, повторов и положения в файле |
| Преобразование модели | Обработка объявленных полей и команд, локальных переменных, требований и вариантов |
| Локализация | Разбор строк и подбор названий по ключам и приоритетам |
| Проверка данных | Схема JSON, контекстные ограничения и связи между записями |
| Хранение и отчёт | Запись проверенного результата и диагностики внутри `WORK_DIR` |
| Управление сборкой | Последовательный вызов этапов и итоговый статус; без дублирования их логики |

Чтение и преобразование обмениваются данными в памяти. Отдельные процессы ОС, постоянный кеш исходников и повторный обход всей игры не требуются. Источники перечитываются при явной новой сборке, а не при просмотре результата.

### 3.4. Чтение и разбор источников

Файлы обходятся в воспроизводимом порядке по относительным путям. Парсер сохраняет ID определения, файл и строки, вложенность, операторы, скалярные токены, порядок элементов и повторные присваивания. Комментарии и кавычки обрабатываются как части синтаксиса: символ комментария внутри строки не обрывает значение. Ошибка синтаксиса не должна приводить к молчаливому пропуску определения.

Первичное дерево разбора существует только в памяти и не является рабочей моделью БД. Произвольное синтаксически корректное поле в нём ещё не считается поддержанным. Исходные `.txt` и `.yml` не копируются в рабочую папку; постоянный снимок разбора также не записывается. Отчёт может содержать небольшой фрагмент проблемной строки для диагностики.

### 3.5. Формирование строгой модели

Нормативное описание — [модель первой БД](DATABASE_MODEL_RU.md). Её `format_version` равен `1`; запись технологии имеет `source`, `name`, `name_sources`, `fields`. Условные варианты вложены в `fields.technology_swap`, отдельный `parent_id` не создаётся.

Реализация должна подготовить `schemas/database.schema.json` и явно объявленные правила обработки вложенных команд: контексты, области видимости, операторы, аргументы, типы и кратность. Правила должны покрывать изученные поддерживаемые конструкции; это проверяемый результат разработки, а не разрешение автоматически принимать всё найденное. Неизвестные поля, команды и недопустимые формы — ошибки с отдельной диагностикой. Схема закрыта на каждом уровне, включая `ScriptBlock` и варианты объединённых типов.

Преобразование сохраняет все поддерживаемые значения, включая явные пустые, нулевые и ложные значения, повторы и исходный порядок. Отсутствующее поле не дополняется предполагаемым значением по умолчанию. Противоречащие повторные значения сохраняются через `RepeatedValue` по модели и отмечаются в отчёте; произвольного выбора значения нет.

Вычисляются только результаты, однозначно выводимые из объявленных входов: локальные числовые цепочки в пределах одного файла, логическая структура `prerequisites`, проверяемые ссылки на технологии, категории и известные уровни. Производные связи можно строить в памяти для проверки, но дополнительные коллекции в БД не вводятся. Нет чтения внешних определений или подстановки значений из исследовательского аудита.

Неразрешённые локальные ссылки, неоднозначность и циклы переменных сохраняют `resolved: null` с диагностикой по модели. Известные внешние ссылки сохраняются только в объявленной форме. Условия `potential`, `starting_potential`, веса и триггеры вариантов сохраняются раздельно; их нельзя превращать в дополнительные требования-предшественники или принимать за выполненные.

### 3.6. Названия технологий

После разбора определений формируется набор ключей: ID базовых технологий и `name_key` вариантов. Каждый язык обрабатывается независимо. Выбираются только названия, с сохранением ключа, источника, файла и строки.

Соблюдаются правила модели: приоритет по ключу, переход вниз только при его отсутствии, пустая строка остаётся пустой, отсутствующее название и его источник равны `null`. Идентификатор, текст другого языка или заново написанный перевод не подставляются. Разметка, грамматические маркеры, ссылки и управляющие последовательности сохраняются без вычисления.

Одинаковые дубли в выбранном источнике дают детерминированный источник по пути и строке; различающиеся значения выбранного ключа в одном уровне — ошибка. Проверяется языковой заголовок файла. Отсутствующий перевод — предупреждение, допустимое моделью, а не причина потери технологии.

### 3.7. Проверки и диагностика

Схема JSON проверяет поля, типы, обязательность, допустимые значения и отсутствие лишних свойств. Отдельно проверяются команды по контексту, уникальность ID, корректность ссылок, группы `all` / `any`, граф требований, варианты и происхождение названий. Проверки циклов не распространяются на все упоминания технологий внутри произвольных условий.

Отчёт содержит итоговый статус, число обработанных файлов, технологий и вариантов, число ошибок и предупреждений и список диагностик. Диагностика содержит уровень, устойчивый код, этап, описание, а при наличии — имя источника, относительный путь файла, строку, ID определения и путь проблемного поля. Недоступные сведения явно отсутствуют или равны `null` по объявленной структуре отчёта. Сам отчёт имеет отдельную проверяемую схему; эти поля не добавляются в БД.

Ошибки конфигурации, чтения, синтаксиса, неизвестных конструкций, схемы, дубли базовых ID и повреждённые внутренние ссылки препятствуют успешной сборке. Предусмотренные моделью пропуски названий, неразрешённые ссылки и сохранённые повторы отражаются отдельно и не объявляются ошибками только из-за своей допустимой формы. Неожиданная ошибка не маскируется пустым значением или успешным статусом.

### 3.8. Сохранение и перестроение

Сборка полностью перечитывает выбранные источники и строит новый результат. Изменение путей или приоритетов применяется к следующему запуску. Предыдущая база не используется как источник недостающих данных и не дополняет новые входы.

Новый JSON записывается во временный файл внутри `WORK_DIR`, повторно читается и проверяется перед заменой рабочей базы. Ошибка до замены сохраняет прежнюю базу без изменений. При первом неудачном запуске отсутствие базы не подменяется частичным результатом. Временный файл располагается рядом с целевым; замена должна исключать наблюдение частично записанной БД. Ошибки сохранения отчёта также сообщаются вызывающей стороне, а не скрываются.

Успешная БД сохраняется в UTF-8; порядок вывода воспроизводим. Одинаковые входы и настройки дают одинаковый файл БД. Временные отметки и ход сборки относятся к отчёту. Источники нужны для перестроения; готовую БД можно прочитать и проверить по схеме при недоступной игре.

### 3.9. Запуск и результаты разработки

Первый запуск сборки предоставляется через команду Python из `src/backend/` с указанием файлов общих переменных и настроек обработки. Код возврата `0` означает успешную сборку, ненулевой — ошибку. Общая функция сборки возвращает структурированный результат и вызывается из этой команды; логика преобразования не зависит от терминала или будущего веб-сервера.

Результаты реализации: модульный код бэкэнда, конфигурация обработки, схема БД и правила команд, схема отчёта, проверки и двуязычная инструкция запуска. В `WORK_DIR` создаются база и отчёт. `src/frontend/` на этом этапе остаётся местом для последующей разработки интерфейса.

Исследовательские скрипты в `TMP/WEB_STTV/` служат проверочными материалами и не являются зависимостью продукта. Конкретные зависимости и их версии фиксируются при подготовке реализации; они должны быть необходимы этому объёму работы. Выпуск portable-приложения и проверки интерфейса из раздела 1 не являются критериями завершения этого этапа.

### 3.10. Критерии приёмки

1. Сборщик получает все пути и настраиваемые параметры из конфигурации. Проверены относительный и абсолютный `WORK_DIR`, запуск из другой текущей папки, подстановки, ошибочные настройки и недоступные источники.
2. Проверено отсутствие изменений исходников и их копий в рабочей папке. Запись в источники через ошибочную настройку выходного пути отвергается.
3. На небольших контрольных данных проверены строки, комментарии, вложенность, операторы, переменные, повторы и ошибки синтаксиса без потери исходного положения.
4. База соответствует объявленной схеме; неизвестное поле или вложенная команда, неправильный тип и лишнее свойство вызывают диагностируемую ошибку. Поддержка вложенных команд явно перечислена и покрыта проверками.
5. Проверены локальные цепочки переменных, внешние и циклические ссылки, `all` / `any`, отсутствующие и пустые значения, `RepeatedValue`, варианты и ссылки между записями.
6. Проверены оба языка, приоритеты, неполные переводы, пустые строки, одинаковые и конфликтующие дубли, BOM и сохранение разметки. В БД нет локализованных описаний.
7. Выполнена сборка на текущих источниках; состав определений сопоставлен с входными файлами. Исследовательские 679 технологий и 206 вариантов используются только как ориентир для того же набора файлов, а не константы программы.
8. Повторная сборка на одинаковых источниках даёт одинаковую БД. Изменение источника или приоритета отражается после перестроения; данные предыдущей сборки не примешиваются.
9. Проверены сохранение прежней БД при ошибке до замены, корректный отчёт, ненулевой код ошибки и чтение готовой БД без исходников. Сценарии записи проверяются в разрешённой рабочей папке.
10. Проверены разделение модулей, повторяемая логика, отсутствие настраиваемых констант в коде и размеры файлов по разделу 2. Обоснованные исключения перечислены отдельно.

Критерии первого этапа проверены 2026-11-15: 29 синтетических сценариев, сборка на текущих источниках, сверка состава и значений, воспроизводимость и сохранность исходников. Подробности приведены в [результатах проверки](BACKEND_STAGE_1_RU.md#проверки). Синтетические проверки не подтверждают поведение игрового движка.
