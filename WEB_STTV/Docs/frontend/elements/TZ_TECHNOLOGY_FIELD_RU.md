## Статус и назначение

Документ фиксирует согласованные пользователем требования к полю технологий на 2026-11-16, включая группировку при равенстве числа технологических требований. Реализация элемента ещё не начата.

Основа — [концепт интерфейса](../CONCEPT_RU.md) и [список UI-элементов](../UI_ELEMENTS_RU.md). Поле определяет размещение карточек. Его видимую часть и прокрутку обеспечивает отдельная [рабочая область просмотра](TZ_TECHNOLOGY_VIEWPORT_RU.md).

## Состав и входные данные

Поле собирается из [областей науки](TZ_RESEARCH_AREA_RU.md), [столбцов уровней](TZ_TIER_COLUMN_RU.md) и общих [карточек технологий](TZ_TECHNOLOGY_CARD_RU.md).

| Данные или настройка | Назначение |
| --- | --- |
| Базовые ID технологий | Устойчивая идентичность карточек, сопоставление требований и порядок внутри групп |
| Текущие представления | Основная версия или выбранный блок `technology_swap` каждой технологии |
| Область науки | Размещение в физике, социологии или инженерии с учётом выбранного представления |
| Уровень `tier` | Назначение столбца |
| Структура `prerequisites` | Технологические зависимости, число требований и набор непосредственных предшественников |
| Данные локализации карточек | Ссылки на готовые названия и описания текущих представлений в БД |
| Настройки геометрии | Общие размеры карточек, отступы и промежутки между элементами раскладки |
| Состояние приложения | Язык, тема и выбор представления для каждой технологии |

Таблица описывает необходимые сведения. Логический состав каталога и представлений закреплён в [ТЗ адаптера БД](../TZ_DATABASE_ADAPTER_RU.md); окончательная программная форма определяется при проектировании реализации. Источником служит подготовленная БД. В поле отображается одна карточка на базовую технологию с её текущим представлением.

## Области науки и столбцы

Области расположены сверху вниз в фиксированном порядке:

- Физика — `physics`.
- Социология — `society`.
- Инженерия — `engineering`.

Столбцы соответствуют значению `tier` и идут слева направо по возрастанию: `Level-0`, `Level-1`, …, `Level-5` для текущих данных игры. Столбцы одного уровня выровнены между областями науки.

Заголовки «Уровень N» / «Level N» повторяются в каждой области. Столбцы имеют общую настроенную ширину, соответствующую ширине карточки; пустой столбец сохраняет ширину, позицию и заголовок, не сдвигая соседние уровни. Размещение заголовка и карточек следует ТЗ столбца.

Каждая область содержит локализованный заголовок над столбцами и занимает ширину поля. Её высота определяется самым высоким столбцом с учётом заголовка и отступов. Следующая область начинается ниже с настроенным промежутком; заголовок прокручивается вместе с областью по её ТЗ.

Карточки внутри столбца одной области располагаются одна под другой. Межобластные зависимости сохраняются в данных связей и не меняют порядок областей. Требование к технологии из другого столбца не переносит карточку из столбца её собственного `tier`.

Поле поддерживает расположение связанных карточек рядом без обязательной единой горизонтальной строки на каждую цепочку. Согласованный первый шаг такой группировки описан ниже; ручное определение семейств относится к последующим этапам.

## Технологические требования

Для раскладки используются только требования к технологиям из `prerequisites`. Условия из `potential`, проверки государства, вида, DLC, зданий и другие ограничения доступности в этот подсчёт не входят.

Адаптер передаёт дерево требований, а отдельный общий обработчик по [ТЗ адаптера](../TZ_DATABASE_ADAPTER_RU.md#технологические-требования) вычисляет число требований, непосредственных предшественников и связи. Поле использует эти результаты для группировки и раскладки; правила вычисления не дублируются в карточках.

[ТЗ технологических требований](../TZ_TECHNOLOGY_REQUIREMENTS_RU.md) определяет корневой `AND`, узлы `technology`/`group` и связи с `requirementPaths`. Пути сохраняют логический контекст каждого упоминания. Правила ниже относятся к обязательным требованиям и альтернативам `AND`/`OR`; использование `NOT`, `NAND`, `NOR` в подсчёте и вертикальном порядке ещё предстоит согласовать.

Правила подсчёта:

- Отдельная обязательная технология даёт одно требование.
- Одновременно обязательные технологии суммируются.
- Группа альтернатив `OR` считается одним требованием.
- При отсутствии технологических требований число равно нулю.

Число требований и набор непосредственных предшественников — разные характеристики. Набор содержит ID технологий, непосредственно упомянутых в `prerequisites`, включая участников альтернатив. Порядок перечисления ID не меняет набор; предшественники этих технологий в него дополнительно не включаются.

Например, обязательные технологии `A` и `B` дают два требования, а группа `OR` из `A` и `B` — одно. Набор непосредственных предшественников в обоих случаях одинаков, но число требований различается. Группировка для отображения сохраняет исходную логическую структуру требований.

## Вертикальный порядок и группировка

Правила применяются внутри одного столбца одной области науки со следующим приоритетом:

1. Предшественник располагается выше зависимой технологии, если обе карточки находятся в этом столбце и области. Это относится ко всей последовательности зависимостей.
2. С соблюдением первого правила выше располагаются технологии с меньшим числом технологических требований.
3. При равенстве числа требований технологии с одинаковым набором непосредственных предшественников размещаются подряд.
4. Внутри такой группы используется стабильный порядок по базовым ID технологий.

При конфликте правил приоритет имеют технологические зависимости, затем число требований. Группировка и порядок по ID не могут поставить зависимую технологию выше её предшественника. Отсутствие предшественников соответствует пустому набору и нулю требований.

Группировка не зависит от локализованных названий и не объединяет разные технологии в один объект. При неизменных данных и выбранных представлениях смена языка сохраняет порядок карточек. Наборы предшественников определяются по базовым ID; подписи «(Вариант N)» на группировку не влияют.

Порядок между разными группами с равным числом требований и согласование их вертикальных позиций между столбцами требуют дальнейшего проектирования.

## Геометрия и область просмотра

Все карточки используют одинаковые настроенные размеры по собственному ТЗ. Отступы и промежутки задаются настройками раскладки.

Поле выровнено слева. Перед `Level-0` остаётся только небольшой настроенный отступ; дополнительное свободное пространство не добавляется, даже если поле уже рабочей области просмотра.

Изменение размеров окна или раскрытие и сворачивание меню меняют видимую часть поля, сохраняя размеры карточек и назначенные им позиции. Полосы прокрутки, начальная позиция просмотра и сохранение допустимого смещения относятся к ТЗ рабочей области просмотра.

## Выбор вариантов и обновление отображения

Поле учитывает ручной выбор представления каждой технологии по ТЗ карточки. Если выбранный вариант задаёт область науки, используется она; иначе берётся область основной технологии.

При изменении области науки карточка переносится в соответствующую область. Сохраняются базовый ID, `tier` и технологические зависимости; к новой раскладке применяются те же правила вертикального порядка и группировки. Возврат к основной версии восстанавливает её область науки. Остальные технологии сохраняют собственные выбранные представления.

Смена языка обновляет тексты, а смена темы — оформление; эти действия не меняют порядок карточек. Сохранение состояния между запусками рассматривается отдельно в общем механизме приложения.

## Оформление

Используется максимально простой дизайн первого этапа. Цвета и шрифты задаются именованными переменными отдельного [словаря оформления](../CONCEPT_RU.md#словарь-цветов-и-шрифтов) для обеих тем. Вложенные карточки, списки выбора и тултипы используют собственные ТЗ и роли оформления.

## Критерии приёмки

Проверки выполняются после реализации:

- Области расположены в порядке физика, социология, инженерия; столбцы соответствуют `tier` и выровнены между областями.
- В каждом столбце карточки расположены одна под другой; на базовую технологию приходится одна карточка.
- В подсчёте участвуют только `prerequisites`; условия доступности не меняют число технологических требований.
- Проверены отсутствие требований, одна обязательная технология, несколько одновременно обязательных технологий и группа `OR`.
- Предшественник и последовательность его зависимых технологий в одном столбце и области сохраняют вертикальный порядок, даже если другие правила предлагают обратный порядок.
- При соблюдении зависимостей технологии с меньшим числом требований располагаются выше.
- При равном числе требований одинаковые наборы непосредственных предшественников образуют последовательные группы; внутри групп порядок стабилен по ID с сохранением приоритета зависимостей.
- Разный порядок перечисления одинаковых предшественников не создаёт разные группы; одинаковый набор при разном числе требований не отменяет сортировку по числу требований.
- Межобластные зависимости не переставляют области, а требования из других столбцов не меняют `tier` карточки.
- Перед `Level-0` нет дополнительного свободного пространства; изменение размеров окна и меню сохраняет размеры карточек и их позиции внутри поля.
- Смена языка и темы сохраняет порядок и выбранные представления; тексты и оформление обновляются по соответствующим ТЗ.
- Выбор варианта с другой областью науки переносит единственную карточку технологии, сохраняя её базовый ID, `tier` и зависимости; возврат к основной версии восстанавливает область.

## Детали последующей реализации

По решению пользователя 2026-11-17 первый интерфейс показывает карточки без линий связей. Данные связей сохраняются. Детали реализованного порядка и геометрии описаны в [руководстве первого интерфейса](../FRONTEND_STAGE_1_RU.md#детали-отображения). Ручная группировка технологических семейств и выравнивание связанных групп между столбцами будут рассмотрены отдельно.

Требования к области науки и столбцу закреплены в их ТЗ, логический состав входных данных — в ТЗ адаптера БД. Отдельного проектирования требуют точные значения отступов, программное представление данных и алгоритм раскладки, выполняющий согласованные приоритеты. Поведение при загрузке, отсутствии или некорректности данных также определяется отдельно. Эти оставшиеся детали не считаются утверждёнными настоящим документом.
