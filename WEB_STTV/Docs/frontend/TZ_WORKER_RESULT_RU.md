## Статус и границы

С 2026-11-17 требования этого документа к одному файлу и неквалифицированным ссылкам заменены утверждённым [ТЗ второго этапа](TZ_FRONTEND_STAGE_2_RU.md). Актуальная реализация открывает три БД версии 5 одним набором и использует ссылки `{ database, pointer }`; остальные применимые требования сохраняются.

Документ фиксирует согласованные контейнер `ready`, поля записи технологии, идентификаторы представлений и строковые ссылки на исходные узлы. Он уточняет [ТЗ адаптера](TZ_DATABASE_ADAPTER_RU.md) и [протокол Worker](TZ_WORKER_PROTOCOL_RU.md). Реализация в этой итерации не выполняется.

Общая диагностическая запись и контейнер ответа `error` определены [ТЗ диагностики](TZ_DIAGNOSTICS_RU.md); точные схемы подробностей для отдельных кодов ещё уточняются. Формат локализации определён [ТЗ записей индекса](TZ_LOCALIZATION_INDEX_RU.md). Узлы `prerequisites`, записи `links` и подсчёт для `AND`/`OR` определены [ТЗ технологических требований](TZ_TECHNOLOGY_REQUIREMENTS_RU.md); использование отрицаний в подсчёте и раскладке ещё не согласовано. Наличие разделов в контейнере не означает утверждения их ещё не описанной внутренней структуры.

## Контейнер результата

Успешный ответ содержит `type: "ready"`, актуальный `operationId` и объект `data`. Общая форма показана на пустом результате:

```json
{
  "type": "ready",
  "operationId": 7,
  "data": {
    "technologies": {},
    "links": [],
    "localization": {
      "ru": {},
      "en": {}
    },
    "diagnostics": []
  }
}
```

Все четыре раздела `data` присутствуют и в пустом результате.

| Поле | Тип и назначение |
| --- | --- |
| `technologies` | Словарь: базовый ID → запись технологии |
| `links` | Массив записей `from`, `to`, `requirementPaths` по ТЗ технологических требований |
| `localization` | Объект с индексами `ru` и `en`; каждый индекс сопоставляет ID строки записи локализации |
| `diagnostics` | Массив неблокирующих проблем подготовки данных |

Каталог, требования, связи и локализация относятся к одной открытой БД и публикуются вместе. Полное дерево и исходная JSON-строка не входят в `data`; они не копируются в состояние интерфейса. Корректный пустой каталог остаётся успешным результатом по ТЗ открытия БД.

## Запись технологии

Каждая запись `data.technologies` соответствует одной базовой технологии. Ключ словаря совпадает с полем `id` записи.

| Поле | Тип и назначение |
| --- | --- |
| `id` | Строка: базовый игровой ID технологии |
| `tier` | Целое число: уровень для назначения столбца |
| `prerequisites` | Дерево узлов `technology` и `group` с корневой группой `AND` по ТЗ технологических требований |
| `prerequisiteIds` | Массив уникальных строковых ID непосредственно упомянутых технологий, включая альтернативы |
| `requirementCount` | Неотрицательное целое число: результат подсчёта требований по согласованным правилам сортировки |
| `representations` | Упорядоченный массив: основное представление, затем варианты в исходном порядке |
| `sourceRef` | Строковый путь к исходному узлу базовой технологии в загруженной БД |

`prerequisites` извлекается только из одноимённого поля базовой технологии. Проверки государства, вида, DLC, зданий и другие условия доступности не включаются. `prerequisiteIds` и `requirementCount` вычисляет общий обработчик требований; потребители используют готовые значения.

В `prerequisiteIds` не добавляются транзитивные предшественники. Порядок ID не меняет состав набора. Массив не заменяет дерево: упоминание технологии среди альтернатив не делает её отдельно обязательной.

Для `tech_titans` в текущей БД непосредственно указаны `tech_battleships` и `tech_stinger_growth_2` внутри `OR`. Поэтому `prerequisiteIds` содержит два ID, а `requirementCount` равен `1`. Это пример фактических данных, а не специальное правило для этой технологии.

По ТЗ технологических требований узел технологии даёт `1`, `AND` суммирует дочерние значения, группа `OR` даёт `1`, пустой корневой `AND` — `0`. Формат дерева предусматривает все пять известных операторов; подсчёт и раскладка для `NOT`, `NAND` и `NOR` требуют отдельного согласования. До него по дополнительному решению пользователя открытие таких данных останавливается с `invalid_database`; ответ `ready` не возвращается.

## Представления технологии

Область науки и ID текстов принадлежат представлению. Базовые `id`, `tier` и технологические требования сохраняются при смене варианта.

| Поле | Тип и назначение |
| --- | --- |
| `id` | Строка: `base` для основного представления, `swap:1`, `swap:2` и далее для вариантов |
| `variantNumber` | Положительное целое число варианта; у `base` поле отсутствует |
| `area` | Итоговая область: `physics`, `society` или `engineering` |
| `nameId` | ID строки названия из `requested_key` |
| `descriptionId` | ID строки описания из `requested_key` |
| `sourceRef` | Строковый путь к исходному узлу технологии или соответствующему блоку `technology_swap` |

Первым в массиве всегда идёт `base`. Варианты следуют за ним в порядке исходных блоков `technology_swap`; номер в `swap:N` совпадает с `variantNumber`. Разные варианты с одинаковыми названиями и ключами локализации сохраняют отдельные идентификаторы.

Идентификатор представления уникален внутри базовой технологии. Полная идентичность задаётся парой «базовый ID технологии + ID представления». Номера и расположение вариантов не считаются устойчивыми между разными сборками БД.

Итоговая `area` уже учитывает наследование от основной технологии, если вариант не задаёт собственную область. Названия и описания не дублируются текстами внутри представлений: они разрешаются через общий индекс локализации.

## Ссылки на исходные узлы

`sourceRef` — строковый путь внутри загруженного JSON-дерева, которое хранится в Worker. Он не является путём к файлу на диске. Пример фактического пути к узлу `tech_titans` в текущей БД:

```text
/documents/7/items/5
```

Ссылка относится только к той открытой БД, из которой получена запись. При замене БД прежние ссылки удаляются вместе с каталогом. Тождество пути в двух разных файлах не означает тождества технологии или варианта.

Разрешение ссылки выполняется владельцем исходного дерева в Worker. Этот этап не добавляет отдельную команду получения узла; первый экран использует подготовленные данные. Стабильность ссылок после перестроения БД не обещается.

## Локализация и диагностика

`data.localization.ru` и `data.localization.en` содержат только локализацию открытой БД. Приложение подключает этот индекс как источник `database` общего механизма поиска. Встроенные интерфейсные строки загружаются отдельно и не передаются обратно в результате Worker.

Поиск по источнику `database`, выбранному языку и ID строки приводит к соответствующей записи этого индекса. Ключом поиска остаётся `requested_key`, а текстом — сохранённое `text`, согласно [ТЗ локализации](TZ_LOCALIZATION_RU.md). Запись содержит `status` (`resolved` или `missing`), `text` и `origins` по [ТЗ записей индекса](TZ_LOCALIZATION_INDEX_RU.md). Одинаковые тексты объединяются с сохранением происхождения; разные тексты под одним ID и языком являются блокирующей ошибкой подготовки, ответ `ready` не возвращается. Состояния `conflict` в индексе нет.

`diagnostics` содержит только предупреждения с `severity: "warning"` по [ТЗ диагностики](TZ_DIAGNOSTICS_RU.md). Общие поля записи: `severity`, `code`, `phase`, `params`, `details`. При отсутствии предупреждений передаётся пустой массив. Блокирующая ошибка открытия возвращается отдельной записью `error` в одноимённом ответе вместе с накопленными предупреждениями; она не входит в `ready` и не маскируется успешным пустым результатом.

## Критерии приёмки

Проверки выполняются после реализации:

1. Ответ `ready` содержит все четыре раздела `data`, включая результат с пустым каталогом.
2. Ключ каталога совпадает с `id` технологии; производные значения требований подготовлены общим обработчиком.
3. Пример альтернативных требований `tech_titans` даёт два непосредственных ID и число требований `1`.
4. Каждая технология имеет первое представление `base`; варианты получают последовательные `swap:N` и соответствующие `variantNumber`.
5. Совпадающие названия не объединяют разные варианты, а смена языка не меняет их идентификаторы.
6. `sourceRef` указывает на соответствующий исходный узел текущей БД; после замены прежние ссылки не используются.
7. Индекс RU/EN подключается как `database`; тексты не копируются в каждое представление.

## Дальнейшее проектирование

- Подсчёт и раскладка для `NOT`, `NAND`, `NOR`; структура дерева, связи с путями и правила `AND`/`OR` уже определены.
- Программные типы вложенных полей `details` по согласованному составу ТЗ диагностики; для текущих кодов `params` равен `{}`.
- Программные типы и интерфейсы модулей для производного результата; ошибки преобразования обрабатываются по [разделению ответственности](TZ_DATABASE_OPENING_RU.md#ответственность-за-проверки), без повторной валидации исходной БД.
