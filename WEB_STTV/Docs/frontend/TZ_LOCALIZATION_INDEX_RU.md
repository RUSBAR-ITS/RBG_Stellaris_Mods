## Статус и границы

С 2026-11-17 требования этого документа к одному файлу и неквалифицированным ссылкам заменены утверждённым [ТЗ второго этапа](TZ_FRONTEND_STAGE_2_RU.md). Актуальная реализация открывает три БД версии 5 одним набором и использует ссылки `{ database, pointer }`; остальные применимые требования сохраняются.

Документ фиксирует согласованный пользователем 2026-11-17 формат записи индекса локализации. Он уточняет [общий механизм локализации](TZ_LOCALIZATION_RU.md) и [результат Worker](TZ_WORKER_RESULT_RU.md). Противоречивые тексты считаются ошибкой данных, требующей ручного разбора; прежнее правило вывода маркера при конфликте заменено этим решением.

На этом этапе оформляется документация. Реализация фронтенда, изменение бэкэнда и пересборка БД не выполняются.

## Адрес и запись индекса

Адрес строки в общем механизме: источник → язык → ID. Компонент передаёт источник и ID, язык предоставляет состояние приложения. Для источника `database` используются `data.localization.ru` и `data.localization.en` ответа `ready`; ключ каждой записи берётся из `requested_key` исходной локализации.

Источник, язык и запрошенный ID определяются положением записи в индексе и внутри неё не дублируются. Запись содержит три обязательных поля:

| Поле | Тип и назначение |
| --- | --- |
| `status` | `resolved` — текст найден; `missing` — текст отсутствует |
| `text` | Строка при `resolved`, включая `""`; `null` при `missing` |
| `origins` | Массив сведений об исходных записях |

Пример записи `data.localization.ru.tech_titans` по текущей БД:

```json
{
  "status": "resolved",
  "text": "Титаны",
  "origins": [
    {
      "recordRef": "/documents/7/items/5/enrichments/localization/ru/name",
      "key": "tech_titans",
      "raw": "Титаны",
      "source": {
        "tier": "RU_LOC_TIER_2",
        "file": "technology_l_russian.yml",
        "line": 51
      },
      "inheritedFrom": null,
      "unresolvedReferences": []
    }
  ]
}
```

`resolved` означает наличие готового текста для отображения. Сохранённые игровые подстановки и нераскрытые ссылки сами по себе не делают строку отсутствующей; обработка игровой разметки этим этапом не вводится.

## Происхождение строки

Каждый элемент `origins` для БД содержит следующие обязательные поля:

| Поле | Тип и источник |
| --- | --- |
| `recordRef` | Строковый путь к исходной записи локализации внутри открытой БД |
| `key` | Фактически использованный ключ перевода; строка либо `null` при отсутствии перевода |
| `raw` | Исходная строка до раскрытия статических ссылок бэкэндом; строка либо `null` |
| `source` | Объект происхождения перевода либо `null`: `tier` и `file` — строки, `line` — положительное целое число |
| `inheritedFrom` | Значение исходного `inherited_from`: путь к основной технологии либо `null` |
| `unresolvedReferences` | Массив строк из исходного `unresolved_references` |

`recordRef` адресует запись `name` или `description`, а `inheritedFrom` — узел основной технологии. Оба пути относятся к JSON текущей БД, а не к файлам на диске; при замене БД прежние ссылки удаляются вместе с индексом.

`source` описывает происхождение перевода и отличается от источника поиска `database`. Метаданные копируются из результата бэкэнда; повторного чтения файлов локализации не происходит.

Итоговый `text` хранится один раз на запись индекса. В элементах `origins` он не дублируется; `raw` сохраняется как отдельное исходное значение, даже если оно совпадает с итоговым текстом. Все исходные записи объединённой строки остаются представленными в `origins`.

## Объединение и отсутствие текста

Сопоставление выполняется внутри сочетания источник/язык/ID. ID и тексты сравниваются как сохранённые строки, без изменения регистра, пробелов или разметки. `null` означает отсутствие текста и не является отдельным текстовым вариантом.

| Входные записи для одного ID | Результат |
| --- | --- |
| Один найденный текст | `resolved`, найденный `text` |
| Несколько одинаковых найденных текстов | `resolved`, один итоговый текст, все исходные записи в `origins` |
| Все тексты равны `null` | `missing`, `text: null`, сохранённое происхождение |
| Один однозначный текст вместе с пропусками `null` | `resolved`, найденный текст, происхождение найденных и отсутствующих переводов |
| Найденная пустая строка `""` | `resolved`, `text: ""` |
| Два или более различающихся найденных текста, включая сочетание пустого и непустого | Ошибка подготовки данных |

При поиске отсутствующего ID или записи `missing` общий механизм выводит `⟦ID⟧`. Создание записи для каждого произвольного отсутствующего ID не требуется. Найденная пустая строка выводится пустой. Подмена выбранного языка другим не выполняется.

## Противоречивые тексты

Разные итоговые тексты при одинаковых источнике, языке и ID считаются ошибкой данных, требующей ручного разбора. Подготовка индекса завершается ошибкой. Диагностика содержит:

- Источник поиска, язык и ID строки.
- Различающиеся итоговые тексты.
- Ссылки на исходные объекты и записи локализации.
- Сведения об источниках переводов и наследовании.

При открытии БД ошибка возвращается ответом `error` по [протоколу Worker](TZ_WORKER_PROTOCOL_RU.md). Каталог, связи и индекс не публикуются частично или как успешный пустой результат. Дальнейшее исправление причины и повторное открытие выполняются по решению пользователя согласно [ТЗ открытия БД](TZ_DATABASE_OPENING_RU.md#ошибки-и-повтор).

В готовом индексе состояния `conflict` нет. Маркер отсутствующего перевода не используется для обхода ошибки противоречивых текстов. Для этой ошибки используется `localization_conflict` с `severity: "error"` по [ТЗ диагностики](TZ_DIAGNOSTICS_RU.md). В `details` каждый различающийся текст связывается со своим происхождением по существующей структуре `origins`; `params` равен `{}`. Точные программные типы вложенных полей уточняются отдельно.

## Наследование и встроенные строки

Наследование уже выполнено бэкэндом. Ключом индекса остаётся `requested_key`, фактический `key` и родитель сохраняются в `origins`. Например, `tech_biogenesis_titans_desc` остаётся ID поиска, даже если его описание получено по `tech_titans_desc`. Фактический ключ не создаёт дополнительный псевдоним в индексе; при его собственном присутствии он индексируется обычным порядком.

Если наследование от разных родителей приводит к различающимся текстам под одним ID, действует общее правило ошибки. Фронтенд не выбирает родителя самостоятельно и не повторяет разрешение переводов.

Встроенные файлы `locales/ru.json` и `locales/en.json` сохраняют простой формат `ID → строка`. Их обработчик приводит найденную запись к той же структуре, например:

```json
{
  "status": "resolved",
  "text": "Язык",
  "origins": []
}
```

Для встроенных строк `origins` на этом этапе пуст. Общий поиск одинаков для обоих источников; подстановка параметров интерфейсных шаблонов остаётся отдельной операцией по ТЗ локализации.

## Передача и использование

Worker подготавливает оба языковых индекса БД и передаёт их вместе с каталогом и связями только после успешного завершения всей подготовки. Основной поток подключает результат как источник `database`. Встроенный источник подготавливается отдельно из ресурсов фронтенда.

Поиск и вывод используют готовые записи без обхода дерева и сообщений Worker для каждой строки. Смена языка выбирает другую ветку индекса; смена источника данных заменяет соответствующий индекс. Полное дерево остаётся в Worker, файлы БД и игры не изменяются.

## Критерии приёмки

Проверки выполняются после реализации:

1. Запись содержит `status`, `text`, `origins`; допустимы только согласованные состояния и соответствующие типы текста.
2. Одинаковые тексты объединяются с сохранением происхождения всех записей; итоговый `text` в `origins` не дублируется.
3. Все значения `null` дают `missing`; сочетание пропусков и одного однозначного текста даёт `resolved` с полным происхождением.
4. Отсутствующий ID и `missing` дают маркер; `""` остаётся найденной пустой строкой. Подмена языка отсутствует.
5. Различающиеся тексты, включая пустой и непустой, дают ошибку с предусмотренными сведениями; `ready` и частичные данные не публикуются.
6. Наследованное описание находится по `requested_key`, сохраняет фактический ключ и родителя; неоднозначность при наследовании также считается ошибкой.
7. `recordRef` указывает на исходную запись локализации текущей БД; метаданные переданы без повторного чтения игровых файлов.
8. Встроенные строки приводятся к общей структуре с пустым `origins`; RU/EN используют один механизм поиска без повторного построения индекса при смене языка.

## Дальнейшее проектирование

Этот документ определяет запись индекса и правила её подготовки; работа с ошибками некорректных параметров интерфейсных шаблонов уточняется отдельно.
