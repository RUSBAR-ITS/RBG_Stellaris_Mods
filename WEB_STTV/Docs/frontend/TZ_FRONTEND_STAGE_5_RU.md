## 1. Статус и границы

**Утверждено пользователем и реализовано 2026-11-19, фронтенд 0.0.5.** Согласованные решения собраны в [правилах цепочек и сортировки](TECHNOLOGY_CHAINS_AND_SORTING_RU.md). Фактические результаты и ограничения — в [руководстве реализации](FRONTEND_STAGE_5_RU.md).

Заменить независимую сортировку столбцов сеткой деревьев по сохранённым `parent_tech` и `children`. Использовать готовый набор [этапа 17](../TZ_BACKEND_STAGE_17_RU.md) и результаты [этапа 16](../TZ_BACKEND_STAGE_16_RU.md). Родителей рассчитывает Python; фронтенд определяет только порядок и координаты карточек.

Пользователь выбрал первый этап для **готовой комбинации**. Варианты берутся из её параметров. Интерактивная смена вариантов, вызов Python из браузера, HTTP API и новый пересчёт родителей не входят в этап. Автоматическая генерация БД, запись в исходный набор, сохранение координат между запусками и portable-упаковка также не добавляются.

Области идут сверху вниз: физика, социология, инженерия. Дизайн остаётся простым: существующие карточки с названием, тултип с названием и описанием, RU/EN, темы, меню, панель состояния и прокрутка. Линии связей, дополнительные пререквизиты и особые способы получения пока не отображаются.

## 2. Данные и комбинация

Сохранить явное открытие каталога и потоковый читатель этапа 4. Начальное открытие читает манифест и документы технологий; остальные 14 видов не нужны для размещения и не загружаются ради повторения отбора родителей.

Расширить компактную проекцию адаптера, не передавая весь AST в основной поток:

| Источник | Необходимые данные |
| --- | --- |
| Определение технологии | Базовый ID, `tier`, `start_tech`, `levels`, технологические требования и `NodeRef` |
| Представление | ID `base` / `swap:N`, эффективная область, ссылки на название и описание |
| `node.enrichments.technology_tree[combination_id]` | `parent_tech`, `children`, `status` |
| `manifest.technology_tree` | Версия обогащения, выбранная комбинация, её параметры, входные и итоговые ревизии |

При отсутствии `start_tech` использовать `false`. `levels` без явного значения не считать бесконечным повторением. `start_tech` и `levels` читать из базового определения, не из номера в ID. Игровой `tier` сохраняется отдельно от уровня отображения.

Одинаковые повторы `start_tech = yes`, ранее зафиксированные у трёх технологий в [исследовании стартовых технологий](STARTING_TECHNOLOGIES_RU.md), дают одно значение признака. Противоречащие значения завершают открытие ошибкой.

Комбинация выбирается конфигом; начальное значение — `reference_default`. Открывать именно её, а не первую найденную. Все представления выбирать по полному нормализованному `parameters.variants` сохранённой комбинации. Не допускать отображения изменённого варианта с родителями базовой комбинации.

При отсутствии нужной комбинации, неподдерживаемой версии, неполных записях или несовпадении её входных ревизий с манифестом открытие завершается диагностикой. Не запускать бэкенд автоматически, не подставлять другую комбинацию и не возвращаться к старой сортировке. Набор после внешнего обогащения открывается заново явным действием пользователя.

## 3. Настройки и модули

Предлагаемый отдельный конфиг — `config/frontend/tree_layout.json`. Он задаёт ID комбинации, приоритет стартовых корней, удаляемые при сравнении ID цифры `0–9`, соответствие RU/EN языкам сортировки и правило переноса повторяемых технологий: `levels = -1`, игровой `tier = 5`, наличие хотя бы одного технологического пререквизита → уровень отображения 6. Не ограничивать область этого пререквизита.

Имена извлекаемых игровых полей добавить в действующий конфиг адаптера. Порядок областей брать из существующей настройки; размеры карточки, интервалы, заголовки и отступы — из `config/frontend/interface.json`, цвета и шрифты — из словаря оформления. Не дублировать числа в расчёте координат и CSS.

Отделить извлечение обогащения, подготовку деревьев, сравнение названий, расчёт геометрии и React-представление. Предлагаемое место чистых модулей геометрии — `src/frontend/data/tree/`. Удалить прежнее независимое упорядочивание столбцов и его вызов из проверки адаптера; не оставлять его как запасной режим.

Общие функции переиспользуются. Ориентир — до 200 строк кода на файл; свыше 200 проверить разбиение, свыше 300 вынести самостоятельные части. Не вводить библиотеку автоматической раскладки графов или дополнительный пул Worker. Извлечение остаётся в существующем Worker; компактную геометрию вычисляет чистый модуль фронтенда.

## 4. Деревья внутри областей

Для размещения использовать область выбранного представления. Началом отдельного дерева внутри области является технология:

- с сохранённым `status = root` и `parent_tech = null`;
- с `status = ambiguous` и `parent_tech = null`: карточка сохраняется, состояние попадает в отчёт;
- с подтверждённым родителем из другой области науки.

В последнем случае связь остаётся в исходных данных, но не участвует в геометрии между областями. Не менять `parent_tech`, не удалять ребёнка из сохранённого `children` и не искать ему замену. При подготовке дерева обходить только детей той же эффективной области; каждый переход между областями начинает другое дерево. Возврат потомка в первоначальную область также образует отдельное начало там.

Все технологии должны размещаться ровно один раз. Наличие одного или нескольких пререквизитов не исключает карточку из поля. `weight = 0` и особые условия получения сейчас не меняют состав поля, порядок или оформление. Дополнительные пререквизиты не задают вертикальные ограничения между выбранными ветвями.

## 5. Порядок деревьев и ветвей

Сначала размещать целые деревья, начальная технология которых имеет `start_tech = yes`, затем остальные. Стартовый потомок не меняет группу дерева и не переносится отдельно. Это заменяет прежнее требование размещать все стартовые карточки выше всех нестартовых.

В каждой группе сравнивать отображаемые названия начальных технологий на текущем языке. Использовать тот же механизм локализации, что и карточка, включая существующее поведение при отсутствии текста. Названия сравнивать средствами языковой сортировки с явно заданным языком; равные результаты разрешать стабильным сравнением базовых ID. Порядок не зависит от чтения файлов или перечисления свойств JSON.

Для каждого родителя первым размещать ребёнка, чей ID точно совпадает с родительским после удаления цифр `0–9`; остальные символы сохраняются. Его потомки занимают свою ветвь до следующего ребёнка. Остальные дети сортируются по названию на текущем языке, затем ID. Если совпадений нет, этот порядок применяется ко всем детям.

**Утверждённое техническое дополнение:** если совпадений ID несколько, сначала разместить всю группу совпавших детей, внутри неё применить название и ID. Это не выбирает нового родителя и не объявляет игровую альтернативу обязательной. В текущем наборе таких случаев нет; поведение проверяется синтетически.

## 6. Расчёт строк и высоты

Координата карточки для раскладки — `(area, column, row)`. `column` равен уровню отображения; `row` — неотрицательное целое внутри области. Каждый столбец использует общие номера строк, поэтому пустые позиции сохраняются. Глубина дерева не определяет столбец.

Предлагаемый алгоритм — последовательный обход сверху вниз с учётом уже занятых клеток:

1. Первое дерево начинается со строки 0. Разместить его корень в своём столбце.
2. Упорядочить детей по разделу 5. Первый ребёнок пробует строку родителя, если его столбец отличается; при том же столбце начинает со следующей строки.
3. Если целевая клетка занята, в том числе предком, найти первую свободную строку ниже, не нарушая нижнюю границу для этой ветви. Затем рассчитывать потомков относительно найденного положения. Предков и уже размещённые соседние ветви не сдвигать.
4. Разместить всю ветвь этого ребёнка. Следующий ребёнок начинает ниже её самой нижней занятой строки, даже если в более ранних строках есть свободные клетки.
5. Нижняя граница дерева/ветви — максимум строк её корня и всех потомков. Высота в строках равна `bottom_row - root_row + 1`: учитываются и пустые строки. Высота листа равна 1.
6. Следующее целое дерево начинается со строки `bottom_row + 1` предыдущего дерева. Не уплотнять его в пустотах предыдущего дерева. Отступ между соседними строками задаётся обычным интервалом карточек.

Сдвиг применяется к началу соответствующей дочерней ветви и её дальнейшему построению, а не к родителю. Если конфликт возникает у более глубокого потомка, сдвигается его ветвь; уже свободно размещённый промежуточный предок сохраняет строку.

Согласованный пример: `A1 → A2 → A3 → A4`, а `B1 → B2` — другая дочерняя ветвь `A1`. Приоритет прямого продолжения сохраняет пустое место справа от `A1`:

```text
Уровень 1   Уровень 2   Уровень 3
   A1
   A2           A3          A4
                B1          B2
```

Согласованный пример `A → B → C`: уровни 3 → 4 → 3. Клетка `C` в строке родителя занята `A`, поэтому ниже начинается только ветвь `C`:

```text
Уровень 3   Уровень 4
   A            B
   C
```

Переходы через несколько уровней оставляют промежуточные столбцы пустыми. Переход к меньшему уровню занимает столбец левее родителя; при свободной клетке строка сохраняется. Номер уровня не исправляется ради направления связи.

## 7. Отображение и взаимодействие

Преобразовывать столбцы и строки в пиксели через существующие размеры и интервалы. Высота области: заголовки плюс `row_count × cardHeight + max(0, row_count − 1) × cardGap`. Для пустой области `row_count = 0`. Между областями действует существующий `areaGap`. Общая ширина учитывает столбцы от 0 до максимального уровня отображения, включая пустые промежуточные столбцы.

Перед столбцом 0 нет искусственного резервного столбца; сохраняется только обычный отступ поля. Карточки не растягиваются из-за пустых строк. Можно использовать CSS Grid или явные позиции, но порядок DOM и клавиатурного обхода должен следовать видимому порядку областей, деревьев и ветвей, а не прежним независимым спискам столбцов.

Смена языка пересчитывает названия, порядок деревьев/детей и геометрию по уже подготовленным данным. Она не меняет родителей и параметры комбинации, не читает документы повторно и не вызывает бэкенд. Смена темы, открытие тултипа и сворачивание меню не меняют координаты сетки. Геометрия зависит от снимка, выбранной комбинации, языка и настроек размещения; её переиспользование в памяти допустимо только при совпадении этих входов.

В этом этапе карточка показывает представление из комбинации. Ручной список вариантов скрыт; нельзя менять только текст или область, оставляя старых родителей. Новая настройка выбора комбинации в меню не добавляется: другую готовую комбинацию можно задать конфигом и явно открыть набор.

Пересчёт поля сохраняет текущую прокрутку насколько позволяют новые границы, затем ограничивает её размерами поля. Всплывающие элементы продолжают позиционироваться относительно карточек. Обновление страницы и запуск приложения не открывают БД и не запускают генерацию.

## 8. Проверки входа и диагностика

Не дублировать полную проверку AST по JSON Schema, семантический отбор родителей или анализ 15 видов объектов. Сохраняются хеширование читаемых документов и проверки формата этапа 17. Дополнительно проверяется только контракт данных, необходимых новой сетке.

Сопоставить `source_set_id` комбинации с `set_id` манифеста и сохранённые `inputs[].hash` с `datasets[kind].source_revision`. Это сравнение подготовленных метаданных, а не чтение файлов всех видов или повторный расчёт Python-ревизий. В отчёте сохранять `calculation_revision` и `result_revision`, не объявляя это новым аудитом всех входов.

При извлечении и обходе проверять наличие записи выбранной комбинации у каждой технологии, допустимый статус, существование указанного варианта и родителя, отсутствие повторов в детях, согласованность используемых родительских/дочерних ссылок, отсутствие цикла, покрытие всех карточек и отсутствие наложений. Пропущенная запись обогащения не равна `root`. Некорректный граф завершает подготовку поля диагностикой; автоматическое исправление или выдуманный родитель не допускаются.

`ambiguous` — корректное сохранённое состояние с предупреждением и самостоятельным началом дерева, а не ошибка формата. Его лог содержит ID, `NodeRef`, комбинацию и её параметры/ревизии, язык и настройки поля. Не выдумывать трассу отбора: подробности решения остаются в отчёте бэкенда.

Добавить в существующий отчёт фронтенда ID комбинации, выбранные варианты, ревизии, язык, настройки размещения, число технологий/деревьев по областям, число скрытых межобластных родительских связей, размеры сетки и время подготовки геометрии. Ошибки отсутствующей/устаревшей комбинации, неполного обогащения и невозможности размещения должны различаться; сообщения RU/EN идут через существующие словари и панель состояния.

## 9. Синтетические проверки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Лист, линейная цепочка, пропуск уровней | Свои столбцы; продолжения разделяют строку, если она свободна |
| Родитель и ребёнок одного уровня | Ребёнок ниже; одинаковая клетка не используется |
| Развилка с основным продолжением по ID | Сначала вся основная ветвь; боковая ветвь не заполняет пустоту над ней |
| Переход 3 → 4 → 3 | Схема из раздела 6: `A` и `B` в одной строке, `C` ниже |
| Несколько обратных переходов и вложенных развилок | Нет наложений; нижние границы включают всех потомков |
| Несколько деревьев | Целые деревья не перемешиваются, следующее начинается после предыдущего |
| Стартовый корень и стартовый потомок | Приоритет только у дерева со стартовым корнем; потомок остаётся в своей ветви |
| Родитель другой области и возврат потомка обратно | Самостоятельные начала в соответствующих областях; исходные связи сохранены |
| Бесконечное повторение | Только `levels = -1`, `tier = 5` и наличие технологического пререквизита дают столбец 6; исходный `tier` остаётся 5 |
| RU/EN, одинаковые названия, несколько совпадений ID | Воспроизводимый порядок по выбранному языку и ID, без смены родителей |
| Другой порядок документов и массивов `children` | Те же координаты при тех же входах |
| Неполная/устаревшая комбинация, неизвестный вариант, цикл, неверные ссылки | Точная диагностика без старой сортировки или автоматического пересчёта |
| Сохранённая неоднозначность | Карточка и потомки размещены, предупреждение содержит контекст поля |

Проверки геометрии должны сверять ожидаемые позиции и инварианты, а не повторять реализацию алгоритма. Проверить обе согласованные схемы отдельными примерами, в том числе случай, когда целевая клетка свободна и сдвиг не нужен.

## 10. Реальный набор и приёмка

Использовать готовый набор `data/stage17/database_set/manifest.json`, не пересобирать игру ради проверки интерфейса. Для `reference_default` показать все 679 технологий ровно один раз; сохранённые 178 корней и 501 выбранный родитель не меняются. Число деревьев для размещения считать отдельно: оно также включает ветви с родителем из другой области.

Проверить лазеры, пять мутаций уровня 3 с родителем уровня 4, `tech_arkship_exodus_jump`, `tech_mine_dark_matter`, а также физические `tech_encryption_1` и `tech_decryption_1` с социологическим родителем. Эти примеры служат проверкой, а не захардкоженными исключениями. Технологии с нулевым весом остаются обычными карточками.

Отдельно открыть другую подготовленную комбинацию через конфиг и подтвердить использование её вариантов, областей и связей; на контрольном наборе доступна `reference_variants`. Файлы набора и их хеши после просмотра не меняются. Переключение языка не читает их заново; другие 14 видов остаются незагруженными.

Выполнить относящиеся модульные тесты TypeScript, typecheck, сборку и браузерные сценарии: явное открытие, ошибки комбинации, поле и отсутствие наложений, RU/EN, темы, меню, прокрутка, тултипы, отсутствие ручного выбора варианта и сохранение отчёта. Адаптировать прежние тесты сортировки и переключения вариантов к согласованным границам этапа.

Визуально проверить обе темы и оба языка. Зафиксировать время открытия и пересчёта геометрии, реально прочитанные документы и отзывчивость без обещания заранее заданного ускорения. Пользовательская проверка нужна для удобства размещения на реальном поле; это веб-интерфейс, запуск Stellaris для приёмки этого этапа не требуется.

## 11. Результаты этапа

Ожидаются обновлённая проекция адаптера, конфиг размещения, независимые модули деревьев и геометрии, интеграция в поле, локализованные сообщения, отчёт и проверки. Двоюзычное руководство реализации фиксирует фактически выполненные проверки и ограничения. Обновить README и changelog; при реализации увеличить патч-версию фронтенда с 0.0.4 до 0.0.5.

Публикация `location` в БД, постоянный кэш координат, ручной выбор вариантов с пересчётом, линии всех требований и отметки особого получения остаются отдельными этапами. Формат хранения БД и правила выбора родителей в этом этапе не меняются.
