## Статус и назначение

Правило согласовано 2026-11-18 для будущего алгоритма выбора `parent_tech`. Это часть проектирования цепочек, а не ТЗ на реализацию. Текущая итерация меняет только документацию.

Прямое улучшение здания или компонента помогает выбрать продолжение среди оставшихся технологических пререквизитов. Выбранный `parent_tech` служит опорой размещения; полный граф игровых требований сохраняется.

## Входные данные

- Текущая технология `T` и оставшееся множество кандидатов `C` после предыдущих критериев.
- Явная направленная связь объектов `A → B`: `upgrades` у здания либо `upgrades_to` у компонента. Каждый указанный переход рассматривается отдельно.
- Технологические требования `prerequisites` обоих объектов и ссылки на их источники.

Если в `C` уже один кандидат, отбор завершён и правило не применяется.

## Правило сопоставления

1. Рассмотреть одну прямую связь `A → B`.
2. Убедиться, что требования каждого объекта состоят только из обязательных положительных ссылок на технологии: обычный список или объединение через `AND`.
3. Получить множества требований `R_A` и `R_B`. Повтор одного ID не создаёт дополнительного требования.
4. Найти общую часть `S = R_A ∩ R_B` и для сравнения получить `D_A = R_A − S`, `D_B = R_B − S`.
5. Связь подтверждает продолжение `P → T`, только если `D_A = {P}`, `D_B = {T}` и `P` входит в текущий набор `C`.

Простой случай «объект A требует только P, объект B требует только T» следует тому же правилу: общая часть пуста. Если после вычитания с любой стороны осталось ноль или несколько технологий, эта связь не подтверждает единственного продолжения.

Вычитание общей части — аналитическое сравнение. Требования объектов и технологий в БД не сокращаются и не перезаписываются.

## Результат отбора

Собрать множество `M` всех кандидатов из `C`, подтверждённых хотя бы одной подходящей связью:

| Результат | Действие |
| --- | --- |
| В `M` один кандидат | Выбрать его и завершить отбор. |
| В `M` несколько кандидатов | Передать `M` следующему критерию. |
| `M` пусто | Пропустить критерий, сохранив прежний набор `C`. |

Кандидаты, исключённые раньше, не возвращаются. Число подтверждающих объектов не даёт дополнительных голосов: варианты компонента для разных размеров кораблей не должны перевешивать другую цепочку. При этом все подтверждения и ссылки на исходную связь и требования обоих объектов сохраняются для объяснения результата.

## Границы правила

- Требования с `OR`, отрицанием или иной сложной логикой на этом шаге не используются как доказательство. Их исходная структура сохраняется; альтернативы не превращаются в обязательные требования.
- Рассматривается один явный переход между объектами. Автоматический проход через промежуточные улучшения относится к дальнейшему проектированию косвенных связей.
- Общий `component_set`, `building_sets`, название или назначение сами по себе не подтверждают прямого улучшения.
- Сопоставление специальных условий доступности и функционального родства — отдельные последующие критерии.

## Примеры

Примеры проверены по локальным файлам Stellaris 4.5.4. Таблица показывает подтверждающую пару, а не результаты нового полного прогона алгоритма.

| Предшественник `P` | Продолжение `T` | Прямая связь объектов |
| --- | --- | --- |
| `tech_cloaking_3` | `tech_cloaking_dark_matter` | [SCIENCE_CLOAKING_3 → SCIENCE_CLOAKING_DARK_MATTER](E:/SteamLibrary/steamapps/common/Stellaris/common/component_templates/00_utilities_aux_first_contact.txt:1249) |
| `tech_basic_health` | `tech_frontier_health` | [building_medical_1 → building_medical_2](E:/SteamLibrary/steamapps/common/Stellaris/common/buildings/07_amenity_buildings.txt:732) |
| `tech_xeno_diplomacy` | `tech_xeno_relations` | [building_embassy → building_grand_embassy](E:/SteamLibrary/steamapps/common/Stellaris/common/buildings/02_government_buildings.txt:763) |

Пример общей обязательной технологии: [BIO_DRIVE_2](E:/SteamLibrary/steamapps/common/Stellaris/common/component_templates/00_utilities_drives.txt:337) улучшается до [BIO_DRIVE_3](E:/SteamLibrary/steamapps/common/Stellaris/common/component_templates/00_utilities_drives.txt:367).

```text
R_A = {tech_hyper_drive_2, tech_hyper_drive_bio_integration}
R_B = {tech_hyper_drive_3, tech_hyper_drive_bio_integration}
S   = {tech_hyper_drive_bio_integration}
D_A = {tech_hyper_drive_2}
D_B = {tech_hyper_drive_3}
```

Это подтверждает переход `tech_hyper_drive_2 → tech_hyper_drive_3`, если первый ID остаётся кандидатом для второго. Сам пререквизит присутствует в [определении технологии](E:/SteamLibrary/steamapps/common/Stellaris/common/technology/00_phys_tech.txt:2669).
