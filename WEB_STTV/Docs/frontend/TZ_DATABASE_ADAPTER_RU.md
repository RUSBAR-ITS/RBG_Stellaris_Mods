## Статус и назначение

Документ фиксирует модель данных интерфейса и границы ответственности адаптера, согласованные пользователем 2026-11-16. Реализация адаптера ещё не начата.

Основа — [концепт интерфейса](CONCEPT_RU.md), [ТЗ поля технологий](elements/TZ_TECHNOLOGY_FIELD_RU.md), [карточки](elements/TZ_TECHNOLOGY_CARD_RU.md) и [общего механизма локализации](TZ_LOCALIZATION_RU.md).

Адаптер выделяет из подготовленной БД данные для первого экрана и формирует каталог в памяти. Компоненты получают понятные объекты технологий и представлений; правила чтения дерева сосредоточены в адаптере.

Адаптер реализуется модулями TypeScript и выполняется в Web Worker по [ТЗ открытия БД](TZ_DATABASE_OPENING_RU.md#чтение-файла-и-web-worker). Чтение файла и протокол сообщений отделяются от извлечения технологий и обработки требований. Полное дерево остаётся в памяти Worker; основной поток получает подготовленные данные для отображения. `sourceRef` разрешается на стороне Worker, где хранится соответствующий исходный узел.

## Исходные данные и границы

Источник — подготовленная БД с деревом результатов парсинга и обогащением `enrichments.localization`. Адаптер использует сохранённые данные; повторный разбор игровых файлов и вычисление условий конкретного государства не входят в его работу.

Исследование текущей БД этапа 10 установило:

| Показатель | Значение |
| --- | --- |
| Базовые технологии | 679; у всех заданы `area` и `tier` |
| Варианты `technology_swap` | 206 |
| Варианты, меняющие область науки | 7 |
| Логические блоки в `prerequisites` | 21 блок `OR` |
| Неразрешённые ссылки на технологии в `prerequisites` | 0 |
| Прочие определения категорий и уровней исследований | 19; не становятся карточками технологий |

Числа описывают исследованные данные и не зашиваются в реализацию. Принадлежность к технологиям определяется по игровым определениям и их расположению, а не по наличию перевода или префиксу отдельного поля. Точные настройки выборки фиксируются при проектировании реализации.

Каталог является производным представлением в памяти. Состав исходной БД, её структура и сохранённые игровые механики не меняются. Поля, не нужные первому экрану, остаются доступны в исходных узлах; они не копируются в каждую карточку.

## Каталог технологий

Результат адаптера — словарь по базовому ID технологии. Одна запись соответствует одной базовой технологии и одной карточке поля.

| Поле | Содержимое |
| --- | --- |
| `id` | Строка: базовый ID технологии из БД; совпадает с ключом каталога |
| `tier` | Целое число: уровень технологии для назначения столбца |
| `prerequisites` | Дерево технологических требований с сохранением логических операций |
| `prerequisiteIds` | Массив уникальных ID непосредственно упомянутых технологий, включая альтернативы; результат общего обработчика требований |
| `requirementCount` | Неотрицательное целое число требований по согласованным правилам; результат общего обработчика требований |
| `representations` | Упорядоченный массив: основное представление и варианты |
| `sourceRef` | Ссылка на исходный узел базовой технологии в загруженной БД |

Область науки хранится у представления: выбранное представление определяет итоговую область карточки. Значения `tier` и требований относятся к базовой технологии и сохраняются при ручном переключении её вариантов по ТЗ карточки.

Уровень извлекается из данных, а не из имени технологии. Диапазон `0…5` соответствует текущей БД и не заменяет чтение `tier`.

## Представления технологии

У каждой технологии обязательно есть основное представление. За ним идут отдельные представления для всех её блоков `technology_swap` в исходном порядке БД.

| Поле | Содержимое |
| --- | --- |
| `id` | Идентификатор основного представления или конкретного блока варианта; различает представления внутри базовой технологии |
| `variantNumber` | Положительный номер варианта, начиная с 1; у основного представления поле отсутствует |
| `area` | Итоговая область науки: `physics`, `society` или `engineering` |
| `nameId` | ID строки названия для общего механизма локализации |
| `descriptionId` | ID строки описания для общего механизма локализации |
| `sourceRef` | Ссылка на исходный узел основного представления или соответствующий блок `technology_swap` |

У основного представления `area` берётся из базовой технологии. У варианта используется собственная область, если она задана, иначе — область основной технологии. В каталоге представление уже содержит итоговое значение, поэтому карточка не вычисляет это наследование.

`variantNumber` определяется порядком блоков `technology_swap`, а не совпадением названий или порядком локализованных подписей. Он нужен для суффиксов по ТЗ карточки и не заменяет идентичность представления.

Пример для `tech_titans`:

| Представление | Номер варианта | Итоговая область | `nameId` |
| --- | --- | --- | --- |
| Основное | Отсутствует | `engineering` | `tech_titans` |
| Первый блок варианта | 1 | `engineering`, унаследована | `tech_nomads_titans` |
| Второй блок варианта | 2 | `society`, задана вариантом | `tech_biogenesis_titans` |

Условия `trigger` не используются для автоматического выбора или исключения вариантов. На первом этапе пользователь переключает представление вручную.

## Идентичность и ссылки на источник

Базовый ID сохраняется при смене представления, языка, темы и области науки. Выбранное представление различается сочетанием базовой технологии и идентификатора конкретного представления.

Разные блоки с одинаковыми названиями или ID локализации остаются разными представлениями. Идентификатор представления не строится только из отображаемого текста или ключа его названия.

По [ТЗ результата Worker](TZ_WORKER_RESULT_RU.md) основное представление имеет ID `base`, варианты — `swap:1`, `swap:2` и далее в исходном порядке. Номер в `swap:N` совпадает с `variantNumber`; у `base` поле `variantNumber` отсутствует.

Идентичность представлений гарантируется в пределах загруженной БД. Сопоставление выбранного варианта после перестроения БД относится к проектированию постоянного состояния; стабильность номера или расположения блока между разными сборками не предполагается.

`sourceRef` — строковый путь к исходному узлу внутри загруженного дерева БД, например `/documents/7/items/5` для `tech_titans` в текущем файле. Ссылка относится только к той БД, из которой получен каталог; при замене БД прежние ссылки удаляются вместе с каталогом. Разрешение пути выполняется в Worker, где хранится дерево.

## Технологические требования

Адаптер извлекает только `prerequisites` базовой технологии и сохраняет вложенность и логические операции. Условия из `potential`, проверки DLC, государства, вида, зданий и другие ограничения доступности не добавляются в это дерево.

Обычный список сохраняет смысл одновременных требований. Отсутствие `prerequisites` означает отсутствие технологических требований. Группы альтернатив не превращаются в список одновременно обязательных технологий.

Например, требования `tech_titans` имеют структуру:

```text
OR
├─ tech_battleships
└─ tech_stinger_growth_2
```

Отдельный общий обработчик требований получает это дерево и вычисляет:

- Набор непосредственных предшественников: уникальные ID непосредственно упомянутых технологий, включая участников альтернатив, без транзитивного расширения.
- Число требований: отдельная обязательная технология даёт одно, одновременно обязательные требования суммируются, группа `OR` считается одним, отсутствие требований даёт ноль.
- Связи от предшественников к зависимой технологии для дальнейшей работы поля.

Для приведённого примера набор содержит два ID, а число требований равно одному. Дерево остаётся источником логики: связи сами по себе не означают, что все альтернативы обязательны. Порядок перечисления ID не меняет набор предшественников; исходное дерево при этом сохраняется.

Правила вычисления не дублируются в карточках, группировке и прочих потребителях. [ТЗ технологических требований](TZ_TECHNOLOGY_REQUIREMENTS_RU.md) задаёт узлы `technology` и `group`, корневой `AND`, правила подсчёта для `AND`/`OR` и связи `from`/`to` с массивом `requirementPaths`. Использование `NOT`, `NAND` и `NOR` в подсчёте и раскладке требует отдельного согласования.

## Связь с локализацией

`nameId` и `descriptionId` соответствуют `requested_key` записей названия и описания выбранного представления. Потребитель передаёт их механизму локализации с источником БД; язык предоставляет приложение.

Тексты, сведения об их происхождении, объединение повторов и наследованное описание следуют [ТЗ локализации](TZ_LOCALIZATION_RU.md) и [ТЗ записей индекса](TZ_LOCALIZATION_INDEX_RU.md). Запись содержит `status`, `text`, `origins`; отсутствующие переводы допускают просмотр с маркерами, противоречивые тексты блокируют подготовку результата и требуют ручного разбора. Адаптер не формирует копию перевода для каждого языка внутри представления и не раскрывает игровую разметку.

Выбор представления меняет используемые ID строк. Смена языка меняет результат их разрешения, сохраняя базовую технологию и выбранное представление.

## Разделение ответственности

| Часть | Ответственность |
| --- | --- |
| Адаптер БД | Извлечение технологий и представлений, итоговая область, ID строк, дерево требований и ссылки на источник |
| Общий обработчик требований | Вычисление непосредственных предшественников, числа требований и связей |
| Механизм локализации | Получение текста по источнику, ID и системному языку |
| Поле технологий | Учёт выбранных представлений, группировка и размещение по согласованным правилам |
| Состояние приложения | Хранение выбора представления для каждой базовой технологии |
| Карточка и тултип | Отображение переданных данных через элементы UI-кита |

Адаптер не назначает координаты карточек, не выбирает представление за пользователя и не сохраняет пользовательское состояние. Извлечение данных отделено от раскладки и отображения.

## Обновление отображения

При ручном выборе варианта используется соответствующий элемент `representations`. Если меняется `area`, поле перемещает ту же карточку в другую область и применяет согласованные правила порядка. `id` базовой технологии, `tier` и `prerequisites` сохраняются.

Смена языка или темы не требует повторного извлечения каталога и пересчёта технологических требований. При замене исходной БД каталог и относящиеся к нему производные данные обновляются из новой БД. Порядок загрузки и согласованной замены данных уточняется вместе со связью фронтенда и локальной служебной части.

## Критерии приёмки

Проверки выполняются после реализации:

1. Каталог содержит по одной записи на базовую технологию; определения категорий и уровней не попадают в карточки. Для исследованной БД ориентир — 679 технологий и 206 вариантов, без фиксирования этих чисел в коде.
2. Все записи имеют базовый ID, числовой `tier`, дерево требований, массив представлений и ссылку на исходный узел.
3. Основное представление идёт первым и не имеет `variantNumber`; варианты следуют порядку БД и нумеруются от 1.
4. Проверены собственная область варианта и наследование области основной технологии. Переключение на `tech_biogenesis_titans` меняет область карточки на `society`, сохраняя базовый ID, уровень и требования.
5. Блоки с одинаковыми названиями и ключами локализации различаются по идентичности представлений и исходным ссылкам.
6. Проверены отсутствие требований, обязательная технология, несколько обязательных технологий и `OR`. Логическая структура сохраняется; для `tech_titans` получаются два непосредственных предшественника и одно требование.
7. Предшественники не расширяются транзитивно; порядок перечисления не меняет их набор. Условия вне `prerequisites` не влияют на связи и число требований.
8. ID названия и описания соответствуют `requested_key`; получение переводов, включая наследованные описания, выполняет общий механизм локализации.
9. Смена языка и темы сохраняет каталог, требования и выбранные представления. Поле отвечает за раскладку; координаты не вычисляются адаптером.
10. `sourceRef` приводит к соответствующему исходному узлу в загруженной БД. Формирование каталога не меняет файл БД и его игровые данные.

## Детали последующей реализации

Адаптер получает данные только после явного открытия готового JSON пользователем по [ТЗ запуска и открытия БД](TZ_DATABASE_OPENING_RU.md). Подготовка каталога в памяти не запускает генератор, не читает игровые источники и не изменяет файл БД. Запуск приложения и обновление страницы сами по себе не загружают БД.

Сообщения и операции определены [протоколом Worker](TZ_WORKER_PROTOCOL_RU.md), контейнер `ready`, поля технологии, идентификаторы представлений и строковые `sourceRef` — [ТЗ результата](TZ_WORKER_RESULT_RU.md), дерево и связи — ТЗ технологических требований. Предстоит определить API модулей, настройки выборки и использование отрицательных логических операций в подсчёте и раскладке. Адаптер использует контракт БД, проверяемый бэкэндом; полная валидация исходного дерева не повторяется. Диагностика проблем, обнаруженных при преобразовании в модель отображения, уточняется в пределах [разделения ответственности](TZ_DATABASE_OPENING_RU.md#ответственность-за-проверки). Каталог публикуется вместе со связями и локализацией только после успешной подготовки; блокирующая ошибка не подменяется пустым каталогом, результаты отменённой операции не используются.

Порядок между группами технологий, согласование позиций между столбцами и отображение линий связей остаются задачами проектирования поля. Детали обмена сообщениями с Worker, постоянное хранение состояния и сопоставление вариантов между сборками БД рассматриваются отдельно. Эти оставшиеся детали не считаются утверждёнными настоящим документом.
