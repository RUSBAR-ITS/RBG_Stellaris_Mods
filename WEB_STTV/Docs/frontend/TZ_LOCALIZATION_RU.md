## Статус и границы

Документ фиксирует поиск строк, согласованный пользователем 2026-11-16, и решение выводить текст без обработки игровой разметки на этом этапе. Формат индекса и обработка противоречивых текстов уточнены решением от 2026-11-17 в [ТЗ записей индекса](TZ_LOCALIZATION_INDEX_RU.md). Реализация механизма ещё не начата.

Основа — [ТЗ элемента «Текст»](elements/TZ_TEXT_RU.md), [выбор языка](elements/TZ_LANGUAGE_SELECTOR_RU.md), [карточка технологии](elements/TZ_TECHNOLOGY_CARD_RU.md) и [хранение локализации в БД](../BACKEND_STAGE_10_RU.md#хранение-и-чтение-бд).

Механизм обслуживает встроенные строки интерфейса и готовые названия и описания технологий и их вариантов в БД. Приоритеты игровых источников, раскрытие статических ссылок и наследование описания уже применены бэкэндом. Фронтенд использует этот результат.

## Контракт поиска

Для поиска нужны три значения:

| Значение | Откуда поступает | Назначение |
| --- | --- | --- |
| Источник | Использующий компонент; по умолчанию встроенный | Выбор набора локализованных строк |
| ID строки | Использующий компонент; обязателен | Поиск записи внутри источника |
| Язык | Состояние приложения | Выбор `ru` или `en` |

Компонент передаёт ID и при необходимости источник. Язык предоставляет система. Для интерфейсного шаблона дополнительно допускаются именованные параметры; они не меняют адрес строки.

Пример запроса для карточки:

```text
source: database
id: tech_titans
```

При системном языке `ru` результат — «Титаны», при `en` — «Titans». Для описания передаётся ID строки описания, например `tech_titans_desc`. Дополнительные параметры `name`, `description`, ID технологии или конкретного блока варианта для поиска строки не нужны.

Идентичность выбранного варианта карточки сохраняется отдельно от ID его текста. Совпадение названий или ID строк не объединяет варианты в интерфейсе.

## Встроенные строки

Встроенная локализация хранится в двух отдельных JSON-файлах: `locales/ru.json` и `locales/en.json`. Это относительные имена внутри ресурсов фронтенда; их полный путь и загрузка определяются при проектировании сборки.

Каждый файл представляет собой словарь `ID → строка`. Набор ключей одинаков для обоих языков. Новые интерфейсные ключи имеют префикс `sttv_`; собственные ключи игровых строк сохраняются.

Пример русского словаря:

```json
{
  "sttv_language_label": "Язык",
  "sttv_variant_suffix": " (Вариант {number})"
}
```

Пример английского словаря:

```json
{
  "sttv_language_label": "Language",
  "sttv_variant_suffix": " (Variant {number})"
}
```

Подписи, подсказки и названия действий для средств доступности получают текст из этого источника через общий механизм. Игровые переводы во встроенные файлы не переносятся.

## Источник БД

Обработчик читает записи из `enrichments.localization` технологий и их `technology_swap`. Для каждого языка он учитывает оба поля — `name` и `description` — и использует:

| Поле записи | Использование |
| --- | --- |
| `requested_key` | ID строки в индексе |
| `text` | Текст для отображения |
| `key` | Фактически выбранный ключ перевода; служебные сведения |
| `source` | Происхождение перевода; служебные сведения |
| `inherited_from` | Происхождение наследованного описания; служебные сведения |
| `raw`, `unresolved_references` | Сохранённые сведения бэкэнда; повторное разрешение не запускается |

При наследовании описания вариант сохраняет свой `requested_key`, а `key` и `text` относятся к найденному описанию основной технологии. Поэтому поиск выполняется по `requested_key`; `key` не становится дополнительным ID поиска.

Источник запроса и поле `source` записи — разные понятия: первый выбирает хранилище, второе описывает происхождение перевода.

При исследовании текущей БД этапа 10 обнаружены 3540 записей локализации, 3400 уникальных пар язык/ID и 124 повторяющиеся пары. Во всех повторах тексты совпадают; отсутствующих и пустых текстов в этой выборке нет. Эти числа описывают исследованную БД и не являются ограничениями реализации.

## Конфигурация источников

Отдельный конфиг описывает встроенный источник и БД. Для каждого источника задаются:

- Тип обработчика: словарь строк или обогащённые узлы БД.
- Расположение данных и записей локализации.
- Выбор файла или ветки данных по языку.
- Поле или ключ, сопоставляемый с ID строки.
- Поле итогового текста.

Для двух согласованных форматов используются два небольших обработчика, подготавливающих общий индекс. Конфиг задаёт сведения о структуре источника; обход и чтение выполняет соответствующий обработчик. Знание внутренних путей не дублируется в UI-элементах.

По [ТЗ структуры фронтенда](TZ_STRUCTURE_RU.md) конфиг размещается в `WEB_STTV/config/frontend/`, механизм локализации — в `src/frontend/localization/`, встроенные строки — в `src/frontend/locales/ru.json` и `src/frontend/locales/en.json`. Полная схема конфига, его имя и программные имена обработчиков определяются при проектировании реализации.

## Индекс в памяти

Общий индекс имеет следующую логическую структуру:

```text
source → language → string ID → text record
```

Он строится при загрузке источника для обоих языков. При отображении текста выполняется обращение к индексу; повторный обход дерева БД для каждой карточки или тултипа не требуется.

Индекс является производными данными в памяти. Его запись содержит `status` (`resolved` или `missing`), `text` и `origins` по [ТЗ записей индекса](TZ_LOCALIZATION_INDEX_RU.md). Сведения об исходных записях БД сохраняются в `origins`; обработчик встроенных строк использует ту же структуру с пустым `origins`. Локализация в файле БД остаётся внутри объектов; сохранение индекса в БД или отдельный постоянный файл этим этапом не вводится.

По [ТЗ открытия БД](TZ_DATABASE_OPENING_RU.md#чтение-файла-и-web-worker) обработчик локализации БД выполняется в Web Worker. Он подготавливает индекс RU/EN с предусмотренными служебными сведениями и передаёт его основному потоку для подключения как источника БД. Встроенные интерфейсные строки загружаются отдельно из ресурсов фронтенда. Общий поиск по источнику, языку и ID выполняется в основном потоке; для показа каждой строки обмен с Worker не требуется. Полное дерево БД остаётся в Worker.

## Повторы и отсутствие текста

Сопоставление выполняется внутри сочетания источник/язык/ID. Одинаковые ID в разных источниках или языках не конфликтуют. ID и тексты сравниваются как сохранённые строки, без изменения регистра, пробелов и разметки.

| Ситуация | Поведение |
| --- | --- |
| Один найденный текст | `resolved`, вернуть его текст |
| Несколько записей с одинаковым текстом | `resolved`, объединить с сохранением всех исходных записей в `origins` |
| Несколько записей с различающимися найденными текстами | Ошибка подготовки данных с диагностикой для ручного разбора; готовый результат не публикуется |
| ID отсутствует или все тексты равны `null` | Считать строку отсутствующей; для имеющихся записей с `null` — `missing` |
| Один однозначный текст вместе с пропусками `null` | `resolved`, использовать найденный текст и сохранить происхождение всех записей |
| Найден текст `""` | `resolved`, вывести пустой текст; сочетание с непустым текстом под тем же ID является ошибкой |

При отсутствии строки выводится маркер `⟦ID строки⟧`, например `⟦tech_titans⟧`. Автоматическая подмена выбранного языка другим не выполняется. Противоречивые тексты являются блокирующей ошибкой открытия БД: диагностика содержит источник поиска, язык, ID, различающиеся тексты, ссылки на исходные объекты и записи, сведения об источниках переводов и наследовании. Состояния `conflict` в готовом индексе нет; после ручного разбора и исправления причины пользователь повторяет открытие БД.

## Параметры интерфейсных строк

Именованные параметры нужны для встроенных шаблонов, например `{number}` в суффиксе варианта. Компонент передаёт значения отдельно от ID строки; механизм подставляет их в найденный интерфейсный шаблон.

Для `sttv_variant_suffix` и номера `2` результатом будет ` (Вариант 2)` или ` (Variant 2)` в зависимости от языка. Номер определяется порядком блока варианта по ТЗ карточки. Название берётся из БД, суффикс — из встроенного источника; их соединение не меняет исходные строки.

Подстановка именованных параметров интерфейса не применяется к игровому тексту БД. Детали программного представления параметров и диагностики некорректного вызова уточняются при проектировании реализации.

## Вывод без обработки разметки

На этом этапе полученный из БД `text` отображается как обычный текст. Поле `raw` вместо него не используется.

Игровые коды цвета `§…`, обозначения иконок `£…`, сохранённые токены `$…$`, выражения в квадратных скобках и другие фрагменты остаются в строке как есть. Их не удалять, не раскрывать и не превращать в оформление или изображения. Буквальная последовательность обратной косой черты и `n` также не преобразуется дополнительным обработчиком в перенос строки. Обычное декодирование JSON остаётся частью чтения данных.

Строка не интерпретируется как HTML или Markdown. Роль оформления общего элемента «Текст», перенос по ширине и согласованное ограничение строк продолжают действовать; они не меняют содержимое строки в источнике. Числовая подстановка встроенного суффикса варианта следует предыдущему разделу.

Обработка игровой разметки относится к последующему этапу и не входит в это ТЗ.

## Смена языка и обновление данных

Смена языка обновляет все видимые строки, включая открытые тултипы и списки вариантов, по прежним источникам и ID. Используется уже подготовленный индекс другого языка. Повторная сборка БД, получение переводов из файлов игры и перестроение индекса при каждом переключении не требуются.

При замене или обновлении источника перестраивается относящаяся к нему часть индекса. Прежние записи заменённого источника больше не используются. Изменение языка не меняет выбранный вариант технологии и остальные настройки интерфейса.

Сохранение языка между запусками остаётся задачей [общего механизма состояния](CONCEPT_RU.md#сохранение-настроек-и-состояния).

## Критерии приёмки

Проверки выполняются после реализации:

1. Одинаковый ID встроенной строки возвращает RU/EN из соответствующего JSON-файла; отсутствие явно заданного источника выбирает встроенный.
2. Название и описание технологии и варианта находятся по `requested_key`; для наследованного описания возвращается подготовленный `text`, даже когда `key` отличается.
3. Карточка и тултип передают ID строк без выбора внутренних полей `name` / `description` и без дополнительного ID объекта.
4. Повторяющиеся записи с одинаковым текстом объединяются с сохранением происхождения; различающиеся тексты дают блокирующую ошибку с диагностикой, готовый результат не публикуется.
5. Отсутствующий ID и только значения `null` дают маркер; пропуски вместе с однозначным текстом дают `resolved`, найденная пустая строка остаётся пустой. Автоматической подмены языка нет.
6. Совпадение ID между источниками или языками не смешивает их записи.
7. Встроенный шаблон с `{number}` получает переданный номер; игровой текст не проходит через обработчик этих параметров.
8. Игровые коды цвета, иконок и подстановок, HTML-подобный текст и буквальные последовательности экранирования сохраняются как обычный текст. Для вывода используется `text`, а не `raw`.
9. Смена RU/EN обновляет видимые тексты и открытые всплывающие элементы без повторного обхода БД, чтения игровых локализаций и сброса выбранных вариантов.
10. Замена источника обновляет его индекс и удаляет устаревшие записи из поиска; файл БД не изменяется.

## Детали последующей реализации

Структура записи индекса определена [отдельным ТЗ](TZ_LOCALIZATION_INDEX_RU.md). Общая запись, предупреждение `missing_localization` и ошибка `localization_conflict` определены [ТЗ диагностики](TZ_DIAGNOSTICS_RU.md). Предстоит определить программный API, полную схему и пути конфига, загрузку ресурсов и программные типы подробностей отдельных кодов. Состав `details` и пустой `params` текущих кодов уже закреплены ТЗ диагностики. Открытие, отмена, повтор и замена БД следуют [ТЗ открытия БД](TZ_DATABASE_OPENING_RU.md#ошибки-и-повтор): индекс публикуется вместе с каталогом после успеха, отсутствие отдельных строк не блокирует просмотр, противоречивые тексты блокируют подготовку. Подробная обработка других отказов целого источника локализации и некорректных параметров шаблона требует отдельного уточнения.

Транспорт между фронтендом и локальной служебной частью, постоянное хранение состояния и обработка игровой разметки проектируются отдельно. Этот документ закрепляет общий поиск, правила объединения и вывода текста.
