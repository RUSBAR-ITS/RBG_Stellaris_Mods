## Статус и назначение

Согласовано 2026-11-18 как критерий выбора `parent_tech` после прямых улучшений объектов и перед функциональным родством. Документ фиксирует решение для будущего ТЗ; алгоритм размещения в этой итерации не изменяется.

Совпадение условий помогает выбрать продолжение среди оставшихся технологических пререквизитов. Оно не создаёт новых игровых зависимостей и не определяет фактическую доступность технологии конкретной империи.

## Сравниваемые данные

Используются текущая технология `T`, оставшийся набор кандидатов `C` и блоки `potential` технологий после раскрытия вставок.

Сравнение учитывает полное содержимое и структуру блоков: команды, значения, операторы, вложенность и переходы области видимости. Пути файлов, номера строк и другие метаданные происхождения не участвуют в сравнении. Форматирование исходного текста не является содержимым дерева условий.

Сопоставление ограничено непустыми блоками `potential`. Отсутствующий или пустой блок не подтверждает совпадение специальных условий. Не сравниваются условия из `weight_modifier` и `ai_weight`: они относятся к весам выбора.

## Правило отбора

1. Если в `C` уже один кандидат, отбор завершён и правило не применяется.
2. Если у `T` отсутствует непустой `potential`, пропустить критерий.
3. Среди текущих кандидатов оставить только те, у которых непустой `potential` полностью совпадает с `potential` технологии `T` по описанному структурному сравнению.
4. При одном совпавшем кандидате выбрать его и завершить отбор. При нескольких — передать полученный набор следующему критерию.
5. Если совпадений нет, пропустить критерий и сохранить прежний набор `C`.

Ранее исключённые кандидаты не возвращаются. Исходные требования и условия технологий сохраняются в БД.

## Границы правила

- Частичное совпадение, общий отдельный ключ или одинаковая проверка внутри разных логических выражений не используются как доказательство.
- Структурное совпадение не требует вычисления условий для империи. Доказательство логической эквивалентности по-разному записанных выражений не входит в это правило.
- `technology_swap.trigger` отвечает за выбор представления технологии и не подменяет её `potential`. Этот критерий не вводит автоматическое объединение этих двух блоков.
- Условия строительства объектов и условия применения их бонусов имеют другой контекст и не сравниваются с `potential` технологии вместо её собственного блока.
- Правило не назначает этику, происхождение или иные параметры пользовательской империи. Фильтр обычной империи остаётся отдельным критерием.

## Пример

В локальных файлах Stellaris 4.5.4 технология [tech_transcendent_faith](E:/SteamLibrary/steamapps/common/Stellaris/common/technology/00_soc_tech.txt:5830) требует `tech_consecration_fields` и `tech_galactic_administration`.

У неё и у [tech_consecration_fields](E:/SteamLibrary/steamapps/common/Stellaris/common/technology/00_soc_tech.txt:5803) одинаковые исходные блоки:

```text
potential = {
    OR = {
        is_spiritualist = yes
        AND = {
            is_gestalt = no
            has_make_spiritualist_perk = yes
        }
    }
}
```

Это компактная запись до раскрытия именованных проверок; в сравнении используются раскрытые блоки. У [tech_galactic_administration](E:/SteamLibrary/steamapps/common/Stellaris/common/technology/00_soc_tech.txt:4721) собственный `potential` отсутствует. Если оба пререквизита остаются кандидатами, правило выбирает `tech_consecration_fields`.

Пример подтверждает применимость критерия к этой паре; новый полный прогон БД в рамках документирования не выполнялся.
