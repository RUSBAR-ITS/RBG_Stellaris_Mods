## Статус и границы

Документ фиксирует согласованный пользователем 2026-11-17 формат диагностики подготовки данных фронтенда и ответа `error`. Он уточняет [протокол Worker](TZ_WORKER_PROTOCOL_RU.md), [контейнер результата](TZ_WORKER_RESULT_RU.md), [открытие БД](TZ_DATABASE_OPENING_RU.md) и [индекс локализации](TZ_LOCALIZATION_INDEX_RU.md).

Определяются общая запись, начальные коды, разделение предупреждений и блокирующей ошибки, передача и сохранение полученной диагностики в основном потоке. По [ТЗ сохранения отчёта](TZ_DIAGNOSTIC_REPORT_RU.md) подробности на первом этапе выгружаются в JSON для просмотра во внешнем редакторе. В этой итерации изменяется документация; реализация фронтенда и изменение отчётов бэкэнда не выполняются.

## Общая диагностическая запись

Предупреждения и ошибки используют одну структуру из пяти обязательных полей:

| Поле | Тип и назначение |
| --- | --- |
| `severity` | `warning` — обработка продолжается; `error` — подготовка завершается ошибкой |
| `code` | Строка: постоянный идентификатор проблемы |
| `phase` | `reading`, `parsing`, `preparing`; `null`, если обработка ещё не началась |
| `params` | Для всех текущих кодов — `{}`; поле сохранено для будущих сообщений с именованными подстановками |
| `details` | Объект технических сведений для разбора причины; состав определяется кодом |

Этапы соответствуют протоколу Worker. Запись не содержит готового локализованного пользовательского сообщения: основной поток выбирает строку по `code` через общий механизм локализации. На первом этапе сообщения диагностики не используют подстановки, поэтому `params` всегда равен `{}`. Конкретные пути, ID и технические причины находятся в `details`.

Принадлежность операции задаётся `operationId` сообщения и состоянием приложения; внутри каждой записи номер не дублируется. Содержание `details` для текущих кодов определено ниже; точные вложенные имена и типы полей уточняются при проектировании программных типов. Непустые `params` потребуют отдельного согласования новых сообщений.

## Начальный перечень кодов

| Код | `severity` | Значение |
| --- | --- | --- |
| `file_read_failed` | `error` | Не удалось прочитать выбранный файл |
| `invalid_json` | `error` | Содержимое не разбирается как JSON |
| `unsupported_database` | `error` | Формат или версия БД не поддерживается |
| `invalid_database` | `error` | Адаптер не может преобразовать используемые данные БД в модель отображения |
| `missing_localization` | `warning` | Отсутствует перевод |
| `localization_conflict` | `error` | Под одним языком и ID получены разные тексты |
| `worker_failed` | `error` | Не удалось запустить Worker либо произошёл необработанный сбой его выполнения |

Это начальный согласованный набор. По [разделению ответственности](TZ_DATABASE_OPENING_RU.md#ответственность-за-проверки) валидация БД остаётся на бэкэнде. Во фронтенде обрабатываются ошибки открытия, неподдерживаемые формат и версия и проблемы собственных преобразований адаптера. `invalid_database` обозначает обнаруженную при преобразовании невозможность подготовить данные, а не результат отдельного повторного обхода по схеме БД. Состав подробностей, пустой `params`, ID и тексты встроенных строк для текущих кодов определены настоящим документом; программные типы уточняются отдельно.

## Ответ с блокирующей ошибкой

Ответ содержит обязательные `type: "error"`, `operationId`, `error` и `diagnostics`. Условный пример:

```json
{
  "type": "error",
  "operationId": 7,
  "error": {
    "severity": "error",
    "code": "invalid_json",
    "phase": "parsing",
    "params": {},
    "details": {
      "message": "Unexpected token at position 120."
    }
  },
  "diagnostics": []
}
```

`error` — одна диагностическая запись с причиной остановки и `severity: "error"`. `diagnostics` — массив предупреждений с `severity: "warning"`, накопленных до остановки; при их отсутствии передаётся `[]`. Причина остановки второй раз в массив не добавляется.

Пример технического сообщения не фиксирует текст, который обязан возвращать JSON-парсер, и не является пользовательской строкой интерфейса.

Блокирующая ошибка завершает подготовку: каталог, связи и локализация не публикуются частично, ответ `ready` не возвращается. Приложение принимает ответ только от актуального Worker с актуальным `operationId` по правилам протокола.

Если Worker не смог отправить ответ из-за сбоя запуска или необработанного сбоя выполнения, обработчик основного потока оформляет `worker_failed` по общей структуре и связывает его с текущей попыткой. Самостоятельное сообщение от неработающего Worker для этого не требуется.

## Предупреждения успешной подготовки

При успехе предупреждения передаются в `ready.data.diagnostics`. Массив содержит только записи с `severity: "warning"`; при отсутствии проблем он пуст. Записи с `severity: "error"` в успешный результат не входят.

Отсутствующие переводы обрабатываются по ТЗ индекса: просмотр допускается, для отсутствующего текста выводится маркер. Предупреждения не превращают корректный результат в состояние ошибки и не меняют число базовых технологий в сообщении панели состояния.

## Технические подробности

Состав `details` согласован для каждого текущего кода:

| Код | Содержание технических подробностей |
| --- | --- |
| `file_read_failed` | Название и техническое сообщение ошибки чтения |
| `invalid_json` | Сообщение JSON-парсера |
| `unsupported_database` | Полученные и поддерживаемые формат и версия БД |
| `invalid_database` | Путь к данным и причина невозможности их преобразования адаптером |
| `missing_localization` | Источник поиска, язык, ID строки и ссылки на использующие её записи |
| `localization_conflict` | Источник поиска, язык, ID строки, различающиеся тексты и происхождение каждого |
| `worker_failed` | Доступные сведения об ошибке запуска или выполнения Worker |

Название ошибки чтения означает имя ошибки среды выполнения, а не имя выбранного файла. Сведения об исключении сохраняются в доступном объёме; отсутствующие технические данные не придумываются.

Для происхождения каждого конфликтующего текста используется уже согласованная структура `origins` из [ТЗ индекса локализации](TZ_LOCALIZATION_INDEX_RU.md#происхождение-строки). Она сохраняет `recordRef`, `key`, `raw`, `source`, `inheritedFrom` и `unresolvedReferences`. Происхождение связывается с соответствующим различающимся текстом; общий список без этой связи недостаточен для разбора конфликта. Источник поиска, например `database`, отличается от `source` внутри записи происхождения, описывающего файл перевода.

Полное дерево БД и полный исходный JSON в диагностику не копируются. Ссылки на записи адресуют текущую БД и сами по себе не сохраняют дерево после завершения Worker. Сведения о противоречивых текстах передаются в диагностике, чтобы их можно было разобрать после освобождения дерева.

Этот раздел задаёт содержание подробностей для семи текущих кодов и повторное использование `origins`. Он не вводит универсальный набор полей для всех ошибок или дополнительные проверки БД. Точные вложенные имена и типы полей оформляются в программном контракте на основе этого состава.

## Сообщение интерфейса

Для текущих кодов согласованы следующие строки источника `builtin`. Идентификаторы используют префикс `sttv_diagnostic_`:

| Код | ID строки | Русский текст | English text |
| --- | --- | --- | --- |
| `file_read_failed` | `sttv_diagnostic_file_read_failed` | Не удалось прочитать файл БД. | Could not read the database file. |
| `invalid_json` | `sttv_diagnostic_invalid_json` | Не удалось открыть БД: некорректный JSON. | Could not open database: invalid JSON. |
| `unsupported_database` | `sttv_diagnostic_unsupported_database` | Формат или версия БД не поддерживается. | Unsupported database format or version. |
| `invalid_database` | `sttv_diagnostic_invalid_database` | Не удалось подготовить данные для отображения. | Could not prepare data for display. |
| `missing_localization` | `sttv_diagnostic_missing_localization` | Для некоторых строк отсутствует перевод. | Some translations are missing. |
| `localization_conflict` | `sttv_diagnostic_localization_conflict` | В БД найдены противоречивые переводы. | Conflicting translations found in the database. |
| `worker_failed` | `sttv_diagnostic_worker_failed` | Не удалось завершить обработку БД. | Could not complete database processing. |

Тексты размещаются в `src/frontend/locales/ru.json` и `src/frontend/locales/en.json` относительно `WEB_STTV`. Оба файла содержат одинаковые ID; соответствие «код → ID строки» задаётся конфигурацией диагностики в `WEB_STTV/config/frontend/` по [ТЗ структуры](TZ_STRUCTURE_RU.md#конфигурация-и-рабочие-данные). Тексты остаются в локализации, а не дублируются в конфигурации или компоненте панели. Конкретное имя конфигурационного файла и способ его загрузки определяются при проектировании реализации.

При блокирующей ошибке [панель состояния](elements/TZ_STATUS_PANEL_RU.md) показывает одно соответствующее сообщение. Предупреждение `missing_localization` сохраняется в диагностике и не заменяет согласованное сообщение об успешной загрузке с количеством технологий. Наличие строки предупреждения в словаре само по себе не добавляет нового состояния или уведомления интерфейса.

Worker передаёт код и пустой `params`, а основной поток выбирает язык. Смена языка обновляет сообщение без повторного открытия БД. Техническое `details.message`, если оно присутствует, не используется вместо пользовательского объяснения.

Начальный перечень кодов не добавляет новых элементов интерфейса и действий в панели состояния. Явное действие «Сохранить отчёт» находится в меню по отдельному ТЗ; подробности просматриваются во внешнем редакторе. Встроенное окно диагностики отложено.

## Хранение в текущем сеансе

Полученная диагностика хранится в основном потоке вместе с результатом текущей попытки: предупреждения — с успешным результатом, причина остановки и накопленные предупреждения — с состоянием ошибки. При завершении Worker после ошибки эти сведения сохраняются; промежуточные данные каталога и полное дерево отбрасываются по ТЗ открытия БД.

Сбой Worker также сохраняется на стороне приложения по общей структуре. Устаревшие ответы и результаты отменённых или заменённых операций не изменяют диагностику текущей попытки. Диагностика сохраняет связь со своим `operationId`.

Настоящий документ закрепляет хранение полученных сведений в памяти текущего сеанса. Явная выгрузка текущей завершённой попытки определена [ТЗ отчёта](TZ_DIAGNOSTIC_REPORT_RU.md). Постоянное хранение состояния, история попыток, автоматический файловый журнал и встроенный интерфейс просмотра требуют отдельного проектирования.

## Критерии приёмки

Проверки выполняются после реализации:

1. Ошибки и предупреждения используют общие поля `severity`, `code`, `phase`, `params`, `details`; этапы соответствуют протоколу, до начала обработки допустим `null`.
2. `error` содержит одну блокирующую запись, а соседний `diagnostics` — только накопленные предупреждения; ошибка в массиве не дублируется.
3. `ready.data.diagnostics` содержит только предупреждения; блокирующая ошибка не превращается в успешный или частичный результат.
4. Отсутствующий перевод допускает просмотр с предупреждением, противоречивые тексты дают `localization_conflict` и предусмотренные сведения для ручного разбора.
5. Для всех семи текущих кодов `params` равен `{}`, конфигурация сопоставляет `code` согласованному ID источника `builtin`. Тексты RU/EN соответствуют таблице, имеют одинаковые ID и не содержат подстановок; смена языка обновляет сообщение без перезапуска обработки, техническое сообщение не подменяет пользовательское.
6. Полученная причина ошибки и предупреждения доступны в основном потоке после завершения Worker; полное дерево в диагностике отсутствует.
7. Сбой запуска или необработанный сбой Worker оформляется как `worker_failed` для актуальной попытки, даже если ответ от Worker не получен.
8. Устаревшие ответы и повторные итоги не меняют текущую диагностику; правила отмены, замены и явного повтора сохраняются.
9. `details` соответствует согласованному содержанию своего кода. Каждый конфликтующий текст сохраняет относящиеся к нему `origins`; ссылки, метаданные и причины остаются в отчёте после завершения Worker.
10. `missing_localization` остаётся предупреждением в диагностике и не заменяет сообщение успешной загрузки с количеством технологий.

## Дальнейшее проектирование

- Конкретное имя файла конфигурации диагностики, его программная схема и загрузка; соответствие кодов ID, тексты RU/EN и корневой каталог конфигурации уже определены.

- Программные типы, интерфейсы модулей и проверки структуры сообщений.
