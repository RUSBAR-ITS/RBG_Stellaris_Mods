## Статус и границы

С 2026-11-17 требования этого документа к одному файлу и неквалифицированным ссылкам заменены утверждённым [ТЗ второго этапа](TZ_FRONTEND_STAGE_2_RU.md). Актуальная реализация открывает три БД версии 5 одним набором и использует ссылки `{ database, pointer }`; остальные применимые требования сохраняются.

Документ фиксирует согласованный протокол открытия готовой БД между приложением и Web Worker. Он уточняет [ТЗ открытия БД](TZ_DATABASE_OPENING_RU.md): сообщения, различение операций, отбрасывание устаревших ответов и отмену. Код в этой итерации не реализуется.

Предусмотрены одна команда `open_database` и три вида ответов: `progress`, `ready`, `error`. Контейнер `ready`, поля технологии, идентификаторы представлений и строковые `sourceRef` закреплены в [ТЗ результата Worker](TZ_WORKER_RESULT_RU.md), дерево и связи — в [ТЗ технологических требований](TZ_TECHNOLOGY_REQUIREMENTS_RU.md). Записи локализации определены [ТЗ индекса](TZ_LOCALIZATION_INDEX_RU.md); формат диагностики и вложенный ответ `error` определены [отдельным ТЗ](TZ_DIAGNOSTICS_RU.md). Полное дерево БД остаётся в Worker.

## Общие поля и актуальная операция

Каждое сообщение содержит:

| Поле | Назначение |
| --- | --- |
| `type` | Строковый тип сообщения из перечня ниже |
| `operationId` | Положительный целочисленный номер попытки открытия, назначенный приложением |

Приложение назначает новый номер при каждом открытии выбранного файла и каждом повторе. Номера не переиспользуются в пределах текущего запуска. Worker возвращает номер полученной операции во всех её ответах.

Приложение принимает ответ только при совпадении `operationId` с актуальной операцией и получении сообщения от соответствующего текущего Worker. Ответы завершённых отменой или заменённых операций не изменяют состояние, данные или диагностику текущей БД.

Для попытки открытия допускается один итог: `ready` либо `error`. После принятия итога сообщения `progress` и повторные итоги этой попытки не меняют состояние. Успешно завершивший подготовку Worker продолжает хранить открытую БД.

## Сообщения

| Направление | `type` | Содержимое помимо общих полей |
| --- | --- | --- |
| Приложение → Worker | `open_database` | `file`: выбранный пользователем объект `File` |
| Worker → приложение | `progress` | `phase`: обозначение текущего этапа |
| Worker → приложение | `ready` | `data`: полностью подготовленный результат и диагностика неблокирующих проблем |
| Worker → приложение | `error` | `error`: блокирующая диагностическая запись; `diagnostics`: накопленные предупреждения |

Передаётся объект выбранного файла. Основной поток не читает полную JSON-строку для отправки её Worker. Чтение, разбор и подготовка выполняются на стороне Worker.

Контейнер `data` ответа `ready` содержит `technologies`, `links`, `localization` и `diagnostics` по ТЗ результата. Записи диагностики содержат `severity`, `code`, `phase`, `params`, `details` по [ТЗ диагностики](TZ_DIAGNOSTICS_RU.md). В ответе `error` причина остановки передаётся отдельной записью `error`, накопленные предупреждения — массивом `diagnostics`; состав `details` определён ТЗ диагностики, для всех текущих кодов `params` равен `{}`. Программные типы вложенных полей уточняются отдельно.

## Этапы обработки

| `phase` | Выполняемая работа |
| --- | --- |
| `reading` | Чтение содержимого файла |
| `parsing` | Разбор JSON |
| `preparing` | Проверка необходимой структуры и подготовка каталога, требований, связей и локализации |

Worker сообщает о переходе к этапу перед выполнением соответствующей работы. Проценты выполнения не передаются. Пример сообщения:

```json
{
  "type": "progress",
  "operationId": 7,
  "phase": "parsing"
}
```

Основной поток сопоставляет `phase` со встроенной интерфейсной строкой и показывает её в [панели состояния](elements/TZ_STATUS_PANEL_RU.md). Worker не выбирает язык сообщения. Изменение языка обновляет текст текущего этапа без перезапуска обработки.

## Успешный результат

`ready` содержит одновременно подготовленные каталог технологий и представлений, технологические требования и связи, индекс локализации RU/EN и диагностику неблокирующих проблем. Приложение публикует этот набор целиком после успешного завершения подготовки; промежуточные части не становятся данными экрана.

Корректная БД без технологий также возвращает `ready` с пустым каталогом. Приложение выбирает состояние «Пустой каталог» вместо «Готово». Ошибки чтения, структуры и подготовки не превращаются в успешный пустой результат.

Полное дерево БД и исходная JSON-строка не включаются в результат. В основной поток поступает производная модель для отображения. Worker сохраняется после успеха, включая случай пустого каталога; исходные узлы остаются у владельца дерева.

## Ошибки и диагностика

`error` сообщает о блокирующей ошибке текущего открытия. Стабильный код, например `invalid_json`, позволяет приложению выбрать локализованную интерфейсную строку. Параметры подставляются в неё общим механизмом локализации. Технические подробности предназначены для диагностики и не заменяют пользовательское объяснение в панели состояния.

Сбой запуска или выполнения самого Worker также переводит приложение в состояние ошибки, даже если Worker не смог отправить `error`. Обработчик на стороне приложения связывает такой сбой с актуальной попыткой и применяет те же правила завершения и повтора. Для такого сбоя используется `worker_failed` из начального перечня кодов в ТЗ диагностики. Точные схемы технических подробностей уточняются отдельно.

При блокирующей ошибке Worker завершается, промежуточные данные отбрасываются. Полученная причина ошибки и предупреждения сохраняются в основном потоке и не удаляются вместе с Worker. Ссылка на выбранный `File` сохраняется в текущем сеансе для явного повтора. Неблокирующие проблемы, включая отсутствующие строки локализации, сопровождают успешный результат и обрабатываются по [ТЗ локализации](TZ_LOCALIZATION_RU.md). Противоречивые тексты под одним ID и языком являются блокирующей ошибкой подготовки по [ТЗ индекса](TZ_LOCALIZATION_INDEX_RU.md); вместо `ready` возвращается `error` со сведениями для ручного разбора.

## Отмена, замена и повтор

Отмена загрузки выполняется приложением: оно сначала помечает операцию неактуальной, затем вызывает `worker.terminate()`, отбрасывает промежуточные данные и возвращается в состояние «БД не открыта». Отдельной команды `cancel` и ожидания подтверждения от Worker нет. Метод `terminate()` останавливает Worker без ожидания завершения его работы; см. источник ниже.

При замене БД старая операция становится неактуальной, старый Worker завершается, прежние данные интерфейса удаляются. Новый Worker с новым `operationId` создаётся после выбора нового файла. Пока стандартный диалог выбора открыт, текущая БД сохраняется; отмена этого диалога не считается отменой загрузки.

«Повторить» создаёт новый Worker и новый `operationId` для сохранённого объекта `File`. Автоматических повторов нет. Поздние сообщения от предыдущего Worker отбрасываются по общим правилам, независимо от того, началась ли новая попытка.

## Размещение и ответственность

По [ТЗ структуры](TZ_STRUCTURE_RU.md) запуск Worker, сообщения и их обработка относятся к `src/frontend/workers/`; состояние приложения и пользовательские действия — к `app/`. Самостоятельные алгоритмы из `data/` и `localization/` вызываются обработчиком Worker и не зависят от протокола или React.

Смена языка, темы и выбранного представления технологии использует уже подготовленные данные основного потока. Для этих действий сообщения открытия БД не отправляются.

## Критерии приёмки

Проверки выполняются после реализации:

1. Открытие передаёт `File` с новым `operationId`; ответы содержат тот же номер.
2. Этапы `reading`, `parsing`, `preparing` отображаются через встроенную локализацию без процентов.
3. `ready` публикует полный подготовленный набор; корректный пустой каталог отличается от ошибки.
4. Сообщения старого Worker, ответы с неактуальным номером и повторные итоги не меняют текущие данные и состояние.
5. Отмена во время чтения, разбора или подготовки завершает Worker без ожидания ответа и очищает состояние загрузки.
6. Повтор использует сохранённый `File`, новый Worker и новый номер; замена не удерживает два полных дерева БД.
7. Ошибка открытия и сбой самого Worker завершаются состоянием ошибки с локализованным объяснением и диагностикой.
8. Изменение языка обновляет сообщение этапа или ошибки без повторной обработки БД.

## Дальнейшее проектирование

- Программные типы вложенных полей `details` на основе согласованного состава; общая запись, пустой `params` текущих кодов и контейнер `error` определены. Правила использования отрицаний в требованиях остаются открытыми.
- ID и тексты интерфейсных сообщений, встроенный просмотр диагностики; явное сохранение JSON текущей попытки определено [ТЗ отчёта](TZ_DIAGNOSTIC_REPORT_RU.md) и не добавляет сообщения Worker.
- Общие типы сообщений и необходимые проверки их структуры, точные файлы и интерфейсы обработчиков.
