## 1. Статус и границы

ТЗ утверждено пользователем 2026-11-17. Реализация и проверки описаны в [руководстве второго этапа фронтенда](FRONTEND_STAGE_2_RU.md).

Этап добавляет совместное открытие технологий, компонентов и зданий, их каталоги, локализацию и явные межобъектные связи. Технологическое поле сохраняет действующий способ отображения. Новый алгоритм цепочек, его сортировка, линии на поле, карточки/экраны зданий и компонентов, изображения и вычисление условий государства не входят в этап. Правила L-01–L-08 остаются требованиями к будущему размещению.

После утверждения этот документ заменяет положения первого этапа об одном файле и неквалифицированных ссылках на узлы. Остальные требования UI-кита, текста, тем, языка, тултипов, ручных вариантов и ответственности бэкэнда сохраняются.

## 2. Открытие набора

В меню вместо «Открыть БД» использовать «Открыть набор БД» / «Open database set». Одна кнопка UI-кита вызывает стандартный диалог множественного выбора файлов. Пользователь выбирает ровно три JSON: технологии, компоненты, здания. Порядок выбора и имена файлов произвольны; тип определяется полем `dataset.kind` внутри каждого файла.

Условия готового набора:

- Формат каждого файла — `sttv.parse_database`, поддерживаемая версия 5.
- Каждый из видов `technologies`, `components`, `buildings` присутствует ровно один раз.
- У всех трёх одинаковый непустой `dataset.set_id` ожидаемого формата SHA-256.
- Данные, требуемые адаптерами, доступны для подготовки.

Недостающий файл, повтор роли, неподдерживаемый формат и несовпадающий набор — ошибки открытия, без частичного режима и подстановки старого участника. Фронтенд не ищет соседние файлы автоматически и не открывает игровые каталоги. Метка набора — контроль принадлежности результатов одной сборке, не криптографическая проверка всего содержимого в браузере.

Запуск интерфейса и обновление страницы не читают БД и не запускают Python, генерацию или локализацию. Открытие использует только явно выбранные файлы в режиме чтения. При закрытии диалога без выбора текущее состояние сохраняется.

## 3. Worker и состояния

Команда открытия передаёт `operationId` и массив `files`, а не один `file`. Один Worker читает и разбирает выбранные файлы последовательно, освобождая текст после JSON-разбора, определяет роли и затем вызывает адаптер набора. Полные деревья остаются в Worker; основной поток получает только подготовленные каталоги, индексы, связи и диагностику.

Сохранить существующие фазы `reading`, `parsing`, `preparing`; сообщение прогресса дополнить номером файла, общим количеством и известной ролью. До чтения роль может быть неизвестна. Подготовка связей начинается после чтения всех трёх деревьев. Прогресс в панели состояния должен быть понятен пользователю, без выдачи внутренних технических имён вместо локализованных названий этапов.

Поле появляется только после единого `ready` для всего набора. При ошибке не публиковать частичные каталоги. При начале новой операции после выбора файлов прежний Worker освобождается, прежнее поле очищается согласно действующей модели замены. Старый набор при ошибке не восстанавливается автоматически.

«Повторить» использует те же три выбранных объекта `File`. «Отмена» завершает Worker, очищает операцию и возвращает начальное состояние. Ответы устаревших `operationId` игнорируются. Корректные пустые каталоги не считаются ошибкой; отсутствие технологий даёт существующее пустое состояние независимо от количества компонентов и зданий.

## 4. Адресация и каталоги

Разделить игровую идентичность и адрес узла:

```typescript
type SttvDatasetKind = 'technologies' | 'components' | 'buildings';
type SttvNodeRef = { database: SttvDatasetKind; pointer: string };
type SttvObjectRef = { database: SttvDatasetKind; id: string };
```

`pointer` — JSON Pointer внутри соответствующей БД. Одинаковые ID разных видов и одинаковые пути в разных файлах не конфликтуют. Принадлежность всему набору передаётся одним `setId` в результате, не копируется во все ссылки. Внутренние ссылки, сохранённые бэкэндом внутри файла, квалифицируются ролью файла при адаптации.

Готовый результат содержит существующие `technologies`, `links`, `localization`, `diagnostics` и новые `setId`, `datasets`, `components`, `buildings`, `objectRequirements`, `objectUpgrades`, `upgradeEvidence`. `datasets` содержит роли и сведения о выбранных файлах для сообщений и отчёта. Полные AST в результат не входят.

| Каталог | ID | Минимальная запись |
| --- | --- | --- |
| Технологии | ключ определения | Существующая запись технологии и вариантов с квалифицированными `sourceRef` |
| Компоненты | прямой `key` шаблона | `id`, тип шаблона, `sourceRef`, `nameId`, `descriptionId`, дерево `prerequisites` и его ссылка |
| Здания | ключ определения | `id`, `sourceRef`, `nameId`, `descriptionId`, дерево `prerequisites` и его ссылка, условные описания |

Условное описание здания содержит ссылку на исходный `desc`, `descriptionId` и ссылку на `trigger`, если он есть. Условия остаются в дереве Worker, в основном потоке их не вычислять. Не добавлять понятие активного описания здания без отдельного согласования.

Определять первичные объекты по явным настройкам каталогов/типов и полям после раскрытия. Повтор корневого `utility_component_template` допустим; повтор `key` компонентов — ошибка. Служебные определения категорий/уровней технологий не становятся карточками. Не обходить метаданные раскрытия и локализации как самостоятельные игровые объекты.

## 5. Локализация

Собрать общий индекс RU/EN по сохранённым `requested_key` всех трёх БД, включая условные описания зданий. Контракт текста остаётся прежним: источник `database`, ID строки, язык системы. Игровые виды не превращаются в три новых источника для UI-текста.

В `origins` каждой индексной записи квалифицировать `recordRef`, `inheritedFrom` и ссылку `fallback.source_ref` соответствующей БД. Сохранить фактический ключ, исходный текст и источник перевода. Одинаковые тексты одного ID объединяют происхождения; конфликтующие найденные тексты одного ID и языка — ошибка с обоими источниками, без выбора первой записи.

Обработка целей с одним описанием должна быть явной: у условного `desc` не требовать `name`, но у основной технологии, варианта, здания и компонента проверять оба локализационных поля. Отсутствующий перевод с корректной записью об отсутствии — предупреждение; отсутствие требуемого обогащения — ошибка подготовки.

Фронтенд не перечитывает локализацию игры, не раскрывает `$key$` повторно, не угадывает общие описания по ID и не интерпретирует игровую разметку. Названия и описания отображаются как сохранённый текст по действующим требованиям. Переключение языка использует уже подготовленные оба индекса.

## 6. Связи требований и улучшений

Сохранять три разные группы данных:

1. `links` — исходные технологические пререквизиты, как в первом этапе.
2. `objectRequirements` — связь требования технологии с компонентом/зданием, включая пути её вхождений в логическом дереве. Направление — технология → требующий объект.
3. `objectUpgrades` — явное улучшение компонент → компонент через `upgrades_to` либо здание → здание через `upgrades`. Каждая запись хранит квалифицированные концы и ссылки на исходные поля. Несколько улучшений здания сохраняются все.

Отсутствующие или пустые `prerequisites` означают отсутствие технологических требований. Для непустого дерева сохраняются группы, порядок и операторы; перечисление ID не делает альтернативы `OR` обязательными. У объектов допускается структурное сохранение логических требований без подсчёта для раскладки. Для технологий действующее согласованное ограничение на отрицательные требования сохраняется до отдельного ТЗ сортировки.

`upgradeEvidence` — отдельные свидетельства возможного продолжения технологий. На этом этапе формировать их только когда у обоих концов явного улучшения имеется простой список с ровно одним скалярным технологическим пререквизитом, технологии различны и технология источника уже присутствует в исходных `prerequisites` технологии назначения. Для каждого свидетельства сохранить пару технологий и ссылки на объекты/поля, которые её подтверждают.

При нескольких требованиях, логических альтернативах или отсутствии технологического требования сохранять объектное улучшение, но не угадывать единственную технологическую пару. Несколько свидетелей одной пары сохранять как список доказательств, не как несколько технологических зависимостей. Новые `links` из свидетельств не создаются; принадлежность области/категории и выбор главного продолжения относятся к следующей сортировке.

Пример приёмки: `AFTERBURNER_1` → `AFTERBURNER_2` подтверждает `tech_afterburners_1` → `tech_afterburners_2`; требование `tech_thrusters_3` остаётся исходной дополнительной связью. Свидетельство само по себе не переставляет карточки.

## 7. Диагностика

Не переносить JSON Schema, полный валидатор AST или парсер игры во фронтенд. Проверять оболочки трёх файлов и данные, необходимые непосредственно для построения каталогов и ссылок. Ошибки, обнаруженные при преобразовании, не скрывать.

Блокируют открытие: неправильный состав набора/версия/метки; недоступная для преобразования форма необходимого поля; дубли ID внутри вида; конфликт текстов; отсутствующая цель используемой технологической ссылки или `upgrades_to`/`upgrades`. В диагностике указывать роль БД, файл, ID и путь проблемного поля. Условия `potential`, внешние ресурсы и другие неиспользуемые поля не проверять как межбазовые ссылки.

Отсутствие свидетельства продолжения при нескольких требованиях не является ошибкой. Отсутствующие строки локализации дают предупреждения. Коды новых ошибок сопоставляются с короткими RU/EN сообщениями через конфигурацию интерфейса; подробности остаются в диагностическом отчёте.

Обновить экспорт отчёта: сведения обо всех трёх файлах, `setId`, роли, фаза ошибки и квалифицированные ссылки. Экспорт остаётся отдельным действием меню и не запускает запись в рабочую папку автоматически.

## 8. Конфигурация и модули

Обновить `config/frontend/adapter.json`: поддерживаемый формат, необходимые роли, селекторы объектов и поля ID/требований/улучшений. Большой реестр игровых команд не вводится. Локализационные и диагностические конфиги обновляются по своей ответственности.

В `data/` разделить адаптер набора, адаптеры объектов и сборку межобъектных связей. Общие функции чтения AST, требований и ссылок переиспользуются. `workers/` занимается жизненным циклом и сообщениями; локализационный индекс остаётся в `localization/`; меню и панель состояния собираются из UI-кита. Соблюдать ограничения размеров файлов, английский язык кода и раздельные словари оформления.

## 9. Проверки и приёмка

1. Синтетический набор из трёх файлов открывается одним действием при любом порядке и переименовании файлов. Все три роли и локализации присутствуют в подготовленных данных.
2. Проверены один/два/четыре файла, повтор роли, разные `set_id`, старый формат, повреждённый JSON и отсутствующее обогащение: поле не строится, причина доступна в отчёте.
3. Проверены отмена диалога, отмена операции, повтор, замена набора и устаревшие ответы Worker. Обновление страницы не открывает и не создаёт БД.
4. Одинаковые ID разных видов и одинаковые JSON Pointer не смешиваются; дубли внутри вида и конфликтующие тексты диагностируются с обеими позициями.
5. Проверены названия и описания RU/EN трёх видов, общее описание компонента и все условные описания здания без выбора по условиям. Существующие варианты технологий и тултипы работают.
6. Проверены прямые/альтернативные/пустые требования, несколько улучшений, отсутствующая цель ссылки и объединение свидетелей одной пары. Неоднозначные требования не превращаются в однозначную пару технологий.
7. Реальный набор этапа 11 успешно открывается. Для известных 16 случаев улучшения из исследования сохраняются подтверждающие пары, включая форсажные камеры и боевые компьютеры; полнота новых результатов после раскрытия проверяется отдельно.
8. Проверены типы TypeScript, сборка, соответствующие модульные и браузерные сценарии. Измерены чтение/подготовка набора и отзывчивость интерфейса; полные деревья не копируются в основной поток.
9. Текущее размещение карточек и отсутствие линий сохраняются. Обновлены руководство пользователя, модель ответа Worker, документация адресации и changelog RU/EN с фактическими результатами.
