## Статус и место в отборе

Согласовано пользователем 2026-11-18. Критерий размещается **непосредственно перед фильтром по империи**, после родства через производственные бонусы. Текущий порядок соседних этапов: косвенное функциональное родство → производственные бонусы → лимиты объектов → фильтр по империи → старшинство по игровому уровню.

Это решение для будущего ТЗ. В текущей итерации меняется документация; код продукта, БД и предыдущий исследовательский расчёт не меняются.

## Основание связи

Если собственный модификатор технологии `T` увеличивает лимит объектов, а оставшийся кандидат `P` открывает объект, использующий этот лимит, это подтверждает функциональное родство.

Проверяемая последовательность: **модификатор → увеличиваемый лимит → использующий его объект → открывающая объект технология-кандидат**. Самой `T` не требуется открывать объект.

Соответствия модификаторов, типов объектов и игровых полей задаются в конфигурации. Первый подтверждённый пример: `country_starbase_capacity_add` сопоставляется с `starbase_levels.starbase_capacity_used > 0`; поле `ship_size` связывает уровень звёздной базы с корпусом из `ship_sizes`, а его `prerequisites` — с технологией-кандидатом.

Имена технологий, сходство названий и заранее заданные пары ID не служат основанием выбора. Это аналитический критерий справочника, а не утверждение о заданном игрой единственном родителе.

## Условия и подтверждения

- Подтверждается увеличение конкретного лимита и использование именно этого лимита объектом. Произвольный модификатор со словом `capacity` не получает такую связь автоматически.
- Используются собственные эффекты выбранного представления технологии с учётом `technology_swap` и `inherit_effects`; модификаторы весов выбора не являются бонусами исследования.
- Сохраняются контекст, знак бонуса, условия использования лимита и доступа к объекту. Условная связь не объявляется безусловной; текущее количество объектов у игровой империи не вычисляется.
- Свидетельство содержит модификатор, сопоставление из конфигурации, поля использования лимита, промежуточные ссылки объектов, кандидата и источники каждого звена.
- Неизвестное соответствие не даёт подтверждения и не заменяется догадкой по ID.

## Отбор кандидатов

Правило действует только на текущий набор кандидатов `C`, если в нём больше одной технологии.

1. Собрать множество `M` кандидатов с подтверждённой связью через лимит объектов.
2. Если в `M` один кандидат, выбрать его и завершить отбор.
3. Если кандидатов несколько, заменить `C` на `M` и перейти к фильтру по империи.
4. Если `M` пусто, сохранить `C` и перейти к фильтру по империи.

Ранее исключённые кандидаты не возвращаются. Число объектов и подтверждений не даёт дополнительных голосов. Все исходные игровые пререквизиты и их логика сохраняются.

## Пример мегапроектирования

Проверено по текущим данным Stellaris 4.5.4:

| Звено | Подтверждение |
| --- | --- |
| Мегапроектирование (`tech_mega_engineering`), уровень 5 | Собственный бонус `country_starbase_capacity_add = 3`. |
| Цитадель | В `starbase_level_citadel` указаны `starbase_capacity_used = 1` и `ship_size = starbase_citadel`. Корпус требует `tech_starbase_5`, уровень 4. |
| Корабль-ковчег третьего класса | Например, `starbase_level_civilian_arkship_3` содержит `starbase_capacity_used = 1` и `ship_size = civilian_arkship_tier_3`; корпус требует `tech_arkship_tier_3`. |
| Линкоры (`tech_battleships`), уровень 4 | Открываемые корпуса не подтверждают использование лимита звёздных баз. |

До фильтра империи в рассматриваемом случае остаются `tech_arkship_tier_3`, `tech_battleships` и `tech_starbase_5`. Новый критерий оставляет `tech_arkship_tier_3` и `tech_starbase_5`. Затем согласованный профиль обычной некочевой империи исключает кочевой вариант. Ожидаемый результат: `tech_mega_engineering.parent_tech = tech_starbase_5`, то есть цепочка **Цитадель → Мегапроектирование**.
