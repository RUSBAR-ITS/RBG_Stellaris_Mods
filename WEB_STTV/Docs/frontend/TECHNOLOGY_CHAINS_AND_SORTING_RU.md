## Назначение и статус

Рабочий документ от 2026-11-17 для постепенного накопления правил определения цепочек, их порядка и размещения карточек. Новые правила добавляются по итогам обсуждения с пользователем; предложения отделяются от принятых решений.

Это пока не ТЗ следующей реализации. Пользователь задал первые правила древовидного размещения; полный алгоритм ещё проектируется. Документ не меняет действующую сортировку.

## Опорные требования

Ранее согласованные требования, которые необходимо учитывать при проектировании:

| ID | Требование |
| --- | --- |
| R-01 | Показывать развитие связанных технологий как цепочки; одной независимой сортировки каждого столбца недостаточно. |
| R-02 | Области науки идут сверху вниз: физика, социология, инженерия. |
| R-03 | По умолчанию столбцы соответствуют игровому `tier`; номер в идентификаторе технологии не определяет столбец. Исключение L-12 переносит подходящие бесконечно повторяемые технологии в столбец отображения 6, сохраняя игровой `tier = 5`. |
| R-04 | Для технологических связей используются требования к технологиям из `prerequisites`. Условия по государству, признакам, зданиям и другим объектам не становятся технологическими предшественниками. |
| R-05 | В одном столбце карточки располагаются вертикально. Внутри одной ветки предшественник должен быть выше зависимой технологии, если обе находятся в одном столбце одной области науки. Требования из других веток сохраняются как игровые связи, но не навязывают этот вертикальный порядок. |
| R-06 | Варианты `technology_swap` остаются представлениями одной базовой технологии. Ручная смена варианта сохраняет базовый ID, уровень и технологические зависимости. |
| R-07 | Смена темы не меняет порядок карточек. После уточнения пользователя сортировка зависит от названия на текущем языке, поэтому смена RU/EN может менять порядок. |

Действующая реализация первого этапа сортирует столбцы по числу требований, набору предшественников и ID согласно [прежнему ТЗ поля технологий](elements/TZ_TECHNOLOGY_FIELD_RU.md#вертикальный-порядок-и-группировка). Новые правила ниже описывают желаемую замену этого подхода. Прежние приоритеты не переносятся автоматически в новый алгоритм; новое решение об алфавитном порядке заменяет требование независимости порядка от языка.

## Первые правила древовидного размещения

Первые правила заданы пользователем 2026-11-17 и дополнены 2026-11-18. Столбцы соответствуют уровням с исключением L-12; вертикальные места согласуются между столбцами: строится древовидное размещение, допускающее пустые позиции.

| ID | Правило |
| --- | --- |
| L-01 | Стартовые технологии (`start_tech = yes`) размещаются в самом верху своей области науки; остальные — ниже. |
| L-02 | Если у стартовой технологии есть пререквизит, она размещается ниже своего пререквизита. |
| L-03 | Далее применяется алфавитный порядок по отображаемому названию на текущем языке. При переключении RU/EN расположение может изменяться. |
| L-04 | Если технология продолжает ту же ветку и требует другую технологию того же уровня и той же области науки, она размещается непосредственно под ней. Требование к технологии другой ветки само по себе не обязывает размещать карточку ниже неё. |
| L-05 | Если пререквизит находится на предыдущем уровне, зависимая технология размещается непосредственно справа от него. |
| L-06 | Если технология является пререквизитом нескольких технологий следующих уровней, они размещаются за ней с резервированием места для ветвления; под исходной технологией образуется пустое место. |
| L-12 | Бесконечно повторяемую технологию (`levels = -1`) с игровым `tier = 5` и хотя бы одним технологическим пререквизитом размещать в столбце отображения 6. Область науки пререквизита не ограничивается. |
| L-09 | При нескольких пререквизитах первым применяется точное совпадение ID пререквизита и зависимой технологии после удаления всех цифр `0–9`. Остальные символы сохраняются. |
| L-07 | После L-09 кандидаты для размещения последовательно отбираются по совпадению области науки (`area`), затем научной категории (`category`) с зависимой технологией. |
| L-08 | Среди кандидатов, отобранных по L-07, обязательный технологический пререквизит имеет приоритет перед необязательным участником группы `OR`. |
| L-11 | При неоднозначности в режиме справочника исключать из кандидатов на опору пререквизиты, доступность которых требует нестандартного типа империи. Выбирать путь обычной империи; в дальнейшем исходным контекстом станет настройка пользовательской империи. |
| L-13 | Для технологий из L-12 при неоднозначном выборе опоры оставлять пререквизиты с наибольшим игровым `tier` среди текущих кандидатов. При одинаковом максимальном `tier` неоднозначность сохраняется. |
| L-10 | Если после остальных правил остаётся несколько кандидатов, последним блоком проверяется функциональная связь открываемых объектов. Пользователь задал желаемые продолжения для трёх случаев; общий механизм классификации ниже предложен к обсуждению. |

Порядок выбора опоры, дополненный пользователем 2026-11-18: L-09 → область науки по L-07 → научная категория по L-07 → обязательность по L-08. Кандидатами служат только существующие непосредственные пререквизиты. На каждом шаге при наличии совпадений остаются совпавшие кандидаты; если совпадений нет, текущий набор сохраняется для следующего критерия. При единственном кандидате выбор однозначен. Все исходные требования сохраняются, включая дополнительные зависимости и логическую структуру `AND`/`OR`. Совпадение ID или направления не превращает альтернативу в обязательное требование.

Нумерация служит для ссылок на правила. Полный порядок разрешения их пересечений ещё предстоит определить; неоговорённые случаи не получают автоматического решения только из номера правила.

## Последовательное применение правил

Уточнение пользователя от 2026-11-18:

1. Начальный набор — уникальные ID непосредственных технологических пререквизитов. Если их нет, выбирать опору не из чего.
2. При одном кандидате выбор немедленно завершается; следующие правила не проверяются и не могут заменить результат.
3. Каждое правило применяется только к текущему набору. Оно не возвращает кандидатов, исключённых предыдущими правилами.
4. Если результат правила непустой, он заменяет текущий набор.
5. Если результат пустой, правило пропускается, а прежний набор полностью сохраняется. Это не ошибка и не повод создавать новую зависимость.
6. Если после всех правил остаётся несколько кандидатов, родитель не назначается. Неоднозначность записывается в [лог со снимком состояния и настроек поля](CHAIN_AMBIGUITIES_RU.md); алфавитный порядок не выбирает родителя автоматически. Ручной выбор на этом этапе не вводится.

Общие правила размещения карточек выполняются отдельно от отбора опоры. Порядок и содержание критериев уточняются в отдельных документах ниже; ранние прогоны и первоначальное размещение L-10 в конце отбора не фиксируют окончательный порядок обновляемого алгоритма.

Текущий согласованный порядок: ID без цифр → область → категория → обязательность → прямые улучшения → совпадение `potential` → **функциональные группы → прямые функциональные связи** → косвенное родство → родство через производственные бонусы → родство через лимиты объектов → фильтр по империи → старшинство по игровому уровню.

Перестановка групп и прямых связей принята после [сравнения на текущих 679 базовых технологиях](CHAIN_CRITERIA_ORDER_REVIEW_RU.md) от 2026-11-19: изменился только Джаггернаут, с Цитадели на Линкоры; наборы остальных 678 технологий после сравниваемой пары совпали. Положения остальных критериев сохраняются. Это проверка влияния перестановки, а не полный новый прогон всех дополнений или проверка геометрии карточек.

## Прямые улучшения объектов

Согласованный критерий вынесен в [отдельный документ](CHAIN_DIRECT_UPGRADES_RU.md): сопоставление явного улучшения здания или компонента с технологиями, удаление общих обязательных требований только при сравнении и отбор среди оставшихся кандидатов. Подтверждения не суммируются как голоса. Правило ещё не подключено к размещению карточек.

## Совпадение условий доступности

Согласовано [полное структурное совпадение непустых блоков `potential`](CHAIN_AVAILABILITY_RU.md) после раскрытия вставок. Критерий следует за прямыми улучшениями и предшествует функциональному родству. Метаданные происхождения не сравниваются; частичные совпадения и условия весов не используются. Пустой результат сохраняет прежний набор кандидатов. Правило записано для будущей реализации.

## Прямые функциональные связи объектов

Согласован [критерий явной связи открываемых объектов](CHAIN_DIRECT_RELATIONS_RU.md): текущая технология открывает объект, который требует или усиливает объект кандидата. Сохраняются условия, альтернативы и отрицания; стоимость, расход ресурсов и веса ИИ не служат таким свидетельством. По уточнённому порядку правило действует на кандидатов, оставшихся **после функциональных групп**.

## Функциональные группы

Согласовано [сравнение назначения через функциональные группы](CHAIN_FUNCTIONAL_GROUPS_RU.md), выполняемое **перед прямыми функциональными связями**. Группы выводятся из признаков открываемых объектов по настраиваемым правилам, без заранее выбранных пар технологий. Сохраняются кандидаты с хотя бы одной общей подтверждённой группой; пустой результат пропускается. Первый пример — подвижный боевой корабль по скорости и боевым ролям, различающий линкоры и цитадель при анализе джаггернаута.

2026-11-19 добавлена группа [«Изменение класса планеты»](CHAIN_FUNCTIONAL_GROUPS_RU.md#изменение-класса-планеты): объект `terraform_link` с различающимися `from` и `to`, связанный с технологией через `has_technology` в `condition`. Она даёт ожидаемую цепочку Изменение формы суши → Вулканическое терраформирование; требование Проектирования глубоких слоёв коры сохраняется как дополнительная игровая зависимость. Выбор родителя не отменяет размещение карточки между двумя ветвями. Порядок критериев не меняется.

Группа [«Вооружение против кораблей»](CHAIN_WEAPONRY_RU.md), согласованная 2026-11-19, определяется оружейным компонентом либо явной связью открываемого объекта с действием и событием нанесения урона кораблям. При изолированном сравнении всех 679 базовых технологий она меняет только выбор Звёздной пушки: УФ-лазеры становятся единственным кандидатом до фильтра империи и старшинства. Остальные 678 выходных наборов кандидатов совпадают. Последующий общий прогон всех дополнений описан ниже.

## Косвенное функциональное родство

Согласован [поиск функционального свидетельства через пререквизиты кандидата](CHAIN_INDIRECT_AFFINITY_RU.md). Начальная глубина — один переход от кандидата назад по исходному графу требований; глубина настраивается. Используется полный граф с сохранением логики, а не `parent_tech`. Найденный предок служит свидетельством в пользу кандидата и не заменяет его. Пример — связь закалки брони с металлокерамическими сплавами через `tech_ship_armor_2`.

## Родство через производственные бонусы

Согласован [критерий собственного производственного бонуса технологии](CHAIN_PRODUCTION_AFFINITY_RU.md): модификатор → экономическая категория → профессия → предоставляющий её объект → технология-кандидат. Он действует перед критерием лимитов объектов и фильтром по империи, сохраняет условия свидетельств и общую процедуру отбора. Разобранный пример поддерживает Металлокерамические сплавы → Голографические литейные формы. Правило записано для будущей реализации.

## Родство через лимиты объектов

Согласован [критерий увеличения лимита используемых объектов](CHAIN_CAPACITY_AFFINITY_RU.md): собственный модификатор технологии → лимит → использующий его объект → открывающий объект кандидат. Соответствия модификаторов и полей объектов задаются в конфигурации. Критерий действует после производственных бонусов, непосредственно перед фильтром по империи. Для Мегапроектирования `country_starbase_capacity_add` связан с `starbase_capacity_used`; после исключения кочевого варианта профилем империи ожидается цепочка Цитадель → Мегапроектирование. Код пока не меняется.

## Неразрешённые неоднозначности

Согласовано [журналирование неоднозначных технологий](CHAIN_AMBIGUITIES_RU.md) с кандидатами, ходом отбора и состоянием/настройками поля на момент расчёта. `parent_tech` остаётся `null`; отображение продолжается самостоятельной ветвью на своём уровне с сохранением игровых зависимостей. Ручные назначения и их конфигурация отложены. Снимок должен позволять различать случаи в будущих режимах поля.

## Общий аналитический прогон

[Полный проход согласованной последовательности от 2026-11-19](CHAIN_RULES_FULL_REVIEW_RU.md) завершён: из 679 базовых технологий 178 не требуют родителя, у остальных 501 родитель выбран однозначно. Разрешены все 89 случаев с несколькими пререквизитами; неоднозначностей и циклов нет, все 12 контрольных примеров совпали. Ручные назначения не использовались.

Относительно предыдущего полного прохода изменились пять решений: Джаггернаут, Металлокерамические сплавы, Мегапроектирование, Звёздная пушка и Вулканическое терраформирование. Результат относится к базовым представлениям и согласованному профилю обычной империи; переключения вариантов и координаты карточек отдельно не проверялись. В продукт алгоритм пока не перенесён.

## Обычная империя в режиме справочника

Решение пользователя от 2026-11-18: при неоднозначном выборе продолжения цепочки справочник ориентируется на путь обычной империи. Для этого применяется фильтр L-11 по условиям доступности технологий-кандидатов.

- Фильтр влияет на выбор опоры для размещения. Все технологии, исходные пререквизиты и структура `AND`/`OR` остаются в БД; исключение кандидата не удаляет карточку или игровое требование.
- На разобранном примере обычная империя является некочевой и не использует биологические корабли. `potential = { is_nomadic = yes }` исключает кандидата; аналогично действует требование `country_uses_bio_ships = yes`. Соответствующие условия с `no` не служат основанием для исключения.
- Проверять логический смысл условия доступности, включая вложенные отрицания и альтернативы. Наличие специальной ветви внутри `OR` не исключает технологию, если есть подходящая обычной империи ветвь. Упоминание признака в весах исследования или ИИ само по себе не ограничивает доступность.
- Неизвестное или ещё не разобранное условие не доказывает принадлежность к нестандартной империи. Полный состав признаков обычной империи и поддерживаемые условия предстоит определить отдельно; остальные параметры государства не назначаются автоматически.
- Сохраняется общая процедура отбора: при одном кандидате остановиться; при пустом результате фильтра пропустить его, сохранив предыдущий набор. Если кандидатов осталось несколько, продолжить применение правил.
- Фильтр относится к критериям до заключительного функционального отбора L-10. Его точное место относительно ID, области, категории, обязательности и свидетельств улучшения объектов ещё не определено; прежний порядок этих критериев этим решением не переставляется.
- В дальнейшем пользователь сможет задать свою империю, и всё дерево будет пересчитываться с учётом её параметров. Состав настройки и механизм перестроения относятся к последующему проектированию.

Пример `tech_juggernaut`: из полного набора кандидатов исключаются `tech_arkship_construction` (кочевники) и `tech_harbinger_growth_2` (биологические корабли). Остаются `tech_starbase_5` и `tech_battleships`. Фильтр сам по себе не выбирает Линкоры: продолжение корабельной цепочки требует последующего функционального критерия.

- Следовательно, сравнение эффектов целевого объекта с эффектами объектов, открываемых предшественниками кандидатов, различает эти два пути. Сравниваются ключи эффектов в соответствующем контексте, а не названия технологий или совпадение числового бонуса.
- Обход должен использовать полный граф игровых пререквизитов, а не уже выбранную цепочку отображения. Принятая производственная опора сплавов не убирает их игровое требование броневых материалов, поэтому косвенное свидетельство сохраняется. Для общего алгоритма ещё нужно определить глубину поиска, обращение с альтернативами `OR` и приоритет непосредственного совпадения над косвенным; произвольная общая дальняя технология не должна автоматически склеивать ветви.

Это проверка одного примера, не утверждение и не реализация универсального правила. Источники: [броневой компонент](E:/SteamLibrary/steamapps/common/Stellaris/common/component_templates/00_utilities.txt:147), [компонент закалки](E:/SteamLibrary/steamapps/common/Stellaris/common/component_templates/00_utilities_aux.txt:250), [пререквизиты и эффект сплавов](E:/SteamLibrary/steamapps/common/Stellaris/common/technology/00_eng_tech.txt:2853), [улучшенное литейное здание](E:/SteamLibrary/steamapps/common/Stellaris/common/buildings/04_manufacturing_buildings.txt:97). Свидетельства подтверждены также в `data/databases/components.json` и сохранены с JSON Pointer в `data/chain_analysis/armor_function_evidence.json`.

Наблюдение о числе кандидатов подтверждено: в предыдущем остатке у всех **девяти** технологий было ровно **два** кандидата. Но исходно среди 89 неоднозначных технологий у 71 было два пререквизита, у 14 — три, у одной — четыре, у трёх — пять. Поэтому последовательный отбор остаётся рассчитанным на произвольное число кандидатов; размещение между двумя — отдельный случай геометрии.

## Направления исследований и выбор предшественника

Направление задаётся полем `category`, например `category = { propulsion }`; область науки — отдельным полем `area`. В текущей БД у всех 679 базовых технологий ровно одна категория, хотя синтаксически поле является списком.

| Область | Направления базовых технологий текущей БД |
| --- | --- |
| Физика | Частицы (`particles`), вычислительная техника (`computing`), управление полями (`field_manipulation`) |
| Социология | Искусство управления (`statecraft`), военная теория (`military_theory`), биология (`biology`), новые миры (`new_worlds`), археоисследования (`archaeostudies`), псионика (`psionics`) |
| Инженерия | Промышленность (`industry`), материалы (`materials`), реактивная тяга (`propulsion`), освоение пустоты (`voidcraft`) |

Это распределение наблюдаемых данных, а не жёсткое ограничение языка игры. Определения категорий находятся в `common/technology/category/00_category.txt`. Русские названия сверены с `Localisation_Base/1-Prio_Russian_Localization_Fix_RE/russian/technology_l_russian.yml` и `ancient_relics_l_russian.yml`; переопределений этих ключей в `replace` не найдено. Английские ключи сверены с одноимёнными файлами английской локализации игры.

Проверка L-07 по базовым представлениям 89 технологий с несколькими непосредственными пререквизитами:

| Пререквизиты с совпадающими `area` и `category` | Технологий |
| --- | ---: |
| Ровно один кандидат | 44 |
| Несколько кандидатов | 39 |
| Нет кандидатов | 6 |

Из 44 случаев с единственным кандидатом в 11 одна только область науки оставляла несколько кандидатов: именно категория позволяет различить их. В подсчёте учитываются ID, упомянутые в `prerequisites`, включая альтернативы `OR`; условия игры не вычисляются.

Пример: **Планетарный репроцессор** (`tech_arkship_planetary_refinery`, `engineering / industry`) требует **Планетарную инженерию** (`tech_planetary_engineering`, `engineering / industry`) и **Совершенный корабль-ковчег** (`tech_arkship_tier_3`, `engineering / voidcraft`). По L-07 предпочтительной опорой становится Планетарная инженерия; требование корабля-ковчега сохраняется.

Пример оставшейся неоднозначности: **Улучшенные форсажные камеры** (`tech_afterburners_2`) требуют `tech_afterburners_1` и `tech_thrusters_3`; все три относятся к `engineering / propulsion`. Одного L-07 здесь недостаточно.

Материалы проверки: `data/chain_analysis/category_analysis.json`, исходная БД `data/stage10/database.json`. У 11 блоков `technology_swap` найдено переопределение категории. Следует отдельно решить, выбирать опору по базовым или текущим отображаемым категориям; приведённая статистика рассчитана по базовым.

## Приоритет обязательного пререквизита

Правило L-08 согласовано пользователем 2026-11-17. Обязательность определяется структурой `prerequisites`, без вычисления состояния государства. Само присутствие ID в одной из альтернатив `OR` не делает этот ID обязательным. Все требования и альтернативы сохраняются; меняется только предпочтение при выборе продолжения для размещения.

Если подходящих обязательных кандидатов несколько, L-08 не выбирает одного из них. Если таких кандидатов нет, выбор между альтернативами остаётся отдельной задачей. Правило не меняет приоритет области и направления по L-07.

В исследованных 39 случаях правило выделяет единственного кандидата ещё для пяти технологий:

| Технология | Предпочтительный пререквизит |
| --- | --- |
| `tech_arkship_tier_2` | `tech_arkship_construction` |
| `tech_arkship_tier_3` | `tech_arkship_tier_2` |
| `tech_growth_chamber_1` | `tech_stingers` |
| `tech_growth_chamber_2` | `tech_growth_chamber_1` |
| `tech_military_arkship` | `tech_arkship_construction` |

С учётом 21 случая, поддержанного улучшениями объектов или совпадающими эффектами, основания для выбора найдены для 26 из 39; остаются 13 неоднозначных случаев. Это результат исследования и согласования L-08, а не утверждение всего алгоритма или выполненная реализация сортировки.

## Дополнительные базы для анализа цепочек

Пользователь определил следующий объём работ: бэкэнд должен создавать ещё две БД — компонентов и зданий; фронтенд должен работать с тремя БД, включая технологическую.

| База | Основной каталог игры | Данные для связывания |
| --- | --- | --- |
| Технологии | `common/technology` | ID, `prerequisites`, область, направление и эффекты |
| Компоненты | `common/component_templates` | `key`, `prerequisites`, `upgrades_to` |

Предлагаемая основа — общий существующий парсер и отдельные настраиваемые наборы источников и выходов. Каждая БД сохраняет результаты полного штатного разбора и раскрытия, а извлечение связей выполняется отдельной обработкой. Фронтенду понадобятся отдельные индексы объектов и ссылки с указанием БД; одинаковый JSON Pointer в разных файлах обозначает разные узлы.

Подготовлены [ТЗ этапа 11 бэкэнда](../TZ_BACKEND_STAGE_11_RU.md) и [ТЗ этапа 2 фронтенда](TZ_FRONTEND_STAGE_2_RU.md). Общая метка набора, адресация узлов, диагностика, правила локализации компонентов/зданий и извлечение свидетельств улучшения предложены в этих документах для утверждения. ## Подходы к построению цепочек

Ранее выделены два подхода. Первые правила выше описывают желаемое поведение; выбор полного метода и его реализация ещё не завершены.

| Подход | Содержание | Последствия |
| --- | --- | --- |
| Ручной | Явно задавать принадлежность технологий к цепочкам и порядок; способ хранения ещё предстоит выбрать. | Проще непосредственно задать нужный результат, но изменения состава технологий и связей потребуют пересмотра этих данных. |
| Аналитический | Выводить цепочки из данных по общим правилам. | Правила придётся разрабатывать итерационно, проверяя развилки, объединения и другие неоднозначные случаи. |

Предложение для аналитического подхода: отдельно определять состав цепочек и отдельно размещать их в столбцах. Начать с нескольких примеров, затем проверять правила на всей БД. Это предложение к обсуждению, а не утверждённый алгоритм.

## Правила для дальнейшего обсуждения

Пока открыты следующие решения:

- Как выбирать опору при оставшейся неоднозначности после L-07 и L-08 либо отсутствии совпадений; как выбирать между несколькими альтернативами `OR`.
- Как сочетать верхнее размещение всех стартовых технологий с выравниванием их нестартовых продолжений справа, а требование «ниже пререквизита» — с размещением в соседнем столбце.
- Как делить место при нескольких зависимых технологиях одного уровня, рассчитывать высоту ветвей и применять алфавитный порядок при равных условиях; как разрешать одинаковые названия.
- Как учитывать связи через несколько уровней, между областями науки и в сторону меньшего `tier`.
- Как ручная смена варианта и его категории влияет на выбор опоры и перестроение ветви.

Для проверки предложений уже есть примеры из исследования: лазеры, реакторы, ракеты, добывающие станции, космические базы и `tech_akx_worm_1…3`. Совпадение ID после удаления цифр определено в L-09. Произвольная общая часть ID, отсутствие предшественников или принадлежность одной связной компоненте сами по себе не приняты как правила выделения цепочки.
