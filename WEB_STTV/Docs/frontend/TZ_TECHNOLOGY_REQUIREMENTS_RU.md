## Статус и границы

Документ фиксирует согласованные форматы `prerequisites` и `links`, а также вычисление `prerequisiteIds` и `requirementCount` для одновременных требований и альтернатив. Он дополняет [ТЗ результата Worker](TZ_WORKER_RESULT_RU.md), [адаптера](TZ_DATABASE_ADAPTER_RU.md) и [поля технологий](elements/TZ_TECHNOLOGY_FIELD_RU.md).

В этой итерации оформляется документация. Исходная БД и парсер не изменяются. Требования берутся только из `prerequisites` базовой технологии; условия доступности из других полей не добавляются.

## Исследованные данные

Проверка текущей БД `data/stage10/database.json` охватила 679 базовых технологий. Найдены обычные списки требований и 21 логический блок `OR`; `NOT`, `NAND` и `NOR` в исследованных требованиях отсутствуют. У четырёх технологий явно задан пустой список. Неизвестных ID технологий среди требований не обнаружено.

Эти числа характеризуют исследованный файл и не ограничивают реализацию. Структура модели допускает вложенные группы и все пять уже известных логических операторов; правила использования отрицаний в раскладке пока не согласованы.

## Узлы дерева требований

Предусмотрены два вида узлов:

| Вид | Поля | Назначение |
| --- | --- | --- |
| Технология | `kind: "technology"`, `technologyId: string` | Ссылка на базовый игровой ID технологии |
| Группа | `kind: "group"`, `operator`, `items` | Логическая операция и упорядоченный массив вложенных узлов |

`operator` хранит одно из значений `AND`, `OR`, `NOT`, `NAND`, `NOR`. `items` содержит узлы технологий и/или вложенные группы. Вычисление истинности условий для конкретного государства не выполняется.

## Корневая группа и вложенность

`prerequisites` всегда имеет корневую группу `AND`. Она представляет обычный список одновременно выполняемых требований. Отсутствующее поле и явно пустой список приводятся к одной форме:

```json
{
  "kind": "group",
  "operator": "AND",
  "items": []
}
```

Исходные узлы остаются в дереве БД, доступном через `sourceRef`. Приведение к общему корню относится только к производной модели интерфейса.

Порядок элементов и вложенность логических групп сохраняются. Вложенный `OR` не превращается в набор обязательных технологий; повторные упоминания не удаляются из дерева.

Пример для условной технологии `D`: нужна `A` и одна из `B` или `C`.

```json
{
  "kind": "group",
  "operator": "AND",
  "items": [
    {
      "kind": "technology",
      "technologyId": "A"
    },
    {
      "kind": "group",
      "operator": "OR",
      "items": [
        { "kind": "technology", "technologyId": "B" },
        { "kind": "technology", "technologyId": "C" }
      ]
    }
  ]
}
```

## Производные значения

Общий обработчик получает дерево и вычисляет данные один раз при подготовке каталога:

| Поле | Правило |
| --- | --- |
| `prerequisiteIds` | Уникальные ID всех узлов технологий в данном дереве, включая альтернативы, без обхода собственных требований этих технологий |
| `requirementCount` | Узел технологии даёт `1`; `AND` суммирует значения дочерних узлов; группа `OR` даёт `1`; пустой корневой `AND` даёт `0` |

Для примера выше набор равен `A`, `B`, `C`, а число требований — `2`. Две группы `OR` внутри корневого `AND` дают число `2`. Правило `OR = 1` относится к группе целиком, а не к сумме её альтернатив.

`requirementCount` — согласованный показатель сортировки карточек. Он не вычисляет минимальное число исследований во всей цепочке. `prerequisiteIds` представляет набор: порядок перечисления не меняет группировку. Логическое дерево остаётся источником смысла требований.

Для деревьев с `NOT`, `NAND` или `NOR` формула подсчёта пока не определена; правила для `AND` и `OR` не подменяют её автоматически.

## Записи связей

`data.links` содержит одну запись на упорядоченную пару базовых ID технологий:

| Поле | Тип и назначение |
| --- | --- |
| `from` | Строка: ID упомянутой технологии |
| `to` | Строка: ID технологии, чьё дерево требований содержит упоминание |
| `requirementPaths` | Массив путей ко всем соответствующим узлам в `prerequisites` технологии `to` |

Направление связи — от упомянутой технологии к зависимой. Если одна технология упоминается несколько раз в требованиях другой, создаётся одна связь с несколькими путями. Обратная пара ID является другой связью.

Связь сама по себе не обозначает безусловную обязательность. Принадлежность к `OR` и другим группам определяется через дерево и сохранённые пути. Сведения о логике не заменяются одним признаком «обязательная/альтернативная».

Связи используют базовые ID. Ручной выбор представления, изменение языка или темы не перестраивают их; перемещение карточки в другую область науки сохраняет её связи. Вид линий остаётся предметом проектирования поля.

## Пути к упоминаниям

Каждый путь — массив неотрицательных целых индексов, отсчитываемых от нуля. Первый индекс выбирает элемент `items` корневой группы; каждый следующий — элемент `items` очередной вложенной группы. Путь заканчивается на узле `technology`, чей `technologyId` совпадает с `from`.

Для связи `B → D` в примере:

```json
{
  "from": "B",
  "to": "D",
  "requirementPaths": [[1, 0]]
}
```

Путь `[1, 0]` ведёт ко второму элементу корня, группе `OR`, затем к её первому элементу `B`. Для `A` путь равен `[0]`, для `C` — `[1, 1]`.

Эти пути относятся к производному `data.technologies[to].prerequisites`. Они не являются `sourceRef` и не адресуют исходный JSON напрямую. При замене БД дерево и пути заменяются вместе с остальными данными результата.

## Отрицательные логические операции

Формат группы сохраняет `NOT`, `NAND` и `NOR` вместе с их вложенными узлами. Их влияние на `requirementCount`, положение карточек и использование связей в качестве предшественников требует отдельного согласования.

Отрицательное условие нельзя автоматически считать требованием предварительно исследовать упомянутую технологию. По дополнительному согласованию пользователя 2026-11-17 наличие `NOT`, `NAND` или `NOR` в `prerequisites`, включая вложенные группы, останавливает подготовку с `invalid_database`. Сообщение панели — «Не удалось подготовить данные для отображения», путь и причина сохраняются в отчёте. Произвольная формула или числовая заглушка не вводятся; частичный каталог не публикуется. В проверенной текущей БД этого случая нет.

## Критерии приёмки

Проверки выполняются после реализации:

1. Отсутствующие и явно пустые требования дают корневой `AND` с пустым `items`, пустой набор ID и число `0`.
2. Одиночные, одновременные и альтернативные требования сохраняют порядок, вложенность и различие операций.
3. Пример `A AND (B OR C)` даёт три уникальных ID и число требований `2`; две группы `OR` дают число `2`.
4. Каждой паре `from`/`to` соответствует одна связь; повторные упоминания сохраняются отдельными путями.
5. Каждый путь разрешается в узел `technology` с ID `from` в дереве технологии `to`.
6. Прямое требование, альтернатива и вложенная группа различимы через дерево без потери логики в плоском списке связей.
7. Выбор представления сохраняет базовые ID и связи; транзитивные предшественники не добавляются.
8. Структурное представление отрицательных операторов не считается утверждением правил их подсчёта и раскладки.
