## 1. Статус и границы

ТЗ утверждено пользователем 2026-11-18; реализация и приёмочные проверки завершены. Полный опубликованный набор успешно открыт в собранном интерфейсе; результаты приведены в [руководстве этапа](FRONTEND_STAGE_3_RU.md). Пользователь согласовал открытие полного набора из 15 БД и RU/EN-локализацию новых объектов. Состав и правила подготовки задаёт [этап 12 бэкэнда](../TZ_BACKEND_STAGE_12_RU.md).

Этап расширяет загрузку, адресацию, каталоги и общий индекс локализации. Технологическое поле сохраняет действующее отображение. Новые экраны объектов, линии, функциональная классификация технологий, применение новых правил цепочек и выполнение игровых условий не входят в этот этап.

ТЗ заменяет требования второго этапа о трёх файлах, списке ролей и удержании всех полных деревьев в Worker. Остальное согласованное поведение UI сохраняется.

## 2. Открытие и состояния

Одна кнопка «Открыть набор БД» вызывает множественный выбор файлов. Пользователь выбирает ровно 15 JSON; порядок выбора и имена произвольны. Список требуемых ролей берётся из общего `config/datasets.json`, а принадлежность каждого файла — из `dataset.kind`.

Условия принятия:

- `format = sttv.parse_database`, `format_version = 6`.
- Ровно один файл каждого из 15 согласованных видов; нет недостающих, повторных или неизвестных ролей.
- Общий непустой `set_id` формата SHA-256.
- Доступны данные, необходимые адаптерам и индексам текущего интерфейса.

Сводный отчёт сборки не является участником набора. Не подставлять старые файлы и не открывать неполный набор. Не искать соседние файлы автоматически. Проверка `set_id` не является пересчётом хешей всех БД в браузере.

Запуск приложения и обновление страницы не открывают файлы, не запускают генератор и не обращаются к исходникам игры. Закрытие диалога без выбора сохраняет текущий экран. После выбора нового набора прежняя операция и поле освобождаются согласно действующей модели замены.

«Повторить» использует выбранные 15 объектов `File`; «Отмена» прекращает Worker и возвращает начальное состояние. Ответы устаревших `operationId` игнорируются. Ошибка не публикует частичное поле. Единственный `ready` отправляется после подготовки всего набора.

## 3. Подготовка в Worker

Сохранить фазы `reading`, `parsing`, `preparing`, прогресс по текущему файлу и общему количеству. Счётчик и сообщения не содержат зашитого числа три. Имена видов в сообщениях берутся из интерфейсной локализации.

Обрабатывать файлы последовательно: чтение → JSON-разбор → проверка метки → адаптация необходимых данных. Освобождать текст после разбора, полное дерево — после извлечения компактных данных этого участника. Не держать одновременно 15 полных AST и их строковые копии. Основной поток получает только каталоги, локализацию, существующие связи, сведения о наборе и диагностику.

Межфайловые связи существующих адаптеров окончательно проверяются после обработки всех участников. Порядок выбора файлов не должен влиять на результат: требующаяся технология может быть прочитана позже здания. Сохранить текущие `objectRequirements`, `objectUpgrades`, `upgradeEvidence` для компонентов/зданий; не расширять их на новые виды без согласованных предметных правил.

Worker хранит ссылки на выбранные `File` и адреса узлов. Освобождение AST не удаляет данные из исходного JSON. Возможный будущий просмотр подробного дерева сможет читать нужный файл отдельно; механизм такого просмотра сейчас не реализуется. Текущие условия и варианты, нужные существующему интерфейсу, извлекаются до освобождения дерева.

Один отдельный файл всё ещё может быть большим. При реальной проверке измерить время, размеры и доступные показатели памяти, особенно для `events.json`. Не заявлять поддержку объёма без успешного открытия полного набора. Если стандартный JSON-разбор одного участника превышает пределы среды, зафиксировать это как блокер и отдельно согласовать изменение представления или чтения; не молча исключать события и не менять набор на частичный.

### Согласованное дополнение: потоковый JSON

Пользователь согласовал потоковое чтение после проверки: форматированный файл компонентов размером 871 070 973 байта привёл к пустой строке из `File.text()` в Chromium 159.0.8154.6. Worker читает байтовый поток через декодер UTF-8 и разбирает JSON порциями, без строкового представления всего файла.

Первый проход извлекает метаданные набора и число документов без сохранения игровых деревьев. Второй проход передаёт документы адаптерам по одному, сохраняя исходные индексы JSON Pointer. Он удерживает только поля, потребляемые адаптерами, и локализацию; служебные метаданные раскрытия, координаты и неподдерживаемые UI игровые поля остаются в исходном файле. Каталоги накапливаются, а межобъектные ссылки проверяются после чтения всего набора. Порядок ключей JSON не ограничивается расположением метки в начале файла.

Разбор проверяет корректность структуры JSON, включая границы порций внутри строк, Unicode и чисел. Незаконченный или ошибочный поздний фрагмент завершает операцию ошибкой без частичного `ready`. Отмена прекращает Worker вместе с чтением. Эти изменения не меняют формат БД, не запускают генерацию и не удаляют данные из файлов.

## 4. Адресация и каталоги

Расширить квалифицированную ссылку на узел: `{database, pointer}`, где `database` — одна из 15 ролей, `pointer` — JSON Pointer внутри файла. Один `setId` хранится в общем результате. Внутренние ссылки обогащений квалифицируются соответствующей ролью при адаптации.

Для новых видов добавить компактные каталоги определений по ролям. Запись содержит ссылку на корневое определение, тип конструкции, игровой ID при его наличии и адреса/ID доступных локализованных текстов. Список записей сохраняет исходный порядок; индексы игровых ID строятся отдельно и не заменяют список. Полные тела эффектов и событий в ответ `ready` не копируются.

Существующие каталоги технологий, компонентов и зданий сохраняют необходимые UI поля. Новые виды не обязаны притворяться технологией или иметь `tier`, `area`, `nameId`, `descriptionId` и технологические требования, когда таких данных нет.

- Для события игровой ID берётся из `id`, а `country_event` и подобные ключи являются типом. Все описания индексируются по собственным адресам, без назначения активного.
- У `terraform_link` игрового ID нет: запись адресуется через `{database, pointer}`, хранит значения `from`/`to` и ссылки на их локализацию. Равные пары классов планет не сливаются.
- Для повторных фрагментов `on_actions` индекс имени ведёт к массиву определений. Не выбирать один фрагмент и не исполнять обработчик.
- Именованные одиночные объекты проверяются на дубли в своём виде. Совпадение имён разных видов допустимо.
- Директивы, переменные, метаданные раскрытия и узлы локализации не становятся самостоятельными игровыми объектами.

Указатели и каталоги подготавливают данные для будущего анализа; этот этап не строит новый граф поведения «действие → обработчик → событие».

## 5. Локализация

Общий индекс источника `database` пополняется текстами всех 15 БД. Контракт UI-текста прежний: источник, ID строки, язык системы. Не добавлять отдельный источник текста для каждого вида БД.

Правила бэкэнда определяют, есть ли у цели название, описание или оба поля. Для скрытого события или служебного обработчика отсутствие неприменимой текстовой роли допустимо. Отсутствующий перевод выбранного ключа остаётся предупреждением; отсутствие обязательного обогащения объявленной цели — ошибка подготовки.

Учитывать цели на `title`, `desc`, вложенных текстах описаний, `activity_key`, `from`/`to` и корневых объектах согласно конфигурации и сохранённым обогащениям. Обход не должен превращать исходные строки в метаданных расширения в повторные цели.

Индексируется сохранённый `requested_key`; совпадающие тексты одного ключа и языка объединяют происхождения, конфликтующие найденные тексты дают ошибку с обоими источниками. Квалифицировать `recordRef`, наследование и иные ссылки на узлы соответствующей ролью. Не раскрывать ссылки повторно, не вычислять условия и не форматировать игровую разметку. Переключение RU/EN использует подготовленные индексы.

## 6. Диагностика и конфигурация

Общий реестр ролей используется для выбора файлов, метаданных, диагностики и счётчиков. Отдельные правила адаптации и текстовые роли остаются декларативными. Не копировать логику открытия для каждого вида БД. Генерируемые схемы согласованы с бэкэндом.

Сообщения о неверном количестве файлов показывают фактическое и ожидаемое количества; технический отчёт перечисляет недостающие/повторные роли, файл, этап и квалифицированный адрес при наличии. Локализованные подписи видов хранятся в словарях UI. Сохраняется существующий экспорт диагностического JSON с переносами и отступами в два пробела.

Фронтенд проверяет контракт набора и данные, которые потребляет, но не повторяет полную серверную проверку AST, раскрытие вызовов или валидацию смысла игровых команд.

## 7. Проверки и приёмка

1. На контрольном наборе открыть 15 файлов в разных порядках и с произвольными именами; итог одинаков. Отдельно проверить каждый вид и ссылки одинакового вида/ID из разных БД.
2. Проверить 14/16 файлов, повтор роли, неизвестную роль, файл отчёта вместо БД, версию 5, разные `set_id`, ошибочный JSON и отсутствующие потребляемые данные. Частичного `ready` нет.
3. Проверить обогащения только с названием или только с описанием, условные описания событий, нулевые текстовые цели, локализацию концов терраформирования, конфликты строк и сохранение всех происхождений.
4. Проверить повторяемые переходы и фрагменты обработчиков, уникальность настоящих ID, отсутствие выдуманного игрового ID у `terraform_link` и отсутствие ложных технологических требований.
5. Проверить отмену, повтор, замену набора, устаревшие ответы Worker и прогресс на поздних файлах. В основном потоке нет полных AST; предыдущие полные деревья не накапливаются в Worker.
6. Реальный полный набор, собранный этапом 12 с форматированными JSON, открывается целиком. Зафиксировать браузер, суммарный/максимальный размер файла, время и доступные показатели памяти. Загрузку маленьких фикстур не выдавать за проверку полного набора.
7. Регрессия: технологии и варианты, оба языка, темы, тултипы, меню, состояние и существующие связи компонентов/зданий. Новые цепочки и сортировка не появляются неявно.
8. Обновить инструкции, сообщения, changelog RU/EN и версию интерфейса по принятому правилу. Код модульный, общий разбор и индексирование переиспользуются. Portable-поставка остаётся отдельной задачей.
