## 1. Статус и границы

**ТЗ утверждено пользователем 2026-11-19 и реализовано.** Фактические проверки, запуск и ограничения — в [руководстве этапа](FRONTEND_STAGE_4_RU.md).

Заменить выбор 15 монолитных JSON открытием каталога нового формата. Сохранить карточки, названия и описания RU/EN, варианты, тему, меню, состояния открытия, отмену, повтор и отчёт. Сортировка и размещение не меняются; использование сохранённых `parent_tech`/`children` для новой сетки и вызов Python из браузера остаются отдельными этапами.

Автоматическая сборка, открытие на старте, восстановление доступа между запусками, HTTP API и запись в БД из браузера не добавляются. Старый способ открытия 15 файлов не поддерживается параллельно с новым. Исторические ТЗ сохраняются как история.

## 2. Выбор каталога

Существующая кнопка «Открыть набор БД» / «Open database set» открывает выбор одной папки. Ожидается корень набора, содержащий манифест. Старт приложения и обновление страницы ничего не читают до явного действия пользователя.

Использовать `<input type="file" webkitdirectory>` и карту файлов по относительным путям. Браузер выдаёт список `File` со свойством `webkitRelativePath`; это позволяет восстановить структуру выбранного каталога. Список файлов сам по себе не означает чтения их содержимого. Основание: [выбор каталога](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/webkitdirectory) и [относительные пути](https://developer.mozilla.org/en-US/docs/Web/API/File/webkitRelativePath).

Убрать один общий начальный сегмент выбранной папки и искать манифест только в её корне. Имя манифеста брать из общего конфига хранения, по умолчанию `manifest.json`; не дублировать значение в компонентах. При отсутствии поддержки выбора каталога показывать локализованное сообщение; не подменять сценарий загрузкой монолитной БД.

Проверить все объявленные пути по карте выбранных файлов. Отсутствующий документ делает набор неполным, даже если он пока не нужен полю. Одинаковые имена в разных подпапках допустимы; совпадение нормализованных относительных путей — ошибка. Посторонние файлы и старые версии, на которые манифест не ссылается, игнорируются без чтения. Не искать манифесты рекурсивно и не угадывать нужный набор.

Нельзя получить произвольный файл диска только по пути из манифеста: используются исключительно выбранные пользователем `File`. URL, абсолютные пути и выход за корень не разрешаются. Данные не отправляются во внешние сервисы.

## 3. Подготовка данных

Начальное открытие читает манифест и все документы вида `technologies`, необходимые действующему адаптеру. По ним готовятся полный каталог технологий, варианты, технологические требования и локализация. Документы прочих 14 видов не нужны для текущего поля и не читаются только ради регистрации набора или счётчиков.

Все 15 видов присутствуют в каталоге манифеста; их доступность и загрузка — разные состояния. Сведения о файлах, типах и ID доступны сразу, содержимое — после явного запроса потребителя к читателю. Состояние вида/документа различает `not_loaded`, `loading`, `loaded`, `failed`. Не представлять незагруженный вид пустым массивом успешно прочитанных объектов.

Читатель поддерживает загрузку указанного вида целиком и загрузку объектов по `ObjectRef`: необходимые документы определяются через индекс, одинаковый документ читается один раз. Для фрагментного вида возвращаются все записи ID; анонимные объекты адресуются через `NodeRef`. Эти функции являются внутренним интерфейсом, отдельные кнопки просмотра зданий или событий не вводятся.

Адаптеры компонентов, зданий и остальных видов сохраняют своё извлечение данных, но запускаются по запросу вместо обязательного вызова при открытии. Подготовка межвидовых свидетельств запускается только после загрузки нужных входов. Правила извлечения не меняются. Готовность поля означает готовность его технологических данных, а не полный разбор всего набора.

Начальный набор загружаемых видов задаётся в конфиге открытия `config/frontend/opening.json`, предлагаемое значение `initial_datasets = ["technologies"]`. Не вводить отдельные захардкоженные списки 15 видов: использовать действующий общий реестр. Контракт нового манифеста и ссылки соответствует ТЗ бэкенда.

## 4. Чтение и хеширование

Потоковый разбор JSON в Worker сохраняется и адаптируется к отдельному документу. Один проход по байтам одновременно считает SHA-256, декодирует UTF-8 и извлекает компактную проекцию. Не делать прежний проход всего содержимого ради заголовка, а затем второй ради объектов: метаданные доступны из манифеста, конверт проверяется в основном проходе.

Для большого документа не использовать `File.text()` или накопление полного `ArrayBuffer`. Неизвестные проекции узлов и история остаются в файле, но не копируются в основной поток. Неподходящие для просмотра поля не удаляются из самой БД.

Нативный `SubtleCrypto.digest()` не принимает поток и требует буфер целиком; это ограничение описано в [документации](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest). Предлагается небольшой отдельный модуль хеширования на `@noble/hashes` с последовательными обновлениями SHA-256: [API библиотеки](https://github.com/paulmillr/noble-hashes#implementations). Использовать только нужный импорт, закрепить выбранную совместимую версию в зависимостях и lock-файле при реализации. Собственный криптографический алгоритм не писать.

Проекция файла становится доступной только после успешной проверки размера, хеша, конверта и соответствия индексируемых записей. Неверный хеш — ошибка чтения набора с точным адресом. Непрочитанные документы имеют статус `not_checked`. Полный аудит всего набора выполняет отдельная команда бэкенда; кнопка аудита в этом этапе не добавляется.

Worker остаётся один; число 10 относится к процессам Python. Новый пул браузерных Worker в этап не входит. Кэш проверенных компактных данных действует только в текущем открытом снимке и освобождается при закрытии/смене набора; каждый последующий сеанс проверяет используемые файлы заново.

## 5. Снимок и ссылки

После чтения фиксируются `set_id` и `snapshot_revision` манифеста. `SttvNodeRef` получает `{database, document_id, pointer}` вместо ссылки на глобальную позицию документа. Обновить адаптеры, локализацию, наследование описаний, отчёт и диагностику. Варианты используют вложенный указатель того же документа.

Файлы из нового снимка не примешиваются к уже открытому. Изменение манифеста на диске не вызывает автоматического открытия или пересчёта. После внешнего обогащения пользователь заново выбирает каталог. Если ранее выбранный `File` стал недоступен, сообщить об ошибке и предложить повторное открытие.

Смена языка, темы и варианта продолжает использовать уже подготовленные технологии и не читает документы повторно. Локализация остаётся при объектах БД; манифест её не дублирует. Значения вычисленных связей сохраняются в исходных файлах и не становятся новым алгоритмом размещения в этой итерации.

## 6. Worker и состояние приложения

Сообщение открытия передаёт Worker карту выбранных файлов и ID операции. Worker читает манифест, проверяет каталог и загружает начальные виды. Добавить запросы загрузки вида/объектов с ID запроса и ревизией снимка; ответ относится только к этому снимку. Повторные одновременные запросы одного документа объединяются, чтобы не читать его дважды.

`ready` содержит технологический каталог, сведения обо всех видах из манифеста, состояния загрузки, локализацию загруженных объектов и диагностику. Полный AST и содержимое незагруженных видов в сообщение не включаются. Наличие метаданных в `ready` не выдаётся за полную проверку БД.

Сохранить текущие состояния интерфейса и их действия. Начальная загрузка публикует поле только после готовности всех её входов. Отмена завершает Worker и чтение, устаревшие ответы игнорируются. Повтор использует выбранные файлы текущего сеанса; закрытие/выбор нового каталога освобождает прошлый снимок. Ошибка последующей загрузки не подменяется успешным пустым результатом; она не уничтожает ранее проверенные технологические данные.

Подписи, подсказки и сообщения RU/EN добавляются в существующие словари; UI-компоненты и словарь оформления повторно используются. Панель состояния сообщает этапы выбора/чтения манифеста и подготовки нужных документов, без новой панели или требований к дизайну.

## 7. Диагностика и отчёт

Обновить отчёт: имя выбранного корня, ревизии, объявленные виды/документы/объекты, реально загруженные и проверенные документы, незагруженные виды, прочитанные байты, время и ошибки. Количество объектов в индексе и количество загруженных объектов показываются как разные показатели.

Использовать `NodeRef` и относительные пути. При расхождении хеша фиксировать ожидаемое/фактическое значение. Ошибки отсутствия файла, неверного формата, неоднозначного ID, неверной ссылки и повреждения различимы. Существующие диагностические случаи технологических требований, включая неподдержанные отрицательные требования, сохраняются.

## 8. Проверки и приёмка

Проверить выбор корня, отмену диалога, отсутствие манифеста, неполный набор, лишние файлы, одинаковые имена в разных папках, конфликт путей и несовместимую версию. Добавить синтетические наборы нового формата и проверки адаптеров/протокола/локализации.

Инструментировать чтение: начальное открытие не читает байты остальных 14 видов; запрос события открывает только содержащие его документы; повторный запрос не читает их снова. Повреждение загружаемого файла вызывает ошибку; повреждение неиспользуемого файла не объявляется проверенным. Проверить SHA-256 по эталонным байтам Python, в том числе UTF-8 и границы блоков.

Проверить большой документ без загрузки полной строки, прерванный поток, отзывчивость, отмену и игнорирование устаревшего ответа. Проверить изменения снимка между открытиями, вложенные варианты, наследование описаний, анонимные объекты и все фрагменты `on_actions`.

На реальном наборе этапа 17 сопоставить технологический каталог и тексты с предыдущим фронтендом, проверить язык, тему, меню, тултипы, варианты и сохранение отчёта. Отдельно запросить остальные виды и сравнить их компактные данные с прежними результатами, нормализовав только ссылки. Выполнить typecheck, сборку, относящиеся тесты TypeScript и браузерные сценарии.

Замерить время открытия, реально прочитанные байты и память. Счётчики из манифеста не заменяют эти измерения. Фактические проверки и замеры приведены в руководстве этапа. Обновить двуязычные инструкции запуска и changelog, увеличить патч-версию фронтенда при реализации.
