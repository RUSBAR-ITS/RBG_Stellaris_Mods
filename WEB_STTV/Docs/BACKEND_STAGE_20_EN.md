## Startup

From the repository root in a separate PowerShell terminal:

```powershell
$env:PYTHONPATH = (Resolve-Path WEB_STTV/src/backend).Path
WEB_STTV/data/.venv/Scripts/python.exe -X utf8 -B -m sttv.service
```

The service listens on `127.0.0.1:8765`; Vite proxies `/api/sttv` from the interface origin. Starting it neither builds nor enriches data. Stop with Ctrl+C.

Configuration: `config/service.json`; select another file using `--config <path>`. Its `variables` points to `data/stage20/variables.json`, whose `WORK_DIR` is `data/stage20`. `config/storage.json` defines the relative set location. To register another set, change configuration and restart. Configuration paths stay within the repository; the browser never sends absolute paths.

The public Python function `sttv.enrichment.technology_tree.enrich_technology_tree` accepts `dlc_enabled=None` for all DLC or a list of IDs. Omitting the argument performs regular prepared-combination enrichment without DLC filtering. `variants` preserves explicitly selected representations. This does not invoke the game parser.

## Rules and storage

`config/enrichment/dlc.json` declares predicates, constants, transparent wrappers and weight fields. `config/enrichment/technology_tree.json` references it. DLC ID/technical-name matching comes from the `dlcs` database.

Evaluation distinguishes `true`, `false`, `unknown`. To prove a DLC cause, it compares results against the same condition with unknown DLC states. Base `weight = 0` and independent `always = no` do not cause exclusion by this filter. Unsupported weight actions retain uncertainty; probability is not calculated.

The `dlc_<hash>` combination depends on DLC selection, reference profile and variants. Metadata records source, rule, implementation and result revisions. Each technology result includes `visibility`, reasons/evidence, `parent_tech`, `children`, `status`. Hidden technologies remain in the database without links in this combination. A visible technology losing every candidate becomes a root with `no_visible_parent`; original prerequisites survive.

Only technology documents change. New file versions are immutable; the manifest switches atomically. Unchanged files are reused. Cancellation is checked before publication; publication and cancellation acceptance share a lock. A published result counts as completed.

## Service and snapshots

Modules: `sttv/enrichment/dlc`, `sttv/service`, integration in `sttv/enrichment/technology_tree`. New `dlc.schema.json` and `service.schema.json` are generated by the shared generator. Combination, asset and asset-configuration schemas were extended.

Main routes relative to `/api/sttv`:

| Method and path | Purpose |
| --- | --- |
| `POST /connect` | Match `setId`/`snapshotRevision`, create a session |
| `POST /operations` | Apply `enabled` and `baseCombinationId` to the requested revision |
| `GET /operations/{id}` | Retrieve status/result |
| `POST /operations/{id}/cancel` | Request cancellation |
| `GET /snapshots/{revision}/manifest` | Retrieve the consistent manifest |
| `GET /snapshots/{revision}/documents/{kind}/{document_id}` | Read a declared document |
| `GET /snapshots/{revision}/images/{hash}` | Read a declared image |

The session token uses `X-Sttv-Session`. One calculation runs at a time. Undeclared resources, foreign Origins, set mismatches and stale revisions produce diagnostics. Requests cannot run commands or select arbitrary files. Full operation reports are stored under `WORK_DIR/reports/dlc/`; the main enrichment report retains its configured location.

The frontend receives a new manifest and streams changed documents through the API, checking hashes. Existing `File` objects are not treated as updated bytes. Unchanged catalogs and verified images remain cached.

## Images

`config/enrichment/assets.json` defines `dlc_thumbnails`: the `thumbnail` field and `DLC_DIR` variable. Paths are relative to their DLC descriptor and confined to the DLC directory. Existing PNG conversion and the asset registry are reused; `presentation.dlc_icons` maps DLC IDs to resources.

The 36 catalog rows have 32 prepared thumbnails. `dlc001`, `dlc003`, `dlc010`, `dlc011` have no suitable thumbnail and retain placeholders. The set contains 822 unique images; 805 previous image requests reused cache, and 32 sources were converted. Asset preparation did not rewrite database documents.

## Validation

Passed 94 enrichment/storage module tests and 3 schema-generation tests. Full audit verified 543 documents and 822 images. Following final recalculation, all 35 technology documents and all images were reverified; the other 508 descriptors were confirmed unchanged by comparison. Results: `full_audit.json`, `post_recalculation_audit.json`.

Synthetic checks cover three-valued logic, negation/wrappers, independent prohibitions, zero modifiers, unknown DLC, parent exclusion, unchanged sources, reuse, cancellation, atomic publication and API boundaries. Browser results are described in the [interface guide](frontend/FRONTEND_STAGE_10_EN.md#validation).

Acceptance reports/logs reside under `data/stage20/`. Checks do not simulate Stellaris condition execution or determine Steam DLC ownership. Game files were not changed.

A coverage gap was confirmed after acceptance: DLC dependency through `uses_ship_category` and ship-set definitions remains unknown, leaving weaver weapons visible without BioGenesis. The checks above do not establish completeness of indirect restrictions. Recursive analysis of these relations is proposed in the [stage 21 draft](TZ_BACKEND_STAGE_21_EN.md).
