## Запуск

Утверждённый [этап 14](TZ_BACKEND_STAGE_14_RU.md) реализован. Оба режима проверены полной сборкой набора из 15 БД.

Из каталога `WEB_STTV` сначала выбрать **один** режим:

```powershell
$env:PYTHONPATH = 'src/backend'
# Prepare libraries from source and build all fifteen databases.
& ./data/.venv/Scripts/python.exe -B -m sttv.database_sets --rebuild-libraries
# Verify and load saved libraries, then build the databases again.
& ./data/.venv/Scripts/python.exe -B -m sttv.database_sets --reuse-libraries
```

Для отдельной подготовки или проверки библиотек без сборки БД:

```powershell
& ./data/.venv/Scripts/python.exe -B -m sttv.libraries --rebuild-libraries
& ./data/.venv/Scripts/python.exe -B -m sttv.libraries --reuse-libraries
```

Оба CLI поддерживают `--variables` и `--config`. Одиночная сборка: `python -B src/backend/main.py --config <single_build_config> --reuse-libraries`; одиночный конфиг содержит `sources`, `outputs`, `parser` и `libraries`. Python API: `build_database_set(..., library_mode='rebuild' | 'reuse')`, `build(..., library_mode=...)`.

`rebuild` всегда готовит библиотеку заново. `reuse` проверяет существующий снимок и не пересоздаёт его автоматически при ошибке. БД в обоих режимах собираются заново. Отсутствие режима и одновременная передача двух ключей являются ошибкой.

## Конфигурация и файлы

`config/backend.json` выбирает `config/libraries.json` ссылкой `base`/`path`. Для каждой библиотеки задаются `id`, `kind`, имя переменной каталога, `pattern`, `recursive`, `encoding` и `output`. `manifest` и `report` также настраиваются. Пути выходов отсчитываются от `WORK_DIR`; источники разрешены внутри `STELLARIS_ROOT`. Настройки чтения удалены из дублирующих конфигов парсера.

| Вид | Переменная | JSON по умолчанию |
| --- | --- | --- |
| Inline-шаблоны | `INLINE_SCRIPTS_DIR` | `libraries/inline_scripts.json` |
| Эффекты | `SCRIPTED_EFFECTS_DIR` | `libraries/scripted_effects.json` |
| Триггеры | `SCRIPTED_TRIGGERS_DIR` | `libraries/scripted_triggers.json` |
| Вычисления | `SCRIPT_VALUES_DIR` | `libraries/script_values.json` |
| Общие статические переменные | `SCRIPTED_VARIABLES_DIR` | `libraries/scripted_variables.json` |

Описание снимка — `libraries/manifest.json`, отчёт операции — `reports/libraries.json`. Библиотека имеет собственные версии формата и подготовки. В интерфейсе по-прежнему открываются только 15 файлов из `data/databases/`; библиотечные JSON в этот набор не входят.

Генератор схем создаёт четыре новых контракта: `libraries.schema.json`, `library.schema.json`, `library_manifest.schema.json`, `library_report.schema.json`. Всего активны 22 схемы. JSON записывается с переносами LF, отступом в два пробела и читаемым Unicode.

## Подготовленное представление

Снимок содержит таблицы исходников, определений, окружений и планов. Ссылки `$ref` внутри служебного JSON — индексы объектов этой таблицы. Они сохраняют совместное использование фрагментов и связи окружений; это не адреса Python и не ссылки на игровые команды.

План хранит диапазоны и виды токенов, параметры с исходными координатами, признак условных фрагментов и подготовленные узлы для постоянного тела. При загрузке JSON исходный игровой текст заново не парсится.

Постоянное тело инстанцируется в отдельное дерево. В параметризованном теле переиспользуются целые неизменённые токены; подставленные фрагменты и границы соединения разбираются заново, чтобы сохранить текстовую семантику. Условия, значения по умолчанию и вложенные вызовы продолжают использовать общие правила парсера. Неиспользованная ветвь не раскрывается.

Подготовка выполняется один раз на операцию. Каждый участник набора получает собственные счётчики, историю вызовов и локальные окружения. Общие определения и планы не содержат состояния вызовов основных документов. Координаты, оригинальный текст, история, логические оболочки и границы `script_value` сохраняются.

## Актуальность и ошибки

Проверяются состав источников, SHA-256 исходных байтов, разрешённые корни, параметры чтения, синтаксис, подстановки, правила вызовов, переменных и исключений, версия подготовки. Добавление, удаление, переименование и изменение файла требуют `rebuild`; совпадения размера и времени изменения недостаточно. Разрешённые исключениями файлы без расширения также учитываются.

Изменение обычных объектов, переводов или путей выходных БД само по себе библиотеку не инвалидирует. Перед публикацией проверяется, что входы текущей операции не изменились. `reuse` читает исходники для сверки хешей; это не автономный режим без игры.

Повреждённый JSON, неверный хеш, неизвестная версия, неполный набор, неверные ссылки и диапазоны плана отклоняются с диагностикой. Для восстановления пользователь явно выбирает `--rebuild-libraries`. Проверка структуры библиотечного JSON выполняется один раз при загрузке, а не на каждом вызове.

Результаты подготовки сначала пишутся во временные файлы, затем заменяются артефакты и последним — manifest. Это не транзакция всех файлов. Прерванная публикация обнаруживается по составу и хешам. Файл `.sttv-libraries.lock` в каждом выходном каталоге библиотек, manifest и отчёта запрещает одновременную запись, даже если процессы выбрали разные имена manifest. После аварийного завершения процесса оставшийся lock удаляется вручную только после проверки, что владеющий процесс остановлен; автоматического удаления чужого lock нет.

## Применение и аналитика

Сервис `libraries.operation.library_operation(settings, mode)` управляет сроком жизни снимка. Внутри него `sources.expansion.expansion_context()` создаёт независимый контекст. Аналитические входы `script.audit_corpus`, `database.audit_values` и `database.audit_build` принимают те же ключи. Чистый синтаксический разбор без раскрытий библиотеку не требует.

| Модули | Назначение |
| --- | --- |
| `libraries/configuration.py`, `inventory.py` | Пути, состав, хеши и актуальность |
| `libraries/snapshot.py` | Подготовка и контексты потребителей |
| `libraries/codec.py`, `references.py`, `payloads.py` | Служебный граф и проверка ссылок |
| `libraries/storage.py`, `validation.py` | Сохранение и проверенная загрузка |
| `libraries/operation.py`, `ownership.py` | Режим, владение каталогами, общий снимок и отчёт |
| `script/prepared.py`, `metrics.py` | Планы, повторное использование и измерения |

## Измерения

`reports/libraries.json` содержит режим, статус, `library_set_id`, объём JSON, определения и файлы по видам, подготовки планов, загрузки, контексты и применения. `source_reads` относится к первоначальному чтению источников библиотечным сервисом; `verification_reads` отдельно считает его повторные чтения для проверки. Существующие отчёты БД сохраняют логические счётчики источников и раскрытий.

Префиксы `prepare_` и `apply_` разделяют токены, реально разобранные лексером, переиспользованные токены, синтаксические разборы, постоянные инстанцирования и применения планов. Время `dynamic_parsing` включено в `application`, а проверки перед публикацией входят также во время соответствующей операции: вложенные интервалы нельзя суммировать как независимые.

Артефакты приёмки сохраняются в `data/stage14/`: `acceptance_summary.json`, `rebuild_acceptance.json`, `reuse_acceptance.json`, контрольные хеши этапа 13 и изолированная контрольная реализация.

Полные последовательные сборки на этой машине:

| Режим | Полное время, с | Минуты | Пик рабочего набора процесса, ГиБ |
| --- | ---: | ---: | ---: |
| Контроль этапа 13 | 2 065,194 | 34,4 | 1,65 |
| Этап 14, `rebuild` | 1 763,117 | 29,4 | 2,04 |
| Этап 14, `reuse` | 2 035,117 | 33,9 | 2,50 |

В `rebuild` подготовка заняла 22,326 с, сохранение — 112,336 с. В `reuse` загрузка и проверка библиотечных JSON заняли 56,375 с. Проверки входов библиотечным сервисом: соответственно 0,872 и 0,943 с, включая начальное чтение и последующие сверки. Это отдельные реальные прогоны, не гарантия времени на другом запуске.

В этом замере `reuse` медленнее `rebuild`, хотя загрузка дешевле подготовки с сохранением. Применение вставок заняло 371,269 с против 277,565 с; выросло также время неизменных хеширования, проверки и записи основных БД. Приёмка `reuse` частично пересекалась с тестами и потоковым чтением набора фронтендом. Эти замеры не изолируют влияние режима, нагрузки и памяти; считать загрузку готового JSON безусловно самым быстрым режимом нельзя.

Пять JSON библиотек занимают 535 747 873 байта (около 511 МиБ). Подготовлено 4 689 планов: 632 inline-файла, 1 691 эффект, 1 692 триггера, 674 script values; отдельно сохранено 2 917 общих статических определений. В `reuse` подготовлено ноль планов, загружено пять артефактов. В обоих режимах один снимок обслужил 15 контекстов.

При применении выполнены 103 071 обращение к планам и 79 185 инстанцирований постоянных деревьев. Переиспользовано 8 078 298 токенов; заново лексически разобрано 4 777 195. Числа в обоих режимах совпали. Первичное чтение библиотечных источников — 750 файлов, последующие проверки — ещё 1 500 чтений; эти показатели не означают полностью автономную работу без чтения игры.

Контрольные микропроверки выполнены после завершения полных сборок: медианы трёх серий по 120 верхнеуровневых вызовов. Деревья и история каждого примера совпали по SHA-256 со старым механизмом. Счётчики работы и `tracemalloc` получены отдельным проходом, чтобы измерение памяти не искажало время.

| --- | ---: | ---: | ---: | ---: |

| Параметры | 1 | 0,611 | 0,326 | 60 000 → 24 120 |

В смешанном примере число экземпляров синтаксического анализатора сократилось с 10 923 до 8 045, пик отслеживаемых Python-выделений вырос с 1 035 978 до 1 080 085 байт. Все шесть замеров памяти, лексических/синтаксических проходов и времени сохранены в `*_benchmark_work.json`, `*_benchmark_final.json` и сводном отчёте. Сокращение повторной работы подтверждено счётчиками и не объясняется только прогревом дискового кэша.

## Проверки

Полный прогон бэкэнда: 230 тестов. После завершающей доработки владения каталогами пройдены 18 библиотечных тестов, включая один новый, и 21 интеграционный тест сборщика, настроек и переменных. Итого проверен 231 уникальный backend-тест.

Фронтенд: 33 проверки пройдены без пропусков, включая потоковое открытие всех 15 реальных БД с `STTV_DATABASE_DIR=data/databases`. Получены 679 технологий, 1 506 компонентов, 498 зданий и каталоги остальных 12 видов; подтверждены 16 ранее исследованных примеров связей. Сохранены 214 предупреждений об отсутствующей локализации. Браузерный прогон и запуск игры не требовались.

Обе полные сборки побайтно совпали между собой и с контролем этапа 13: 15 файлов, 11 762 739 507 байт, 450 документов. Совпали `set_id`, хеши 1 612 игровых/локализационных входов, логические счётчики и статусы всех участников. Сборка не добавляет повторного полного аудита уже записанных БД; сравнение хешей выполнено отдельно для приёмки.

`database.audit_values --reuse-libraries` проверил три реальных фрагмента и четыре вызова ванильных определений: вложенные аргументы, scope, значения по умолчанию и условные фрагменты; 300 узлов. Исходники не изменились. Отчёты сохранены в `data/stage14/analytics_acceptance.json` и `analytics_library_report.json`.

## Ограничения

Обработка остаётся последовательной. Параллелизм, инкрементальная пересборка библиотеки и кэш готовых раскрытий не добавлены. Снимок занимает дополнительную память и место; проверка его актуальности, чтение JSON и восстановление объектов имеют собственную стоимость. Сборка сохраняет все игровые деревья, локализацию и формат `sttv.parse_database` версии `6`. Запуск игры для проверки этого этапа не требуется.
