## 1. Статус и цель

ТЗ утверждено пользователем 2026-11-17. Реализация и проверки описаны в [руководстве этапа 11](BACKEND_STAGE_11_RU.md).

Бэкэнд формирует БД технологий, компонентов и зданий из одного набора игровых источников. Все три сохраняют результаты существующего универсального парсера и локализационное обогащение. Это подготовка данных для последующего определения цепочек. Новый алгоритм сортировки и выбор главного предшественника в этот этап не входят.

## 2. Источники и границы

Добавить две переменные в `global_variables.json`; пути разрешаются относительно `STELLARIS_ROOT`:

| БД / `dataset.kind` | Переменная | Значение по умолчанию |
| --- | --- | --- |
| `technologies` | существующая `TECH_PATH` | `common/technology` |
| `components` | новая `COMPONENTS_DIR` | `common/component_templates` |
| `buildings` | новая `BUILDINGS_DIR` | `common/buildings` |

Для каждой БД независимо настраиваются каталог через переменную, маска, рекурсивность и кодировка. По умолчанию — `*.txt`, рекурсивный обход, `utf-8-sig`. Общие библиотеки inline-вставок, scripted effects/triggers/values и статических переменных используются через существующие настройки и не становятся самостоятельными объектами этих БД.

Входы игры и Workshop остаются доступны только для чтения. Рабочая папка задаётся `WORK_DIR`. Никаких копий исходных каталогов и произвольного раскрытия путей вне разрешённых источников.

CSV/ODS с числовыми характеристиками оружия в `component_templates` в этот этап не входят. БД компонентов содержит определения из TXT, достаточные для ID, технологических требований и улучшений; полнота всех боевых характеристик не заявляется. Каталог `component_sets` не добавляется отдельным источником: для поиска общего описания используется явное значение поля `component_set` в компоненте.

Исследование до реализации: `data/stage11/specification_research/object_inventory.json`. В прямом разборе 83 файлов компонентов и зданий обнаружены три вида шаблонов компонентов, 498 определений зданий и 9 зданий с блоками `desc`. Часть ID компонентов появляется через inline-вставки. Эти числа не являются нормативом полного раскрытого результата и не зашиваются в код.

## 3. Конфигурация и результаты

Расширить `config/backend.json`: общие настройки парсера задаются один раз; раздел `datasets` содержит именованные наборы источников и путей результатов. Не копировать конфиги парсера для каждого вида БД. Параметры конкретного запуска передаются общему сборщику через координатор набора.

Рекомендуемые выходы относительно `WORK_DIR`, изменяемые конфигурацией:

| Вид | БД | Отчёт разбора | Отчёт локализации |
| --- | --- | --- | --- |
| `technologies` | `databases/technologies.json` | `reports/technologies_build.json` | `reports/technologies_localization.json` |
| `components` | `databases/components.json` | `reports/components_build.json` | `reports/components_localization.json` |
| `buildings` | `databases/buildings.json` | `reports/buildings_build.json` | `reports/buildings_localization.json` |

Сводный отчёт — `reports/database_set.json`, также настраиваемый. Пути должны быть различными, находиться в разрешённой рабочей папке и не пересекаться с исходниками, конфигами и кодом.

В `config/enrichment/localization.json` сохранить общие языки, приоритеты, чтение и раскрытие ссылок. Выбор целей и правила ключей разделить по видам объектов; пути БД и отчётов передаёт координатор. В конфиги выносятся виды корневых конструкций, поля ID, суффиксы описаний и разрешённое использование `component_set`.

## 4. Формат и принадлежность набору

Предлагаемый формат — `sttv.parse_database`, версия 5. Игровые узлы и порядок записей сохраняются. Добавляется корневая метка:

```json
{
  "format": "sttv.parse_database",
  "format_version": 5,
  "dataset": {
    "kind": "technologies",
    "set_id": "<sha256>"
  },
  "documents": []
}
```

Три файла набора имеют разные `kind` и одинаковый `set_id`. Имя файла не определяет его роль. `set_id` обозначает конкретное содержимое набора, а не версию Stellaris и не проверку корректности его игрового смысла.

Для детерминированности: после обогащения вычислить SHA-256 каждого документа БД без корневого `dataset`, затем SHA-256 словаря `kind -> hash`. Каноническая сериализация для обоих шагов — UTF-8 JSON с сортировкой ключей, без пробелов между элементами, без ASCII-экранирования Unicode и без NaN/Infinity. Время, абсолютные пути окружения и отчёты в этот расчёт не включаются. Одинаковые результаты дают одинаковый `set_id` и одинаковые файлы БД.

Универсальный низкоуровневый сборщик может создавать самостоятельные деревья без `dataset`; он не привязывается к трём игровым каталогам. Фронтенд нового этапа принимает только полный набор с метками. Автоматическая миграция старой одиночной БД не требуется: для нового интерфейса набор пересобирается.

## 5. Сборка и публикация

Одна явная команда Python формирует полный набор. Предлагаемая точка входа — `python -m sttv.database_sets` с путями к переменным и конфигу; конкретный запуск записать в итоговое руководство. Разбор и обогащение остаются отдельными функциями, пригодными для самостоятельных проверок.

1. Проверить конфиги, источники и выходы для всех трёх БД.
2. Для каждого набора выполнить существующий полный разбор: раскрытие вложенных inline-вставок, scripted effects/triggers, script values и подстановку статических переменных в установленном порядке. Сохранить происхождение и служебные метаданные согласно действующим этапам.
3. Обогатить все целевые объекты RU/EN. Индекс локализации и неизменяемые общие данные можно переиспользовать; локальные переменные и контекст раскрытия разных документов не должны смешиваться.
4. Проверить схемы, целостность обогащений и неизменность прочитанных источников для всего запуска, включая общие файлы, прочитанные разными сборками. При разных хешах одного источника остановить публикацию.
5. Подготовить все три результата во временных файлах рабочей папки, вычислить `set_id`, проверить финальные файлы.
6. Опубликовать подготовленные БД и записать сводный отчёт с фактически записанными файлами.

До подготовки и проверки всего набора действующие БД не заменяются. Замена отдельного файла атомарна существующим способом; замена трёх файлов не объявляется одной атомарной операцией. При сбое между заменами отчёт отражает частичную публикацию, а разные `set_id` не позволят фронтенду открыть смешанный набор. Отдельный механизм отката не вводится.

Память не должна одновременно содержать три лишние копии полных деревьев: допустима последовательная подготовка через временные результаты. Пересоздание сводного отчёта не должно скрывать уже совершённые записи при ошибке.

Существующее отдельное обогащение одного файла не должно незаметно менять участника готового набора с прежним `set_id`. Для таких файлов оно выдаёт диагностику с предложением пересобрать набор. Самостоятельные БД без `dataset` остаются доступны низкоуровневым операциям; обновление только локализации готового набора без повторного разбора можно проектировать отдельно.

## 6. Выбор объектов локализации

Выбор выполняется после раскрытия вставок; исходное дерево не ограничивается перечисленными полями.

| Цель | Идентификатор / ключ названия | Основной ключ описания |
| --- | --- | --- |
| Технология | ключ корневого определения | `<id>_desc` |
| `technology_swap` | прямое поле `name` | `<name>_desc`, затем описание основной технологии по этапу 10 |
| Компонент | прямое поле `key` | `<key>_DESC`, затем `<component_set>_DESC` по разделу 7 |
| Здание | ключ корневого определения | `<id>_desc`; явные `desc` обрабатываются по разделу 7 |

Компоненты выбираются из корневых `weapon_component_template`, `utility_component_template`, `strike_craft_component_template`; список вынесен в конфиг. Сами имена этих конструкций повторяются и не являются ID компонентов. Не извлекать `name` вложенной ауры как название компонента.

Для зданий выбираются корневые определения в их настроенном каталоге. Документы комментариев, скалярные директивы и переменные не становятся объектами локализации. Выбор основных технологий сохраняет действующее исключение служебных подпапок категории/уровня из целей локализации, хотя их деревья остаются в БД.

Для первичного объекта обязательны один непустой скалярный ID и отсутствие неоднозначности полей, из которых выбираются ключи. Ошибки выбора имеют координаты. Одинаковые ID объектов внутри вида не объединяются: это ошибка для ручного разбора. ID разных видов принадлежат разным пространствам.

## 7. Описания и происхождение строк

Приоритеты остаются прежними: RU — `RU_LOC_TIER_1`, затем 2 и 3; EN — `EN_LOC_TIER_1`. Поиск каждого ключа проходит все приоритеты этого языка. Отсутствие русского текста не запускает подмену английским. Найденная пустая строка отличается от отсутствующей.

Сохраняются `requested_key`, выбранный `key`, `raw`, раскрытый `text`, `source`, `inherited_from`, `unresolved_references`. Статические `$key$` раскрываются; игровые динамические подстановки и разметка сохраняются. Правила отсутствия, конфликтов, циклов и ограничений раскрытия остаются как на этапе 10.

**Компоненты.** Если `<key>_DESC` отсутствует во всех приоритетах языка, а прямой `component_set` — один непустой скаляр, искать `<component_set>_DESC`. Это правило общего описания, а не вывод семейства технологии. Например, `SMALL_RED_LASER` ссылается на `RED_LASER`, для которого есть `RED_LASER_DESC`. Не удалять размерные префиксы и числовые суффиксы из ID. Название ищется по самому `key`.

Для этого случая добавить в запись строки необязательное поле `fallback`: `{ "kind": "component_set", "source_ref": "<JSON Pointer to component_set assignment>" }`. `requested_key` сохраняет первый запрошенный ключ, `key` — реально найденный; `inherited_from` остаётся `null`. Проверка сопоставляет ссылку с полем того же компонента и выбранным ключом. При обычном выборе или наследовании описания технологии `fallback` отсутствует. Пустое найденное описание не заменяется общим.

**Здания.** Основное описание берётся из `<id>_desc`. Если имеется единственный прямой скалярный `desc`, он явно задаёт вместо него ключ. Для повторяемых блоков `desc = { trigger = ... text = ... }` локализовать каждый прямой скалярный `text`, сохраняя порядок и условия в исходном дереве. Не вычислять `trigger` и не назначать первый условный вариант действующим.

Переводы условного описания размещать на самом присваивании `desc` в `enrichments.localization.<language>.description`. У такой цели нет поля локализованного названия. Схема допускает эти цели с одним `description`; для основных объектов и вариантов технологий по-прежнему проверяются оба поля каждого языка. Основное `<id>_desc` сохраняется независимо от условных описаний; если ключа нет, фиксируется отсутствие. Смесь несовместимых форм `desc`, неоднозначный `text` или неподдержанная конструкция выбора получают диагностику, без выдумывания описания.

## 8. Диагностика и проверки

Сводный отчёт содержит статус, `set_id` при его вычислении, входные конфиги и хеши источников, пути трёх результатов, отдельные статусы разбора/локализации/публикации, количества объектов и строк по видам/языкам, ошибки и предупреждения. Время и измерения памяти допустимы только в отчётах. Ссылки диагностики включают вид БД и путь узла.

Ошибка разбора, неоднозначный ID или ключ, конфликт выбранной локализации и изменение источника блокируют публикацию набора. Отсутствующие тексты и сохраняемые динамические ссылки остаются диагностируемыми предупреждениями по правилам этапа 10. Строки ошибок кода — английские; пользовательские сообщения фронтенда — из локализации интерфейса.

Бэкэнд проверяет сохранённые деревья и обогащение. Правила цепочек, пригодность кандидата в главные предшественники и состояние государства здесь не проверяются. Подготовка межобъектных ссылок для фронтенда определена отдельным ТЗ.

## 9. Организация кода

Добавить компактный координатор набора; переиспользовать `builder`, `database`, `sources` и `enrichment/localization`. Общую публикацию и работу с отчётами вынести в хелперы только там, где действительно повторяется логика. Не создавать по копии парсера и локализатора на вид БД.

Обновить генераторы схем БД, конфигурации сборки, локализации и соответствующих отчётов; сводному отчёту дать собственную генерируемую схему. Не редактировать сгенерированные схемы независимо от их исходного кода. Следовать установленным ограничениям размеров файлов и правилам DRY.

## 10. Критерии приёмки

1. Настраиваемая команда создаёт три валидных локализованных JSON с правильными ролями и общим детерминированным `set_id`.
2. Во всех трёх работает штатное вложенное раскрытие и статическая подстановка; поля, порядок, неизвестные игровые конструкции и происхождение сохраняются.
3. Проверены ID компонентов после вставки, повторяющиеся имена корневых шаблонов, разные пространства ID и диагностика настоящих дублей.
4. RU/EN и приоритеты проверены для каждого вида; проверены `_desc` и `_DESC`, общее описание компонента, пустые/отсутствующие строки и условные описания зданий без выбора условий.
5. Обогащение меняет только служебные поля; прежние технологические варианты и наследование описаний сохраняют поведение.
6. Повтор по неизменным входам даёт побайтно одинаковые БД. Изменение содержимого любого участника меняет общий `set_id`.
7. Проверены недоступный источник, ошибка третьей БД после успешной подготовки первых, изменение общего входа и сбой публикации между файлами. Отчёт отражает фактический результат, смешанный набор распознаётся фронтендом.
8. Реальный прогон трёх каталогов фиксирует размеры, время, количество объектов, предупреждения и хеши неизменных исходников. Исследовательские числа до раскрытия не используются как ожидаемый итог.
9. Обновлены руководство запуска, changelog RU/EN и ссылки на документы. Все проверки описывают реально выполненные действия; запуск игры для проверки формата этих БД не требуется.
