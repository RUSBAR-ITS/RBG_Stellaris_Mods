## 1. Статус и цель

**Утверждено пользователем и реализовано 2026-11-19.** Запуск и результаты — в [руководстве этапа 18](BACKEND_STAGE_18_RU.md). Связанный документ — [фронтенд, этап 8](frontend/TZ_FRONTEND_STAGE_8_RU.md).

Подготовить используемые карточками игровые изображения внутри набора БД и RU/EN-названия научных категорий. Открытие готового набора должно обходиться без доступа браузера к установленной игре. Основа — [раздельное хранение этапа 17](TZ_BACKEND_STAGE_17_RU.md).

Этап охватывает основные технологии, их `technology_swap` и три значка исследовательских ресурсов. Изображения остальных видов объектов, расчёт состояния империи, интерактивная смена вариантов и генерация данных из браузера не входят в задачу.

## 2. Операция подготовки

1. Добавить самостоятельную Python-операцию по существующему набору с манифестом. Технологии читать через действующий читатель набора, без повторного парсинга игры и без загрузки остальных 14 видов БД.
2. Подготовить изображения всех представлений технологий, включая варианты вне текущей комбинации дерева; это не вычисление условий выбора варианта.
3. Подготовить названия используемых категорий существующим механизмом локализации.
4. Проверить результат и опубликовать его средствами хранения набора.
5. Предусмотреть вызов этой же операции в явно запущенной подготовке нового набора. Порядок: исходные документы и локализация → подготовка ресурсов; обогащение дерева может уже существовать или выполняться после неё.

Повторный запуск переиспользует неизменившиеся подготовленные изображения после сверки исходного содержимого и настроек преобразования. Изменение изображения не требует повторного разбора технологических файлов. Запуск интерфейса, открытие каталога и обновление страницы не запускают эту операцию.

## 3. Конфигурация

Добавить `config/enrichment/assets.json` с версией формата и ссылками на действующие конфиги хранения и локализации. Вынести в него:

- корень источника `STELLARIS_ROOT`, каталог `gfx/interface/icons/technologies`, исходное расширение `.dds`;
- соответствие областей файлам `gfx/interface/icons/resources/physics_research.dds`, `society_research.dds`, `engineering_research.dds`;
- имена полей `icon`, `technology_swap`, `name`, `inherit_icon`, `category` и правила наследования;
- каталог подготовленных ресурсов относительно набора, формат PNG, параметры преобразования и переиспользования;
- адрес отчёта и правила извлечения ключей локализации категорий.

Это конфигурация правил и адресов, а не ручной список всех технологий или изображений. Фактический реестр формируется автоматически. Рабочие адреса следуют `WORK_DIR` и конфигу хранения; абсолютные адреса текущего компьютера в код не вносить.

Игровые источники доступны только для чтения. Подготовленные файлы и отчёты записываются в рабочий каталог проекта. Пути внутри набора остаются относительными; применять существующие ограничения путей этапа 17.

## 4. Выбор и преобразование изображений

| Представление | Правило выбора |
| --- | --- |
| Основная технология | Непустое `icon`, если задано; иначе ID технологии. Значение разрешается в настроенном каталоге технологий с исходным расширением |
| Вариант с `inherit_icon = yes` | То же изображение, что у основной технологии |
| Вариант с `inherit_icon = no` | Собственное изображение по имени варианта `name`; явно заданное собственное `icon`, если встретится, учитывать по конфигу |
| Вариант без `inherit_icon` | Для текущего корпуса применять настроенное правило собственного изображения по `name`; не выдавать это предположение за доказанное поведение движка во всех версиях |
| Значок стоимости | Ресурс эффективной области представления: физика, социология или инженерия |

В текущем наборе 679 технологий: 12 имеют явное `icon`. У шести вариантов без `inherit_icon` имеются файлы изображений по их `name`. Проверить разрешение всех фактических ссылок при реализации, включая явные переопределения.

Подготавливать PNG-копии с сохранением пропорций, исходного разрешения и прозрачности. Размер показа задаёт фронтенд; не увеличивать исходные пиксели на стадии подготовки. Хранение второй копии оригинального DDS не требуется. Файлы с одинаковым подготовленным содержимым используют один ресурс; происхождение каждого обращения сохраняется в данных/отчёте.

Отсутствие источника или ошибка декодирования конкретной иконки фиксируется диагностикой с технологией, вариантом и проверенным адресом. Запись получает явное отсутствие изображения; не подменять её произвольной чужой иконкой. Фронтенд использует нейтральную заглушку. Ошибка публикации набора не должна оставлять частичный результат.

## 5. Хранение и публикация

Рекомендуемое размещение — `assets/<content_hash>.png` внутри каталога набора. Реестр в манифесте содержит для каждого ресурса ID, относительный путь, MIME-тип, байтовый размер, SHA-256 и размеры изображения. Отдельно хранится соответствие трёх областей значкам исследовательских ресурсов.

При основной технологии и варианте добавить служебную ссылку на ресурс в `enrichments.presentation`; исходные поля AST не переписывать. Ссылка содержит ID ресурса либо явное отсутствие; одинаковые изображения не встраиваются в каждый JSON и не кодируются в Base64.

Новые сведения о представлении и изображения имеют собственную версию контракта и ревизию. Они участвуют в ревизии снимка набора и проверке прочитанных файлов, но не меняют смысловые входы выбора `parent_tech`. Точечно отделить новое обогащение от хеша входов дерева, чтобы добавление картинок не делало готовые комбинации устаревшими. Существующие правила учёта прежних обогащений не пересматривать в этом этапе.

Сохранить все комбинации, `parent_tech`, `children`, локализацию технологий, идентификаторы документов и адреса узлов. Перезаписывать только фактически изменённые документы, обновляя их байтовые хеши. Использовать действующую публикацию: сначала подготовленные файлы, затем целостный манифест. При прерывании прежний опубликованный набор остаётся доступен.

Расширить генерируемые схемы и аудит новым контрактом. Проверка изображений при обычном открытии выполняется при чтении; отдельный полный аудит охватывает все объявленные ресурсы. Не вводить повторную проверку полного AST ради добавления изображений.

## 6. Названия научных категорий

Собрать уникальные ID из `category` основных технологий и вариантов. Категории варианта при наличии заменяют список основной технологии; иначе используется основной список. Несколько категорий сохраняются без произвольного выбора одной.

Добавить в служебные данные представления набора общий словарь названий категорий RU/EN, доступный через манифест. Он является частью набора БД; фронтенд не читает игровые файлы локализации. Ключи строятся по конфигу из ID категории, а существующий механизм локализации сохраняет исходную строку, результат раскрытия статических ссылок и происхождение.

Приоритеты прежние: RU — `RU_LOC_TIER_1`, затем `RU_LOC_TIER_2`, затем `RU_LOC_TIER_3`; EN — `EN_LOC_TIER_1`. Использовать существующий конфиг, не создавать независимую копию правил приоритетов. Названия и описания самих технологий не переводятся заново.

Отсутствующее название категории обрабатывается действующей диагностикой локализации с показом её ID. Добавление словаря категорий само по себе не меняет выбор родителей.

## 7. Модули и диагностика

Отделить выбор ресурсов, чтение/декодирование, запись/переиспользование и публикацию. Использовать общие хелперы конфигурации, хеширования, локализации и отчётов. Соблюдать правила компактных модулей проекта; не дублировать сборщик БД.

Отчёт содержит число технологий и вариантов, обращений к изображениям, уникальных ресурсов, преобразованных и переиспользованных файлов, отсутствующих/повреждённых источников, категорий по языкам, записанных байтов и время этапов. Диагностика связывает проблему с ID технологии, представлением и исходным узлом. Чувствительные абсолютные пользовательские адреса не нужны готовому браузерному набору.

Конкретные параметры командной строки и модуль запуска описать в руководстве реализации. Операция должна также вызываться из Python без пользовательского консольного диалога.

## 8. Проверки и результаты

- Проверить основное имя, `icon`, наследование, собственное изображение варианта, повторное использование и отсутствие источника.
- Проверить PNG-размеры и прозрачность, уникальность ресурсов и ссылки из всех подготовленных представлений.
- Проверить названия категорий RU/EN, приоритеты и замену/наследование списка у вариантов.
- Повторить подготовку: неизменившиеся файлы не преобразуются и не переписываются. Изменение входной иконки или настроек обновляет соответствующий результат.
- Проверить прерывание публикации и обнаружение повреждённого изображения при чтении/аудите.
- На текущем реальном наборе подтвердить сохранность всех 679 технологий и готовых комбинаций дерева; остальные 14 видов БД не перечитывать для подготовки картинок.
- Зафиксировать время, размер ресурсов и проблемы источников. Отдельно проверить открытие подготовленного набора без доступа к игре.

Результаты этапа: код операции, конфиг, расширенные схемы, подготовленный рабочий набор, отчёт и двуязычное руководство. Изменения записать в оба changelog. Проверка в Stellaris не требуется; визуальная приёмка выполняется совместно с фронтендом этапа 8.
