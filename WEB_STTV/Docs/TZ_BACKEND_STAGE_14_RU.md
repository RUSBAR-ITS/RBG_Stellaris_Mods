## 1. Статус и цель

**ТЗ утверждено пользователем 2026-11-18. Реализация и приёмка завершены; команды, измерения и ограничения — [BACKEND_STAGE_14_RU.md](BACKEND_STAGE_14_RU.md).**

Подготовить сохраняемую в JSON библиотеку повторяемых элементов Stellaris. При раскрытии основных документов использовать её в памяти, сокращая повторное чтение, поиск параметров и разбор неизменных частей вставок. Один снимок библиотеки используется всеми участниками одной сборки с одинаковыми входами и настройками.

Пользователем согласованы сохранение JSON между запусками, отдельные ключи подготовки с нуля и переиспользования, вынесение состава библиотек, адресов и настраиваемых параметров в конфиги. Контракты ниже утверждены вместе с ТЗ.

Параллельное выполнение относится к следующему этапу. Здесь создаётся пригодная для него граница между неизменяемыми определениями и состоянием обработки конкретного документа. Ускорение заранее не обещается.

## 2. Исходная реализация

- `script/inlining/loader.py` уже кеширует прочитанный текст inline-файлов в памяти. Один файл не перечитывается при каждом вызове в рамках одного контекста.
- `sources/scripted.py` читает определения эффектов, триггеров и значений и строит индекс. Тело определения остаётся доступно как исходный текст с координатами и окружением.
- `script/inlining/expansion.py`, `script/scripted/expansion.py` и `script/values/expansion.py` после подстановки снова вызывают `parse_source()` для тела каждого вызова. Подстановка также повторяет лексические обходы.
- `database/collection.py` создаёт новый контекст раскрытия для каждого участника набора; библиотеки и общие переменные подготавливаются повторно при переходе к следующей БД.
- После этапа 13 итоговые документы обрабатываются, обогащаются, проверяются и записываются последовательно без накопления всей БД. Этот порядок и отсутствие повторного полного аудита сохраняются.

Простое сохранение исходного текста в JSON не считается выполнением задачи: необходимы подготовленные структуры, используемые непосредственно при раскрытии.

## 3. Состав и границы этапа

| Библиотека | Источник через `global_variables.json` | Назначение |
| --- | --- | --- |
| `inline_scripts` | `INLINE_SCRIPTS_DIR` | Шаблоны, вызываемые по относительному пути, включая вложенные вызовы |
| `scripted_effects` | `SCRIPTED_EFFECTS_DIR` | Именованные эффекты |
| `scripted_triggers` | `SCRIPTED_TRIGGERS_DIR` | Именованные триггеры с сохранением существующих границ логического результата |
| `script_values` | `SCRIPT_VALUES_DIR` | Именованные вычисления; игровые вычисления не выполняются |
| `scripted_variables` | `SCRIPTED_VARIABLES_DIR` | Общие статические определения как вспомогательная часть снимка; не новый вид вызова |

Локальные переменные основных документов не становятся общими. Локальные объявления файлов библиотек сохраняются со своим окружением. Каталоги библиотек остаются исключёнными из обхода самостоятельных объектов.

Входят подготовка, сохранение, проверяемая загрузка, применение шаблонов, использование одного снимка набором из 15 БД и одиночной сборкой, необходимые настройки, схемы и отчёты. Аналитические операции, использующие тот же раскрыватель, получают библиотеку через общий механизм. Синтаксический разбор без раскрытия остаётся независимым от библиотеки.

Не входят многопроцессность, MongoDB, новый интерфейс, изменение состава 15 пользовательских БД, кэш готовых раскрытий по комбинациям аргументов, инкрементальная пересборка части библиотеки, изменение игровых правил, новые исключения импорта и удаление истории раскрытия. `scripted_actions`, `on_actions` и `events` остаются обычными БД: сходство названий не делает их библиотеками подстановки.

## 4. Конфигурация библиотек

Предлагаемый отдельный конфиг — `config/libraries.json`. Его путь задаётся в конфигурации бэкэнда стандартной ссылкой `base`/`path`; он не зашивается в раскрыватель. Записи имеют стабильный `id` библиотеки и поддерживаемый `kind` обработчика. Настройки размещения и чтения описываются данными, алгоритмы обработчиков остаются в коде.

| Поле конфигурации | Требование |
| --- | --- |
| `format_version` | Версия контракта конфигурации |
| `libraries[].id`, `libraries[].kind` | Идентификатор библиотеки и тип подготовки; уникальные и проверяемые |
| `libraries[].source.variable` | Имя существующей переменной каталога, а не второй экземпляр самого пути |
| `libraries[].source.pattern`, `recursive`, `encoding` | Маска файлов, рекурсивность и кодировка каждой библиотеки |
| `libraries[].output` | Относительный путь JSON библиотеки от `WORK_DIR` |
| `manifest` | Относительный путь общего описания сохранённого снимка от `WORK_DIR` |
| `report` | Относительный путь отчёта подготовки или загрузки от `WORK_DIR` |

Начальные выходы: `libraries/inline_scripts.json`, `libraries/scripted_effects.json`, `libraries/scripted_triggers.json`, `libraries/script_values.json`, `libraries/scripted_variables.json`; описание снимка — `libraries/manifest.json`, отчёт — `reports/libraries.json`. Это значения поставляемого конфига, а не константы механизма. Все адреса можно изменить настройками.

Правила синтаксиса, регистра, параметров, директив, ограничений раскрытия и исключений остаются в существующих `config/parser/*.json`. Дублирующиеся настройки чтения каталогов переносятся из конфигов парсера в конфиг библиотек с обновлением схем и потребителей; два конкурирующих источника значений недопустимы. Параметр расширения inline-ссылки остаётся правилом разрешения ссылки, а маска обхода — правилом выбора исходных файлов.

Пути исходников разрешаются от `STELLARIS_ROOT` по существующим правилам. Выходы проходят действующие ограничения `WORK_DIR`, запрет пересечения с источниками и проверки совпадающих путей. Список известных исключений файлов включает явно разрешённые цели без расширения, даже если они не подходят под `*.txt`. Произвольный доступ за пределы разрешённых каталогов не вводится.

Версии формата и реализации подготовки являются техническими признаками совместимости, а не пользовательскими переключателями. Реестр игровых команд и универсальный язык описания алгоритмов в конфиге не создаются.

## 5. Режимы запуска

| Ключ CLI | Значение API `library_mode` | Поведение |
| --- | --- | --- |
| `--rebuild-libraries` | `rebuild` | Подготовить все библиотеки с нуля по текущим источникам, сохранить новый снимок и использовать его |
| `--reuse-libraries` | `reuse` | Проверить сохранённый снимок и его актуальность, загрузить его в память без повторной подготовки шаблонов |

Ключи взаимоисключающие. Операция, которой требуется раскрытие, должна получить режим явно; отсутствие обоих или указание обоих — ошибка аргументов до запуска сборки. API принимает то же обязательное решение. Скрытого режима автоматической пересборки и выбора по наличию файлов нет.

В `reuse` отсутствующий, неполный, повреждённый или устаревший снимок вызывает диагностику с причиной и указанием `--rebuild-libraries`. Этот режим не изменяет сохранённые библиотеки; запись отчёта разрешена. Недоступные игровые источники не позволяют подтвердить актуальность: автономное доверие старому снимку без исходников не входит в этап.

В `rebuild` существующий снимок не используется как вход подготовки. Полный набор подготавливается независимо от его состояния. Новый вызов сборки с этим ключом действительно заново подготавливает библиотеки, а не маскирует переиспользование под пересборку.

Предусмотреть отдельную операцию подготовки/загрузки библиотек без сборки пользовательских БД и подключение тех же ключей к CLI сборки набора. Программные одиночные сборки и аналитические операции используют тот же сервис; интерактивного консольного диалога нет. Новые команды помечаются в документации как доступные только после реализации.

## 6. Сохраняемое представление

Снимок состоит из общего описания и пяти JSON библиотек. Это внутренние рабочие файлы, не дополнительные участники набора фронтенда. JSON: UTF-8 без BOM, LF, отступ два пробела, читаемый Unicode, завершающий перевод строки.

Минимальное описание снимка:

| Поле | Содержание |
| --- | --- |
| `format`, `format_version` | Собственный контракт библиотеки, независимый от формата пользовательской БД |
| `preparation_version` | Версия алгоритма подготовки; изменение значимого алгоритма требует смены версии |
| `library_set_id` | Идентификатор конкретного полного содержимого сохранённого набора библиотек |
| `input_fingerprint` | Отпечаток источников и значимых настроек подготовки |
| `sources` | Инвентарь: корень, относительный путь, SHA-256 исходных байтов, принадлежность библиотекам |
| `configuration` | Отпечатки фактически применённых правил, исключений и настроек выбора источников |
| `artifacts` | Идентификаторы, пути, версии и SHA-256 файлов библиотек |

`library_set_id` не заменяет `dataset.set_id` пользовательских БД. Нельзя образовать циклическую зависимость хешей: хешируемое содержимое библиотек не включает итоговый идентификатор собственного набора. Показатели времени, дата запуска и абсолютные рабочие пути не определяют содержимое библиотеки.

Запись шаблона содержит его `kind`, точное имя или путь, ключ поиска по действующим правилам регистра, источник и диапазоны, исходные фрагменты для `raw` и диагностики, подготовленный `plan`, описания параметров и условных фрагментов, ссылки на вложенные вызовы и описание окружения определения. Общие исходные фрагменты могут храниться в таблице источников и использоваться по ссылкам, без копирования целого файла в каждую запись.

`plan` различает неизменные части, места подстановки и условные части. Постоянные участки представлены пригодными для повторного использования узлами или токенами. Параметризованный путь либо имя вложенного вызова хранится выражением шаблона, а не заранее выбранной целью. Динамические участки могут включать целые конструкции, а не только значения скаляров.

Точное машинное описание планов добавляется в существующий генератор схем вместе с моделью конфигурации, описанием снимка и расширениями отчётов. Имена полей, варианты служебных записей и ссылки строго определены; значения игровых команд остаются свободными. Независимый ручной реестр команд не нужен.

В JSON нет Python-объектов, `pickle`, адресов памяти, текущих аргументов, счётчиков, стеков и идентификаторов конкретных вызовов. Ссылки между определениями задаются устойчивыми идентификаторами. Загрузка восстанавливает подготовленные структуры без повторного разбора исходного текста средствами игрового парсера.

## 7. Подготовка и применение шаблонов

Подготовка последовательно формирует инвентарь, читает и хеширует исходные байты, подготавливает общие статические определения, собирает inline-шаблоны и именованные определения, включая определения из корневых inline-вставок. Затем формирует планы, проверяет служебные ссылки, сохраняет снимок и предоставляет его потребителям. Общий физический источник читается для подготовки один раз; контрольное чтение для проверки неизменности учитывается отдельно.

Порядок подготовки разрешает обращения к определениям, находящимся ниже или в другом файле. Вложенные вызовы сохраняются до применения шаблона: полного рекурсивного раскрытия всех библиотек на стадии подготовки нет. Не требовать значений ещё не переданных аргументов и не искать ещё не вычисленную динамическую цель.

При вызове берётся неизменяемый план, создаётся отдельное окружение вызова, применяются аргументы и условия, формируется экземпляр результата, раскрываются выбранные вложенные вызовы. Статические переменные, логические обёртки и границы `script_value` обрабатываются с прежней семантикой. Итоговый порядок игровых записей сохраняется.

Обязательные свойства:

- Неизменные части не перечитываются и не проходят заново полный поиск параметров и лексический разбор при каждом вызове. Однотипные обращения используют уже подготовленную структуру.
- Подстановки в именах команд, ключах, путях, строках и формулах, пустые аргументы и аргументы из нескольких конструкций сохраняют текстовую семантику. Склейка фрагментов учитывает границы токенов и экранирование; замена только `Scalar.text` недостаточна.
- Для участков, чья структура определяется аргументом, допускается необходимый разбор подставленного фрагмента или сборка из подготовленных токенов. Эти расходы измеряются. Возврат к прежнему полному текстовому циклу для всех вызовов не считается оптимизацией библиотеки.
- Значения по умолчанию, условные фрагменты и регистр следуют действующим конфигам. Отброшенная ветвь не вызывает вложенную вставку, не требует её параметров и не даёт ошибку отсутствующей цели.
- Аргументы передаются только явно; вложенный вызов не наследует все аргументы родителя. Окружение аргумента и окружение определения сохраняются раздельно, включая существующую диагностику неоднозначного статического окружения.
- Игровые условия, игровые scope и арифметика `script_values` не вычисляются по состоянию государства. Подготовка плана не меняет границы текущего парсера.
- Повторные вызовы получают независимые изменяемые деревья. Изменение результата одного вызова не меняет библиотеку и результаты остальных.

Проверки вызова, циклов, глубины, числа раскрытых узлов, недостающих и лишних аргументов продолжают работать. Ускоренный путь не обходит их. Неподдержанная конструкция плана требует явной диагностики и решения в рамках ТЗ; автоматический скрытый переход к старому движку не вводится.

## 8. Актуальность и сохранение

Для `reuse` проверить формат, версию подготовки, целостность всех артефактов, внутренние ссылки и соответствие текущим входам. Файлы JSON проверяются один раз при загрузке снимка, а не при каждом вызове и не заново для каждой БД.

`input_fingerprint` включает состав выбранных библиотечных файлов, SHA-256 их байтов, разрешённые корни и относительные имена, параметры чтения, активные правила синтаксиса, подстановки, статических переменных, разрешения вызовов и исключений. Добавление, удаление, переименование и изменение файла, в том числе по разрешённому исключению без расширения, делают снимок неактуальным. Одних времени изменения и размера недостаточно.

Изменение основных файлов объектов, переводов или пути итоговой БД само по себе не требует пересоздания библиотеки. Значимые части конфигурации выделяются явно: нельзя инвалидировать её от любого изменения большого `backend.json`, но нельзя и пропускать настройку, влияющую на подготовленный результат. Изменение контракта или алгоритма подготовки требует `rebuild`; автоматические миграции не нужны.

Подтверждение актуальности требует чтения исходных байтов для сравнения хешей. Оно не называется режимом «без чтения диска». Внутри операции общие входы и проверки дедуплицируются между 15 потребителями; перед публикацией сохраняется контроль изменения источников и состава каталогов. Обнаруженное изменение останавливает операцию, а не запускает незаметную пересборку.

Результаты `rebuild` сначала записываются во временные файлы внутри `WORK_DIR`. После успешной подготовки и проверки входов публикуются артефакты, последним — описание полного снимка. Неполный набор и несовпадающие хеши не принимаются в `reuse`. Атомарность каждой замены не объявляется транзакцией всех файлов. Если сбой прервал публикацию, отчёт фиксирует состояние и необходимость пересборки; пользовательские БД не подменяются результатом неуспешной подготовки.

Завершённый снимок остаётся пригодным, если последующая обработка основного документа завершилась ошибкой. Ошибка основного документа сама по себе не повреждает библиотеку. Параллельная запись двух процессов в один каталог библиотек не поддерживается этим этапом и должна завершаться понятным отказом при конфликте владения, а не смешиванием файлов.

## 9. Интеграция и состояние вызовов

Владелец снимка — операция сборки набора или одиночная операция. Подготовка/загрузка выполняется один раз для одинаковых входов и правил. `sources/expansion.py` получает подготовленную библиотеку, а не заново читает её каталоги для каждого участника. Смена значимых настроек не должна незаметно использовать снимок от другого контекста.

Отделить неизменяемые определения и планы от `Coordinator`, изменяемых таблиц переменных, кеша разрешений конкретного окружения, статистики, цепочки вызовов и истории. Счётчики и идентификаторы продолжают следовать принятому порядку текущей последовательной сборки. Служебные сведения подготовки не переносятся в историю вызовов основных документов.

Сохранить происхождение шаблона и аргументов, исходные и сгенерированные диапазоны, `parent_id`, адреса вставок, обёртки отрицательных/сравниваемых триггеров и отдельный scope вычислений. Корневые определения не превращаются в вызовы из-за совпадения имени. Действующие исключения источников применяются в прежнем контексте; исправление для одного места вызова не изменяет общий шаблон.

Одиночная сборка, набор и аналитика сохраняют сведения об использованных источниках и диагностике на путях `rebuild` и `reuse`. Счётчики логических операций отделяются от количества фактических чтений и подготовок: попадание в библиотеку не должно делать статистику источников или раскрытий нулевой.

Пользовательская БД сохраняет формат `sttv.parse_database` версии `6`, полный состав данных, локализацию, форматирование, последовательность документов и текущий алгоритм `dataset.set_id`. На этом этапе изменение служебных идентификаторов ради будущего параллелизма не требуется. Библиотечные JSON не добавляются в выбор 15 файлов во фронтенде.

## 10. Проверки и диагностика

Сохранить разделение проверок: конфигурация и снимок при подготовке/загрузке, конкретный вызов при применении, готовый документ один раз перед записью. Повторный полный аудит готовой пользовательской БД в обычную сборку не возвращается. Контроль хешей артефактов не выдаётся за доказательство правильности алгоритма раскрытия.

Ошибки библиотеки различают отсутствие снимка, несовместимую версию, изменение источников/правил, повреждение JSON, несовпадение хеша, неверную ссылку плана, неизвестный тип библиотеки, небезопасный путь и сбой записи. При `reuse` отчёт указывает конкретные различия и необходимость явного `rebuild`.

Ошибки раскрытия сохраняют исходный документ, файл определения, координаты, аргументы, цепочку вызовов и действующий код причины там, где причина не менялась. Ошибку нельзя маскировать пустой вставкой. Неиспользуемые параметры и применённые исключения остаются в диагностике; режим загрузки кеша не должен их скрывать.

Отчёт содержит режим, статус, `library_set_id`, причину отказа переиспользования, число файлов и определений по видам, количество физических чтений, подготовок планов, загрузок и использований, размер артефактов, времена проверки входов, подготовки, загрузки, сохранения и применения. Для раскрытия отдельно учитывать необходимый разбор динамических участков. Показатели библиотек и их версии не добавляются в игровые узлы.

## 11. Измерения и приёмка

| Область | Обязательные сценарии |
| --- | --- |
| Настройки | Перенос источников и выходов через конфиг; отсутствующие переменные; конфликт путей и ID; цель inline-исключения без расширения |
| Режимы | Ровно один ключ; `rebuild` игнорирует старый снимок; `reuse` не подготавливает планы, не перезаписывает библиотеки и не исправляет их автоматически |
| Актуальность | Изменение байтов при прежнем размере/времени; добавление/удаление/переименование; изменение правил, исключений или версии подготовки; перевод и посторонний основной файл не инвалидируют снимок |
| Формат | Загрузка в новом процессе; испорченный JSON/хеш/ссылка/версия; смешанный или неполный набор артефактов |
| Параметры | Значения по умолчанию, пустые значения, регистр, склеенные ключи, строки и экранирование, формулы, блоки и целые конструкции из аргумента |
| Вложенность | Все четыре вида вызовов в смешанной цепочке, динамические пути/имена, явная передача, отброшенная ветвь, циклы и границы лимитов |
| Окружение | Глобальные/локальные статические переменные, одинаковые аргументы в разных окружениях, исходное происхождение и отдельные деревья повторных вызовов |
| Интеграция | Один снимок для 15 БД, одиночная сборка, аналитика, независимый синтаксический парсер, дубль определения и корневые определения |
| Отказы | Ошибка подготовки и записи, изменение входа во время операции, отсутствие доступа, прерванная публикация, конфликт владельцев каталога |

До замены механизма сохранить контрольные результаты текущего раскрытия на фиксированных исходниках. Сравнивать игровые деревья, последовательность записей, метаданные происхождения/истории, локализацию и диагностику. Одинаковые количества узлов не заменяют сравнение содержания. Набор из 15 опубликованных файлов этапа 13 можно использовать как контроль только при совпадении входов.

На повторяющихся вставках выполнить минимум три сопоставимых измерения текущего и нового пути и сравнить медианы: без параметров, с параметрами, с условными фрагментами, со смешанными вложенными вызовами и динамическим фрагментом. Зафиксировать число вызовов, уникальных планов, лексических/синтаксических разборов и расход памяти. Контрольный старый путь нужен для приёмки, а не как запасной рабочий движок.

Выполнить одну полную сборку с `rebuild`, затем одну с `reuse` в новом процессе на неизменных источниках. Раздельно измерить подготовку/проверку/загрузку библиотеки, раскрытие, остальную сборку, пиковую память и размеры JSON. На обоих путях результаты пользовательских БД должны совпасть между собой и с контролем этапа 13 побайтно при одинаковых входах; это приёмочная проверка оптимизации, не сравнение со старой БД в каждом запуске продукта.

Подтвердить сокращение повторной подготовки между участниками и повторного разбора постоянных частей. Показать отдельно стоимость проверки SHA-256 источников. Улучшение только за счёт прогретого дискового кеша не выдавать за эффект нового алгоритма. Если крупные случаи раскрытия не ускорились либо полный прогон регрессировал, исследовать и отразить причину до объявления оптимизации успешной.

Выполнить действующие проверки бэкэнда и фронтенд-адаптера; при неизменном контракте интерфейса повторный большой браузерный прогон не требуется без новой причины. Материалы — `WORK_DIR/stage14/`. Обновить двуязычные руководство, README и changelog, указать реальные результаты. Запуск игры не нужен; игровые исходники доступны только для чтения.

## 12. Структура реализации

Предлагаемая группа модулей — `src/backend/sttv/libraries/`: настройки, инвентарь/отпечаток, модель планов, подготовка, хранение/загрузка и сервис операции. Разбор динамических участков и применение плана остаются рядом с `script/`; координатор вызовов не превращается в хранилище файлов.

Общие правила параметров, условий, областей статических переменных и происхождения используются совместно. Нельзя поддерживать две расходящиеся реализации семантики для подготовки и обычного раскрытия. Генератор схем, точки запуска, сборщики, отчёты и тесты обновляются вместе с контрактом; модули соблюдают ограничения размера и DRY из общего ТЗ.

Порядок реализации после утверждения: контрольные примеры и замеры → конфигурация и модель снимка → подготовка и применение планов → сохранение и явные режимы → общий жизненный цикл в сборщиках → проверки эквивалентности и производительности → документация. Никакая часть этого ТЗ не разрешает начинать многопроцессное выполнение или менять игровые правила без отдельного этапа.
