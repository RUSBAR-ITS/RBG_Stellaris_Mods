## Статус и состав

По запросу пользователя выделены семейства `is_…`, `has_…`, `set_…`, `add_…` и `remove_…`. Названия отобраны из `data/text_frequency/scalar_analysis/scalar_assignments.txt`; структурные сведения и примеры взяты из соседнего JSON. Это начальные списки для ручного разбора, статус — `pending_semantic_review`. Принадлежность к семейству определяется написанием, а назначение каждого имени ещё предстоит согласовать.

| Семейство | Имен | Всех текстовых вхождений | Употреблений слева |
| --- | ---: | ---: | ---: |
| [is_…](keywords/is/inventory.json) | 235 | 50 814 | 50 731 |
| [has_…](keywords/has/inventory.json) | 184 | 62 120 | 61 590 |
| [set_…](keywords/set/inventory.json) | 132 | 15 700 | 15 700 |
| [add_…](keywords/add/inventory.json) | 40 | 4 127 | 4 127 |
| [remove_…](keywords/remove/inventory.json) | 44 | 6 146 | 6 146 |

Включены только имена из выбранного скалярного списка. Это не полный перечень конструкций этих семейств в языке: другие формы, глобальные одиночные вхождения и содержимое пропущенных inline-вызовов в исходную выборку не входят. Частоты объединяют регистр, но это само по себе не доказывает регистронезависимость каждого игрового идентификатора.

## Структура и дальнейшее деление

```text
language/
  README_RU.md
  README_EN.md
  keywords/
    is/
      inventory.json
    has/
      inventory.json
    set/
      inventory.json
    add/
      inventory.json
    remove/
      inventory.json
```

У каждого семейства сразу есть собственная подпапка. Пока в ней один начальный список; после проверки назначений можно выделять тематические файлы. Возможные направления — условия, параметры определений, пользовательские скриптовые проверки. Это предложения для дальнейшего разбора, а не уже присвоенные категории.

При таком делении полная запись имени должна находиться в одном месте внутри семейства. Если поведение зависит от контекста, варианты описываются в этой записи. При переносе проверенной записи в тематический файл она удаляется из начального списка, чтобы не поддерживать две копии. Глубокую вложенность добавляем только при появлении конкретной крупной группы.

## Содержание начальных списков

Файлы — обычный JSON. Одна запись `keywords` занимает одну строку; новые данные можно оформлять многострочно по мере проверки. В заголовке хранятся семейство, статус, число имён и ссылки на исходные списки с SHA-256. Пути заголовка отсчитываются от `WEB_STTV`.

| Поле записи | Содержание |
| --- | --- |
| Имя свойства в `keywords` | Нормализованное имя конструкции |
| `count` | Общая частота текста в исходном списке, включая употребления справа |
| `key_count` | Число употреблений слева от оператора |
| `operators` | Наблюдавшиеся операторы связи; это не ограничение языка |
| `example` | Один точный пример присваивания или сравнения из исходника |
| `source`, `line` | Файл относительно `STELLARIS_ROOT` и строка примера, начиная с 1 |

Общее `observed_right_hand_type: "Scalar"` фиксирует критерий исходного списка: все учтённые правые части этих имён — скаляры. Это не утверждение, что все они принимают только `yes/no` или имеют одинаковое назначение. Правила обработки и ссылки локализации пока не назначались автоматически. Каталог ещё не подключён к парсеру.

## Что уже видно по примерам

| Конструкция | Пример | Наблюдаемый контекст |
| --- | --- | --- |
| `is_ai` | `is_ai = no` | Условие внутри `trigger` события: `events/achievement_events.txt:11` |
| `is_triggered_only` | `is_triggered_only = yes` | Параметр определения события, рядом с `trigger`: `events/achievement_events.txt:8` |
| `is_rare` | `is_rare = yes` | Параметр технологии: `common/technology/00_ancient_relics_tech.txt:8`; назначение также описано в `common/technology/000_documentation.txt` |
| `is_country_type` | `is_country_type = default` | Условие с текстовым идентификатором: `common/achievements.txt:510` |
| `has_technology` | `has_technology = tech_hyper_drive_1` | Условие наличия технологии: `common/achievements.txt:2013` |
| `has_morale` | `has_morale = no` | Параметр определения армии: `common/armies/00_defense_armies.txt:57` |
| `has_planetary_ascension_tier` | `has_planetary_ascension_tier >= 3` | Числовое сравнение: `common/ai_budget/04_influence_budget.txt:440` |

Примеры показывают, почему одной приставки недостаточно для общего правила обработки. Наблюдение конкретного контекста не означает, что других контекстов у слова нет.

## Порядок разбора

Для каждого имени проверяем исходники и доступную документацию, затем согласуем назначение, формы значений и контексты. После этого дополняем запись правилами обработки, если они нужны. Уже реализованные правила связываем с существующими конфигами, сохраняя одно место их настройки.

При проверке локализации сохраняем подтверждённые игровые ключи и источники. Название команды не преобразуется в ключ локализации по догадке. Отсутствие поля локализации в начальном списке означает «ещё не проверено». Пояснения ведём в документах `_RU` и `_EN` соответствующей категории. Общие согласованные решения доступны в [словаре ключевых слов и значений](../Docs/KEYWORDS_AND_VALUES_RU.md).

## Источники и проверки

[Скалярный анализ](../Docs/RESEARCH_SCALAR_USAGE_RU.md) сохранён в JSON. По отдельному запросу пользователя из рабочего `scalar_assignments.txt` удалены 635 имён пяти выделенных семейств; осталось 3 123 строки. Частотная статистика и файлы семейств не изменены. Хеши источников в заголовках каталогов относятся к полному списку на момент извлечения.

Начальный экспорт: `TMP/WEB_STTV/text_frequency/export_keyword_families.py`. Он проверяет совпадение TXT/JSON, точный отбор по префиксу, количество, отсутствие дублей, порядок частот и наличие полного примера. Повторный запуск отказывается перезаписывать существующие файлы, чтобы сохранить ручные решения. [Отчёт извлечения](../data/text_frequency/keyword_families_report.json).

Игровые исходники использовались только для чтения. Изменения ограничены начальным каталогом, исследовательским экспортом и документацией; поведение парсера не менялось.
